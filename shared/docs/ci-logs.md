# CI ログ運用（組み込みと、失敗時の切り分け）

CI ログは AI エージェント専用なので `main` を汚さない専用ブランチ `ci-logs`（main から分岐・orphan）へ
slice 単位で publish する。このための composite action `.github/actions/publish-ci-logs` は **ops-sync が全 consumer へ
配布する共通インフラ**（`shared/` 同期。手で編集しない）。

## いつ使うか（トリガ）

- **`.github/workflows/` に新しいワークフローを追加するとき**（→ 手順A）。組み込みは全リポジトリ共通の義務。
- **CI が失敗して原因を調べ始めるとき**（→ 手順B）。ログの在り処より先に「そもそもジョブが走ったか」を見る。

## 前提・パラメータ

- **公開先**: 既定は実行したリポジトリの `ci-logs` ブランチ。private リポジトリのものは非公開、public
  リポジトリ（ops-sync 等）のものは**世界公開**になる——後者に機微を出さない（MUST NOT）。
  **ログの公開先は「どのリポジトリが実行したか」ではなく「どのリポジトリ*について*のログか」で決める**
  （MUST。→ 手順A-6）。
- **`ci-logs` は恒久ログ専用**。追記型なので**ファイルを消しても内容は git 履歴に残る**（public
  リポジトリでは削除が削除にならない）。よって「現在値を読ませ続けるもの」（CI ログ・quota 信号）だけを
  置き、**読んだら用済みの一次データを混ぜない**（MUST NOT）。後者は専用の揮発ブランチへ出す
  （例: net-fetch の結果 → `net-fetch-results`。`publish-ci-logs` ではなく `publish-ephemeral` を使う）。
- **2層構成**（使い分けは全リポジトリ共通）:
  - **inline publish**（手順A-3）… 各ワークフローが**毎 run 常時**、自前の要約ログを公開する。
  - **フル生ログ collector**（手順A-4）… `workflow_run` で完了 run の生ログ全体を集約する別ワークフロー。
    **失敗時のみ**回収する。
- **history の保持は 7日**（`publish-ci-logs` の `retention-days` 既定。`history-dir` を使うスライスだけ）。
  `latest` は常に最新で上書きされ、期限の対象外。短く保つのは、CI ログを読むのは**直前に起きたこと**を
  調べるときで、public リポジトリでは残した1エントリがそのまま世界公開の恒久記録になるため。
  もっと長く要るスライスは呼び出し側で `retention-days` を上書きする（MAY）。
- **collector・ログ設計ドキュメントのファイル名や有無はリポジトリ固有**（各 `AGENTS.md` の固有パートに書く）。
- **エージェントに要る能力**: 対象リポジトリの `ci-logs` ブランチを読めること、および手順B では
  **run のページ（または run/check の annotation）を読めること**——ジョブ一覧と usage だけでは足りない
  （手順B-2 の理由）。

## 手順A: 新規ワークフローに CI ログ出力を組み込む

1. ジョブに `permissions: contents: write` を付ける（MUST）。
2. スクリプトログを `logs/ci/scripts/<name>.log` へ出す（MUST）。次の2点を**必ず同じステップに含める**:
   - **出力先ディレクトリを先に作る**（MUST）。クリーンな runner に `logs/ci/scripts/` は存在せず、
     無いまま `tee` に流すと `tee` 自身が失敗する。
   - **`set -o pipefail` を効かせる**（MUST）。パイプの終了ステータスは既定で最後のコマンド（`tee`）の
     ものになるため、`pipefail` が無いとビルド・テスト・デプロイが落ちてもジョブが成功のまま通る
     （＝ログを足したことで結果が変わる）。`pipefail` を使わない場合は `PIPESTATUS` で同等の判定をする。

   ```yaml
   - name: Build
     shell: bash
     run: |
       set -euo pipefail          # pipefail: 本体の失敗を tee が飲み込まない
       mkdir -p logs/ci/scripts   # クリーン runner には無いので先に作る
       ./scripts/build.sh 2>&1 | tee logs/ci/scripts/build.log
   ```

   - 完了条件: 本体コマンドをわざと失敗させた run でジョブが失敗し、かつ `logs/ci/scripts/<name>.log`
     が作られている。
3. ジョブ末尾に「Stage CI log snapshot」と「Publish logs to ci-logs branch」
   (`uses: ./.github/actions/publish-ci-logs`) の2ステップを `if: always()` で足す（＝この inline 公開は
   成功・失敗を問わず常時）。**手順3は例外なく全ワークフローで実施する（MUST）**。
   - 完了条件: 成功 run・失敗 run のどちらでも `ci-logs` に当該 slice が作られる。
4. リポジトリにフル生ログ collector があるなら、その `workflows` リストにワークフロー名を登録する。
   **collector は失敗時のみ回収する（MUST）**——ジョブの `if:` を
   `github.event.workflow_run.conclusion == 'failure' || github.event.workflow_run.conclusion == 'timed_out'`
   でゲートする。比較は**各値ごとに完全形で書く（MUST NOT: `== 'failure' || 'timed_out'` と略す）**——GitHub Actions 式では
   非空文字列 `'timed_out'` が常に真に評価され、成功 run でもゲートを通り抜けて失敗ゲートが無効化されるため。
   緑の run は手順1〜3 で inline に要約ログを公開済みで、フル生ログの真価は失敗トリアージにある。監視対象が
   1つ完了するごとに最低1分課金されるランナーを成功 run でも起動するのは空費（過去に GitHub Actions 分の
   逼迫を招いた実例あり）。collector を**新規に作る**場合も同じ失敗ゲートを付ける（MUST）。
   - 完了条件: 成功 run で collector が起動しないこと（Skipped になる）を1回確認できている。
   - **登録の例外**: **リクエスト単位で毎 run の一次情報を自前で publish** するワークフロー
     （現状 `net-fetch`。結果を専用の揮発ブランチ `net-fetch-results` の `net-fetch/<request_id>/` と
     ジョブログへ `if: always()` で常時出す）は collector に**登録しない**。理由: (1) status/response の
     一次情報は毎 run 自前で出ている、(2) job 失敗は主に「取得先が到達不能」等の**期待される失敗**で
     インフラバグではなく、失敗ゲートの collector を毎回起こすのはノイズ・課金（2026-07-18 の分逼迫と
     同種）。この例外に当たるかは「毎 run 自前で一次情報を出しており、失敗が想定内か」で判断する。
5. リポジトリにログ設計ドキュメントがあるなら、その slice 一覧テーブルに行を足す（collector 由来の
   スライスは「失敗/タイムアウトした run のみ」と明記する）。
   - 完了条件: 手順1〜5 が同一 PR に入っている。
6. **他リポジトリを処理するワークフロー**（cross-repo バッチ。1つの run が別リポジトリの中身を読む・
   書き換える）では、**公開先を「そのログが*何について*のログか」で決める**（MUST）。実行リポジトリが
   public で対象が private のとき、対象の中身に由来するもの——**ファイル名・パス・本文・エラーメッセージ
   の引用**——を実行側の `ci-logs` に出すと、private の内容が世界公開の恒久記録に落ちる（MUST NOT）。
   ログを2つに分ける:
   - **詳細ログ → 対象リポジトリ自身の `ci-logs`**。`publish-ci-logs` の `repository:` 入力に
     `<owner/repo>` を渡す（トークンは対象リポジトリに contents:write を持つもの）。可視性が対象の
     可視性に自動で一致し、**そのリポジトリで作業するエージェントが自分のリポジトリで読める**
     （手順B が同一リポジトリで完結する）。
   - **ロールアップ → 実行リポジトリの `ci-logs`**。出してよいのは**件数・repo 名・成否・PR URL まで**
     （MUST NOT: それ以外の、対象リポジトリの中身に由来する文字列）。集計値はスクリプトから
     `$GITHUB_OUTPUT` で受け取る（詳細ログを grep で削るのではなく、**出す値を作り分ける**）。
   - **詳細を実行側のジョブログに出さない**（MUST）。public リポジトリの run ログは world-readable で、
     保持はリポジトリ設定（Artifact and log retention）任せ。`ci-logs` の置き場だけ分けても、`tee` で
     stdout に流していればジョブログ側から同じものが読める。手順A-2 の `tee` パターンではなく
     **ファイルへリダイレクトする**（`node … > logs/ci/scripts/<name>.log 2>&1`。パイプが無いので
     終了ステータスはそのまま伝わる）。**自分の `run:` を直すだけでは足りない**（MUST NOT: それで
     塞げたと判断する）。ジョブログに落ちる経路は4つあり、後ろ2つは呼び出し側から抑制できない:
     1. 自分の `run:` の stdout/stderr → リダイレクトで塞ぐ。
     1b. **`run:` のスクリプト本文そのもの**。Actions は実行前に `${{ }}` を**展開した後の**スクリプトを
        ジョブログの `Run ...` 見出しに出すので、`git add "${{ steps.collect.outputs.path }}"` は
        リダイレクトの有無に関係なく対象のパスを載せる（`> detail.log 2>&1` は stdout/stderr にしか
        効かない）。**対象由来の値を `${{ }}` で `run:` に直接埋め込まない**（MUST）——値は
        **スクリプトの中で読み出す**（作業ツリーのファイルや `git` の出力から）。ワークフローの YAML に
        書いた `env:` の値も同じ見出しの下に出るので、そこへ移すだけでは塞げない（MUST NOT: `env:` に
        直接書いて塞げたと判断する）。
     2. **`uses:` した action の出力**。例: `peter-evans/create-pull-request` は `git status` /
        `git commit` の出力をそのまま流すので、**対象リポジトリの変更ファイル名が全部載る**。
        `uses:` ステップの出力は抑制できないので、**対象由来のパスに触る git 操作は `run:` に持ち込み**、
        そのリダイレクト先を詳細ログにする（ops-sync では `.github/actions/create-pr-quiet`）。
     3. **`with:` に渡す値そのもの**。`uses:` ステップの入力は必ずログに出る。よって
        **ブランチ名・PR タイトル・コミットメッセージを対象の中身から作らない**（MUST）。
        一意性が要るならハッシュにする（例: cleanup ブランチ名は提案ファイル名の 12 桁ハッシュ。
        同じ入力で同じ名前になる性質は保ちつつ、名前から中身を復元できない）。
   - **ロールアップの成否は `steps.<id>.outcome` で見る**（MUST NOT: 出力値の空だけで判定する）。
     スクリプトが落ちると出力は空のままなので、空を「対象ゼロ」と読むと**恒久ログに成功と読める嘘**が残る。
   - 失敗の詳細をどこへ出すかも同じ基準で決める: **対象が確定する前**に落ちたなら対象由来の文字列は
     まだ出ていないので実行側に出してよい。確定後なら対象リポジトリ側へ出す（＝スクリプトは
     **対象が確定した時点でそれを `$GITHUB_OUTPUT` に出す**。途中で落ちても送り先が分かるように）。
   - 対象が実行リポジトリ自身のとき（自リポジトリも巡回対象に含むバッチ）は、詳細ログが既にそこに
     出ているのでロールアップを重ねて出さない（`if:` で除く）。
   - 対象リポジトリ側の準備は不要（`ci-logs` が無ければ orphan で作られる。`ci-logs` は
     `branch-cleanup` の保護対象なので消えない）。
   - 完了条件: private な対象リポジトリを1つ処理した run で、実行側 slice に対象リポジトリ由来の
     ファイル名・本文が1つも現れず、同じ内容が対象リポジトリの `ci-logs` 側に出ている。

## 手順B: CI 失敗の切り分け（ログを読み始める前に）

1. **その run でジョブが1つでも起動したかをジョブ一覧で確認する**（MUST）。この分類を飛ばすと、
   ジョブ0件の run をログ欠落と読み違えて調査が振り出しに戻る（手順3はこの分類に依存する）。
   - 完了条件: 「ジョブが走った」か「ジョブ0件」かが確定している。
2. **ジョブが走っていれば**、通常どおりログを読む（MUST）。inline slice を先に読み、失敗 run なら
   collector のフル生ログへ進む。**他リポジトリの run が自分のリポジトリを処理した結果**（ops-sync の
   cross-repo バッチ等）も、詳細は**自分のリポジトリの `ci-logs`** にある（手順A-6）——他リポジトリを
   開きに行く前にここを見る。
   - 完了条件: 当該 run の inline slice を読み、失敗の一次原因を示すログ行を引用できる
     （slice が存在しない場合はその事実が確定している）。
3. **ジョブ0件だった場合**は、**run のページ（または run/check の annotation）に出ている文言を
   必ず読む**（MUST）。ジョブが起動していない原因は少なくとも3種類あり、**ジョブ数だけでは区別
   できない**（MUST NOT: 件数だけで原因を断定する）:

   | run ページの文言 | 原因 | 対処 |
   |---|---|---|
   | `Invalid workflow file`・式や `uses:` の参照エラー | **ワークフロー側の不具合**（構文・式・reusable workflow の参照）。**直前の自分の変更が原因**でありうる | ワークフローを直す |
   | `Internal server error. Correlation ID: …` | GitHub 側の一過性障害 | 再実行してよい |
   | 支払い・枠に関する文言 | アカウント側の実行拒否（枠切れ・spending limit） | 復旧を待つ（→ `docs/actions-quota.md`） |
   | conclusion が `cancelled` で、**その run 自身に concurrency による置き換えを示す表示がある**（run ページの取り消し理由・`canceling since ... concurrency group` 等の annotation） | **後続 run に追い越された**（`concurrency` の `cancel-in-progress: true`）。runner 起動前に取り消されるとジョブ0件・課金0で終わる**正常な結果** | 障害として扱わない。置き換えた後続 run の結果を見る |
   | 上記にない文言、または原因を示す文言が無い | **未分類**。既知の原因のどれかと推測しない | 表示全文と run URL を記録してユーザーへ提示し、GitHub Status と再実行結果で追加調査する |

   **この表は網羅ではない**（MUST NOT: 一致する行が無いことを理由に、近い行へ寄せて分類する）。
   一致する行が無ければ最終行の「未分類」として扱い、conclusion と文言を**そのまま記録する**（MUST）。
   分類の根拠は**その run 自身の表示**に限る（MUST NOT: 「後続 run がある」「よくある事象だ」のような
   状況証拠から原因を推定する）。`cancelled` は手動・API 由来でも起こるため、置き換えを示す表示が
   無ければ正常と決めつけず未分類として扱う。

   - 完了条件: 原因が run ページの文言に基づいて確定しているか、確定できなければ「未分類」として表示全文と
     run URL をユーザーへ引き継いでいる。表に無い conclusion や文言を既知の原因へ当てずっぽうで分類しては
     ならない（MUST NOT）。
4. **ワークフローを変更した直後の失敗は、まず自分の変更を疑う**（MUST）。「ジョブ0件だから
   ワークフロー側ではない」は**誤り**——構文・式の不正はジョブ生成前に弾かれるので、まさにこの見え方になる。

## よくある失敗

- **ジョブ0件を「外部要因」と即断する**: 3種類のうち1つは**ワークフロー側の不具合**で、しかも
  自分が直前に触ったときに最も起きやすい。手順B-3 の文言確認を飛ばさない。
- **同時に複数のワークフローが同じ壊れ方をしたのを根拠にアカウント側と断定する**: アカウント側を
  *示唆*するが決め手ではない。GitHub の内部障害も同じ push の run をまとめて巻き込むし、共通の
  reusable workflow を壊せばワークフロー側でも同時多発する。文言で裏を取る。
