# 別スレッドの作業を引き継ぐ（枠切れ・中断からの続行）

あるセッションが枠切れ等で止まった作業を、別のセッションが続行するための手順。
**引き継げる状態を残すこと**と、**元スレッドが後から復活して動いても引き継いだ側の成果を壊せないこと**の
2つを目的とする。

## いつ使うか（トリガ）

- ユーザーから「別スレッドの続きをやって」「枠が切れたので続けて」と依頼されたとき（→「手順」）。
- 「以前のセッションで途中まで作ったブランチ/PR がある」と示され、その続きに手を入れるとき（→「手順」）。
- **中断されうる作業をしているとき＝常時**（→「引き継がれる側が作業中に常にやっておくこと」）。
  こちらは特定のトリガを持たない。要点は常時層（AGENTS.md「ブランチ・PR の規律」）にあり、
  この節はその詳細。
- 適用外: 自分が開いた PR の続き（同一スレッド）、マージ済み PR への追随
  （→ AGENTS.md「ブランチ・PR の規律」）。

**元スレッドが止まったままかを、引き継ぐ側は判定できない**（MUST NOT: 「もう動かないはず」を前提に置く）。
枠は復活し、PR 購読の webhook や cron で**人が見ていないうちに元スレッドが起きる**ことがある。
この手順は元スレッドを止めるのではなく、**動いても壊せない**形にする。

## 前提・パラメータ

- `<元ブランチ>`: 引き継ぐ作業のブランチ名。
- `<元PR>`: `<元ブランチ>` の PR 番号（PR が無いまま止まっていることもある）。
- `<新ブランチ>`: 引き継ぎ後に作業するブランチ名。
- 必要な能力: 対象リポジトリの **PR の `merged`/`state` を読める**・**PR を close できる**・
  **PR にコメントを投稿できる**。いずれかを満たせないときは、別の形に切り替えず
  **停止してユーザーに依頼する**（MUST）。

## 手順

### 1. `<元PR>` の状態を確認する

`merged`/`state` を読む（正本は PR の実状態。`git log` では squash merge を判別できない）。

- **merged** → これは引き継ぎではない。最新の既定ブランチから新しく切る（→「ブランチ・PR の規律」）。
- **closed** → close コメントの引き継ぎ先を読む。
  - **引き継ぎ先が書かれている** → 既に別スレッドが引き継いでいる。**この手順をやり直さない**
    （MUST NOT: 二重に引き継ぐ。close・分岐がもう一度走り、引き継ぎ先の PR と競合する）。
    引き継ぎ先の PR を見て、そちらの続きとして扱えるかをユーザーに確認する。
  - **書かれていない** → 引き継ぎではなく放棄された PR。**停止してユーザーに確認する**（MUST）。
- **open** → 2 へ進む。
- **PR が無い** → `git ls-remote --heads origin <元ブランチ>` で `<元ブランチ>` がリモートに在るか確かめる。
  - **在る** → 2 へ進み、3 は「close するものが無い」として飛ばす（4 で新規に PR を出す）。
  - **無い** → **引き継ぐ対象が存在しない**（最も多い失敗。→「引き継がれる側が作業中に常にやっておくこと」）。
    push されていない作業はコンテナと一緒に消えていて復元できないので、**停止してユーザーに伝える**（MUST）。
    やり直すなら引き継ぎではなく通常の新規作業として最新の既定ブランチから始める。

完了条件: `<元PR>` の `merged`/`state`（PR が無い場合は `ls-remote` の結果）を読んだ記録があり、
上のどの枝に入ったかが確定している。

### 2. `<元ブランチ>` から分岐する

```
git fetch origin <元ブランチ>
git checkout -b <新ブランチ> FETCH_HEAD
```

- **`<元ブランチ>` へ push しない**（MUST NOT）。
- **`<元ブランチ>` を force-push で乗っ取らない**（MUST NOT）。乗っ取ると元スレッドの未 push の成果を
  失わせ、しかも復活した元スレッドからは「壊れた」としか見えない。分岐なら両方が残り、後から選べる。
- 引き継げるのは **push 済みの分だけ**。コンテナはエフェメラルなので、元スレッドの未 push の作業は
  取り戻せない（MUST NOT: 「ローカルに残っているはず」を前提に置く）。

完了条件: `git rev-parse HEAD` が `git ls-remote --heads origin <元ブランチ>` の返す sha と一致する。

### 3. `<元PR>` を close する（引き継ぎ先を書いてから）

close する**前に**、`<元PR>` へ引き継ぎ先（`<新ブランチ>`）を書いたコメントを投稿する（MUST）。
理由の書かれていない close は、復活した元スレッドに reopen されて二重作業に戻る。
（4 で新しい PR を出したら、その番号をこのコメントに追記する。closed PR にもコメントは投稿できる。）

**`<元PR>` に未 resolve のレビュー指摘が残っているなら、そのスレッドの URL を 4 の PR 本文へ引き写す**
（MUST）。マージされずクローズされた PR の指摘は未対応在庫の集計から外れる——「その変更は `main` に
入っていない」が前提だが、**引き継ぎでは同じコミットが `<新ブランチ>` 経由で `main` に入る**ので前提が
成り立たない。引き写さないと、レビュー済みの欠陥が誰にも見えないまま配布される
（→「レビュー指摘は resolve までが1セット」）。

close はこの手順の中心で、2つの効き方をする:

- 復活した元スレッドが **push 前に必ず行う `merged`/`state` 確認**（→「ブランチ・PR の規律」。この確認は
  無条件）が、**closed を拾ってその場で止まる**。引き継ぎ専用のガードを新しく作らずに済む。
- **PR 購読の webhook が枯れる**。これが、人が見ていないところで元スレッドが起きる主経路なので、
  塞ぐ効果が大きい（購読はセッション単位のため、引き継いだ側から元スレッドの購読は解除できない）。

完了条件: `<元PR>` が `state: closed` で、引き継ぎ先を書いたコメントが付いている。

### 4. `<新ブランチ>` で作業し、新しい PR を出す

1依頼=1PR の原則どおりに扱う（→「ブランチ・PR の規律」）。PR 本文に `<元PR>` を**引き継ぎ元**として
書く（MUST）。書かないと、後から見た人・エージェントに元の経緯へ辿る道が残らない。3 で引き写すことに
した未 resolve の指摘があれば、同じ本文に一覧として載せる（MUST）。

PR を出したら、**3 で投稿した `<元PR>` のコメントに新しい PR 番号を追記する**（MUST）。3 の時点では
番号が未定なので、往復はここで閉じる。

完了条件: 新しい PR が open で、`<元PR>` のコメントから新しい PR 番号で辿れる。`<元PR>` に未 resolve の
指摘があったなら、その一覧が新しい PR 本文に載っている。

## 引き継がれる側が作業中に常にやっておくこと

枠切れは**予告なく来る**。中断の予兆を待ってから記録を始める形にはできない（MUST NOT: 「切れそうに
なったら残す」を前提に、残作業の記録を先送りする）。次の2つは予兆と無関係に常時満たしておく。

1. **最初の意味のあるコミットができた時点で push し、PR を開く**（MUST）。作業の完了を待たない。
   引き継ぎが成立しない最大の原因は情報の不足ではなく、**引き継ぐ対象が存在しないこと**——
   push されていない作業はコンテナと一緒に消え、誰も再開できない。
2. **PR 本文を作業ログとして更新する**（MUST）。載せるのは3つ:
   - **判断根拠（なぜ）**。完了時のタスク履歴だけに頼らない（MUST NOT）——履歴の記録は
     「作業完了時の必須手順」なので、**途中で止まったセッションでは走らない**。
     引き継ぎが要る場面でだけ「なぜ」が残らない、という抜けになる。
   - **残作業と、壊してはいけない不変条件**。
   - **実行済みの不可逆な外向き操作**（デプロイ・workflow の dispatch・外部サービスへの投稿・
     本番データの変更）。実行したらその場で1行足す（MUST）。引き継ぐ側はこれを見られないと
     **同じ操作を二度実行する**（二重 dispatch は枠を食う）。

中断が予見できるとき（クライアントの不調・API 上限に当たった等）は、2 を書き切ってから終わる（MUST）。

残作業が PR 本文に収まらない規模なら、別ファイルに切り出してよい（MAY）。その場合も **PR 本文から
そのパスを指す**（MUST。パス1つで cold start からも辿れる形にする）。切り出したファイルは、作業を
完了させる PR で**削除する**（MUST）——残すと「現在形で書く」ルールに反する古い残作業リストが残る。

完了条件: 手元に push していないコミットが無く、PR 本文から「どこまで進んでいるか」「次に何をするか」
「何を二度実行してはいけないか」の3つが読める。

## 復活した元スレッド側がすること

**専用の手順は要らない。** 既存の「push 前に `merged`/`state` を無条件で確認する」がそのまま防衛線になる。
確認して closed だったときの振る舞いだけ、ここで定める:

- **push せず**、close コメントの引き継ぎ先を読む（MUST）。
- **自分で reopen しない**（MUST NOT）。状況をユーザーに伝えて指示を仰ぐ。
- この確認は **push 以外の外向き操作にも効かせる**（MUST）——PR コメント・レビューの resolve・
  workflow の dispatch・デプロイ。push だけを守っても、**二重 dispatch は枠を食う**（枠切れの
  対処が枠を消費しては本末転倒）。

## 限界（この手順が守らないもの）

- **元スレッドが手順を無視して force-push した場合**。協調が前提の仕組みで、強制はできない。
- **二重作業そのもの**。元スレッドが本当に止まっているかは誰にも分からないので、保証するのは
  「動いていても壊れない」ことだけ。同じ作業が2回行われることは起こりうる。
- **未 push の成果**。「引き継がれる側が作業中に常にやっておくこと」の 1 が守られていれば失う幅は
  小さくなるが、規律であって強制ではない（守られなければ消える。→ 手順 2）。
- **元スレッドが引き継ぎに気づく速さ**。気づくのは次に外向き操作をしようとした瞬間なので、
  それまでの読み取り・思考ぶんの枠は消費される。
