# タスク履歴の規約（全リポジトリ共通）

タスク履歴の**目的は2つ**: (1) スレッド（セッション）間で「さっきのあれ」を通じさせる**短期記憶**、
(2) コードに残らない判断根拠（「なぜ」）の**恒久保管**。(1) のために直近分は小さく保ち、
(2) のために古い分はアーカイブへ移して捨てない。

## いつ使うか（トリガ）

- 作業を完了してユーザーへ報告する直前に、その作業の判断根拠を記録するとき。
- 「さっきの作業」「昨日の変更」など、過去スレッドの文脈を照合するとき。

## 前提・パラメータ

- `<タスクスラッグ>`: 作業内容を表す短い ASCII 英数字・ハイフンの名前。ブランチ名を材料にしてもよいが、
  `work` のような汎用ブランチ名そのものを一意性の根拠にはしない。
- `<短いタイトル>`: ユーザーとのやりとりで使った対象名を含む、1行の日本語または英語。

## 場所（全リポジトリ共通）

エントリは**書く場所と読む場所が分かれている**（並行 PR のコンフリクトを避けるため。理由は下記「なぜ
フラグメント方式か」）:

- **書く**（エージェント）: `scripts/new-task-history.mjs` で
  **`docs/history-inbox/<YYYY-MM-DD>T<HHMMSS>Z-<タスクスラッグ>-<ランダムID>.md`** に**新規ファイル1つ**として
  置く（＝未統合フラグメント。既存ファイルには一切追記しない）。このディレクトリは常に追跡された
  `README.md` プレースホルダを持つ（ops-sync が配布・維持）＝全フラグメントを統合して空になっても
  ディレクトリごと消えない。この `README.md` は消さない・バッチの取り込み対象外。
- **統合先**: **`docs/AI_TASK_HISTORY.md`**（新しいエントリが上）。inbox のフラグメントを ops-sync の集中
  バッチがここへ取り込む（下記「統合とアーカイブ」）。エージェントはこのファイルを直接編集しない。
- **アーカイブ**: **`docs/history-archive/<YYYY>.md`**（年ごと。こちらも新しいエントリが上）。

「さっきのあれ」を**読む**ときは、`docs/AI_TASK_HISTORY.md`（統合済み・直近2作業日分）**と
`docs/history-inbox/` 内の全ファイル**（未統合の最新分）の**両方**を見る。より古い経緯は
`docs/history-archive/` を grep。

## 手順

1. 過去の作業を参照する場合は、`docs/AI_TASK_HISTORY.md` と `docs/history-inbox/` 内の全ファイルを MUST で
   読む。より古い経緯が必要な場合は `docs/history-archive/` を検索する。照合対象が確認できれば完了。
2. 作業を記録する場合は、リポジトリルートで次を MUST で実行する。

   ```bash
   scripts/new-task-history.mjs <タスクスラッグ> "<短いタイトル>"
   ```

   このスクリプトは
   `docs/history-inbox/<YYYY-MM-DD>T<HHMMSS>Z-<タスクスラッグ>-<ランダムID>.md` を排他的に新規作成する。
   例: `docs/history-inbox/2026-07-26T142731Z-codex-public-slices-a4f91c2ed894.md`。
   時刻は可読性、12桁の暗号学的ランダムIDは別ブランチ・同秒の並行セッション間の衝突回避を担う。
   ブランチ名は一意性の根拠にしてはならない（MUST NOT）。コマンドが新規ファイルのパスを1行出力し、
   そのファイルが存在すれば完了。
3. 作成されたファイルには、`## YYYY-MM-DD 短いタイトル` の見出しに続けて、「**なぜ**」
   （コードに無い制約・判断根拠・ハマりどころ）を数行で MUST 記録する。`# ` の H1 や前置きは MUST NOT
   追加しない。「何を変えたか」はコード・PRで分かるので書かない。見出しと本文がエントリ本体だけなら完了。

   ただし、**次に同じ作業をする人に効く教訓は履歴に書いて終わりにしない**（MUST NOT）。履歴が読まれるのは
   「さっきの◯◯」のように**過去スレッドの文脈が前提の依頼**のときだけで（上記トリガ）、`docs/` の doc と違って
   **その作業のトリガでは開かれない**——置いても次の人には届かない。再利用できる知見・ルール・落とし穴は
   該当する doc（共通なら ops-sync の配布 doc、そのリポジトリ固有なら自分の `docs/`）へ書き、
   履歴には**そう判断した理由**と、必要なら doc の**パス**（日付付きの履歴エントリへの相互リンクは張らない。
   下記5）を残す。振り分けの基準は共通ブロック「再利用可能な知見・ルール・ファイルに気づいたときの振り分け」。
   **判定**: そのエントリの一文が「今後は〜する」と読めるなら、それは履歴ではなく doc に置くもの。
4. **1タスク（スレッド）= 1フラグメント = 1エントリ**を MUST で守り、既存ファイルへは MUST NOT 追記する。
   `git status --short` で今回生成した新規フラグメントが1つ表示されれば完了。
5. 他の恒久docから履歴の特定エントリへ「日付付き」でリンクしてはならない（MUST NOT）。エントリは下記
   アーカイブで `docs/history-archive/<YYYY>.md` へ移動するため、日付付きポインタは移動後に壊れる。
   経緯を恒久docに残す場合は、その事実をdoc内に書き切る。履歴ファイルの「場所そのもの」を説明する言及
   （本規約・`docs/README.md`など）は対象外。恒久docに移動後壊れるリンクがなければ完了。

## よくある失敗

- 日付と汎用ブランチ名だけの旧形式で手作業すると、同日の Codex セッション同士で衝突する。
  ファイル名を手で決めず、生成スクリプトが作る
  `<YYYY-MM-DD>T<HHMMSS>Z-<タスクスラッグ>-<ランダムID>.md` を使う。
- ローカルで同名がないことだけを確認しても、未マージの別ブランチは見えない。排他的作成に加えてランダムIDを
  必須にするのはこのため。

### なぜフラグメント方式か

`docs/AI_TASK_HISTORY.md` は「新しいエントリが上」なので、全セッションが**同じ行位置（先頭）に挿入**
する。並行 PR が2つあればほぼ確実にコンフリクトし、アーカイブバッチの自動 PR とも衝突しうる。
1エントリ＝1新規ファイルにすれば、各セッションが**別々のパスに触れる**だけになり衝突が原理的に消える
（changelog の towncrier / changelog.d と同型）。本体ファイルの書き手を集中バッチ1つに絞れる副次効果もある。

## 統合とアーカイブ（自動 — エージェントは何もしない）

- **統合（consolidate）**: ops-sync の集中バッチ（archive-task-history workflow）が `docs/history-inbox/` の
  全フラグメントを `docs/AI_TASK_HISTORY.md` の先頭へ日付順で取り込み、取り込んだフラグメントファイルを
  削除する（本文はそのまま・書き直さない）。統合されるまでの間は上記「読む」のとおり両方を見れば最新も拾える。
  ただし本体に既にある同一本文のエントリは取り込まず、そのフラグメントは削除して掃除する（重複記録の防止。
  見出しだけの一致では消さない＝同日別タイトルの正当なエントリは残る）。
- **保持量**: 統合後、本体に残すのは**エントリのある日付で数えて直近2日分**（同日の複数エントリはまとめて
  1日と数える。暦日ではなく作業日: 間に作業のない日を挟んでも、エントリのある直近2日分を残す）。
  件数でなく日数で数えるのは、短期記憶の必要量が経過時間で決まるため。
- **アーカイブ（archive）**: 3日分以上になった古い日付のエントリを、同じバッチが
  `docs/history-archive/<YYYY>.md` へ丸ごと移す（既存エントリと日付降順にマージするので、
  バックデートしたフラグメントでも年内が「新しいものが上」に保たれる）。統合・アーカイブとも
  1つの PR を自動生成・マージする。
- エージェントは**フラグメントを1つ置くだけ**でよい（MUST NOT: セッション内で本体への統合・手動
  アーカイブをしない。超過に気づいても放置してよい——決定的なファイル移動にトークンを使わない。
  次のバッチが処理する）。
- アーカイブはオンデマンド層: 過去の経緯が要るときだけ読む・grep する。

## 各リポジトリ側に書くこと

- 各 AGENTS.md の固有パートに書くのは**この規約からの逸脱（例外）だけ**。原則、何も書かなくてよい。
- この規約自体を直したいときは outbox の `shared-file` 提案（`対象パス: docs/task-history.md`）。
  → `docs/outbox-proposal.md`
