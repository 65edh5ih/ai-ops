# リポジトリ横断タスク（`.ops-sync/tasks/`）の使い方

「このリポジトリでやったのと同じ作業を別リポジトリでもやってほしい」等、**別リポジトリでの作業が
必要になったとき**の依頼経路。1セッション=1リポジトリの制約下で、依頼を ops-sync 経由で対象リポジトリの
手元（`.ops-sync/tasks/`）まで物理的に届ける。Notion 等の外部ツールへの転記は不要。

経路: 依頼元から `種別: task` を ops-sync へ出す（正本への直接 PR か `.ops-sync/outbox/` 提案。選び方は
[`docs/outbox-proposal.md`](outbox-proposal.md)）→ ops-sync の `tasks/<owner>/<repo>/` → sync で
対象リポジトリの `.ops-sync/tasks/` へ配布 → 対象リポジトリのセッションが実行 → `種別: task-done` で消化。
途中に**オーナーがマージする PR が必ず挟まる**ので、届いているタスクは承認済みとみなしてよい。
どの PR を挟むかは経路で変わる（直接 PR なら ops-sync の PR、outbox 提案なら提案を載せた依頼元の PR。
ops-sync の取り込み PR は private 発なら自動マージされる。→ `docs/outbox-proposal.md`）。
最後に対象リポジトリの同期 PR が入って手元に届く。

## 依頼する側（タスクを書くとき）

本文を読むのは**このセッションの文脈を何も持たない**、対象リポジトリのエージェント。次を必ず含める:

1. **目的（なぜ）**: 何を達成したいか。依頼元で何があったか。
2. **作業内容（何を）**: 具体的に。依頼元リポジトリのファイルは参照できないので、必要なコード・設定・
   手順は**本文に貼り込む**（「◯◯リポジトリの △△ を見て」は書かない——見えない）。
3. **完了条件**: 何ができたら終わりか。
4. 分かるなら対象リポジトリ側の関連パス・注意点。

依頼を出したら（経路と書式: [`docs/outbox-proposal.md`](outbox-proposal.md)）、**ユーザーに次を伝える**:

1. **オーナーがマージする PR を経路に合わせて伝える**（MUST）。直接 PR なら「ops-sync の PR →
   対象リポジトリの同期 PR の順にマージされると届きます」。outbox 提案なら「この PR →（ops-sync の
   取り込み PR。public 発のときはこれもマージが要ります）→ 対象リポジトリの同期 PR」。
2. 起票経路の完了条件を確認する（MUST）: 直接 PR は ops-sync の open PR URL、outbox は提案を含む open PR URLを示す。
3. **対象リポジトリのセッションに貼るコピペ用の指示文**を示す（MUST。1つずつ・冒頭に1行の概要。
   Claude Code は最初の入力からセッションタイトルを生成するため）:

  ```
  <作業の1行概要>
  .ops-sync/tasks/<ファイル名> に依頼があります。読んで作業してください。
  ```

## 受ける側（`.ops-sync/tasks/` にファイルがあるとき）

1. **着手するかを判断する**（MUST）。現在のユーザー依頼がそのタスクを指しているなら、そのまま実行する。
   別件の作業中に気づいた場合は、現在の依頼と両立するときだけ対応し、そうでなければ存在をユーザーに
   伝えるに留める（勝手にセッションの目的を乗り換えない）。
2. **依頼本文の完了条件を満たす**（MUST）。作業結果を検証し、作業の「なぜ」は通常どおりこのリポジトリの
   履歴ファイルに残す。
3. **依頼本文の完了条件をすべて満たし、その結果の検証に成功し、実装が main に入った後にだけ、ops-sync 側の正本
   `tasks/<owner>/<repo>/<ファイル名>` を消す経路を確保する**（MUST）。完了条件を満たしていない、検証が失敗した、
   または実装が未マージのいずれかなら正本を消してはならない（MUST NOT）。先に消すと、作業や検証が失敗した場合、
   または実装 PR が close された場合も
   タスクだけが配布対象から消える。満たし方は起票と同じ2経路（選び方は → `docs/outbox-proposal.md`）:
   - **outbox**: `種別: task-done` の提案を**実装 PR に含める**（MUST）。提案は実装 PR が main にマージされるまで
     collect の走査対象にならないため、実装より先にタスクを消さない。consumer ではこの経路を優先する。
     - **例外: 完了条件の検証がマージ後にしか取れないタスク**（deploy の成功・本番での挙動確認・cron の初回実行など）は
       この経路を使ってはならない（MUST NOT）。実装 PR に同梱した `task-done` は**マージ直後に collect の対象になる**ため、
       検証が終わる前に——検証が失敗した場合でも——タスクが配布対象から消える。この場合は `task-done` を実装 PR に
       含めず、**検証の成功を確認してから**別の変更として `task-done` 提案（または下の直接 PR）を出す（MUST）。
       どちらの経路かは「完了条件が実装 PR のマージ時点で確定するか？」で判断する。
   - 正本への**直接 PR**: 実装 PR のマージを確認した後に、`tasks/<owner>/<repo>/<ファイル名>` を削除する PR を作る。
     実装のマージ前に削除 PR を出す場合は、削除 PR を draft にして実装 PR のマージを解除条件として明記し、
     先にマージされないようにする（MUST）。
   手元の `.ops-sync/tasks/` は同期管理下なので直接消してはならない（MUST NOT）。正本を消す経路を確保しないと
   次の sync で復活し、別のセッションが同じ依頼を再実行する。
4. **セッション内の完了条件を確認する**（MUST）。outbox は実装 PR に `task-done` 提案が含まれ、その open PR URL を
   ユーザーに伝えてあれば完了とする（マージ後検証タスクで `task-done` を後出しにした場合は、実装 PR の URL と
   「検証後に `task-done` を出す」旨をユーザーに伝えてあれば、そのセッションの完了とする）。直接 PR は、実装が main に入っていることと、削除 PR が open でその URL を
   ユーザーに伝えてあることを確認する。`git status --short` で意図しない未コミット変更がないことも確認する。
   消化が効くのは非同期（実装のマージ→〔outbox 経路なら〕collect の cron→削除のマージ→sync）なので、
   `.ops-sync/tasks/` から実際に消えるまで待って作業を止めない（MUST NOT）。

## ops-sync 側でできること

ops-sync のセッション（またはオーナー）は、`tasks/<owner>/<repo>/` にファイルを直接コミット／削除して
起票・消化できる（consumer のセッションが直接コミットすることはなく、正本への PR か outbox 提案を
経由する。→ `docs/outbox-proposal.md`）。ops-sync 自身への依頼はタスク機構を
使わず、ユーザーが ops-sync のセッションに直接指示する。
