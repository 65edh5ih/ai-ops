# D1 の運用（全リポジトリ共通）

## 目的

Cloudflare D1 を扱うときの共通規約を1か所に集約する。扱うのは3つ:

1. **容量**（上限は**アカウント内「全 D1 データベースの合計」**で 5GB。複数リポジトリ・複数 Worker が
   同一アカウントの D1 を使うため、容量は**リポジトリ横断**の制約になる）と、各 DB を上限内に保つ
   retention 実装のノウハウ。
2. **本番データの直接確認**（一度きりの移行・是正が完了したかを、推測でなく実データで確定させる）。
3. **不要になったスキーマの撤去**（役目を終えた列・テーブルを消すときの順序と前提条件）。

2・3 は容量の話ではないが、いずれも「本番の D1 に対して何をしてよいか」の判断なので同じ doc に置く
（発火トリガも1つにまとめて、常時ロード層のコストを増やさないため）。

## いつ使うか（トリガ）

- 新しい D1 データベースを作る / 既存 D1 に定常的な書き込み（ログ等）を足すとき。
- D1 の容量・retention（古い行の削除）を設計・実装・レビューするとき。
- 「D1 が一杯になったらどうなるか」を確認するとき。
- **一度きりの移行・是正が完了したか等、本番 D1 の実データを確認したいとき**（新規 DB 作成でも
  定常書き込みでもない一過性の検証。「確認する手段がない」と結論する前に必ずここを読む）。
- **役目を終えた列・テーブルを本番 D1 から消すとき**（移行機能の撤去に伴うスキーマの後片付け。
  消す順序を間違えるとアプリが作り直すので、コードの撤去とセットで読む）。

## 前提: D1 無料枠（Cloudflare 公式・2026-07 時点）

- ストレージ: **5GB（アカウント内全 D1 の合計。テーブルも索引も加算）**
- 書き込み: 10万 rows_written/日（**INSERT・UPDATE・DELETE すべて**が rows_written に加算）
- 読み取り: 500万 rows_read/日
- 日次リセット 00:00 UTC。egress 課金なし。
- 超過時のエラー文言（参考）: `Exceeded maximum DB size.`（単一 DB）/
  `Your account has exceeded D1's maximum account storage limit ...`（アカウント合計）。

## 容量の測り方

- **アカウント合計**: Cloudflare MCP / API の `d1_databases_list` が全 DB の `file_size`（バイト）を
  1回で返す → 合計する。これが正（DB 一覧をハードコードしない）。API 側（cron / エージェント）
  からのみ取得できる。
- **単一 DB の現在サイズ**: 全 D1 クエリ結果の `meta.size_after`（バイト）。Worker / Pages Function
  内から**自 DB のサイズだけ**が追加コストなしで取れる（他 DB・アカウント合計は関数内からは見えない）。

## 本番データの直接確認（容量測定以外の検証）

一度きりの移行・是正が本番で完了したか、ある状態の行が本当に0件かを、**推測でなく実データで**
確定させる手順。互換コード・防御的分岐を残すか外すかの判断根拠にする。

**要求（経路によらない）**: その判断の前に**本番に対する読み取り専用クエリで実証する**（MUST）。
実証できないなら**停止してユーザーに確認経路を依頼する**（MUST）。「このセッションから確認する
手段がない」を根拠に推測で結論しない（MUST NOT）。

### 前提・パラメータ

- `<database_id>`: **いま動いている Worker がバインドしている** D1 の ID。**リポジトリの設定ファイルだけを
  根拠にしない**（MUST NOT）——設定は本番より進んでいることも遅れていることもあり、環境別バインディング
  （`[env.<name>.d1_databases]` 等）があれば**トップレベルの定義が本番とは限らない**。設定ファイルの形式も
  リポジトリによって違う（`wrangler.toml` / `wrangler.json` / `wrangler.jsonc`）。
  **デプロイ状態から解決する**（MUST）: 稼働中バージョンのバインディングを見る（`wrangler deployments status` /
  Cloudflare API の Worker version 情報など、手段は問わない）。設定ファイルから読んだ ID は、その
  バインディングと**一致することを確認してから使う**（MUST）。一致しないまま設定側の DB を数えると、
  期待どおりの 0 件が返っても**本番が別の DB を向いたまま**互換コードを消すことになる。
- `<検証SQL>`: 「残っていてはいけない行」を数える集計クエリ。**期待値を先に決める**（通常 0）。

### 手順

1. 読み取り専用の D1 クエリ経路を1つ特定する。満たし方はランタイム依存で、以下はいずれも実装例
   （手段を限定しない）: MCP の D1 query ツール／Cloudflare REST API の D1 query／
   `wrangler d1 execute <db> --remote --command '<SQL>'`。
   **完了条件**: 経路が1つ特定できている。1つも無ければ**ここで停止**してユーザーに読み取り経路の付与を
   依頼する（MUST）。別の判断（推測で互換コードを残す等）へ勝手に切り替えない（MUST NOT）。
2. `<database_id>` が**いま動いているバージョンのバインディング**と一致することを確認する
   （`wrangler deployments status` / Cloudflare API の Worker version 情報など）。設定ファイルの
   定義は**候補**として使ってよいが、それだけを根拠にしない（MUST NOT）。名前の似た staging/preview を
   掴んでいないかもここで見る。
   **完了条件**: **稼働中バージョンが報告したバインディング**と ID が一致している。設定ファイルとの
   一致だけでは完了にしない（MUST NOT）——設定が本番より進んでいる／遅れていると、期待どおりの 0 件が
   返っても本番は別 DB を向いたままになる。一致を示せないなら停止して確認する（MUST）。
   **ステージングの 0 件を本番の証拠として報告しない**（MUST NOT）。
3. `<検証SQL>` を実行する。**読み取りのみ**（MUST）。`UPDATE`/`DELETE`/`INSERT` は使わない
   （MUST NOT。本番データを直接変えてしまう。書き込みが必要ならアプリの Worker/Function 経由で行う）。
   - **返す行を最小化する**（MUST）: 既定は `COUNT(*)`・`EXISTS` 等の集計/存在確認にする。実行結果は
     セッションの記録（MCP・CLI のログ）に残るため、**読み取り専用でも中身の露出は防げない**。行の中身を
     見る必要があるときだけ**非機微な列に限定**し、小さい `LIMIT` を付ける（メールログのような機微データを
     含む DB では特に）。
   - **読み取り量を抑える**（SHOULD）: 索引の効かない述語の `COUNT` はテーブル全体を走査しうる。索引のある
     列で絞る等で最小化し、結果の `meta.rows_read` を確認する（上記「前提: D1 無料枠」の 500万 rows_read/日は
     **アカウント共有**の枠で、大きなテーブルの無造作な全走査は他の本番クエリを枯渇させうる）。
   **完了条件**: 件数が返り、期待値と一致するか否かを判定できている。
4. 判断とその根拠をタスク履歴に残す。対象 DB・テーブルに加えて、**実行した `<検証SQL>`（述語）と
   期待値・実測値**を残す（MUST）。同じテーブルでも述語が違えば `0` の意味は別物なので、述語の無い
   「0 件だった」は後から再現も監査もできない（互換コードを外した判断の根拠として使えない）。
   述語に機微な値が入るときは、非機微な形に言い換えて残す。
   **完了条件**: 「どの述語を数えて何件だったので互換コードを外した／残した」が履歴から辿れ、
   同じ検証を再実行できる。

## 不要になったスキーマ（列・テーブル）を消すとき

一度きりの移行機能を撤去したあと、その機能だけが使っていた列・テーブルが本番に残る。参照するコードが
無くなっていれば無害だが、消すなら**順序と前提条件**がある。どちらも外すと静かに失敗する。

### 手順

1. **先にコードの撤去を本番へデプロイし、稼働中のコードにその列への参照が無いことを実物で確かめる**（MUST）。
   多くの Worker は起動時やティックごとに**冪等なスキーマ ensure**（`CREATE TABLE IF NOT EXISTS` や
   `ALTER TABLE ... ADD COLUMN` を毎回流して失敗を握りつぶす実装）を持つ。これが生きている間に列を消すと、
   **次の実行が黙って作り直す**。cron 駆動なら数十秒〜数分で戻るので、消したつもりで残る。
   **完了条件**: 「PR がマージされた」ではなく（MUST NOT。マージとデプロイは別物）、デプロイが成功し、
   **稼働中のコードそのもの**にその識別子が無いこと。Workers なら稼働中スクリプトを取得して grep する
   （Cloudflare MCP / API の Worker code 取得、`wrangler deployments status` 等、手段は問わない）。
   撤去していない機能の識別子が同じ取得結果に**存在する**ことも併せて見る（取り違え・古い版を掴んでいない証拠）。
2. **DROP COLUMN の前提条件を確認する**（MUST）。SQLite は**索引・PK・UNIQUE 制約・生成列・
   ビュー/トリガ/CHECK 式に関与する列を DROP できない**。事前に対象テーブルの索引を読む:

   ```sql
   SELECT name, sql FROM sqlite_master WHERE type='index' AND tbl_name IN ('<table>');
   ```

   対象列が索引に含まれるなら、先に索引を落とすか、列を残す判断に切り替える。
3. **DDL を実行する**。`ALTER TABLE <table> DROP COLUMN <col>`。
   これは上記「本番データの直接確認」の**読み取り専用ルール（MUST）の例外**にあたるので、
   **ユーザーの明示依頼があるときだけ行う**（MUST）。エージェントの判断で本番スキーマを変えない（MUST NOT）。
   撤去のためだけにアプリ側へ一時的な移行経路を足すのは本末転倒（「撤去したはずの残骸」を新たに増やす）なので、
   一度きりの DDL は直接実行してよい——ただし依頼が要る、という切り分け。
4. **消えたことと、行データが無傷なことを読み取り専用で検算する**（MUST）。列の消失だけでなく、
   **行数と主要な不変条件**（その機能が触っていた列の分布など）が DDL 前と一致することを見る。
   SQLite の DROP COLUMN はテーブルを書き換えるため、行数の確認は形式的ではない。

   ```sql
   SELECT (SELECT COUNT(*) FROM pragma_table_info('<table>') WHERE name = '<col>') AS col_remains,
          (SELECT COUNT(*) FROM <table>)                                            AS rows_total;
   ```

   **完了条件**: `col_remains` が 0 で、`rows_total` が DDL 前と一致している。
5. **数分（ensure を持つ処理の実行間隔ぶん）おいて、もう一度同じ確認をする**（SHOULD）。手順1を満たしていれば
   列は戻らないが、戻っていれば「古い版がまだ動いている」ことの検知になる。
6. **述語と期待値・実測値を履歴に残す**（MUST。上記「本番データの直接確認」の手順4と同じ要求）。

### よくある失敗（この節に固有）

- **マージ＝デプロイと思い込んで消す**。デプロイが別 workflow・別経路（Cloudflare 側のビルド連携など）だと
  数分のずれがあり、その間に消すと古い版が作り直す。
- **列だけ見て索引を見ない**。DROP COLUMN が実行時エラーになる。事前に `sqlite_master` を読む。
- **消したあとに検算しない**。作り直されていても気づかず、「消した」と報告してしまう。

## 各 DB を自分で上限内に保つ（行数リングバッファ）

5GB はアカウント共有なので、各 DB は自分の取り分を自己管理する（SHOULD: 単一 DB を 1GB 未満など、
明示した目標に収める）。定常書き込みするログ系テーブルは、最新 N 行だけ残すリングバッファに
するのが素直。実装の要点:

1. **MUST: 削除の判定は「バイトサイズ」でなく「行数」で行う。** SQLite(D1) は DELETE しても
   ファイルサイズがすぐ縮まない（空きページは以後の INSERT で再利用されるが `file_size` /
   `meta.size_after` は高止まりする）。バイト超過をトリガーに削除すると、削除してもサイズが
   下がって見えず**毎回削除が走って暴走する**。行数なら削除で確実に減る。
2. **MUST NOT: `OFFSET` で「N 行目」を数えて削除しない。** `... ORDER BY id DESC LIMIT 1 OFFSET N`
   型のサブクエリは行数に比例してテーブルをほぼ全スキャンし、1 挿入あたりの `rows_read` が
   肥大化して 500万/日の読み取り上限を数年で食い潰す。
3. **SHOULD: INSERT の `meta.last_row_id` を使い id 範囲で直接削除する。**
   `DELETE FROM <table> WHERE id <= (last_row_id − MAX_ROWS)`。索引で O(削除行数)・全スキャンなし。
   テーブルは AUTOINCREMENT の整数主キーを持つこと（無ければ rowid か時刻列で代替）。
4. **MUST: DELETE も rows_written に加算されることを踏まえ、刈り込みは「窓から外れた分だけ」に
   留める。** 上限付近で毎挿入ごとに大量削除すると 10万/日の書き込み上限に当たる。id 範囲方式なら
   steady state で1挿入あたり数行の削除で済む。
5. **SHOULD: MAX_ROWS は実効バイト/行から安全側に決め、`size_after` をログして較正する。**
   1行の実効バイトは列の内容＋**索引の本数**で増える（索引1本ごとに加算）。到達時に実測して
   MAX_ROWS を調整する。

参照実装（同型・そのままひな形にできる）:

- `nikki-san`: `functions/api/view.js` の `trimOldRows`（アクセスログ・100万行）
- `private`: `cloudflare_workers/shared/logger.js` の `trimEmailLogs`（メールログ・100万行）

## 満杯にしたときの挙動（対策しない場合）

上限に達すると以降の INSERT が失敗し、その書き込みは失われる（＝最新が捨てられ、古い行は残る）。
リングバッファ（最新 N 行維持）は逆に「古い行から捨てて最新を守る」。どちらもデータ喪失は不可避で、
**何を残したいか**で選ぶ。

## よくある失敗

- **バイトサイズをトリガーにして削除ループが暴走**（no-shrink を見落とす）。→ 行数で判定する（上記 MUST）。
- **`OFFSET N` の刈り込みで読み取り上限に静かに突入**し、ある日から書き込みが `catch` されて記録が
  止まる。→ id 範囲削除にする（上記 MUST NOT / SHOULD）。
- **「本番の実データを確認できない」と早合点し、実は完了している一度きりの移行に互換コードを
  残してしまう**。→ 上記「本番データの直接確認」のとおり、まずそのランタイムで使える読み取り専用の
  確認経路（MCP・API・CLI等）が無いか確認する。
- **ステージング/preview の DB を掴んだまま「0 件だった」と本番の結論にする**。→ 環境別バインディングが
  あるとトップレベル定義は本番とは限らない。手順2で**稼働中バージョンのバインディング**と一致することを先に示す。
