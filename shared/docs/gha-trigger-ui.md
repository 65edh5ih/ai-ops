# GitHub Actions を起動する UI の表示規約（全リポジトリ共通）

管理画面などの UI に **GitHub Actions の workflow を起動するコントロール**（ボタン・リンク・フォーム送信）を
置くときの表示ルール。押す人が**押す前に**「これは Actions の workflow を起動する」と分かる状態を保つのが目的
（コストを伴う run なら、**それが月枠の消費なのか直接の課金なのか**まで分かること。両者は別で、下記
「前提・パラメータ」で区別する）。

## いつ使うか（トリガ）

- UI に **workflow を起動する（`workflow_dispatch` / `repository_dispatch` を投げる）コントロールを
  追加・変更するとき**。新規ページの作成でも、既存ページへの1個追加でも同じ。
- 既存コントロールの**起動有無が変わったとき**（Actions を投げない実装に変えた／逆に投げるようにした）。
- **押した時点では run を作らないが、押した後の実行のされ方を変える操作**を追加・変更するとき
  （→ 手順2b）。**run を作らないので上の判定では対象外**になるが、「押す前に分かるべき副作用」で
  あることは同じ。変わり方は次の2つで、**互いに独立**（片方だけのことも両方のこともある）:
  - **コストが変わる**: 経路を Actions 側に戻すスイッチ等で、押した後の push からコストを伴うジョブが
    実走に変わる。run を作るのは push＝人の操作なので、押した本人が次の run のタイミングを決められる。
    **月枠を消費する場合と直接課金される場合の両方がある**（larger runner を有効化する側なら後者）。
    どちらかは対象 workflow の `runs-on` と可視性で決まる（→ 下記の区別）。
  - **起動が無人になる**: cron・キュー処理などの「開始」ボタンで、以後その処理が区切りごとに
    **自分で** workflow を dispatch する。止める操作をするまで人手なしで run が作られ続ける＝押した
    本人にも回数もタイミングも分からない。**枠を消費するかはこれとは別の条件**（セルフホストランナーの
    ループなら消費しない。それでも無人で run が作られること自体が印の理由になる）。
- 適用外: Actions を起動せず、上の2つ（コスト・無人起動）の**どちらも**変えない操作（ストレージや API を
  直接叩くだけ・設定値を書き換えるだけで実行に影響しない・**自分では workflow を起動しない**定期実行に
  任せるだけ 等）。**これらに印を付けない**（MUST NOT）——印が増えるほど「特別な操作だ」という信号が薄まる。
  **適用外にできるのは条件をすべて満たすときだけ**（MUST）。「cron が挟まるので間接的だ」を
  適用外の理由にしない（MUST NOT）——その定期実行自身が dispatch するなら、それを有効化した操作は
  上の2b の対象。実際にこの読み違いで印が1つ落ちている（無人移行の「開始」ボタン）。

## 前提・パラメータ

- **なぜ要るか**: workflow の起動は、押した本人にも他の人にも見えにくい副作用（run の生成・デプロイ・
  外向きの処理）を伴う。UI 上で通常の保存・確認系ボタンと見分けが付かないと、意図せず起動してしまう。
- **「月枠を消費する」と「課金される」は別**（同じ文言で扱わない。MUST NOT）。月枠＝アカウント単位で
  共有される**込みの実行時間**で、これを消費するのは **private リポジトリ ✕ GitHub-hosted の標準ランナー**。
  枠切れの実行は run の失敗に留まらず spending limit の設定次第で**実費課金**につながる
  （→ [`docs/actions-quota.md`](actions-quota.md)）。一方 **larger runner は込みの対象外で、public でも
  最初から従量課金**——つまり課金対象だが**月枠は消費しない**。セルフホストランナーはどちらでもない
  （private でも枠を消費せず課金もされない）。可視性だけでは決まらないので、枠・課金の文言を付ける前に
  **対象 workflow の `runs-on` を読む**（MUST）。**呼ばれる側まで辿る**（MUST）——起動する workflow が
  `uses:` で別の workflow を呼んでいる（`workflow_call`）なら、実際に走るジョブの `runs-on` は
  **呼ばれた側**にある。入口だけ見ると、呼び先が larger runner でも「無料」と判断してしまう。**枠を消費しない run に「月枠を消費する」と書かない**
  （MUST NOT）——誤った理由づけは印そのものの信頼を落とす。larger runner のように課金だけされる run は
  「**実行のたびに課金される**」と書く（MUST。月枠の話を混ぜない）。印を付けること自体は課金の有無によらず必要。
- **見た目の正本はリポジトリごとに1つ**: クラス名・バッジ文言・配色の実装は、そのリポジトリの UI 共通部品
  （`<UI共通部品のパス>`）に置く。**リポジトリ間で見た目まで揃える必要はない**（揃えるのは「印が付いている」
  という要件のほう）。

## 手順

1. **そのコントロールが本当に Actions を起動するかをコードで確認する**（MUST）。ラベル・置き場所・隣の
   ボタンから推測しない（MUST NOT）。ハンドラを追って `.../actions/workflows/<file>/dispatches` や
   `.../dispatches`（repository_dispatch）への送信があるかを実際に読む。
   - **dispatch が無くても、そこで終わりにしない**（MUST NOT）。押した後に **run を作るのは誰か**まで
     追う。書き換える値が workflow のゲート（`if:` が読む repo variable 等）なら、**その値によって
     課金対象のジョブが実走／skip に変わらないか**を workflow 側で確認する。書き換える値が定期実行・
     キュー処理の有効化フラグなら、**その処理自身が dispatch していないか**を実装側で確認する。
     どちらも該当する向き（実走に変える／無人起動を始める）の操作は手順2b の対象。
   - 完了条件: 画面内の各コントロールについて「起動する／コストを有効化する（月枠 or 直接課金）／無人起動を有効化する／
     どれでもない」が確定している。
2. **対象のコントロールに印を付ける**（MUST）。印は次の2つを**両方**満たす:
   - **一目で他のボタンと区別できる**（配色・バッジなどの視覚的な差）。
   - **ホバーしなくても読めるテキストで、Actions を起動することが分かる**（可視のバッジ・ラベル・
     コントロール近傍の説明文）。**`title` 属性だけで済ませない**（MUST NOT）——タッチ操作とキーボード操作
     では、押す前に `title` を読めない。`title` は補足（枠が逼迫したときの挙動・関連 doc へのポインタ等）に
     使う（MAY）。
   - **その run が月枠を消費する／課金されるなら、そのコストも同じくホバー不要で読める**（MUST）。
     押す前にコストが分かることがこの手順の目的なので、`title` に逃がすとタッチ・キーボードでは
     押すまで分からない。文言は「前提・パラメータ」の区別に従う（月枠を消費する／実行のたびに課金される）。
   - 完了条件: 追加・変更したコントロールが両方を備えていて、ポインタを載せずに（＝静止画のスクリーン
     ショット上で）Actions 起動ボタンだと読み取れ、コストがあるならその文言も同じ画面に読み取れる。
2b. **押した後の実行のされ方を変える操作には、起動用とは別の印を付ける**（MUST）。要件（視覚差＋
   ホバー不要のテキスト）は手順2と同じだが、**起動用の印を流用しない**（MUST NOT）——「いまこの run が
   走る」と「押した後の実行のされ方が変わる」は意味が違い、同じ印にすると手順2の印が「workflow が走る」の
   信号として読めなくなる。**文言は変わる中身に合わせる**（MUST）:
   - コストが変わる操作 … 月枠を消費する側なら「**これ以降の…が実行枠を消費するようになる**」、
     直接課金される側（larger runner 等）なら「**これ以降の…が実行のたびに課金される**」（MUST。
     larger runner に枠消費の文言を使わない。MUST NOT）
   - 起動が無人になる操作 …「**止めるまで…が自動で起動する**」
   どちらも**いま走るのではない**ことが分かる形にする。**枠を消費しない run に枠消費の文言を混ぜない**
   （MUST NOT。→「前提・パラメータ」）——セルフホストランナー等で枠を使わないループなら、無人で起動する
   ことだけを書く。印が要る理由は課金の有無ではなく「押す前に分かるべき副作用」であること。
   - **副作用が減る向き（Actions 側を止める・無人ループを停止する操作）には付けない**（MUST NOT）。
     印は警告なので、減る側に付けると意味を成さない。「開始」に印を付けても、対になる「停止」には付けない。
   - **2b の2類型（コストが変わる／起動が無人になる）も互いに別の印にする**（MUST）。押した後に run を
     作るのが**人の push** か**そのループ自身**かで、読み手の次の行動が変わる（前者は push を控えれば
     止まる・後者は止める操作が要る）。**1つのコントロールが両方を有効化するなら両方の印を出す**（MUST）
     ——ここを弱い要求にすると、両方を兼ねるボタンで片方の印だけが出て「押した後に何が変わったか」を
     読み手が復元できない。完了条件（下記手順4）にも2類型が互いに区別できることを含める。
   - **印は「何が起きるか」しか伝えられない**。無人ループのように**止め方**が要る操作は、
     どの操作で止まるかをコントロール近傍の説明文に書く（SHOULD）。
   - 完了条件: 対象の操作に別印が付いていて、起動用の印と見分けが付く。

3. **印は共通部品経由で付ける**（MUST）。個別ページに配色や文言を直書きしない（MUST NOT）——コピペで
   ばらけると印として読めなくなり、文言を直すときに片方だけ直って drift する。
   - そのリポジトリにまだ共通部品が無ければ、**先に共通部品を作ってから使う**（MUST）。1個目でも直書きしない
     （2個目は必ずコピペされる）。
   - 共通部品側には「視覚差と文言はセットで使う」ことをコメントで残す（SHOULD）。片方だけ使う事故を防ぐ。
   - 完了条件: 対象のコントロールが共通部品を参照していて、ページ側に配色・文言の重複が無い。
4. **実描画で確認する**（SHOULD）。ダーク/ライト両方を持つ UI なら両方見る。配色だけで区別している場合、
   コードを読むだけでは他のボタンとの差が十分かを断定できない。
   - 完了条件: 対象ボタンが他のボタンと区別できること、および 2b の2類型（コストが変わる／起動が
     無人になる）が起動用とも互いにも区別できることを、実際のレンダリングで確認した。

## よくある失敗

- **印の片方だけ付ける**: バッジは足したが共通クラス（配色）を忘れる、あるいは逆。手順2の2要件は
  セットで1つの印。
- **Actions を起動しないボタンにも付ける**: 設定値の書き換えだけ・（自分では dispatch しない）cron 任せの
  ものまで印を付けると、「印＝workflow が走る」の意味が壊れる。手順1のコード確認で切り分ける。
- **cron を挟むと「間接だから対象外」と考える**: 逆側の失敗。適用外は「起動しない**かつ**コストも
  変えない」で、開始ボタンが無人ループを回し始め、そのループが dispatch するなら対象（2b）。
  「押した瞬間に run が出るか」だけを見ると落とす——**押した後に誰が run を作るか**まで追う。
- **dispatch の有無だけで対象を切る**: 経路スイッチのように「値を書くだけ」でも、その値が workflow の
  ゲートなら押した後の実行が課金対象に変わる。手順1の2つ目の確認を飛ばすと丸ごと見落とす。
- **`title` だけで説明した気になる**: 実装した本人はマウスで確認するので気づきにくい。スマホから使う
  管理画面では、`title` の中身は**押すまで読めない**。
- **既存ページをコピペして新ページを作り、印だけ落とす**: 新しい起動ボタンを足すときは、必ずこの doc の
  トリガに当たると認識する（コピー元に印があってもクラス名だけ写して定数の import を落とす等が起きる）。
