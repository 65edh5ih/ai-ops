# GitHub Actions を起動する UI の表示規約（全リポジトリ共通）

管理画面などの UI に **GitHub Actions の workflow を起動するコントロール**（ボタン・リンク・フォーム送信）を
置くときの表示ルール。押す人が**押す前に**「これは Actions の workflow を起動する」と分かる状態を保つのが目的
（その run が課金対象なら、**アカウント共有の月枠を消費する**という意味でもある。下記「前提・パラメータ」）。

## いつ使うか（トリガ）

- UI に **workflow を起動する（`workflow_dispatch` / `repository_dispatch` を投げる）コントロールを
  追加・変更するとき**。新規ページの作成でも、既存ページへの1個追加でも同じ。
- 既存コントロールの**起動有無が変わったとき**（Actions を投げない実装に変えた／逆に投げるようにした）。
- **押した時点では run を作らないが、それ以降の実行が枠を消費するように変える操作**を追加・変更するとき
  （→ 手順2b）。典型は「デプロイ経路を Actions 側に戻す」スイッチで、押した後の push から
  課金対象のジョブが実走に変わる。**run を作らないので上の判定では対象外**になるが、
  「押す前に分かるべき副作用」であることは同じ。
- 適用外: Actions を起動せず、枠消費の有無も変えない操作（ストレージや API を直接叩くだけ・
  設定値を書き換えるだけで実行に影響しない・cron 側の定期実行に任せるだけ 等）。
  **これらに印を付けない**（MUST NOT）——印が増えるほど「特別な操作だ」という信号が薄まる。

## 前提・パラメータ

- **なぜ要るか**: workflow の起動は、押した本人にも他の人にも見えにくい副作用（run の生成・デプロイ・
  外向きの処理）を伴う。UI 上で通常の保存・確認系ボタンと見分けが付かないと、意図せず起動してしまう。
- **枠を消費するかは「その run が課金対象か」で決まる**。典型は private リポジトリ ✕ GitHub-hosted runner で、
  月枠は**アカウント単位**で共有され、枠切れの実行は run の失敗に留まらず spending limit の設定次第で
  **実費課金**につながる（→ [`docs/actions-quota.md`](actions-quota.md)）。可視性だけでは決まらない
  （セルフホストランナーは private でも枠を消費せず、larger runner は public でも課金される）ので、枠の文言を
  付ける前に**対象 workflow の `runs-on` を読む**（MUST）。**枠を消費しない run に枠消費の文言を書かない**
  （MUST NOT）——誤った理由づけは印そのものの信頼を落とす。印を付けること自体は課金の有無によらず必要。
- **見た目の正本はリポジトリごとに1つ**: クラス名・バッジ文言・配色の実装は、そのリポジトリの UI 共通部品
  （`<UI共通部品のパス>`）に置く。**リポジトリ間で見た目まで揃える必要はない**（揃えるのは「印が付いている」
  という要件のほう）。

## 手順

1. **そのコントロールが本当に Actions を起動するかをコードで確認する**（MUST）。ラベル・置き場所・隣の
   ボタンから推測しない（MUST NOT）。ハンドラを追って `.../actions/workflows/<file>/dispatches` や
   `.../dispatches`（repository_dispatch）への送信があるかを実際に読む。
   - **dispatch が無くても、そこで終わりにしない**（MUST NOT）。書き換える値が workflow の
     ゲート（`if:` が読む repo variable 等）なら、**その値によって課金対象のジョブが実走／skip に
     変わらないか**を workflow 側で確認する。実走に変える向きの操作は手順2b の対象。
   - 完了条件: 画面内の各コントロールについて「起動する／枠消費を有効化する／どちらでもない」が
     確定している。
2. **対象のコントロールに印を付ける**（MUST）。印は次の2つを**両方**満たす:
   - **一目で他のボタンと区別できる**（配色・バッジなどの視覚的な差）。
   - **ホバーしなくても読めるテキストで、Actions を起動することが分かる**（可視のバッジ・ラベル・
     コントロール近傍の説明文）。**`title` 属性だけで済ませない**（MUST NOT）——タッチ操作とキーボード操作
     では、押す前に `title` を読めない。`title` は理由の詳細（枠を消費する等）を補うために使う（MAY）。
   - 完了条件: 追加・変更したコントロールが両方を備えていて、ポインタを載せずに（＝静止画のスクリーン
     ショット上で）Actions 起動ボタンだと読み取れる。
2b. **枠消費を有効化する操作には、起動用とは別の印を付ける**（MUST）。要件（視覚差＋ホバー不要の
   テキスト）は手順2と同じだが、**起動用の印を流用しない**（MUST NOT）——「いまこの run が走る」と
   「これ以降の実行が枠を使うようになる」は意味が違い、同じ印にすると手順2の印が「workflow が走る」の
   信号として読めなくなる。文言も「**これ以降の…が実行枠を消費するようになる**」と、いま走るのではない
   ことが分かる形にする。
   - **枠を使わなくなる向き（Actions 側を止める操作）には付けない**（MUST NOT）。印は警告なので、
     消費が減る操作に付けると意味を成さない。
   - 完了条件: 対象の操作に別印が付いていて、起動用の印と見分けが付く。

3. **印は共通部品経由で付ける**（MUST）。個別ページに配色や文言を直書きしない（MUST NOT）——コピペで
   ばらけると印として読めなくなり、文言を直すときに片方だけ直って drift する。
   - そのリポジトリにまだ共通部品が無ければ、**先に共通部品を作ってから使う**（MUST）。1個目でも直書きしない
     （2個目は必ずコピペされる）。
   - 共通部品側には「視覚差と文言はセットで使う」ことをコメントで残す（SHOULD）。片方だけ使う事故を防ぐ。
   - 完了条件: 対象のコントロールが共通部品を参照していて、ページ側に配色・文言の重複が無い。
4. **実描画で確認する**（SHOULD）。ダーク/ライト両方を持つ UI なら両方見る。配色だけで区別している場合、
   コードを読むだけでは他のボタンとの差が十分かを断定できない。
   - 完了条件: 対象ボタンが他のボタンと区別できることを、実際のレンダリングで確認した。

## よくある失敗

- **印の片方だけ付ける**: バッジは足したが共通クラス（配色）を忘れる、あるいは逆。手順2の2要件は
  セットで1つの印。
- **Actions を起動しないボタンにも付ける**: 設定値の書き換えだけ・cron 任せのものまで印を付けると、
  「印＝workflow が走る」の意味が壊れる。手順1のコード確認で切り分ける。
- **dispatch の有無だけで対象を切る**: 経路スイッチのように「値を書くだけ」でも、その値が workflow の
  ゲートなら押した後の実行が課金対象に変わる。手順1の2つ目の確認を飛ばすと丸ごと見落とす。
- **`title` だけで説明した気になる**: 実装した本人はマウスで確認するので気づきにくい。スマホから使う
  管理画面では、`title` の中身は**押すまで読めない**。
- **既存ページをコピペして新ページを作り、印だけ落とす**: 新しい起動ボタンを足すときは、必ずこの doc の
  トリガに当たると認識する（コピー元に印があってもクラス名だけ写して定数の import を落とす等が起きる）。
