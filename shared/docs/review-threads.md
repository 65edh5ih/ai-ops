# レビュー指摘の決着（全リポジトリ共通）

PR に付いたレビュー指摘を「誰も見ていない欠陥」にせず、**かつ指摘→修正→再指摘の往復を有限回で終わらせる**
ための手順。常時層（AGENTS.md「レビュー指摘は resolve までが1セット」）が要求する決着を、
どう満たすかがここにある。

## いつ使うか（トリガ）

- **自分の PR にレビューが付いたとき**（対応する前にここを読む。何周目かによって扱いが変わる）。
- **消化依頼を受けたとき**（「Codex の指摘に対応して」等）。
- `.ops-sync/codex-review-inbox.md`（無ければ依頼に添付された全体一覧の当該リポジトリ欄）に
  載っている件に着手するとき。
- **レビュースレッドに返信・resolve するとき**（権限が無くて代行を依頼するときも含む）。

## 前提・パラメータ

- **レビュアーは Codex だけで、人間のレビュアーはいない**。落とした指摘を後から拾う人がいないので、
  未 resolve のスレッド1本＝誰も見ていない欠陥1件。
- **在庫の正本は GitHub の resolve 状態そのもの**（別途の管理表は無い）。直して resolve すれば
  `codex-review-inbox` の次回実行で一覧から消える。
- 指摘には**優先度バッジ**（P1 / P2 / P3）が付く。付かない提案は P3 と同じに扱う。
- `<PR番号>` / `<スレッドURL>` は各作業で置き換える。

## 手順

### 1. 現在の正本を読んでから着手する（MUST）

**指摘文だけを見て直し始めない**（MUST NOT）。古い指摘ほど「既に直っているが未 resolve」の割合が高く、
確かめずに直すと二重に触る。

- **完了条件**: 指摘箇所の現在の内容を読み、既に直っているかを判定している。直っていれば手順5へ
  （返信して resolve するだけで終わる）。

### 2. 修正の置き場を決める（同じ PR に畳めるなら畳む）

- **その PR が未マージなら、同じ PR に積む**（MUST）。指摘1件ごとに PR を立てると、その PR がまた
  レビュー対象になって往復が増える。**別の依頼で作られた PR でも同じ**——常時層「1依頼=1PR」が
  禁じている積み足し（新しい作業を既存 PR に混ぜる）ではなく、**その PR 自身の指摘を閉じる修正**なので、
  1依頼=1PR の明示された例外にあたる。
- **マージ済みなら新しい PR にし、元 PR に残っている未 resolve スレッドの URL を新 PR 本文へ
  引き写す**（MUST）。元 PR を離れると、指摘と修正の対応が誰からも辿れなくなる
  （引き継ぎで分岐したときと同じ理由 → [`docs/agent-handoff.md`](agent-handoff.md)）。
- どちらかの判定に入る前に**マージ状態を実状態で確認する**（MUST。`merged`/`state` が正本。
  → [`docs/merged-branch-guard.md`](merged-branch-guard.md)）。指摘はイベントの数分後に届くので、
  読んでいる間にマージされていることがある。
- **完了条件**: 修正が載る PR が1つ決まっていて、その PR 本文から対象スレッドを辿れる。

### 3. 修正の範囲を、指摘された範囲に閉じる（MUST）

指摘は**具体的な反例**で来る。同種の箇所へ**原則として一般化するのは同じ PR でやらない**（MUST NOT）。

一般化した先には**反転する例外**があり、その場では検証されない。実例: 等値比較で照合順序を緩める規則を
節全体へ広げたところ、**除外**述語では網が逆向きに狭まり、事前確認をすり抜ける欠陥になった
（等値では安全側に働く緩和が、否定文脈では安全側にならない）。指摘1件への対応が、次のレビューで
指摘される新しい欠陥を作る——これが往復の主な燃料になる。

**閉じるのは「規則を新しい対象へ広げること」であって、同じ誤りの取りこぼしを直すことではない**。次の2つは
範囲の拡大に当たらないので、**同じ PR で全部直す**（MUST）:

- **指摘された主張・概念が他の箇所にも書かれている場合**（言い換えられた文・前提を述べたリード文・UI の
  文言・コード内コメントを含む）。1箇所だけ直すと新旧が併存して、どれが現行か読めなくなる
  （常時層「ドキュメントは現在形で書く」の要求。こちらが優先する）。
- **同じ diff の中に同型の箇所が複数あるとき**。

**広げてよいか迷ったら「これは同じ誤りか、それとも別の対象に規則を適用しているか」で判定する**——
前者なら直す、後者なら別 PR（SHOULD）。

- **完了条件**: diff が「指摘された誤りと、同じ主張を述べている全箇所」に収まっており、**指摘されていない
  対象へ規則を拡張した差分が含まれていない**。

### 4. 周回で止めず、優先度で止める（レビュー2周目以降）

レビューは走らせるたびに新しい指摘を返す（実測: 同じ変更への3周目でも新規3件）。**回数の上限を決めても
「あと1周」は正当化できてしまう**ので、止める基準は優先度に置く:

- **P1・P2 は周回によらず着手する**（MUST）。優先度は周回では下がらない。
- **2周目以降に新しく出た P3（優先度の付かない提案を含む）は着手せず、手順5の「対応しない」で
  決着させる**（SHOULD）。周回が進むほど指摘は「より良い書き方」に寄り、直すとまた新しい面ができる。
- **3周目でも P1・P2 が出続けるなら、変更を分割するかユーザーに判断を仰ぐ**（SHOULD）。同じ場所に
  重い指摘が出続けるのは、変更が大きすぎるか前提が誤っている信号で、周回では収束しない。

**これは「後回し」ではない**（放置は禁止のまま）。着手しない判断も**理由を返信して resolve する**ので、
スレッドは決着し、在庫にも残らない。**判断せずに開いたまま終えることだけが禁止**（MUST NOT）。

- **完了条件**: 各スレッドが「着手する」「理由を付けて対応しない」のどちらかに割り当てられており、
  未判定が残っていない。

### 5. 全スレッドを2つの決着状態のどちらかに入れる（MUST）

- **直した** → 修正が `main` に入った時点で resolve（MUST）。何を直したかがスレッドから自明でなければ
  返信も添える。
- **対応しない** → **理由を返信した上で** resolve（MUST）。無言の放置は「未対応」として残り続ける。

**修正が未マージの PR にあるうちは resolve しない**（MUST NOT）。resolve は「直った」の信号なので、
先に消すと未修正の欠陥が在庫から消える。**マージ待ちは決着ではない**——マージ後に resolve するところまでが
担当範囲で、そこまで済ませずにセッションを終えるなら手順7の残件として報告する。

**黙って直して resolve しないのが最悪**（MUST NOT）。スレッドは無視されたものと見分けがつかず、
修正済みの指摘が在庫に積み上がる（実例: 93件の在庫を棚卸ししたところ、大半が「既に直っているが
未 resolve」だった。次のセッションがそれを一から再調査していた）。

- **完了条件**: 対象 PR に未 resolve のスレッドが残っていない。残ってよいのは2つだけ——**修正が
  未マージの PR にあってマージ待ちのもの**（手順7で残件として報告する）と、**手順6の代行依頼分**。

### 6. 返信・resolve の権限が無いなら、代行を依頼する（MUST）

権限が無いことは、スレッドを開いたまま黙って終える理由にならない（MUST NOT）。完了報告に
**そのまま貼れる形**で並べる（MUST）:

```
- <スレッドURL>
  <投稿してほしい本文。対応しない判断ならその理由>
```

「権限が無いので対応できませんでした」だけで終えない（MUST NOT）——依頼されなければユーザーは代行できず、
結局その指摘は誰も見ていない欠陥のまま残る。

- **完了条件**: **権限が無くて自分で決着させられなかった**各スレッドについて、URL と投稿本文が
  完了報告に並んでいる。

### 7. 全件終えられないときは残件を明示して報告する（MUST）

時間・文脈が尽きたら、**残っているスレッドを列挙して報告する**。件数だけ稼いで完了扱いにしない
（MUST NOT）——報告の無い未着手は、次のセッションから「誰も見ていない指摘」と区別がつかない。

- **完了条件**: 「着手した件数」ではなく「残っている件」が報告に出ている。

## よくある失敗

- **指摘文を信じて直し、実は既に直っていた**（手順1）。古い在庫ほど起きる。
- **1件の指摘に1本の PR を立てた**（手順2）。その PR がまたレビューされ、往復が線形に増える。
  未マージなら畳む、が既定。
- **「ついでに他も揃えた」が新しい欠陥になった**（手順3）。指摘の対応で最も多い再発経路。
- **マージされずクローズされた PR の指摘を、その PR の diff に対して直そうとした**。その変更は `main` に
  入っていないので直す先が無く、在庫の表にも載らない（一覧では「対象外」の注記として件数だけ出る）。
  ただし2つは別: **引き継ぎで分岐した場合**（レビュー済みのコミットが後継 PR 経由で `main` に入るため、
  後継 PR 本文へ引き写されている）と、**同じ問題が `main` にも当てはまる場合**（現在の正本を見たうえで
  別途拾う。resolve は不要）。
