## 2026-08-01 無人ループの開始ボタンも印の対象だと明記した

`shared/docs/gha-trigger-ui.md` の適用外「cron 側の定期実行に任せるだけ」を、consumer 側の
エージェント（nikki-san）が「**cron が挟まれば対象外**」と読み、印を1つ落とした。落ちたのは
`/flickr-migration` の「開始（cron 自動処理）」で、押すと Worker の1分 cron が回り始め、以後
移行完了・sweep 完了・新着記事の取り込み完了などの区切りごとに**その cron 自身が**
`flickr-export.yml` を dispatch する（private ✕ `ubuntu-latest`＝枠を消費）。止まるのは
「一時停止」を押したときだけ。オーナーの指摘（「逼迫時に止めないといけないと分からない」）で発覚した。

**doc 側の不足**として直した。適用外は「起動しない**かつ**枠消費も変えない」の2条件だが、例示が
「cron 任せ」としか言っていないため、片方だけ見て適用外に落とせてしまう。直した点:

- 2b のトリガに**類型を2つ明示**した（経路の切替＝run を作るのは人の push／**無人ループの有効化**＝
  ループ自身が作る）。後者はこれまで例が無く、2b は経路スイッチ専用に読めた。
- 適用外に「**自分では workflow を起動しない**定期実行」と限定を入れ、「cron が挟まるので間接的だ」を
  適用外の理由にしない（MUST NOT）を足した。
- 2b の類型どうしも別の印にする（SHOULD）。**押した後に run を作るのが人の push かループ自身かで
  読み手の次の行動が変わる**（前者は push を控えれば止まる・後者は止める操作が要る）ため。
- **印は「何が起きるか」しか伝えられない**ので、止め方が要る操作は近傍の説明文に書く（SHOULD）を足した。
  今回の実装でも、バッジだけでは「どのボタンで止まるか」が伝わらずカード本文に1文足している。
- 「よくある失敗」に逆向きの失敗（cron を挟むと間接だと考える）を追加。既存項目は「起動しないものに
  付ける」側だけを警戒していて、**落とす側**の失敗例が無かった。

**初版では「無人起動」を「枠消費」の一形態として 2b にぶら下げてしまい**、セルフホストランナーで
回る無人ループが**規約内で矛盾**していた（2b は枠消費の文言を要求する／「前提・パラメータ」は枠を
消費しない run に枠消費の文言を書くのを禁じる／印自体は課金の有無によらず必要 → 適合する書き方が無い）。
Codex の指摘で**2条件を独立に**書き直した: 2b のトリガは「押した後の実行のされ方が変わる」で、変わり方が
「枠消費」と「無人起動」の2つ（片方だけのことも両方のこともある）。文言も変わる中身に合わせる。
**印が要る理由は課金の有無ではなく「押す前に分かるべき副作用」**という元からの原則に戻すのが正しかった。

**導線も同じ PR で広げた**（Codex の2件目の指摘）。この SOP はオンデマンド層なので、常時ロード層
（`AGENTS_COMMON.md` の共通ブロック）と skill の description が「dispatch する／枠消費が変わる」しか
言っていないと、**枠を消費しない無人ループを扱うエージェントはこの doc に辿り着かないか、常時層の
「起動せず枠消費も変えないものには付けない」に従って印を落とす**。SOP のスコープを広げるときは、
**発火トリガ側を同時に広げないと届かない**（オンデマンド doc は導線が無ければ存在しないのと同じ）。

consumer 側の対応（`GHA_AUTO_BADGE` の新設と適用）は nikki-san PR #755。

## 2026-08-01 decision を設計 doc の正本パスに publish する

### なぜこの作業が発生したか

`deploy-route-reconcile.yml` の `publish-ci-logs` が `dest: deploy-route/latest` を指しており、
**設計 doc・同 workflow の冒頭コメント・`scripts/deploy-route-reconcile.mjs` の3つが揃って
「出力は `deploy-route/decision.json`」と書いているのに、実際にはそこに無い**状態だった。
consumer（nikki-san / private の admin worker）は正本パスと現在の publish 先の**両方を試す**
実装なので動いてはいたが、正本が 404 のままなのは事実が2つある状態。

### 判断・制約

- **他の slice と違って `<name>/latest` にしない**。この slice は人が読むログではなく
  **consumer の worker が URL 直打ちで取りに来る配布物**で、URL が3箇所の doc/コードに
  書かれている。publish 先だけ慣習に寄せると正本パスが 404 のまま誰も気づかない。
  「なぜ `/latest` が付いていないのか」を後から `/latest` に戻されないよう、workflow に
  理由をコメントで残した。
- `publish-ci-logs` は `rm -rf ${DEST}` してから書くので、`dest: deploy-route` にすると
  **古い `deploy-route/latest/` は自動的に消える**（history-dir は未設定なので巻き添えは無い）。
- consumer 側の fallback（`latest/`）は**残す**。決め打ちにすると publish 先が動いた瞬間に
  404 で自動切替が黙って止まるため、どちらの順で直しても切れ目が出ない形を保つ。
  ただし consumer のコメントが「publish 側はいま latest に出している（是正待ち）」という
  **時点依存の書き方**だったので、時点に依存しない書き方へ直した（別リポジトリの PR）。

### 分かったこと（次に効く）

- **「設計 doc と実装が食い違っている」型の欠陥は、動作テストでは出ない**。今回も consumer が
  両パスを試すおかげで無症状だった。doc に書いた URL が実在するかは、doc とコードの
  **文字列一致**で見るしかない（`grep -rn "deploy-route/" --include=*.md --include=*.yml --include=*.mjs`
  で4箇所すべてが出るので、そこが一致しているかを見る）。

## 2026-07-31 cloudflare-quota: 空ページを認める前に応答形とページング情報を検証する

Pages プロジェクト一覧で `result` を `|| []` に潰していたため、**応答形が壊れているだけのケースが
「プロジェクトが1つも無いアカウント」と同じ経路に落ちていた**。空なら即 complete で、`used=0` から
`ok` が出る——ページング情報の検証（直前の PR で足した total_pages のチェック）を丸ごと素通りする
経路が残っていたことになる。問題は検証の順序で、**空を「終わり」と認める前に応答形とページング情報を
検証する**必要がある。

空ページを本当の「0プロジェクト」と認める条件は **API がそう言っているときだけ**（1ページ目 かつ
`total_pages` が 0 か 1）にした。そのため `total_pages` の下限を 1 から 0 に緩め、代わりに
「中身のあるページで `total_pages=0`」を矛盾として弾く。0 を一律に無効にすると、プロジェクトが
本当に無いアカウントで永久に unknown になりうるため。

この3連続の指摘（total_pages 欠落 → coerce 前検証 → 空ページ）はすべて**同じ穴の別の入口**だった:
「測れなかった状態が `ok` として配られる」。この信号は自動退避の判断に使われるので、判定を足すときは
**経路ごとに「そこは検証を通っているか」を確かめる**（1箇所直して終わりにしない）。モックで応答形3種・
空ページ4種・中身ありページ3種を流して確認した。

## 2026-07-31 cloudflare-quota: Pages 一覧のページ送り完了判定を fail-closed にする

`per_page` を渡さない形に直したことで、1ページあたりの件数を呼び出し側で決め打ちできなくなり、
`items.length < 100` という件数ベースの完了判定を捨てた。その結果 `result_info.total_pages` が
読めないケースが「1ページ目で完了」に倒れる形になっていた（fail-open）。2ページ目以降の
プロジェクトの deployment を丸ごと数え落としたまま `ok` を出しうる。この信号は自動退避の判断に
使われるので、**測れなかったものを `ok` として配るのが最悪の壊れ方**——`unknown` に倒した
（消費側は unknown を逼迫と同じに扱うので安全側）。

fail-closed にする前に、**それが現に効いている緑を壊さないか**を実測で確かめた: 修正版で再実行して
`pages_builds` が `ok` のままだったので、`total_pages` は実際に返ってきており、これまでの緑が
fail-open 分岐に乗っていたわけではないと確認できた。乗っていたなら `unknown` に落ちていたはずで、
確かめずにマージしていたら「Codex の指摘に従ったら信号が死んだ」になっていた。ops-sync は public
なので、この確認の dispatch はアカウント共有の Actions 枠を消費しない（枠が tight でも実行してよい）。

fail-closed への直し方自体も1回では正しくならなかった。`Number(rawValue)` を検証してから弾く形にすると、
`null` も `''` も `0` に化けて「有限の数」チェックを通り、`projectPage >= 0` が真＝1ページ目で完了、に
戻ってしまう（fail-closed にしたつもりで fail-open のまま）。**coerce する前に生の値を見る**必要がある。
モックで `null` / `0` / `''` / `1.5` を流して unknown になることを確認した。

診断の残し方も同じ轍を踏まないようにした。この PR の発端は note に `status 400` しか残っておらず
原因が特定できなかったことなので、`total_pages` が読めないときは `result_info` に**何が入っていたか
（キーだけ）**と値の型を note に載せる。出力先が public な ci-logs なので値は載せない。

## 2026-07-31 Pages の計測が `per_page` を渡していたせいで丸ごと落ちていた

CF 枠信号の `pages_builds` がずっと `unknown`（`pages projects list failed (status 400)`）で、
ブログ本体の自動退避が判断できない状態だった。原因は
**`GET /accounts/{id}/pages/projects` に `per_page` を渡していたこと**:

```
8000024: Invalid list options provided. Review the `page` or `per_page` parameter.
```

**値の問題ではない。** `per_page=100` を「上限超過だろう」と考えて同ファイル内の deployments 呼び出しと
同じ `25` に揃えたが、**それでも同じエラーだった**（実測）。`per_page` を**付けない**形にして初めて通った。
API リファレンスは `page` / `per_page` をどちらも `optional number` と書くだけで、上限も拒否条件も記載が無い。
ページ送りはレスポンスの `result_info.total_pages` で行う（`per_page` を指定しない以上、1ページあたりの
件数をこちら側で決め打ちできないので、`items.length` と定数を比べる完了判定もやめた）。

### 「原因が分かった」と言う前に、直したもので再実行する

`per_page=100` を見つけた時点で原因だと断定し、25 に直した段階で「直った」と報告してしまった。
実際は**同じエラーが続いていた**。**修正を当てた版で再実行して信号が変わったことを確認する**までは、
原因の特定も修正の成功も主張できない。今回は3回目の実行で初めて `ok` になった。

### 原因より、気づけなかった作りのほうが問題だった

note に `status 400` しか残していなかったため、**何が悪いのか誰にも分からない状態で残り続けていた**。
CF は `errors[]` に code と message を返しているのに捨てていた。先に「`errors[]` を note に含める」
修正を入れてから再実行したら、エラーコードが1回で見えた。外部 API のエラーは **status だけでなく
本文の code/message まで残す**。出力先が public な `ci-logs` なので、本文全体ではなく code と message だけ。

### `ci-logs` は orphan で毎回書き換わる（読み戻しの罠）

検証中、`git fetch origin ci-logs` では**古い内容を読み続けていた**。このブランチは publish のたびに
orphan 1コミットへ書き換えられるため、既に `origin/ci-logs` を持っている作業ツリーでは
`git fetch origin +refs/heads/ci-logs:refs/remotes/origin/ci-logs --force` が要る。
危うく「3回目も直っていない」と誤報するところだった。**信号を読み戻して結論を出すときは、
取得が最新かを疑う**（新規 clone では起きないので、Actions 上では顕在化しない）。

### 教訓

- **「docs に書いていない ＝ 渡してよい」ではない。** optional と書かれたパラメータでも、渡すと拒否される
  組み合わせがある。docs に無い任意パラメータを足さないほうが安全。
- **仮説→修正→再実行の再実行を省かない。** 1回目の断定（値の上限）は外れており、実測が唯一の決め手だった。

## 2026-07-31 経路の推奨を「判断」と「実行」に分けて公開する

`*_DEPLOY_POLICY=auto` を配線する突合処理。最初は ops-sync で**判断も実行も**やる形で書いたが、
**自分で書いた MUST NOT に正面から反していた**ので分離した。

### 何と衝突したか

`ops-sync-design.md` に「**ops-sync に置く CF トークンは読み取り専用にする**（MUST NOT: 書き込み権限を
持たせる）。ops-sync は public で、切替に要る Edit 権限の操作は consumer 側の workflow が自分のトークンで
行う」と書いてある。ops-sync で CF 側を反転するには書き込みトークンが要り、これを破る。

secret 自体は public リポジトリでも露出しないが、ops-sync は配布の要でワークフローの改変経路が多い。
「public 側に権限を集中させない」という設計思想でこの規定を置いたので、**規定を緩めるのではなく設計を
合わせる**ことにした（オーナー判断）。

### 分離の形

| | 場所 | 資格情報 | 頻度 |
|---|---|---|---|
| 判断 | ops-sync（public） | **不要** | 6時間ごと・Actions 分は無料 |
| 実行 | 各 consumer（private） | 自分の CF・変数トークン | 切替が要るときだけ |

**判断側が consumer の状態を持たないことが、資格情報を持たないことと表裏一体**になっている。
policy が `auto` か・CF が実際に出せるか・`HUGO_VERSION` が合っているかは、読み手が自分で確かめる。
結果、頻繁に回る側は無料かつ無権限、権限が要る側は年に数回しか動かない。

副次的な利点として、**オーナーが既に持っている consumer 側の CF トークンがそのまま使える**
（ops-sync 用に新しいトークンを発行する必要が無い）。

### 判断の規則

- **片方向ずつ条件が違う**: `github → cloudflare` は「Actions が逼迫 かつ 逃げ先の CF リソースが ok」、
  `cloudflare → github` は「Actions が ok」だけ。戻る先が空いていれば戻ってよく、CF 側の状態は問わない。
- **CF は対象の種類に対応するリソースだけ見る**。実測でこれが効いた: 現在 `pages_builds` は `unknown`
  （Pages のプロジェクト一覧が status 400 で失敗）だが `workers_build_minutes` は `ok` なので、
  全体 state で判定すると Workers 対象まで止まる。リソース別に見れば admin と private は退避可と出る。
- **信号が無い・壊れている・古いときは推奨を出さない**。推測で動かすと、実態と逆向きに倒して枠を焼くか
  配信を止めるかのどちらかになる。

### 残った問題

`pages_builds` が `unknown`（`pages projects list failed (status 400)`）。ブログ本体の自動退避は
これが直るまで動かない。突合とは別件の既存不具合なので、別途調べる。

## 2026-07-31 「枠消費を有効化する操作」を gha-trigger-ui の対象に足す

`gha-trigger-ui.md` は対象を「`dispatch` を投げるコントロール」で切っていた。しかし consumer 側で
**dispatch しないのに枠消費を左右するボタン**が見つかったので、対象定義を広げる。

### 見つかった穴

nikki-san / private のデプロイ経路スイッチは `actions/variables` を書くだけで dispatch しない。
だが書く値（`*_DEPLOY_ROUTE`）は workflow のゲート（`if:`）が読む値で、`github` に戻すと**以後の push で
deploy ジョブが `ubuntu-latest` 実走に変わる**（private リポジトリなので課金対象）。押した瞬間に run は
作られないが、「押す前に分かるべき副作用」であることは規約が守ろうとしているものと同じ。

字面どおりに判定すると**対象外**になり、印が付かないまま「押すと枠を使い始めるボタン」が並ぶ。
オーナーの意図は「**Actions の枠を消費するものに印**」で、そちらが本来の目的だった。

### 起動用の印を流用しない

consumer 側では既存の `GHA_BADGE`（「Actions」）を流用せず、別バッジ（「枠ON」）を新設した。
「いまこの run が走る」と「これ以降の実行が枠を使うようになる」は意味が違い、同じ印にすると
**手順2の印が「workflow が走る」の信号として読めなくなる**——規約自身が MUST NOT にしている
「印の意味が薄まる」がまさに起きる。この判断を規約側にも手順2b として明文化した。

**枠を使わなくなる向き（Actions 側を止める操作）には付けない**ことも明記した。印は警告なので、
消費が減る操作に付けると意味を成さない。

### 判定手順にも1段足した

手順1を「dispatch があるか」で終わらせず、**無くても「書き換える値が workflow のゲートで、課金対象の
ジョブが実走／skip に変わらないか」を workflow 側で確認する**ようにした。今回の見落としはここを
確認していれば防げた。「よくある失敗」にも同じ趣旨で1件足した。

## 2026-07-31 shared-file の本文をバイトそのままで書き込む

`shared-file` のベースハッシュをバイト厳密にした（#133・#134）のに、**書き込み側が正規化したまま**
だった。`stripFrontmatter()` が `.trim()` し、書き込みが `+ '\n'` していたため、提案本文と違うバイトが
書かれる。「ベースが一致したので安全」と判定した直後に境界バイトを黙って書き換えることになり、
バイト厳密にした意味が消えていた（Codex 指摘・#134 のマージ後に付いたもの）。

`stripFrontmatterRaw()`（trim しない）を分け、`shared-file` はそれを使って**そのまま書く**。
空判定は `!fileBody.trim()` に変えて、改行だけの本文が通らないようにしてある。
`common-block-edit`・`task`・`task-done` は従来どおり trim 版を使う（埋め込み・比較用途で、
バイトが意味を持たない）。

## 2026-07-31 feature ブランチからの dispatch が main を書き換えた（target checkout の ref 未指定）

- PR をマージ前に検証するつもりで `archive-task-history` を**自分のブランチの ref で dispatch** したら、
  そのブランチの差分が `main` に自動マージされた（生成された PR #138 に、履歴の統合だけでなく
  ブランチの全変更が入っていた）。**レビュー前のコードが main に入る経路**で、実際に起きた。
- 原因は `Checkout target repo` の **`ref:` 未指定**。`repository:` を指定しても、それが
  *この workflow を走らせているリポジトリ自身*（ops-sync は巡回対象に自分を含む）だと、
  actions/checkout は ref 省略時に **workflow の ref** を取る。consumer 側は別リポジトリなので
  既定ブランチが取れており、**自分自身を対象にしたときだけ**成立する。
  そこから `git checkout -B ops-sync/archive-task-history` → `base: main` の PR → `MERGE_MODE=direct`
  で自動マージ、と一直線に繋がる。
- **この穴は今回の変更で作ったものではない**（checkout ステップは元から同じ）。`peter-evans` 時代から
  あって、feature ブランチから dispatch する人が居なかったので露見していなかっただけ。
  自分でそれをやって踏んだ。
- 対処は `ref: main` の明示。**script source 側の checkout は ref 省略のまま**にする——そちらは
  「そのブランチのスクリプト・action で動かす」ことが dispatch 検証の目的なので、意図的に workflow の
  ref を使う。**取ってくる木（対象）と、動かすコード（スクリプト）で ref の意味が違う**のが要点。
- **collect-outbox にも同型の危険が残っている**: `Checkout ops-sync` が script source と
  「取り込み PR の作業ツリー」を兼ねているので、ブランチから dispatch すると intake PR にブランチの
  差分が乗る。こちらは提案が存在しないと PR 自体が立たないので今回は踏んでいない。分離するには
  checkout をもう1つ足す必要があり、別 PR にする。
- 教訓: **dispatch による事前検証は「読むだけ」ではない**。書き込み側（PR 作成・自動マージ）を持つ
  workflow をブランチ ref で回すのは、それ自体が main への書き込み操作になりうる。回す前に
  「この run が書き込む先はどの ref から作られるか」を確認する。

## 2026-07-31 outbox 経路の承認点を consumer 側 PR のマージとして明文化

自動マージを入れたとき「承認の実体は提案を書いたセッションでのユーザー確認」と書き、それを担保する
つもりで「ユーザーが見ていない提案を outbox に置かない（MUST NOT）」を SOP に足した。これが誤りだった。

第一に、常時層は「ユーザー不在の自律実行では outbox に置け」と指示しているので、2つの MUST が衝突して
自律実行のエージェントはどちらかを必ず破る（Codex が3 consumer すべてで指摘）。第二に、そもそも
**セッションでの確認は ops-sync 側から検証できない**ので、要求として書いても担保にならない。

**実際の承認点は既に存在していた**: outbox 経路の完了条件は「提案ファイルを含む open な PR があり、
`main` へのマージはオーナーが行う」で、提案は**オーナーが consumer 側 PR をマージして初めて main に載る**。
collect が拾うのはその後。つまり承認は消えておらず、**場所が違うだけ**（直接 PR は ops-sync 側、
outbox は提案を載せた consumer 側 PR）。取り込み PR の自動マージは、同じ変更を二度承認させないための
自動化であって、承認の省略ではない。

この整理により3つが同時に解ける:

- 自律実行との矛盾 … 「セッションで見たか」を要求しなくてよい（オーナーの PR マージが承認）。MUST NOT を削除。
- `sop-format.md` の経路等価性の実例 … 承認点が違うのではなく**場所**が違うだけなので、実例として
  引き続き妥当。ただし「マージするのは ops-sync 側」という書き方は不正確だったので直した。
- 「可視性は信頼境界ではない」（Codex P1） … 攻撃者モデルの指摘。このアカウントは全リポジトリ・
  全エージェントがオーナーのもので、write 権を持つ主体が侵害される前提なら outbox の有無に関わらず
  同じ被害が出る（outbox が新しい攻撃面を足すわけではない）。オーナー判断として対応しないことにし、
  理由を返信して resolve した。public/private の区別は、**不特定の第三者が fork/PR で内容を持ち込めるか**
  という別の理由で維持する。

教訓: 検証できない前提を要求として書くと、担保にならないうえに既存の経路と衝突する。書く前に
「その要求は誰がどこで満たすのか」を実在する手順の中で特定する。

**規約が自分と矛盾していたので規約側を直した**。`sop-format.md` の「経路違いの例外」は、条件を
「結果・承認点・保証が**同一**」と書きながら、判別条件を「その分岐で要求が1つでも**緩むか**」と
書いていた。同一のときは両者が一致するので今まで露呈しなかったが、public 発の outbox（承認が1回増える
＝安全側に振れる）で初めて食い違った。厳密な同一を求めると**安全側の経路まで禁止**され、エージェントは
満たせる要求を前に停止するしかない。条件を「同一か、より強い方向にしか変わらない」に直し、判別条件と
一致させた。最初は「判別条件の方が operative だから例外の範囲内」と返信して規約の文言を残そうとしたが、
それは規約の2文のうち都合のいい方だけを採る読み方で、規約を読むエージェントには通用しない
（Codex に再指摘された）。**規約に矛盾があるなら、運用側で読み替えず規約を直す。**

**同じ主張は全箇所を一度に直す**。承認モデルの訂正を SOP 1箇所だけ直したところ、常時層・生成される
取り込み PR 本文・workflow コメント・設計 doc・書き手の表に古い主張が残り、Codex に3回に分けて
指摘された（配布 SOP と常時層が食い違うと、エージェントは SOP を開く前後で違う指示を受ける）。
特に**生成物のテキスト**（取り込み PR 本文）は grep 対象から漏れやすい——自動マージされた PR に
「セッションでユーザーが確認しています」と書かれ続けると、承認の出所として嘘の記録が残る。
主張を変えるときは、その主張を述べている全箇所を grep で洗ってから直す。

## 2026-07-30 指紋一致の outbox 提案を自動マージする

取り込み PR の手動マージは「提案内容の再認可」として機能していたが、提案はそれを書いたセッションで
ユーザーが見ている。同じ内容を2度承認していることになり、その待ち時間のあいだ提案が outbox に居座って
上り経路全体を止めていた（選択は全 consumer 横断の最古1件なので、1件の未マージが他 consumer も止める）。

**自動マージの判定に使えるのは「提案が書かれた後に前提が変わったか」だけ**、という切り分けで設計した。
これはスレッドでの承認では原理的に代替できない情報（承認時点では衝突がまだ存在しない）で、逆にこれ以外
——提案内容そのものの妥当性——は取り込み時に機械が判断できない。よって条件は次の3つに絞った:

- 全文置換（`common-block-edit`／`shared-file`）のベースハッシュが現在の正本と一致すること。
- ベース欄の欠落は「判定不能」であって「問題なし」ではないので保留側に倒す。既定を保留にしておかないと、
  ベースを書き忘れた提案が検査を素通りしてしまい、検査を入れた意味が消える。
- `common-block-edit` の常時層の純増が上限内（`COMMON_GROWTH_LIMIT` = 800 文字）。内容が正しいかと
  「全 consumer の全タスクに常時乗るコストを払う価値があるか」は別の判断で、後者は機械には決められない。
  800 は現状 1 万文字弱の区間に対して「節が1つ増える規模」の目安。厳密な根拠は無いので、実運用で
  保留が多すぎ／少なすぎなら動かしてよい。

`task`／`task-done` は全文置換ではなく巻き戻る対象が無いので、検査の対象外＝常に自動マージ可。

**cleanup PR は取り込みが実際に入った後にだけマージする**。先に outbox を空にすると、オーナーが取り込み
PR を close して却下する逃げ道が消える。例外は却下だけの run（applied=0）で、これは取り込み PR 自体が
無く判断待ちも無いのに、人間待ちにすると壊れた提案1件が最古に居座って全 consumer を止めてしまう。

自動マージで通常経路が緑になるぶん、**残るものが見えなくなる**ので、run の最後に「人間を待っている
もの」（保留された取り込み PR・差し戻した提案）を `::error::` で立てて run を失敗させる。赤の意味を
「壊れた」から「人間が見るまで進まない」に寄せた。この step を最後に置いているのは、失敗で ci-logs の
publish やトゥームストーン掃除を巻き添えにしないため。

**ハッシュの取り方を種別で分けた**（consumer 同期 PR 側の Codex 指摘）。`common-block-edit` は
AGENTS.md のマーカー間から切り出す都合で前後の空白が必ず変わるので `.trim()` が要るが、`shared-file` は
バイト一致で配る実ファイルそのもので切り出しが無く、trim する理由が無い。trim したままだと
「末尾改行だけが変わった」ような境界だけの変更を検出できず、鮮度検査をすり抜けた全文置換がその変更を
黙って巻き戻す。自動マージを入れたことで人間の目が入らなくなるぶん、この穴の危険度が上がっていた。
取り込みの書き込みは `本文 + '\n'` に正規化されるので、バイト厳密にしてもラウンドトリップは安定する
（取り込み後のファイルを次の提案のベースにして一致することを確認済み）。

**この指摘は ops-sync の PR には出ず、consumer 同期 PR（private #483）にだけ出た。**
AGENTS.md「配布変更のダウンストリーム確認」が想定している通りの実例で、確認していなければ
配布物の欠陥がそのまま全 consumer に残っていた。

**認可の根拠を可視性に置いた**（Codex P1 指摘への対応。実際に経路が通ることを確認して受け入れた）。
初版は「提案はスレッドでユーザーが見ている」を自動マージの根拠にしていたが、これは ops-sync 側から
検証できない。提案は consumer の main に置かれたただのファイルで、署名も承認記録も無い。実際、新規の
`shared-file` はベース欄が不要なので保留理由がゼロになり、`shared/.github/workflows/` に任意の workflow を
入れて `OPS_SYNC_TOKEN`（全 consumer に Contents:RW＋Workflows:RW）で全 consumer へ配布できた。
これは設計 doc が「consumer が1つ侵害されると全リポジトリへルールを注入できる増幅経路」として
廃した構造を、トークンではなく**ファイル配置を入口として**再導入していたことになる。

代わりの根拠に **提案元 main への書き込み権**を採った。private なら main に載った時点でオーナーの
アクセス下にあり、置かれたこと自体がスレッドに現れる。public にはこの前提が無い（誰でも fork して
PR を出せる）ので種別によらずレビューに回す。可視性の判定は workflow が行い、**判定できなかった repo は
public 扱い**、判定ステップ自体が動かなかった run は全 consumer を public 扱いにする（fail closed）。
「public が1件も無い」と「判定していない」を同じ空リストで表すと関門が黙って消えるため、
`VISIBILITY_CHECKED` で両者を区別している。

**ダウンストリーム確認の穴を codex-review-inbox に受け持たせた**。自動マージされた取り込み PR は
扱うセッションが居ないので、配布変更の確認（consumer 同期 PR の Codex 指摘を読む）を行う者が居なくなる。
自動マージの条件は「前提が変わっていないこと」しか見ておらず配布物としての正しさは見ていないため、
条件を厳しくしても埋まらない。

調べたところ **inbox は収集側は既に完成していた**——毎時・全リポジトリ横断で未 resolve の Codex
スレッドを集め、マージ済み PR に残るものを 🔴 で最優先表示する。欠けていたのは**エスカレーション**で、
一覧はファイルなので誰かが見に行かない限り気づけない（従来はセッションが生きている前提のルールが
その役目を担っていたが、自動マージ経路にはそのセッションが無い）。そこで 🔴 が1件でもあれば run を
失敗させるようにした。取得失敗も同様に失敗扱いにする——読めなかったものを緑で流すと「指摘ゼロ」と
区別できない。open PR の指摘（🟡）は、その PR を見ている者が居るので失敗させない。

**エスカレーションを入れると「緑」の意味が変わる**（Codex 指摘）。inbox には元々、レビュースレッドが
1ページ（50件）を超えた PR を注記するだけで済ませる経路があった。一覧を読む前提なら注記で足りたが、
run の成否で伝えるようにした以上、**読み残しがあるのに緑**は「確認済み」の嘘になる。取得失敗と同じ
「読めなかったものは落とさない」側に寄せて failures に積む。エスカレーションは既存の fail-open の
許容度を下げる——信号を強くするなら、その信号が依拠する網羅性も上げないと整合しない。

**`create-pull-request` の no-op には2形態ある**（Codex 指摘）。差分が消えたとき、PR が未作成なら
url が空になるが、**前の run で PR を作ってあると既存 PR を close して url を返す**。url の有無だけで
「無変更」を判定すると後者を取りこぼし、掃除がされず提案が最古に居座る。レビュー待ちで保留された提案の
内容が、その後べつの経路で正本に入ると実際に起きる。`pull-request-operation == 'closed'` を併せて見る。

## 2026-07-30 shared-file 提案にベースハッシュ（鮮度検査）を追加

`common-block-edit` にだけ `ベース:` の鮮度検査があり、同じ全文置換である `shared-file` には
何も無かった。提案が書かれてから取り込みまでには cron 1周（約6時間）＋他提案の待ち行列ぶんの
時間が空くので、その間に正本が変わっていると、取り込んだ瞬間にその変更が黙って巻き戻る。
差分上は「提案者が意図的にその行を消した」ようにしか見えず、レビューでも捕まらない。

不一致には2系統の原因があるが区別しない: (1) 提案後に正本が変わった (2) 提案元 consumer に
最新の配布が届いておらず、古いコピーを基に書かれた。(2) は「エージェントがさっき読んだばかり」
でも起こるが、巻き戻る危険は (1) と同じなので、どちらも等しく要確認にする。

提案側は自分のリポジトリの `<対象パス>`（配布されたコピー）をハッシュし、取り込み側は
`shared/<対象パス>` をハッシュする。`apply-shared.mjs` がバイト一致でコピーするので両者は同値になる
（`hash12` は `.trim()` してから SHA-256 なので、末尾改行の差では割れない）。この前提が崩れる
——配布時に内容を変換するようになる——と検査が常時不一致になるので、そのときは両側を合わせて直す。

新規ファイル追加は「差し替える既存内容が無い」ので `ベース:` 無しが正常。逆にベース付きで対象が
存在しない場合は、対象パスの誤りか提案後の削除を疑う状態なので不一致として扱う。

検査は今回も**警告どまり**（無くても取り込む）で、`common-block-edit` と揃えた。将来これを
自動マージの判定に使う場合は、「ベース無し」を自動マージ対象外にする必要がある
（判定不能を「問題なし」と読み替えないため）。

## 2026-07-30 net-fetch の public 側の痕跡を定期 sweep 側で消し切る

#126 の続き。#126 は「読了後の cleanup dispatch を主経路にする」までで、**公開時間の上限が
エージェントの協力に依存していた**（cleanup を投げ損ねると TTL 3日＋sweep 1日 ≒ 4日残る）。
指摘を受けて、上限の担保を**エージェント非依存の側（public の定期 sweep）に移した**。

**判断の軸**: public は Actions 無料なので、ワークフロー側の仕事を増やすコストが 0。
一方エージェントは落ちる・忘れる・中断されるので、**MUST と書いても強制力がない**。
よって「エージェントの cleanup ＝ 正確な信号（秒で消す最適化）」「定期 sweep ＝ 上限の担保」に
役割を分けた。private は露出しないので従来どおり sweep なし・TTL 3日・枠消費ゼロ。

**やったこと**:

- **TTL を可視性で分けた**（public 60分・private 3日）。`publish-ephemeral` の `retention-days` は
  整数日で下限1日だったので、`retention-minutes` を新設した（正の整数のときだけ日側に勝つ。
  空・不正値は日側に fallback＝**タイポで TTL 0 になって読み中のスライスを消さない**方に倒す）。
- **sweep を日次→毎時**。掃除間隔がそのまま TTL の超過分になるので、TTL 60分に対して日次だと
  最大25時間残る。毎時なら上限 ≒ 2時間。
- **public では sweep が「1日より古い成功 run」を run ごと削除する**。本文をログから外しても
  run には `meta`（取得 URL・時刻）と dispatch 入力（`url`/`request_id`）が残り、これは結果ブランチの
  TTL の対象外で Artifact and log retention（ops-runner は7日設定）に従うため、public では
  TTL や cleanup で縮めた公開時間がログ側で無効になっていた。

**なぜ run_id の台帳を作らなかったか**（当初は「run 側が run_id を記録すればよい」と考えた）:
**Actions API が run 一覧そのものを持っている**ので記録は不要。`GET .../workflows/net-fetch.yml/runs
?status=success` を `created_at` で絞れば削除対象が出る。台帳をブランチに置くと、cleanup が
スライスを消したときに記録も消えて run が孤児になる順序問題も抱える。

**なぜログだけ削除（`DELETE .../runs/{id}/logs`）ではなく run ごと削除か**: 前者では run が残り、
**dispatch 入力の URL が見え続ける**ため目的を達しない。

**捨てたもの**: public では1日より後に「いつ何を取得したか」を遡れない（net-fetch は `ci-logs` に
publish しないので他に記録がない）。失敗 run は残すので障害調査は可能——retention 7日は
「エージェントのトークンが切れて後日調べる」ために設定されており、成功 run の削除はこれを損なわない。

**副作用（許容）**: `schedule` は workflow 単位でしか設定できず可視性で cron を分けられないので、
private consumer では毎時 skip の run が履歴に並ぶ（分数は 0）。

**権限**: `actions: write` は **sweep ジョブにだけ**与えた（job-level `permissions`）。
クリーンルームの fetch ジョブには渡さない。

**検討して却下した案**:
- **5分 cron** — GitHub の scheduled run は数十分遅延が常態で高負荷時には落とされるので、上限が名目だけになる。
- **run 内で `sleep` して自分で消す** — public なら無料だが run が `in_progress` のまま居座り、
  エージェントの読み取り合図（run completed）と衝突する。合図をジョブ単位に変える必要が出て、
  エージェントへの要求が増える。
- **遅延 cleanup run の自己 dispatch** — `GITHUB_TOKEN` 起点の `workflow_dispatch` は再帰防止で抑止され、
  PAT が必要になる。`consumers.txt` の「ops-runner に書き込み資格情報を置かない」に反する。

## 2026-07-30 マージ済み PR の Codex 指摘消化（net-fetch cleanup・削除の意味・入力境界）

### 退避スライスの名前は「別 run から再現できる」ことが要件（ops-sync#126）

`request_id` が弾かれた取得の退避先が `_invalid-<時刻>-<PID>` だった。**cleanup は取得とは別 run** なので
この名前は誰にも再現できず、エージェントが持っている生 ID からは到達できない——退避スライスが残ったまま
「nothing to drop」で緑になり、手順6の「緑＝外れた」が嘘になる。生 ID の digest にして決定的にした。

Codex の2案のうち「サニタイズ済みスライス名を渡す」を採らなかったのは、**取得 run の summary から名前を
転記する手順がエージェント側に増え、転記漏れが同じ失敗に戻る**ため。決定的な名前なら手順が増えない。

### 「削除」は到達不能化であって消去ではない（ops-runner#35）

`rm` も TTL もブランチ削除も、ブランチ先端から辿れなくするだけ。到達不能な object はリモートに残り、
公開中に SHA を記録した相手は取得できる（GitHub に GC を強制する手段は無い）。**コード側で解けないので
主張のほうを実態に合わせた**。重要なのは帰結で、**機微性の判断は cleanup の有無ではなくモード選択で行う**
——「あとで cleanup するから数分で消える」を public 経路に流す根拠にしてはいけない。既存ルール
（機微を集約モードに流さない）は正しかったが、根拠が「公開時間が短いから許容」に読める書き方だった。

### 予約・改名は「導入前のデータ」を到達不能にしうる（自 PR の指摘より）

digest 退避先の導入自体が新しい衝突を2つ作り、どちらも Codex に拾われた:

- 退避先 `_invalid-<digest>` を**ユーザーが request_id に選べた**ので、ある ID の cleanup が無関係な結果を
  消しえた。`_invalid-*` を予約して名前空間を分離した。決定的な名前と自由に選べる ID は分離して初めて両立する。
- その予約を**消す側にも掛けてしまい**、予約導入前に `_invalid-foo` で publish された既存スライスが名前で
  指せなくなった。予約の目的は「新しく作らせない」ことなので**作る側だけに掛ける**。削除は常に安全な方向。
  予約・改名を入れるときは**導入前に作られたデータが到達不能にならないか**を必ず見る。

もう1件は、multiline output のデリミタを固定にしていたもの。`__NET_FETCH_SLICES__` 自体が妥当な
request_id なので入力が output を閉じられた。**サニタイズは「値がデリミタと一致しない」ことを保証しない**。
`net-fetch.sh` は既に乱数＋衝突チェックをしていたのに、**同じ出力プロトコルを2箇所で別々に書いたため**
こちらで再発させている。

### ops-sync は自分の配布物の consumer ではない（branch-cleanup の二重管理）

`branch-cleanup.yml` は `shared/` の正本と `.github/workflows/` の実行コピーの**2箇所にある**
（ops-sync 自身は sync の consumer ではないため）。正本だけ直して実行コピーを放置し、
**ops-sync 自身では脆弱なまま**という状態を作った。ファイル冒頭に「変更するときは両方を同時に直す」と
書いてあるのに見落としている——`shared/` を直したときは、それが ops-sync 自身にも要るファイルかを確認する。

### 入力境界は「正規化の前」に要る（private#474）

先頭ゼロ除去が二次時間で、桁数ガードはループの後にあった。**桁数ガード（正規化後）と長さガード（正規化前）は
別物なので両方要る**——`0...0365` は正規化後3桁で通るが、生では任意に長くできる。

## 2026-07-30 CI ログの公開先を『何についてのログか』で決める

- 発端は「public に出て困るログがあるなら、Codex レビュー一覧と同じく private リポジトリへ出したら
  どうか」という提案。実測すると仮定ではなく**実害**があった: ops-sync（public）の `ci-logs` の
  `archive-task-history/<repo>/**` に、private consumer の history-inbox の**ファイル名**（＝タスクスラッグ）が
  毎日出ていた（nikki-san 40件・private 22件が既に公開済み）。`collect-outbox` も提案ファイル名と却下理由を
  出す設計で同じ予備軍だった。`ci-logs.md` は既に「public に機微を出さない（MUST NOT）」と書いていたので、
  規約違反が実装側に残っていた形。
- **宛先を1つの private リポジトリに寄せる案は採らなかった**。理由2つ:
  (1) quota 信号（`quota/actions/actions.json`）は **public であることが要件** ——読み手は全リポジトリの
  エージェントで、public な ops-runner も含む。private に移すと「能力ゼロで読める」（issue ではなくファイルに
  している理由と同根）が崩れる。(2) `ci-logs.md` 手順B は「自分のリポジトリの ci-logs を読む」前提で、
  ops-sync 自身のログを他リポジトリへ移すと CI 失敗調査のたびに `add_repo`＋ユーザー確認が要る。
- 採ったのは**対象リポジトリごとに散らす**形（`publish-ci-logs` に `repository:` 入力を追加）。可視性が
  対象の可視性に自動一致し、かつ読み手（そのリポジトリで作業するエージェント）と同一リポジトリになる、
  この2つを同時に満たせるのはこの形だけ。Codex レビューの全体一覧が private 1箇所でよいのは、あれが
  **人が1本開いてトリアージする成果物**で読み手も置き場も1つだから（性質が違う）。
- 公開側ロールアップの件数は、詳細ログを grep で削るのではなく `$GITHUB_OUTPUT` で**作り分けた**
  （フィルタ方式は新しいログ行が増えるたびに漏れる）。ロールアップに `history-dir` を残したのは、
  齢による prune が効いて**旧方式で積まれた（ファイル名を含む）履歴エントリが保持期間 30 日で枝先から
  落ちる**ため。ただし git 履歴からは消えない（`ci-logs` の作り直しは別途ユーザー判断）。
- 公開してよい上限は**件数・repo 名・成否・PR URL まで**と決めた（既存の `sync/<consumer>/` スライスが
  既にこの粒度で、そこに合わせた）。対象リポジトリの中身に由来する文字列（ファイル名・パス・本文）は出さない。

## 2026-07-29 net-fetch の掃除を定期 sweep 依存から「読了後の cleanup dispatch」へ移す

consumer（nikki-san）で「net-fetch ジョブが落ちている」を調査していて見つけた、配布物側の設計の歪み。

**なぜ変えたか**: 日次 sweep の根拠は `net-fetch.yml` のコメントどおり「集約モードは public なので、
TTL を超えて世界公開する時間を最小化する」こと。この便益は public な ops-runner でしか発生しないのに、
同じファイルが private consumer（nikki-san / private）へ無改変で配られ、そこでは**結果が非公開＝便益ゼロ
なのに Actions 分数だけがアカウント単位の月枠に課金される**状態だった。nikki-san では
`net-fetch-results` ブランチが一度も存在せず、掃除対象ゼロの空振りを毎日スケジュールしていた。

**なぜ repo variable でなく `github.event.repository.private` で分けたか**: 判定軸が
「結果が世界公開されるか」＝リポジトリの可視性そのものなので、可視性を直接読めば consumer 側の
設定作業がゼロで済み、variable の設定漏れによる drift も起きない。

**捨てたもの（意図的なトレードオフ）**: private の保持期間の上限。`publish-ephemeral` は
`prune-only` でなくても同じ失効ロジックを通るので掃除機能自体は残るが、契機が「次の取得」だけになり、
休眠中は最後のスライスが**次に net-fetch を使うまで**残る（上限なし）。非公開なので世界公開には
ならないという判断。この事実は3箇所（`shared/docs/net-fetch.md`・`shared/docs/ops-sync-design.md`・
`README.md`）に書かれていたので全部モード別に書き分けた——**片方だけ直すと「3日で消える」を
private で当てにする読み手が出る**。

**やらなかったこと**: 枠切れ自体の対処。sweep の失敗（nikki-san で 07-27〜07-29 の3 run、いずれも
`runner_id: 0`・`total_ms: 0` のランナー割り当て拒否）は**枠を消費した原因ではなく結果**で、sweep は
一度も成功していない＝1分も課金されていない。枠の実数確認は billing 画面が正本。この PR は枠の
復旧策ではなく、上記の「効かない保証のために枠を払う」構造だけを直すもの。

### レビューで設計を差し替えた（当初案 → 最終案）

当初は上の「public 限定ゲート」だけだったが、ユーザー指摘で**定期 sweep 自体が最善でない**と分かり
2点を追加した。判断の軸は「定期実行は使わない月も課金されるが、後片付けは使ったときだけでよい」。

- **読了後の cleanup dispatch を主経路にした**（`cleanup: 'true'` 入力＋`cleanup` ジョブ、
  `publish-ephemeral` に `drop-slice` 入力を追加）。公開時間が TTL の3日から実際の読み取り時間
  （数分）に縮み、かつ休眠中の課金がゼロになる。日次 sweep は「dispatch をし損ねたとき」の
  バックストップに格下げ（public のみ）。
  - **エージェント自身にブランチを消させるのは却下**: doc が要求している能力は結果の読み取りだけで、
    ops-runner は「書き込み権限を持つ資格情報を置かない」方針（`consumers.txt`）。`add_repo` の
    read 権限でも push できない。dispatch なら既に持っている `actions:write` で足りる。
  - **「5分後に消す」も却下**: 同一ジョブで `sleep 300` すると1取得あたり5分課金で日次 sweep より高い。
    別 cron にすると高頻度 sweep そのもので、しかも GitHub の scheduled run は数十分遅延が常態。
- **応答本文をジョブログに出すのをやめた**（meta＋`bytes`/`sha256` だけに）。ログは git ブランチでは
  ないので TTL が効かず、Artifact and log retention（ops-runner は7日設定）に従って残る——public では
  world-readable のままで、**TTL や cleanup で縮めた公開時間がログ側で無効になっていた**。
  - 併載の元の理由は「ブランチを fetch できないランタイムのため」と読めたが、**実際は往復回数の
    削減にすぎなかった**（doc 自身が読み方に「コンテンツ取得 API」を挙げている＝dispatch できる
    権限があればブランチも読める）。能力の橋渡しではなかったので、落として失うものは無い。
  - retention を1日に下げる案は採らない: ユーザーが Actions のエラー調査用に7日で運用している
    （エージェントのトークンが切れて後日調べる場合に備える）。本文を出さなければ retention は
    長くても無害なので、そちらを維持する。
- **private は TTL 3日のまま**（全消しにしない）。非公開で露出しないため、抑えたいのは Actions 消費だけ。

### レビューで見つかった要注意点（同じ罠を踏まないための記録）

- **`drop-slice` の検証は `net-fetch.sh` と同じ構造検査に揃えた**。当初 `*/*|.|..` だけ弾いていたが、
  それでは**改行を含む値**が通り、ログ出力の `${DROP_SLICE}` 経由で `::workflow command::` を
  注入できた。検査は shell の `case` で値全体に当てる（`grep` の `^`/`$` は行ごとに一致するので
  複数行の1行目だけ正しい値を通してしまう）。
- **生の ID をログに出さない**（digest だけ出す）。`ghp_...` のような token 形は文字種検査
  `[A-Za-z0-9._-]+` を素通りするので、public runner のログに出すと世界公開になる。
  **`SECRET_PATTERNS` を publish-ephemeral 側に複製する案は採らない**——同じリストの二重管理は
  AGENTS_COMMON が警告する drift そのもので、「出さない」なら複製せずに漏洩を塞げる。
  ただし `workflow_dispatch` の入力値は GitHub が run メタデータに記録するので、これは
  多層防御であって完全な封じ込めではない（→ SOP の「よくある失敗」に明記）。
- **`.` は単独で弾く必要がある**（`*..*` では捕まらない・許可文字なので文字種検査も通る）。
  `net-fetch.sh` 側の `structurally_valid_request_id` にも同じ穴があり、こちらは影響が重い:
  dest が `net-fetch/.` になると `cp -a src/. <root>/./` で結果ファイルが SLICE_ROOT 直下に散り、
  失効ループは `-type d` の直下ディレクトリしか走査しないので**どの TTL でも消えなくなる**
  （public なら恒久的に世界公開）。両方に `|.` を追加した。
- **`publish-ephemeral` の push 失敗は既定で警告＋`exit 0`**。「緑＝ブランチが更新された」と
  解釈する呼び出し側（cleanup＝緑なら消えた／fetch＝本文の出口がブランチだけになったので
  publish 失敗＝結果消失）には `fail-on-publish-error: 'true'` を渡す。定期 sweep は既定のままで
  よい（翌日リトライされるため）。
- **cleanup の要求強度はモードで分けた**: 集約（public）は MUST、分散（private）は MAY。
  当初は無条件 MUST と書きつつ private では「その場の判断でよい」と書いており矛盾していた。
  private は枠が課金されるので、逼迫時は省略してよいのが正しい。

## 2026-07-29 レビュー指摘は resolve までを義務化

旧ルールの発火条件は「**積み残し消化系の依頼を受けたら**」だったため、**通常の PR レビュー対応で
指摘を直したエージェントには何の要求も掛かっていなかった**。直しただけで返信も resolve もしないと、
スレッドは「無視された指摘」と機械的に見分けがつかず、在庫に残り続ける。実際 93 件の未対応在庫を
棚卸ししたところ、大半が「既に直っているが未 resolve」で、指摘そのものより**棚卸しコストの方が
大きい**状態になっていた。発火条件を依頼の種類から「指摘に対応した」という行為そのものへ移した。

`resolve` を「直った」の唯一の信号として扱う以上、**早すぎる resolve も同じ害**になる（未修正の欠陥が
在庫から消える）。修正が未マージ PR にあるうちは resolve せず、マージ後に閉じるところまでを担当に
含める、を MUST NOT 側で明記した。この判断は今回の作業で実際に必要になった——共通配布物の修正 11 件は
ops-sync 側の PR がマージされるまで resolve を保留している。

**「Codex 以外にレビューする人がいない」という前提を明記した**のが、この改訂で一番効く部分。これは
ソースからもリポジトリ構成からも読み取れず、書いていないとエージェントは「人間のレビュアーが最後に
見る」「重要なら誰かがまた指摘する」という**存在しない安全網**を暗黙に仮定する。仮定が置ければ指摘を
落とすのは合理的な省力化になってしまうので、MUST を並べる前に前提を壊す必要があった。
今回取得したスレッドの作成者が全件 `chatgpt-codex-connector`（他は所有者の返信のみ）である点とも一致する。

消化依頼そのものにも完了要件が無かった。「載っている＝未対応」は一覧の読み方でしかなく、**全件を
終端状態にする義務も、落とした分を報告する義務も無い**ため、一部だけ直して完了扱いにしても
ルール上は違反にならなかった。全件終端＋残件報告を MUST にした。あわせて「指摘文だけを見て直し始めない
（先に現在の正本を読む）」も入れた——古い指摘ほど修正済みの割合が高く、確かめずに直すと二重に触るため。

**resolve 権限を持たないエージェントがいる**（Codex 自身など）。初稿は「resolve する（MUST）」と
能力を前提に書いていたが、これは `docs/sop-format.md` の「要求するのは能力であって特定ツールではない」
「満たせないときは勝手に別の振る舞いへ切り替えず停止してユーザーに依頼する」に**その規約自身が違反**
していた。要求を「resolve **済みにする**」という結果で書き直し、満たし方（自分でやる／ユーザーに代行を
依頼する）をその下に並べる形へ変更した。同 doc の「例外は結果が同一の経路違いだけ」に照らすと、
代行依頼は結果・承認点が同一なので経路違いとして正当。

代行依頼は**そのまま貼れる形**（スレッド URL＋投稿本文）で出すことまでを MUST にした。「権限が無いので
できませんでした」で終えると、ユーザーは何をどこに貼ればよいか分からず代行できないため、報告の体裁を
とった放置になる。権限の欠如をスレッドを開いたまま終える理由にしないことが要点。

常時ロード層に置いたのは、発火条件が「レビュー指摘に触れたとき」でありオンデマンド doc を開く
きっかけ自体が無いため（+1241 文字・約 410 トークン）。詳細手順ではなく前提と MUST/MUST NOT だけを
置き、一覧の読み方は従来どおり生成物側の冒頭に委ねている。

## 2026-07-29 Codex 指摘の積み残し消化（共通配布物の分）

未 resolve の Codex 指摘 93 件（マージ済み PR 分）の棚卸しで、**大半は正本側で既に直っており、残っていたのは
resolve 操作だけ**だった（例: publish-ephemeral の空 tree push・marker 欠落スライスの削除・スライス境界の
限定、net-fetch の request_id 無害化と summary への伏字受け渡し）。指摘が複数リポジトリの同期 PR に重複して
出るため、件数は実際の欠陥数より大きく見える。以後の棚卸しでも「まず現在の正本を読んで再現するか確かめる」
を先にやる（指摘文だけを見て直すと、直っているものを二重に触る）。

正本にまだ残っていて直したのは4点:

- `branch-cleanup.yml` の `age_days` に検証が無く、空欄・0・負値・非数値で cutoff が 0 や未来になり、
  **prefixes に一致する未保護ブランチが年齢に関係なく全件削除対象になる**（削除は不可逆）。正の整数で
  なければ実行前に落とす。時間ガードが1つしかないので、ここは fail-closed でないと事故が戻せない。
- `apply-common.mjs` はマーカーが片方だけのとき `findRegion` が null を返し、**追記フォールバックに落ちて
  共通ブロックを二重に載せていた**（設計 doc は「片方だけなら失敗する」と書いてあり実装と食い違い）。
  片方だけ・順序逆を検出して exit 1 にした。doc 側を実態に合わせて緩めるのではなく実装を doc に寄せたのは、
  マーカー欠けは手編集・切り詰めの印で、黙って直すと全エージェントが読む AGENTS.md に規約が二重に載るため。
- `ci-logs.md` の必須 tee パターンに `mkdir -p` と `pipefail` が無く、**ログを足すとジョブの成否が変わる**
  （tee の終了ステータスが本体を覆う）状態だった。ログ出力の義務化が結果の握りつぶしを生むのは本末転倒なので
  必須手順そのものに畳み込んだ。
- `cross-repo-tasks.md` の `task-done` を実装 PR に同梱する規則は、**完了検証がマージ後にしか取れないタスク**
  （deploy 成功・cron 初回実行など）だと検証前にタスクが配布から消える。この場合だけ後出しにする例外を足した。

## 2026-07-26 集約モードの実行先を、入口すべてで揃え損ねていた（Codex P1 ×2）

net-fetch の実行先を ops-runner へ移したとき、**手順 doc（`net-fetch.md`）だけ直して、そこへ至る入口を
直し忘れていた**。Codex が nikki-san #681 と private #436 の同期 PR で同時に指摘した。

取りこぼしていた入口:

- **`AGENTS_COMMON.md`（常時ロード層）** — 「集約モード（public な ai-ops 上で実行）」。全タスクで
  読まれる層なので、ここが古いと手順 doc を開く前に誤った前提が入る。
- **`docs/actions-quota.md`** — 枠が逼迫したときの代替案として「public な ai-ops での集約実行」を提示。
  つまり**枯渇時のフォールバック経路が、撤去済みの workflow を指していた**。
- **`net-fetch.yml` のコメント**・**`net-allowlist.txt` のコメント** — 「集約は ai-ops 上で実行」。

### 一括リネームが取りこぼしを悪化させた

さらに悪いことに、直後の `ai-ops` → `ops-sync` 一括置換がこれらを **`ops-sync`** に変えた。
文字列としては置換されるが、**意味としては最悪の方向**——「エージェントが外部コンテンツを持ち込む実行先」が
`OPS_SYNC_TOKEN` のあるリポジトリを指す文になり、今回の分離の目的そのものを打ち消していた。

**学び: 同じ固有名詞でも役割が違えば置換先が違う。** `ai-ops` という文字列には
(1) 実行先 → `ops-runner`、(2) 配布の正本・トークンの置き場・quota 信号の場所 → `ops-sync` の
2種類が混在していた。`net-fetch.md` ではこの区別に気づいて手で分けたのに、**他ファイルには同じ区別が
あることを確認しなかった**。1ファイルで「役割が混在している」と気づいたら、**同じ語を使う全ファイルを
同じ観点で洗う**（grep して意味ごとに仕分ける）。

### 入口の網羅は「発火トリガから逆算」する

手順 doc を直すときは、その doc に**辿り着く経路を列挙してから**直す。今回なら
常時ロード層のトリガ・関連 SOP のフォールバック・実ファイルのコメントの3系統。
doc 単体を直して満足すると、常時層が古いまま残って**doc を開く前に誤判断させる**。

## 2026-07-26 codex-review-inbox の fail-open を塞ぐ（持ち越し）＋ task-done を MUST に

配布直後の同期 PR に付いた Codex 指摘2件。どちらも自分が作ったものへの指摘で、片方は
**この一覧の存在意義を無効化する欠陥**だった。

**1. 一覧が古い指摘を黙って落とす（private #443 P2）**: collector は「直近 N 日に更新された PR」しか
見ないので、未 resolve のスレッドが載った PR が窓から外れると、**resolve されていないのに一覧から消える**。
「未 resolve のスレッド自体がキュー＝取りこぼしを防ぐ」と設計 doc に書きながら、実装は時間で
取りこぼす fail-open だった。

対処: **前回の出力を持ち越しの入力として使う**。生成済み一覧から PR の URL を拾い、直近スキャンの窓に
入らなかったものは**名指しで再確認**する。エントリが消える条件を「古くなった」から「resolve された
（または PR ごと読めなくなった）」に固定した。別の状態ストアを持たずに耐久性を出せるのは、出力自身が
そのまま前回状態になっているため（この一覧が markdown の表であることの副次的な利点）。再確認に失敗した
PR は「取得失敗」行として残す——読めなかったものを落とすと持ち越しの意味が無い。

コストは「未対応の指摘を持つ PR 数」に比例して有界（初回実測で 92 件・PR にして数十）。全 PR を毎回
ページングする案は 15 分間隔だと GraphQL のレート上限に近づくので採らなかった。

**2. task-done の消化に MUST が無い（private #442 P1）**: #101 で2経路化したときに
`cross-repo-tasks.md` の消化手順から強制力が抜けていた（`sop-format.md` 自身が「無キーワード文は説明で
あって要求ではない」と定めているので、実行側は消さずに完了扱いできてしまう）。`.ops-sync/tasks/` は
同期管理下で、消さないと次の sync で復活し**別セッションが同じ依頼を再実行する**。#101 で自分が定めた
「要求を経路によらない MUST として先に置き、経路はその下に満たし方として並べる」形に直した。

教訓（#101 と同型）: 経路を増やす改訂では、**元の文にあった強制力が経路の説明に薄まって消えていないか**を
確認する。2経路化の3箇所目で同じ抜けをやっている。

## 2026-07-26 codex-review-inbox の cron を `*/15` から毎時に落とす

**`*/15` は一度も発火しなかった。** workflow が main に入ってから 12:00 / 12:15 / 12:30 の3枠連続で run が
作られず、`ci-logs` に記録が残らなかった（この workflow は成功・失敗を問わず毎 run ログを publish するので、
記録が無い＝実行されていない）。同じ時間帯に sync の run は動いていたので、アカウント側でも権限でもない。
GitHub は高頻度のスケジュールほど優先度を落として間引くため、**確実に回る頻度に下げる**判断をした。

実行分のコストは関係ない（ops-sync は public で GitHub-hosted runner が無料）。**間引かれるかどうか**だけが
制約なので、「無料だから細かく回す」は成立しない。

実効の気づきは 15〜30分 → 60〜90分に伸びるが、そもそも 15分設定では**永遠に気づかなかった**ので改善。
急ぐときは `workflow_dispatch` で即時に回せる（過去分の洗い直し用に `lookback_days` 入力もある）。

教訓: **「動くはず」の周期実行は、動いた証跡で確認するまで動いていないものとして扱う。** この workflow は
毎 run ログを publish する設計にしてあったので、記録の不在から間引きを特定できた。設計時にログを
`if: always()` にしておいたのがそのまま診断手段になった。

## 2026-07-26 codex-review-inbox の push 競合とレート消費を実測で直す

スライス化（#104）の初回実行が **failure** で終わり、一覧が更新されなかった。実測で分かった2件を直す。

**1. push 競合（実測で発生）**: run は 11:51:04〜11:51:40。その間に private の main が
11:51:20（sync PR #444）と 11:51:35（#445）で2回動き、`--depth 1` の clone から出した push が
non-fast-forward で弾かれた。**15分ごとに回るうえ、対象は sync PR が頻繁にマージされる main** なので、
これは例外ではなく日常的に起きる。同じ run の中で `publish-ci-logs` も1回目の push に失敗しており
（あちらは retry+rebase を持っていて回復する）、対処の前例も社内にあった。

生成物は毎回作り直せるので、マージせず**「main を取り直して上書きし直す」**方式にした:
push 失敗 → `fetch --depth=1 origin main` → `reset --hard FETCH_HEAD` → 退避しておいた生成物を再適用 →
再コミット・再 push（5回まで、指数バックオフ）。再取得の結果すでに同じ内容なら差分ゼロで抜ける。
1リポジトリの失敗で残りを諦めない点は据え置き（他の一覧まで古いまま据え置かれる）。

**2. 直近スキャンの窓を 30日 → 3日に狭めた**: ページング（#104）を入れたら実測が
`nikki-san pages=10 prs_scanned=500`（＝上限に張り付き、30日を見切れず）、`private pages=9`、
合計23ページになった。GraphQL は 5,000 ポイント/時で、この規模を15分ごとに回すと上限に接近する
（1ページあたり PR50件×スレッド50件のノード数を要求している）。

**直近スキャンの役目は「新しい指摘の発見」だけでよい**——Codex は PR イベントの数分後に投稿し、
この workflow は15分ごとに回る。一度載ったものは #103 の持ち越しが resolve まで守る。よって窓は狭くてよく、
広い窓が要るのは**過去分の洗い直し1回だけ**。それは `workflow_dispatch` の `lookback_days` 入力で渡す。
あわせて `rateLimit{ remaining }` をログに出し、消費を観測できるようにした（推測で運用しない）。

補足: ページング導入で件数が **92 → 175** に増えた。増えたのではなく、`first:50` で切れていて
**最初から半分近く見えていなかった**。「件数が安定しているから正しい」とは限らない例。

## 2026-07-26 codex-review-inbox をリポジトリごとのスライス＋グループ化した全体一覧に分ける

初回実行で **92件（うち91件がマージ済み PR）** が出た。ユーザーの判断: 「こんなにあったら1本の通し一覧では
運用が回らない。せめてリポジトリごとにグループ化され、簡単にコピペできる形であってほしい」。あわせて
Codex の指摘（nikki-san #687 P2「受動的なファイルを cron で更新してもセッションは起動しないし、他リポジトリの
エージェントは private のファイルを読めない」）にも応える形にした。

出力を2つに分けた:

- **全体一覧** `.ops-sync/codex-review-inbox-all.md`（private のみ）— リポジトリごとにグループ化し、各グループに
  **そのリポジトリのセッションに貼る依頼文**をコードブロックで添える（`cross-repo-tasks.md` の「コピペ用の
  指示文」と同じ作法。冒頭1行の概要＝セッションタイトル生成のため）。人のトリアージ用。
- **リポジトリごとのスライス** `.ops-sync/codex-review-inbox.md`（各リポジトリ）— 自分の分だけ。

  `.ops-sync/codex-review-inbox.md` を読め」の1文に固定できる。可視性も自然に成立する: スライスは
  そのリポジトリ自身の指摘しか含まないので、public な ops-runner・ops-sync に置いても公開範囲が変わらない。
  全リポジトリ分が混ざる全体一覧だけが private 限定。

副産物として実測で見つけた欠陥も直した: 初回実行のログが `prs_scanned=50` で3リポジトリとも揃っていた
＝GraphQL の `first:50` で切れており、**lookback 期間内でもそれより古い PR は最初から見ていなかった**。
ページングを入れた（上限10ページ＝500件の安全弁つき。上限に当たったら「取得失敗」行として一覧に残す——
黙って諦めると持ち越しの対象にすら入らない）。

push 先を4リポジトリに増やすので、**どのリポジトリも `.ops-sync/` が push トリガの paths に入っていない**
ことを確認した（nikki-san は content/layouts/assets/... と workers/admin、private は cloudflare_workers/**、
ops-runner は push トリガ自体なし、ops-sync の sync.yml は shared/** ほか）。入っていたら15分ごとに CI が
起動して Actions 枠を焼く。consumer に workflow を足すときの注意点として workflow のコメントにも書いた。

## 2026-07-26 上り口を「outbox 一本」から2経路に開いた（Codex 指摘 nikki-san #661 / private #419）

consumer 同期 PR に付いた Codex 指摘2件のうち、生きていたのは「共通 allowlist の直接編集ルートが
共通ブロックの『outbox が唯一の上り口』と矛盾する」というもの（もう1件の「pause 状態を run conclusion
から推定するな」は #84 の実測信号への一本化で既に解消済みだった。なお Codex の事実認識は正しく、
job-level `if` の skip では run の conclusion が `success` になりうる＝あの間接判定はそもそも誤りだった）。

矛盾を消す方向として、直接編集ルートを撤去して outbox に戻す案もあったが、**outbox は Claude Code が
1セッションで複数リポジトリを扱えることを知らずに設計した**ものなので、能力がある側に合わせて上り口を
2つに開く方を選んだ（ユーザー判断）。

書き方は `sop-format.md` の「判断・分岐をツールの有無に紐づけない（MUST NOT）」に抵触しないよう、
**要求（正本だけを直す・人間のマージでしか入らない・自分でマージしない・「なぜ」を1行残す）を経路に
よらない MUST として先に置き、直接 PR / outbox はその満たし方**として書いた。net-fetch のモード選択が
可視性・機微性という判断軸をツール能力にすり替えて壊れた前例があるが、上り口は**どちらの経路でも
結果と承認点が同一**なので、能力で選んでよい種類の分岐だと整理した。

承諾まわりは Codex の指摘どおり穴があったので塞いだ: ops-sync をセッションに足すのは「編集して PR を
出す」用途なので **push 権限付きで足す**必要があり、net-fetch step 2 で ops-runner を足した承諾は
別リポジトリ・別目的なので流用できない。

経緯として、この直接編集ルートを最初に書いたのは #83 自身で、**その PR は `add_repo` で ops-sync を
直接編集したセッションが自分の行動を正本に成文化したもの**だった（逸脱が次のルールになる経路）。
今回はユーザーが明示的に承認した上での成文化なので同じ形ではないが、この経路自体は覚えておく。

## 2026-07-26 Codex レビューの未対応在庫を自動集約する（codex-review-inbox）

Codex 指摘の取りこぼしが増えていた件の対策。ユーザーの困りごとは「メール通知のリンクを1件ずつ辿って
対応済みかを確認する手間」で、求められたのは**検知と統合された一覧まで**（対応の自動化は不要）。

判断の根拠になった制約:

- **「定期 workflow は月枠で動かせない」は ops-sync には当てはまらない。** 枠信号は現在 `tight` だが、
  逼迫しているのは private リポジトリぶん。ops-sync は public なので GitHub-hosted runner が無料で、
  既存 cron 一族（sync 日次・collect-outbox 6h・quota 6h）も現に動いている。だから15分ごとに回せる。
- **一覧を issue にしない。** ユーザーの「AIエージェントも読めますか？」で判断が変わった。issue は
  GitHub API アクセスが要る＝エージェントのランタイム依存になる。`.ops-sync/tasks/` と同じく
  **ファイルとして物理的に置く**ほうが、どのエージェントでも能力ゼロで読める。
- **一覧の置き場は private リポジトリ。** ops-sync は世界公開なので private のレビュー内容を置けない。
  実行（public・無料）と成果物（private）を分ける。ci-logs に出すログは件数と repo 名だけにした。
- **`private` の push トリガは `cloudflare_workers/**` のパス限定**なので、`.ops-sync/` への push で
  CI は起動しない（逼迫している private の枠を食わない）ことを確認した上で直接 push にした。
- **状態を持たせない。** 「未 resolve の Codex スレッド」自体をキューにする。管理表を別に持つと実態と
  ずれるが、resolve 状態を正本にすれば構造的にずれない。
- 取得に失敗したリポジトリは**「取得失敗」行として一覧に残す**。黙って短い一覧を出すと「指摘が無い」と
  「読めなかった」が区別できず fail-open になる（actions-quota の unknown と同じ考え方）。
- 生成時刻だけの差分でコミットしない（15分ごとなので履歴が埋まる）。時刻行を除いて比較する。

ルール側で解けない理由も設計 doc に書いた: `AGENTS.md` の「配布変更のダウンストリーム確認」は
**セッションが生きている間しか効かない**（指摘はセッション終了後に届く。上り提案由来の取り込み PR では
そもそも提案元セッションが居ない）。届かない層があるので機械で埋める、という切り分け。

## 2026-07-26 揮発ブランチの掃除が「最後の1件」を消せなかった（#94 の P1 修正）

`publish-ephemeral` の掃除（`prune-only`）が、**全スライスが期限切れになったときだけ push せずに終了**していた。
結果、最後に残った1件が TTL を過ぎても永久に残る——集約モードは public なので、揮発させる仕組みを入れた
のに最後の取得結果だけ世界公開で残り続ける、という目的を裏切る状態だった。

原因は変更検出の書き方。orphan ブランチに `checkout --orphan` した直後は HEAD が unborn なので、
`git diff --cached --quiet` は**インデックスを空ツリーと比較する**。全スライスを消してインデックスが空に
なると「変更なし」と判定され、`return 0` で push せずに正常終了する（ログには `expiring ...` が出るのに
リモートは変わらない）。**ローカル実行が緑で、ログにも作業した形跡が出るのに、結果が反映されない**タイプ。

直し方は、インデックス比較をやめて**再構築後のツリーと出発点のツリーを直接比較する**（`write-tree` と
`<base>^{tree}`）。空にすることが本物の変更として扱われ、空コミットを作れるよう `--allow-empty` を添える。
副作用として「変更が無いときは push しない」判定も正確になった（掃除が毎日空振りしてもブランチは動かない）。

### なぜローカル検証をすり抜けたか

前段でローカルの bare repo 相手に TTL 失効を確認していたが、テストが**常に残るスライスを1つ持っていた**
ため、ツリーが空になる経路を一度も通っていなかった。境界値（0件）を試していない典型的な穴。
今回は修正前スクリプトで**バグを先に再現**してから直し、(1) 全件失効で空になる、(2) 空になったブランチへ
publish して復帰できる、(3) 失効が無い掃除はブランチを動かさない、の3ケースを実駆動で固定した。

### 発見経路: consumer 同期 PR でだけ出た

この P1 は **ai-ops 本体の PR（#94）には出ず、nikki-san #678 と private #433 の同期 PR で Codex が指摘した**。
AGENTS.md「配布変更のダウンストリーム確認」が想定しているとおりの事象で、あの手順を踏まなければ配布物の
欠陥が全 consumer に残っていた。**shared/ を触ったらマージ後に consumer の同期 PR を見る、は実際に効く**
（今回オーナーから、この確認は都度の許可を取らず自動で行ってよいと承認を得た）。

### ローカルで実駆動検証した（GitHub を回す前に4項目）

action の shell を action.yml から抽出し、remote を `github.com` からローカルの bare repo に差し替えて
実行した。**GitHub 上で回す前に、ローカルの bare repo 相手に一通り確認できる**（次に触る人も同じ手が使える）:

- 結果ブランチが無い状態からの初回作成 → OK（orphan 経路）。
- 2回目の書き込みでもコミット数が 1 のまま → OK（履歴に堆積しない）。既存スライスも保持される。
- TTL 失効 → OK（`.published-at` を10日前にしたスライスが次の書き込みで消える）。`prune-only` の掃除も同じ。
- **並行実行**: clone と push の間に `sleep` を挟んだ変種を同時に走らせてレースさせ、
  `attempt 1 failed ... retrying` → やり直し → **両方のスライスが生存**を確認。

### テストハーネス自身のバグで「リースが効かない」と誤読しかけた

最初のレーステストは `sed` のアンカーがずれて `sleep` が挿入されておらず、**そもそも競合していなかった**
のに「通った」と読みかけた。続けてリース単体を確かめたときは `git push ... | sed` と書いたため、
**パイプの終了ステータスが `sed` のものになり**「push SUCCEEDED（リースが効いていない）」と出た——
実際には git の出力に `! [rejected] (stale info)` が出ており、リースは効いていた。

学び: **緑/赤の判定そのものを疑う**。特に (1) 差し込んだはずの遅延が本当に入ったかを grep で確認する、
(2) パイプした先の終了ステータスで成否を判定しない。action 本体は push をパイプしていないので影響なし。

### 恒久ログと一次データを分ける、を設計 doc に昇格させた

今回の切り分け（`ci-logs`＝恒久・`net-fetch-results`＝揮発）は net-fetch 固有の話ではなく、**git ブランチ
では削除が削除にならない**という一般則から来る。将来また「揮発させたい出力」が出たときに同じ判断へ
辿り着けるよう、`ops-sync-design.md` に節を立て、`ci-logs.md` の前提にも「一次データを混ぜない」を
MUST NOT で書いた。

**artifact 案を再検討させないための記述も同時に入れた**（`net-fetch.md` の「よくある失敗」＋
ops-sync-design）。一見最適に見えて実際は egress で読めない、という失敗は放っておくと必ず再発する。

### ジョブログ併設は「手順の分岐」にしない

ログ本文を取得できるランタイムはブランチを fetch せず1回で読める。ただし sop-format の
「判断・分岐をツールの有無に紐づけない」に従い、**要求（結果を読み戻す）は経路によらない MUST 一つ**とし、
ブランチとジョブログは同格の「満たし方」として並べた。「MCP を持つなら A、無いなら B」とは書いていない。

### 残り

`stop-commands` ガード（外部コンテンツ中の `::error::` 等が workflow command として解釈されるのを止める）
だけは Actions ランタイム固有でローカル再現できない。**マージ後に `::error::` を含む本文を1回取得させ、
run に注釈が出ないことを確認する**こと。

## 2026-07-26 net-fetch の結果を揮発ブランチへ移す（作業途中・引き継ぎあり）

ai-ops をゼロベースで設計し直すなら機能分離すべきか、という相談から派生した作業。net-fetch の取得結果が
public な ai-ops の `ci-logs` に**恒久堆積**している（中断時点で 16 リクエスト・64 ファイル）のを、
専用の揮発ブランチ `net-fetch-results` へ分離して TTL を付ける。**未完**——残作業は
`docs/reference/NET_FETCH_EPHEMERAL_HANDOFF.md` に全部書いた。

### 「artifact に出す」案を実測で潰した

当初 artifact（`retention-days` で自動失効）を推した。これは**間違いで、実測で潰れた**。artifact と run
ログの zip はダウンロード URL が `results-receiver.actions.githubusercontent.com` や blob ホストへ 302 するが、
エージェント実行環境の egress プロキシがそれを拒否する（`curl: (56) CONNECT tunnel failed, response 403`。
プロキシの `recentRelayFailures` にも記録された）。`productionresultssa0.blob.core.windows.net` と
`pipelines.actions.githubusercontent.com` も到達不可。一方 `api.github.com`・`objects.githubusercontent.com`・
`codeload.github.com`・`git fetch` は通る。

しかもこれは特定エージェント固有ではない。`gh run download` も REST も同じホストに当たるので、artifact に
すると**全エージェントで結果を読み戻せなくなる**。MCP の `get_job_logs` だけはサーバ側取得なので通るが、
それに依存すると sop-format の「判断・分岐をツールの有無に紐づけない」に反する。

**学び: `ci-logs` がブランチ方式なのは正解だった**（git と `api.github.com` が egress 制限下で確実に届く
唯一の経路）。出口を動かすのではなく寿命を付けるのが正しい。**設計を変える前に到達性を1回測る**——
測らずに実装していたら net-fetch を全エージェントで壊していた。

### 恒久ログと一次データを同じブランチに混ぜていたのが根因

`ci-logs` は「消しても履歴に残る」ので、public リポジトリでは削除が削除にならない。quota 信号や archive
ログは**現在値を読ませる恒久データ**で残ってよいが、net-fetch の結果は**読んだら用済みの一次データ**。
この2種類を同居させたまま purge しようとすると、恒久側の履歴まで巻き込む。分離してブランチごと
使い捨てにするのが正しい切り分け。

### `publish-ci-logs` を拡張せず別 action にした

`publish-ephemeral` は挙動が大きく違う（追記型 vs 毎回 orphan 書き換え・TTL 失効・force-with-lease）うえ、
`publish-ci-logs` は nikki-san の deploy 系が依存する敏感な経路。AGENTS_COMMON の「敏感なコードの共通化は
挙動を変えない形に留める」に従い、共通化せず新規に分けた。

### 並行実行で他人のスライスを消さない

毎回 orphan で force push する設計なので、素の force だと同時刻の別リクエストの結果を消す。開始時の sha を
`--force-with-lease` のリースにして、拒否されたら相手の状態から作り直す（相手のスライスが生き残る）。

### 外部コンテンツをジョブログに出すときの注入

MCP 等でログ本文を読めるランタイム向けに、結果をジョブログにも出す方針にした。ただし**取得した外部
コンテンツをそのまま出すと本文中の `::error::` 等が workflow command として解釈される**。
`::stop-commands::<ランダムトークン>` で解釈を止めてから出す（トークンを固定値にすると本文側から
推測して止め損なえるのでランダム）。

なお「MCP を持つエージェントはログから、持たないものはブランチから」という書き方は sop-format 違反。
**要求（結果を読み戻す）は経路によらず1つ**で、ログとブランチは「満たし方」の補足として書く。

### セッション中断について

クライアント側の不具合で選択ダイアログ（AskUserQuestion）が消えなくなり、作業継続が不能になった。
実装は composite action 1本まで。**中断時点で既存ファイルは1つも変更していない**ので、残作業は
引き継ぎ doc からそのまま再開できる。

### アクセスした外部 URL

到達性検証のみ: `results-receiver.actions.githubusercontent.com`（403）・
`productionresultssa0.blob.core.windows.net`（到達不可）・`pipelines.actions.githubusercontent.com`（到達不可）・
`api.github.com`・`objects.githubusercontent.com`・`codeload.github.com`（到達確認）。

## 2026-07-26 net-fetch: request_id に貼られた secret が公開結果に残る穴を塞ぐ

P1 のトリアージで net-fetch 系4件を実地確認した結果、**3件は既に修正済みで resolve だけされていない**もの
（2026-07-23 に返信付きで直っていた）、**1件だけが本物**だった。

本物のほう（ops-runner #1）: `request_id` の検証が文字種（`^[A-Za-z0-9._-]+$`）と `..` だけで、
**secret 判定を通していなかった**。GitHub token（`ghp_...`）等は文字種を素通りするので、request_id に
secret を貼ると (1) publish 先パス `net-fetch/<id>`、(2) `meta.txt` の `request_id=`、(3) ジョブログ、の
3経路に生のまま残る。**集約モードの実行先 ops-runner は public** なので世界公開に落ちる。URL 側は
`matches_secret` で弾いているのに、id 側だけ抜けていた（同じ出力に載るのに基準が非対称だった）。

対処: id 検証に `matches_secret` を追加（2箇所の検証条件を揃える）し、出力に載せる id は
`redact_secrets` を通した `SAFE_REQUEST_ID` にした。あわせて `matches_secret` の定義を前方へ移した
——bash は定義を実行するまで関数を呼べず、id 検証は定義より前にあったため。

実駆動で確認: `ghp_...` 形は `invalid request_id` で拒否され `meta.txt` は `[REDACTED-SECRET]`、
通常 id は従来どおり通過、`../escape` も従来どおり拒否。

教訓: **同じ出力に載る入力は、同じ基準で検査する。** URL には secret 判定・SSRF ガード・allowlist と
何重にも掛けていたのに、隣にある request_id は「パスに使うから」という理由で path traversal だけ見ていた。
入力ごとに「何に使うか」で検査を設計すると、出力経路が共通であることを見落とす。

## 2026-07-26 計算基盤 `ops-runner` を consumer として追加（実行基盤分離の第1段）

エージェントが dispatch する計算（現状 net-fetch）を ai-ops から切り出すための下準備。この段階では
**配布先を1つ増やしただけ**で、net-fetch の実行先はまだ ai-ops のまま（切り替えは次段）。

### なぜ分けるか

ai-ops には `OPS_SYNC_TOKEN`（全 consumer への Contents/Workflows:RW）がある。一方 net-fetch は
**エージェントが任意のタイミングで起動でき、任意の外部 URL の中身を持ち込む唯一の経路**で、性質が
まったく違う。現時点で穴が空いているわけではない（fetch ジョブに secret を渡さない・`pull_request`
トリガが無い・fork PR は承認必須・main はブランチ保護）が、その不変条件は **workflow 1つ1つの
レビューで担保している**状態。今後この種の機能は増えるので、リポジトリ境界にして構造で保つ。

**分割線は「計算 vs 配布」ではなく「`OPS_SYNC_TOKEN` が要るか」**。archive-task-history のようなバッチは
計算だが cross-repo write が要るので ai-ops 残留。quota 信号も cron 専用で外部入力を取らないため残留。

### コストが安い理由

新リポジトリを `consumers.txt` に1行足すだけで、既存の配布機構が `net-fetch.yml`・allowlist・
`publish-ephemeral`・共通ルールを届ける。**新しい仕組みはゼロ**。分離完了後は、ai-ops が抱えている
「`shared/` の正本と root の実コピーを byte 一致で手動同期」という二重管理も消える。

### 限界（誤解しないため）

この分離は**一方向**。runner に配るには `OPS_SYNC_TOKEN` が runner にも書き込める必要があるので、
「runner が ai-ops を触れない」は成立するが「ai-ops が runner を触れない」は成立しない。守っているのは
*鍵のある場所に外部コンテンツを持ち込ませない*ことであって、鍵の影響範囲を狭めることではない。

また `ci-logs` が2箇所になる。quota 信号は ai-ops 側に残るので、分散モードのエージェントは
「枠の信号は ai-ops、取得結果は runner」と2箇所を見る。読むだけなので実害は小さいが doc で明示が要る。

### ops-runner は public

無料枠のため（private だと分を消費し、枠はアカウント単位で全 private リポジトリが共有する）。
帰結として、ここへ配る `shared/` の内容も net-fetch の取得結果も世界公開になる。機微な取得は
従来どおり private リポジトリの分散モードで行う（この分離で変わらない）。

## 2026-07-26 リネームの一括置換が、除外指定の副作用で配布ファイルを1つ取りこぼした

原因は置換対象を集めるときの除外指定:


意図は「**このリポジトリ自身の履歴フラグメント**（`docs/history-inbox/`）を書き換えない」ことだったが、
`--exclude-dir` は**名前が一致する全ディレクトリ**に効くため、まったく性質の違う
`shared/docs/history-inbox/`（＝全 consumer へ配る placeholder）まで除外された。

**学び: `--exclude-dir` はパスではなくディレクトリ名で効く。** 同名ディレクトリが別の役割で存在する
リポジトリでは、意図しない範囲まで黙って外れる。除外したいのが特定パスなら
`--exclude-dir` ではなくパスで弾く（`grep -v '^./docs/history-inbox/'` 等）。

**検証の穴も同じ形だった**: 置換後の残存チェックにも同じ除外指定を使ったため、
**取りこぼしたファイルは検証でも見えなかった**。置換と検証で同じフィルタを使うと、
フィルタ自体の誤りは原理的に検出できない。今回は全 consumer をマージ後に突合して初めて見つかった
（＝配布後の実物を見る確認が効いた）。除外条件を変えた再スキャンで、他に漏れが無いことを確認済み。

## 2026-07-26 リポジトリを ai-ops から ops-sync へリネームし、識別子も移行

「ai-ops」という名前をゼロベースで見直した結果の改名。実行基盤の分離（ops-runner）と同時にやることで、
移行ウィンドウを1回に収めた。

### なぜ改名したか

1. **業界用語との衝突**。「AIOps」は Gartner 由来の確立した語で **IT運用にAIを適用する**ことを指す。
   このリポジトリは逆向きで、**AIエージェントのための運用基盤**。しかも読者の主体は LLM エージェントで、
   彼らの学習データには AIOps の一般的な意味が入っているため、名前が読み手を誤誘導する。
2. **「ops」の情報量が低い**。運用スクリプト置き場か IaC かランブック集か制御基盤か判別できない。
   実体は「ルールと共有CIファイルを consumer へ一方向配布し、逆方向は提案として集約する control plane」。

`ops-sync` を選んだのは、**すでにリポジトリ内で使われていた語だから**（設計 doc が `ops-sync-design.md`、
仕組みの呼称も一貫して「同期」）。設計 doc のファイル名を変えずに済み、`ops-runner` と対で読める。

**単体では改名しない判断だった**。名前の改善幅に対して識別子移行のコスト・リスクが見合わないため。
①（実行基盤の分離）をやる回に相乗りさせたのはそのため。

### 何を変えたか

- リポジトリ名（オーナー操作）。GitHub がリダイレクトするので git remote は張り替え不要だった。
- テキスト参照の一括置換（41ファイル）。**履歴系は除外**（`AI_TASK_HISTORY.md`・`history-inbox/`・
  `history-archive/` は過去の記録で、現在形ルールの対象外）。
- 識別子: `AI-OPS:COMMON` → `OPS-SYNC:COMMON`、`.ai-ops/` → `.ops-sync/`、同期ブランチ
  `ai-ops/sync-common` → `ops-sync/sync-common`。**`.ai-ops/` とブランチ名は「ai-ops」を含む文字列なので、
  テキスト置換と同じ一括処理で自然に移った**（別作業にしなくてよかった）。
- 配布ルールファイルの改名: `.clinerules/ai-ops.md` 他4件 → `ops-sync.*`。旧ファイルは manifest 差分で
  consumer から自動削除される。

### 後方互換を入れないと全 consumer が壊れる箇所

**`apply-common.mjs` のマーカー認識が最重要**。consumer の AGENTS.md には旧マーカーが入っているので、
新マーカーだけを探すと見つからず「末尾に追記」の経路へ落ち、**全 consumer で共通ブロックが二重になる**。
新旧どちらの区間も拾って新マーカーで置き換える `findRegion()` を入れた。

`apply-shared.mjs` は削除判定を新旧 manifest の和にし、**旧 manifest ファイル自体も明示的に削除対象へ入れた**
（manifest は manifest に載らないので差分削除では消えない）。旧配置の `.ai-ops/tasks/**` は旧 manifest に
載っているため自動で消える。

`collect-outbox.mjs` は新旧どちらの outbox も走査する。配布 doc が新パスに切り替わる前に始まったセッションが
旧パスへ提案を置きうるため。差し戻し先も**提案が置かれていた側**に合わせた（新パスへ差し戻すと提案者が
自分の置いた場所を見ても見つけられない）。

これらの LEGACY 分岐は、全 consumer から `.ai-ops/` と旧マーカーが消えたら削除してよい（各所にコメント済み）。

### 移行を実駆動で検証した

旧マーカー・旧 manifest・旧 `.ai-ops/tasks/` を持つ偽の consumer を作り、実際に両スクリプトを走らせた:
新マーカー1個・旧マーカー0個（**二重化なし**）、リポジトリ固有パートの保持、`.ai-ops/` の完全撤去、
旧 manifest 記載ファイルの削除、新ルールファイル名の配布、そして**2回目実行が no-op**（冪等）。

移行は outbox が空のときにやる必要があり（走査対象が変わる瞬間に提案があると取りこぼす）、
着手前に両 consumer とも `.ai-ops/outbox/` が存在しないことを確認した。

## 2026-07-26 task-done の完了条件をセッション内で到達できるものに直す（Codex ops-runner #8/#9）

自分が同日に出した2つの変更への指摘。どちらも正当だった。

**1. 完了条件がエージェントに到達不能だった（ops-runner #8 P2）**: `task-done` の消化を MUST に格上げした
とき（#103）、完了条件を「削除が ops-sync の main に入り、次の sync で `.ops-sync/tasks/` から消えている」
と書いた。直接 PR 経路ならまだしも、**outbox 経路ではオーナーのマージ＋collect の cron＋sync を挟む**ので、
エージェントはセッション中にその状態へ到達できない（しかもエージェントは自分でマージしない、と別のルールで
禁じている）。`outbox-proposal.md` が outbox 経路の完了を「提案が consumer の main に載ること」と定義して
いるのとも食い違っていた。

→ **セッション内の完了条件**（エージェントが自分で確認できる範囲）と**非同期の消化条件**（オーナーの
マージ以降）を分けた。あわせて「消えるまで待たない」を MUST NOT で明記した——待っても自力では到達
できないので、待つ実装は無限に止まる。

教訓: 完了条件を書くときは「**その主体が自分で確認できる状態か**」を必ず確かめる。SOP 規約は完了条件に
「検証可能な事実」を求めているが、*誰にとって*検証可能かまでは書いていなかった。強制力（MUST）を足す
改訂ほど、到達不能な条件を書くと実行が止まる。

**2. 設計 doc の記述が実装と食い違っていた（ops-runner #9 P2）**: 出力を2種類に分けた（#104）とき、
「出力」節は直したが**「しくみ」段落の「1本の markdown 一覧に落とす」を直し忘れた**。同じ doc 内に
現行の姿が2通り併存する状態。あわせて #105 で既定の走査窓を3日にした件も doc に反映した
（設計と実装を乖離させない、というこのリポジトリの完了手順）。

教訓: 節を足す形の改訂では、**同じ事実を述べている既存の文**が他にないか探す。今日は「経路を増やす改訂で
強制力が薄まる」パターンを3回、この「節を足して既存記述と二重化」パターンを1回踏んだ。

## 2026-07-25 「ジョブ0・課金0分の failure は workflow 側ではない」を切り分けとして残す

デプロイ経路スイッチ改名の PR をマージした直後、`deploy.yml` と `deploy-admin-worker.yml` が同時に
`failure` になり、**自分の変更した `if:` や新設の検証ステップを疑った**。実際にはどちらの run も
ジョブが1件も起動しておらず（`total_jobs: 0`）、`billable` も空だったので、変更とは無関係だった。

さらにそこから**「枠切れだ」と決めつけてユーザーに報告してしまった**。ジョブ0・課金0という証拠が
示していたのは「workflow の中身が原因ではない」ところまでで、その先（なぜ起動しなかったか）は
推測でしかなかった。ユーザーに billing 画面が 1,992/2,000 のままだと指摘されて誤りが判明し、
run ページを見てもらったところ **`Internal server error. Correlation ID: …`**——GitHub 側の一過性障害だった。

この2段階（**切り分けは正しかったが、その先を推測で埋めた**）が再発しやすいので doc に残した:

- ジョブ0・課金0 で分かるのは「workflow 側ではない」ことだけ。
- 「GitHub の内部エラー」か「アカウント側の実行拒否」かは **run ページの表示でしか分からない**。
  API のジョブ一覧からは区別できないので、推測で断定しない。
- 「同じ push で複数 workflow が同時に同じ壊れ方」はアカウント側を*示唆*するが、決め手ではない
  （今回まさにそれで誤った——内部エラーも同じ push の run をまとめて巻き込む）。

### Codex 指摘 P1×2 で書き直した

最初に書いた「**ジョブ0件・課金0分なら workflow 側の不具合ではない**（MUST NOT: workflow を疑う）」は
**誤り**だった。**invalid workflow file・式の不正・reusable workflow の参照エラーはジョブ生成前に弾かれる**
ので、まさにこの見え方（ジョブ0・課金0）になる。つまりあのルールは、**自分が直前に壊したときにこそ
真犯人から目を逸らさせる**。しかも配布 doc なので全 consumer に伝播していた。

原因は3種類（ワークフロー側の不正／GitHub 内部エラー／アカウント側の実行拒否）で、**ジョブ数と課金では
区別できない**。区別できるのは run ページ（または annotation）の文言だけ。表にして、
「**ワークフローを変更した直後の失敗はまず自分の変更を疑う**（MUST）」を明示した。

皮肉なことに、この doc を書く動機になった今回の私の誤りは「切り分けの1段目で止めず推測で2段目を
埋めた」ことで、最初の草稿は**1段目自体を間違えて**同じ轍を踏んでいた。

あわせて sop-format 準拠に組み直した（「触れたついでに準拠させる」規約）。目的／トリガ／前提・
パラメータ／番号付き手順＋完了条件／よくある失敗、の形にし、**手順A（新規ワークフローへの組み込み）と
手順B（失敗の切り分け）を別立て**にした。既存の内容（2層の使い分け・collector の失敗ゲートと式の
略記禁止・net-fetch の登録例外）は削らずそのまま手順Aに収めてある。

## 2026-07-25 Cloudflare 月枠の信号を追加（`actions-quota` の対）

GitHub Actions の枠が尽きたときの退避先は Cloudflare だが、**CF 側にも月枠がある**（Free: Pages の
ビルド 500回/月・Workers Builds 3,000分/月・ともにアカウント単位）。GitHub 側だけ見て自動退避すると
今度は CF を溶かして「どこにもデプロイできない」に至るので、対になる信号を作った。将来の
`*_DEPLOY_POLICY=auto` の突合が読む前提。

### 実測で分かった、設計を変えた事実

この信号は**先に手で測ってから**設計した。推測で作っていたら間違えていた点が3つある:

1. **枠を消費しない deployment が圧倒的多数**。2026-07 の Pages は deployment 2,079 件のうち課金対象は
   **94 件（4.5%）**だけだった。除外すべきは `deployment_trigger.type == "ad_hoc"`（`wrangler pages deploy`
   ＝Direct Upload。CF のビルド枠を使わない）と、watch paths 不一致で `is_skipped: true` になったもの。
   単純に deployment を数えていたら **20 倍以上**過大評価していた。
2. **使用率だけでは判断できない**。同じ月内で日次レートが不連続に変わる——実測の日次分布は
   `7/19: 32 → 7/20: 32 → 7/21: 14 → 7/22: 5 → 7/23: 3 → 7/24: 6 → 7/25: 2` で、watch paths を絞った
   前後で 10 倍以上違う。そこで**直近 N 日（既定7）の窓**でレートを出し、残枠が月末まで持たなければ
   `tight` にする。**月累計 ÷ 経過日数の平均は使わない**（設定変更の前後をまたぐと実態とずれる）。
   - このセッションで実際に、私は「94 件 ÷ 推定1日 = 94件/日」と外挿して「7/29 に枯渇する」と誤報告した。
     切替日を run 履歴から推測したのが誤りで、実際は7日分だった。**平均レートの罠**そのものなので、
     実装では窓方式を採った。
3. **Workers Builds の「分」は API が返さない**。`running_on`〜`stopped_on` から算出する推定値で、
   Cloudflare の課金定義と一致する保証は無い。桁の把握には足りるが、閾値には余裕を持たせる前提で使う。

### fail-closed の作り

`actions-quota` と同じく、測れなければ必ず `unknown`（消費側は逼迫扱い）。加えてこの信号固有の穴として
**ページングが進まないと黙って過少カウント＝fail-open になる**（＝「まだ余裕がある」と誤って言う）ので、
同じ先頭要素が返り続けたら `unknown` に倒す。数値設定（上限・閾値・窓）が壊れていたら既定へ黙って
戻さず `unknown`——`actions-quota` で踏んだ「`NaN` で割ると `pct >= threshold` が常に false」と同型。

### トークンの置き場

**ai-ops は public** なので、ここに置く CF トークンは**読み取り専用に限る**。切替（Pages の自動デプロイ
反転・watch paths 変更）に要る Edit 権限の操作は、consumer 側の workflow が自分のトークンで行う。
なお Workers Builds API は **user-scoped トークン必須**（account-scoped は "Invalid token"）なので、
public repo に user-scoped トークンを置くことになる——read-only である点が担保。
アカウント ID も secret で持つ（public repo のログに出さないため）。

### 全体 state は最悪値に揃える

`pages_builds` と `workers_build_minutes` の悪いほうを全体 state にする（片方でも逼迫していれば
「CF へ退避してよい」とは言えない）。リソース別の state も併記する——退避先として使えるのが
どちらかで、消費側の判断が変わるため。

検証: CF API をスタブして24ケース実駆動（各リソースの ok/tight/exhausted、閾値未満でも直近レートで
月末超過なら tight、ad_hoc と skip の除外、先月分の除外、片方 tight/unknown のときの全体 state、
exhausted > unknown の優先順、ページング停滞、各種取得失敗、Workers Builds 未接続の 404、
token/account 未設定、数値設定の typo、上限変更）。**生の数値を publish していないことも各ケースで検査**。

### Codex 指摘 P1×2

**1. 同じ `dest` に publish する2つの workflow は互いを消し合う。** `publish-ci-logs` は publish 前に
`rm -rf "${tmp}/${DEST}"` で dest を丸ごと消してから source を置く。`actions-quota` と同じ `dest: quota`
にしていたので、**cron が回るたびに片方がもう片方の JSON を削除する**——既存の Actions 信号を壊す
ところだった。信号ごとに `quota/actions` / `quota/cloudflare` へ分離し、両方の workflow に理由を
コメントで残した（`quota` 自体を dest にしないので、3つ目の信号を足しても同じ事故は起きない）。
消費側のパスが変わるので配布 doc（`actions-quota.md`・`net-fetch.md`）も同一 PR で更新した。
移行の一瞬はファイルが見つからず `unknown` になるが、消費側は unknown を逼迫扱いにするので安全側。

**2. 月初はレート窓が実際より長く割られて fail-open になる。** 当月のレコードしか数えないので、
月の1日目には窓（既定7日）ぶんのデータが存在しない。それでも 7 で割ると**レートを実際より小さく
見積もる**——「1日目に 60 ビルド」が 8.6件/日 と読まれ、`ok` を出してしまう。窓と経過日数の
**小さいほう**で割るよう直した。

この2件目は**月初にしか現れない**ので、今日（25日）のテストでは通らない。時刻を固定できないと
永久に未検証のままなので、テスト専用の時刻上書き `CFQ_NOW` を入れて月初のケースを再現できるように
した（本番では設定しない旨をコメントと doc に明記）。実際、旧実装だと `60 + 8.6*30 = 317 < 500` で
`ok`、新実装だと `60 + 60*30 = 1860 ≧ 500` で `tight` になる——この差をテストで固定した。

### セットアップ手順に直リンクが無かった

共通ルール「ユーザーへの操作指示は直リンク URL で」に反して、README のセットアップ手順が
「本リポジトリの Actions Secret に登録する」と書くだけで **URL を出していなかった**（PAT 発行画面も
同様）。オーナーからの指摘で気づいた。長く残る doc なので、URL に加えてメニュー経路も併記した
（サイト構造が変わって URL が無効になっても辿れるように、という同ルールの後段）。

## 2026-07-25 Actions月枠の逼迫を billing API で実測する共通基盤を追加

同セッションで一度「deploy workflow の run が `skipped` 続きかで枠逼迫を間接判定してよい」と
net-fetch.md に書いたが、ユーザーから「間接判断は危ない」と却下された。妥当な指摘で、あの判定は
**ユーザーが退避スイッチ（`PAUSE_GH_DEPLOY` 等）を入れ忘れていれば「余裕あり」と誤読する**——
逼迫の検出を人間の運用手順の副作用に依存させており、本当に危険なときほど外す。実測に置き換えた。

設計判断（コードに残らない前提）:

- **ai-ops でだけ測る**（`shared/` に置かず consumer へ配布しない）。Actions の月枠は**アカウント単位**で
  `65edh5ih` 配下の private repo が全部同じ枠を共有するので測定は1箇所でよい。加えて ai-ops は public
  なので測定自体が枠を食わない（枠を測るために枠を消費する矛盾を避ける）。consumer に billing PAT を
  配らずに済むのも効く（「consumer に常設トークンを増やさない」原則）。
- **公開先が world-public なので生の使用分数・使用率を出さない**。ai-ops の `ci-logs` は世界公開で、
  アカウントのCI使用状況が晒される。`ok`/`tight`/`exhausted`/`unknown` の band と閾値だけで
  「9割超えたら分散モードを使わない」ルールは成立するため、実数はアカウントの billing 画面に留める。
- **測れなかったら必ず安全側**。token 未設定・API 変更・ネットワーク断・応答形の変化は全部 `unknown` で、
  消費側は `unknown` を `tight` と同じ扱いにする。実装でも2重に塞いだ: (1) `fetch` を try/catch して
  例外で落ちないようにし、(2) それでもスクリプトが結果を残せず落ちた場合に備え workflow 側で
  `unknown` を書く保険ステップを置いた。**これが無いと `ci-logs` に前回の古い `ok` が残り続け、
  消費側が古い ok を掴む fail-open になる**（publish-ci-logs は source-dir が無いと何もせず緑で終わるため）。
- **鮮度も契約に入れた**（`stale_after_hours`・既定24h）。月枠は月初にリセットされ日中に伸びるので、
  古い `ok` を根拠にさせない。ファイル自身に閾値と鮮度を埋めて自己記述にしてある。
- **旧 billing API 優先・enhanced はフォールバック**。「含有枠の何割か」を直接返すのは旧 API だけで、
  enhanced billing platform は金額ベースの明細しか無い。後者では「課金発生＝含有枠超過＝`exhausted`」
  しか断定できず、未課金でも割合は不明なので `ok` と断定せず `unknown` に倒す。どちらの経路が
  このアカウントで生きているかは docs を読んでも確定できなかったため、**両方試して実測で決まる**
  実装にした（初回実行の `source` フィールドに出る）。

閾値90%はユーザー指定。運用中に変えられるよう ai-ops の repo variable
`ACTIONS_QUOTA_THRESHOLD_PCT` で上書き可能にした（未設定なら90）。

検証: billing API をスタブして8ケース実駆動（85%→ok / 89.95%→ok / 90.0%ちょうど→tight /
97.5%→tight / 課金発生→exhausted / 0%→ok / 閾値80に変えて85%→tight / 応答破損→unknown）。
token 未設定・不正tokenの degrade も実行して `unknown` を確認。

### Codex レビューで塞いだ穴（いずれも「安全側に倒すはずが倒れない」系）

- **しきい値の typo で fail-open（P1）**: `Number('9O')` は `NaN` で `pct >= NaN` が常に false になり、
  **使用率にかかわらず `ok` を publish していた**。100超の値も同じく判定が発火しない。しきい値は
  private repo の dispatch を認可する値なので、`(0,100]` の有限数以外は `unknown` に倒すよう検証を追加。
  併せて `threshold_pct` に必ず妥当な数を載せる（`NaN` は `JSON.stringify` で `null` になり消費側が読めない）。
- **workflow の `run:` に `${{ vars.* }}` を直接埋めていた**: このリポジトリの鉄則（注入経路になる）違反で、
  かつ非数値が混ざると actions.json が壊れて消費側が読めなくなる。env 経由＋数値サニタイズに変更。
- **CI ログを残していなかった（P2）**: `docs/ci-logs.md` の手順2-3（`logs/ci/scripts/<name>.log` への tee と
  snapshot の publish）は「例外なく全ワークフローで必須」。net-fetch の例外は collector 登録（手順4）だけで
  ログ出力の免除ではない、と読み違えていた。`unknown` の理由（権限/応答形/ネットワーク）を切り分けるには
  ログが要る。publish 先が世界公開なので token 形の伏字も入れた。
- **SOP の導線不足（P1）**: doc のトリガを「private repo の workflow を自発 dispatch するとき」と
  net-fetch より広く書いたのに、導線が net-fetch.md からのリンクだけだった。広いトリガに合わせて
  `AGENTS_COMMON.md` の1節と skill ラッパーを追加。
- **正本 doc の更新漏れ（P1）**: 新 secret を足したのに README のセットアップ手順と ops-sync-design の
  Secret 表を直しておらず、再構築時に `ACTIONS_QUOTA_TOKEN` が未設定のまま＝全 consumer の自発 dispatch が
  永久に止まる状態になっていた。AGENTS.md の完了手順（仕組みを変えたら両 doc を更新）どおり反映。

## 2026-07-25 Actions月枠の使用率算出（enhanced billing 経路）を完成させる

`docs/reference/ACTIONS_QUOTA_NEXT_STEPS.md` の引き継ぎ手順に沿った作業。判断根拠を残す。

- **含有枠は設定値で持つしかない**（API が返さない）。既定は GitHub Free の 2,000 分（ユーザー確認済み）で、
  repo variable `ACTIONS_QUOTA_INCLUDED_MINUTES` で上書きする。**不正値は既定へ黙ってフォールバックさせず
  `unknown` に倒す**——typo した上書き値を既定で置き換えると「設定したつもりの枠と違う枠で測った ok」を
  publish しうる。`Number('2OOO')`＝`NaN` で割ると使用率が `NaN` になり `pct >= threshold` が常に false ＝
  使用率にかかわらず ok を出す fail-open で、これは `AQ_THRESHOLD` で実際に踏んだ穴と同型。
  上限 1,000,000 分の sanity check は分と秒の取り違え等の桁違いを弾くため（含有枠は最大でも
  Enterprise の 50,000 分程度）。
- **引き継ぎ doc が挙げていた「private リポジトリで publish せずに実レスポンスを確認する」案は使えない**。
  それ自体がエージェント自発の private repo dispatch であり、`quota/actions.json` が `unknown` の間は
  `docs/actions-quota.md` が禁止している行為そのもの（枠の状態を測るために枠のガードを破る循環）。
  実レスポンスの確認はユーザーのローカル実行で行った。
- **API 仕様の裏取りは net-fetch の集約モードで行った**（`docs.github.com` がセッションの egress で 403）。
  public な ai-ops 上の実行なので枠を消費せず、取得対象も公開ドキュメントで機微でない。
- **`quantity` は「素の実行分数」と解釈した**（引き継ぎ doc が「取り違えると数倍ずれる」と警告していた分岐）。
  根拠は実レスポンスの `pricePerUnit` が SKU 別（Linux の分単価が単独の値として出る）で、GitHub の公表単価も
  Linux:Windows:macOS = 1:2:10 の比＝**倍率は価格側で表現されている**こと。よって含有枠の消費は
  `quantity × OS倍率` で数える。取り違えていた場合（＝ `quantity` が倍率換算済みだった場合）この実装は
  使用率を**過大**に見積もる＝早めに `tight` に倒れる安全側に外れる。
- **実レスポンスは docs の例と表記が違った**: `product` は小文字 `"actions"`（docs の例は `"Actions"`）、
  `unitType` は `"Minutes"`（docs の例は `"minutes"`）、`date` は `"2026-07-01T00:00:00Z"`（docs の例は
  `"2023-08-01"`）。**docs の例をそのまま前提に実装していたら全件取りこぼして誤判定していた**ので、
  比較は全部大小無視にした（未確認の仮説で実装しない、という引き継ぎ doc の要求が実際に効いた）。
- **`Actions storage`（GigabyteHours）を分の枠と混ぜない**。含有枠が別建てなので、artifact が溢れて
  storage に課金が乗っただけで `exhausted` にすると、自発 dispatch が無関係な理由で恒久的に止まる。
  分の枯渇は分課金項目の `netAmount` と使用率で直接見る。
- **分課金項目が1件も無い月は `ok`（使用0）ではなく `unknown` にした**。「本当に使用0」と
  「`unitType` の表記が変わって全件落ちた」を区別できず、後者を `ok` と読むと*恒久的な*誤 `ok` になる。
  月初に一時的に `unknown` が出る不便より fail-open を嫌う。同じ理由で未知 SKU の分項目も `unknown`
  （倍率を推測しない）。

## 2026-07-24 403 を「報告して終わり」にする穴を共通ブロック側で塞いだ

Actions storage の作業中に `docs.github.com` が 403 で弾かれ、共通ブロック「外部 URL アクセスの報告」に
従って「接続できなかった URL」として報告した — そこで止めて手元の知識で答えてしまい、net-fetch 手順に
入らなかった（ユーザーの指摘で発覚）。

構造的な原因は**アンチパターンの警告が手順の内側にあったこと**。`docs/net-fetch.md` の「よくある失敗」
冒頭はこの失敗をそのまま書いているが、オンデマンド層の doc は「net-fetch を使おう」と決めた後にしか
読まれない。＝**手順に入らない失敗を、手順に入った人しか読めない場所で防ごうとしていた**。

加えて常時ロード層の 2 節が隣接していて、403 に対して:

- 「外部 URL アクセスの報告」は具体的で即時に完了できる行動（報告する）を与える
- 「外部ネットワーク取得が要るとき」の発火条件は抽象的（「egress 制限で届かず、取得が作業に必要になったら」）

となっており、報告を済ませた時点で義務を果たした感覚になる。そこで常時ロード層の側を直した:
報告節に「報告は取得の代わりにならない・403/407 は net-fetch の発火トリガ」を明記し、net-fetch 節の
発火点を「403/407 で弾かれた瞬間」と具体化した。オンデマンド doc 側は既に正しいので触っていない。

## 2026-07-24 net-fetch SOP: 能力不足時は分散モードへ落とさず停止する（Codex #644/#406）

consumer 同期 PR（nikki-san#644 / private#406）に付いた Codex レビュー2件が、`shared/docs/net-fetch.md`
（ツール中立化 #74 で書いた版）の同じ欠陥を指摘: `add_repo` 等の集約実行能力を持たないエージェントに
「分散モードを既定にする／分散へ切り替える」と書いていた。これは**能力（ツールの有無）でモードを選ぶ**
ことになり、同 doc の原則「モードは可視性・機微性だけで選ぶ／モード切り替えを allowlist 回避に使わない」
（前提節・モード節の MUST NOT）と矛盾していた。具体的な害: 機微でない public 相当の取得でも、ホストが
共通 allowlist に無く `.github/net-allowlist.local.txt` にだけ有る場合、分散に落ちると手順 step 3 が
「許可済み」と扱って共通 allowlist へのユーザー判断を素通りし、public 相当の取得を private の Actions 枠・
非公開 `ci-logs` に落としてしまう。

修正: 集約が正しい（＝機微でない）のに集約を実行できないエージェントは、分散へ回避せず**停止して
ユーザーに集約実行（repo 追加か ai-ops への dispatch/読み取り）を依頼する**（MUST）に統一。分散で起動する
のは step 1 で取得内容が機微＝分散が正しいと判断したときだけ、と明記して doc 内の自己矛盾を解消した。
AGENTS_COMMON 側の net-fetch 節は元から「勝手に分散へ切り替えない」で正しく、修正不要。

追加（Codex private#407、別 sync #75 由来の別指摘）: step 4 で「git ref は既定ブランチを指す」が
**REST 経路だけ MUST**で、`gh`/MCP 経路は無キーワードの説明文だった。SOP 書式では無キーワード文は
「要求ではなく説明」と読まれるため、`gh`/MCP でエージェントが現在ブランチ／feature ブランチの ref を
渡してもルール上は許容され、レビュー済みでない `net-fetch.yml`・allowlist のコピーが走りうる。
修正: 「既定ブランチ ref を指す」を**全 dispatch 手段共通の MUST**（別ブランチ ref を渡すのは MUST NOT）
に格上げし、手段ごとの満たし方（REST=body の `ref`／`gh`=`--ref`／MCP=ref パラメータ）は MUST の下の
補足に整理した。同 PR にまとめた（同一 doc の連続した SOP 是正のため）。

## 2026-07-24 net-fetch: SOP を非 Claude エージェント向けにツール中立化

ユーザーから「net-fetch の GitHub Actions は Claude Code 以外のエージェントで問題を起こさないか」と問われ、評価した。

評価の結論:

- **インフラ本体は問題なし**。workflow / composite action / net-fetch.sh は完全にエージェント非依存で、
  allowlist・SSRF ガード・secret スキャン/伏字・クリーンルームは全部 GitHub Actions 側（サーバ側）で enforce する。
  誰が `workflow_dispatch` しても同じ保護。配布も `apply-shared.mjs` が SKILL を `.codex/.openhands/.gemini/.agents/
  .qwen/.cline` へミラーするので全エージェントが見える。常時注入ではなく on-demand skill 層なので、発火しなければ不活性で
  他エージェントの通常タスクを壊さない。
- **ギャップは SOP の文面**にあった。`shared/docs/net-fetch.md` が Claude Code on the web 固有のツール語彙前提で、
  他エージェント（Codex/Gemini CLI/OpenHands/Qwen/Cline）では次が噛み合わない:
  - step 2/3 の `add_repo`（別リポジトリのセッション追加）は Claude-web 固有ツール。集約モードは「public な ai-ops に
    add_repo して dispatch」する構成なので、これを持たない他エージェントは**既定の集約パスの最初で詰まる**。
  - step 4「workflow_dispatch で起動」・step 5「ci-logs ブランチを読む」は具体手段を書かず特定ツール前提だった。

対処（`shared/docs/net-fetch.md` のみ改訂。SKILL ラッパーと AGENTS_COMMON の常時ブロックは中立・最小なので不変）:

- **能力ベースの前提節を追加**: 「dispatch できる」「ci-logs を読める」「（集約なら）ai-ops を参照できる」を*能力*として列挙し、
  何で満たすか（MCP/`gh`/REST/`git fetch`）はランタイム依存と明記。**満たせなければ停止してユーザーに依頼**（MUST）。
- **モードの適用範囲を明記**: 集約は `add_repo` 等（別リポジトリのセッション追加）が前提。その手段を持たないエージェントは
  **分散モード（作業中リポジトリで完結）を既定**にする。ただし「可視性・機微性でモードを選ぶ」MUST は保ち、能力制約で集約が
  *使えない*ことは、allowlist 回避目的の**モード切替（MUST NOT）とは別**として carve-out した。
- step 4/5 をツール中立化（`gh workflow run` / REST dispatch / `git fetch origin ci-logs` を例示、手段は不問）。

なぜインフラを変えずに doc だけ直したか: セキュリティ保証はサーバ側にあり、エージェント差はワークフローの起動主体だけ。
壊れるのではなく「Claude-web 固有名で書かれた手順が他エージェントで実行不能」というグレースフル劣化だったので、正本 doc の
表現をツール中立にすれば全エージェントで使える（同一ファイルを配る性質上、1回の正本修正で全 consumer 分が直る）。

配布影響あり（`shared/**`）なので、マージ後に consumer 同期 PR（head `ai-ops/sync-common`）の Codex レビュー・CI を見届ける。

## 2026-07-24 net-fetch: 共通 allowlist を root symlink 化（ドリフト解消）＋伏字境界を拒否と一致

#70 マージ後、ユーザーが `shared/.github/net-allowlist.txt` に `hysteria.network` / `*.hysteria.network` を
直接足したが、ai-ops 自身の集約実行が読む **root コピー `.github/net-allowlist.txt` が更新されず**、集約モードで
`hysteria.network` が拒否され続けた（Codex #70 が指摘。「shared だけ更新、root は未反映」）。dual placement
（branch-cleanup と同じ byte-identical copy 方式）を allowlist に使うと、手編集で片側だけ直すドリフトが起きる。

対処:

- **root `.github/net-allowlist.txt` を `../shared/.github/net-allowlist.txt` への symlink に変更**。ai-ops の
  集約実行は symlink 越しに shared の正本を読むので、**手編集は shared 一箇所だけ**でよくなり構造的にドリフトしない
  （`docs/*.md -> ../shared/docs/*.md` と同じ作法。workflow/action は Actions が実ファイルを要求するので copy の
  ままだが、allowlist は script が読むデータなので symlink で問題ない）。consumer には従来どおり sync が実ファイルを配る。
- **伏字境界を拒否パターンと一致**（Codex #70 P2）: `SECRET_QUERY_KEYS` の拒否は `key=` を位置を問わず一致させるのに、
  `redact_secrets` は `?`/`&` 直後の `key=` しか伏字にしていなかった。`https://example.com/path;access_token=secret` は
  拒否されるが `SAFE_URL` に生値が残り公開 ci-logs に漏れうる。伏字の `[?&]` アンカーを外し、値終端を
  `[^[:space:]&#;]*` にして拒否と同じ広さにした。

collector 例外の明文化（ルール整合）: 「新規ワークフローは collector に登録する」は codified rule（`ci-logs.md` 手順4・
nikki-san の DEPLOY_LOGGING_DESIGN.md チェックリスト）。net-fetch を登録しない判断を**ルール未修正のまま放置していた
＝サイレント違反**だったので、`shared/docs/ci-logs.md` に「リクエスト単位で毎 run inline publish するワークフロー
（net-fetch）は collector 登録の対象外」を根拠付きで明記した（黙って回避せず、逸脱はルール側に書く）。

なぜ private に collector が無いか: collector は**リポジトリ固有で配布物ではない**うえ、private は nikki-san とは
**別のログ設計**を採る。private の `deploy-workers.yml` は各 deploy ログを `deploy-logs/<worker>.log` に書いて
artifact 化し、`commit-logs` ジョブが `cloudflare_workers/deploy-logs/` に**コミットして**残す方式で、nikki-san の
`ci-logs` ブランチ＋`publish-ci-logs`＋`collect-deploy-run-logs.yml` の2層モデルを使っていない。よって private に
collector が無いのは抜けではなく設計差（Codex が collector 登録を nikki-san#636 でだけ挙げたのも、collector が
あるのが nikki-san だけだから）。net-fetch 配布で private にも `ci-logs` 系が入り、native の deploy-logs 方式と併存する。

学び: 「片方を直したらもう片方も直す」値（同一 allowlist の2コピー）は、AGENTS_COMMON「コードの重複に気づいたら
共通部品化」の典型。ai-ops 内で同一内容を複数パスに置くなら symlink にして正本を1つに保つ（ops-sync-design の作法）。

## 2026-07-24 net-fetch: REST dispatch 例に必須 `ref` を明記（#74 follow-up）

#74（SOP ツール中立化）が REST dispatch 経路を新たに手順に載せたが、GitHub の workflow-dispatch REST
エンドポイント（`POST .../actions/workflows/{file}/dispatches`）は body に `ref` が**必須**なのに、step 4 は
`url`/`request_id` しか渡すよう書いておらず、**REST 経由のエージェントは 422 で run が作られず ci-logs スライスが
出ない**。マージ後の Codex レビュー（#74 の P2）が指摘。

#74 は既にマージ済みなので、マージ済みブランチに積まず**最新 main から貼り直して新規 PR** で follow-up
（マージ済み PR は再利用しない規約）。

対処: step 4 に「workflow を回す git ref は対象リポジトリの既定ブランチ（通常 `main`）」を明記し、
「REST を使うときは body に `ref` を必ず含める（無いと 422）」を追記。`gh workflow run` は未指定なら既定ブランチを
使うので省略可、MCP dispatch ツールは ref パラメータに既定ブランチを渡す、という手段差も添えた。

学び: ツール中立化で特定経路（REST）を手順に載せるなら、その経路の**必須パラメータを漏れなく**書く。
「どれでもよい」と選択肢を増やすときは、各選択肢が単独で完結する粒度まで書かないと、一番不便な経路
（生 REST）を選んだエージェントだけ静かに詰まる。

追記（同 PR #75 の Codex 2巡目 P2）: 最初の追記は `ref` を「必ず含める」と書いたが、sop-format.md では手順の
必須要求は RFC 2119 大文字キーワードで示し、キーワードの無い文は説明として読まれる規約。省略すると 422 で
壊れる制約なので `含める（MUST）` に改めた。**「必ず／要」等の和文強調は SOP では規範として効かない**——
壊れる制約は MUST を付ける（この doc 群の他制約と同じ作法）。

## 2026-07-24 SOP 書式規約に「ツール中立」節を追加（#644/#406/#407 の再発防止）

net-fetch SOP の2件の Codex 指摘（#406=モード選択をツール能力に紐づけた／#407=`MUST` を REST 経路だけに

## 2026-07-23 net-fetch: 共通 allowlist に実ドメイン追加＋「allowlist 欠落時にモードを勝手に切り替えない」ルール

private リポジトリでの net-fetch テスト（`https://v2.hysteria.network/docs/Changelog/` の取得）で2つ判明:

1. **共通 allowlist が効かない**: ユーザーは `v2.hysteria.network` を「共通許可リストに追加した」認識だったが、
   ai-ops main の正本 `shared/.github/net-allowlist.txt` には入っていなかった（配布コピーやローカルを触った
   か、未マージだった可能性）。共通リストの唯一の正本は ai-ops の `shared/.github/net-allowlist.txt` で、
   sync で各 consumer の `.github/net-allowlist.txt` に配布されて初めて効く。正本に `v2.hysteria.network` を
   追加（＋ai-ops 自身のバイト一致コピー）。public な docs ドメインなので共通ベース（public 経路）に置いてよい。

2. **allowlist 欠落を分散モードで回避しようとした**: private の agent が「集約は outbox→同期→マージで非同期
   だから、今答えるために分散モード（このリポジトリ自身で実行）に切り替える」と判断しかけた。これはモード
   切り替えを allowlist 追加プロセスの回避手段に使うもので、「何を許すかはユーザーが決める」統制を崩す。
   ユーザーが停止させた。

対処（ルール）: モードは**可視性・機微性（将来は枠残量）だけ**で選ぶものと明記し、allowlist に無いドメインを
取得しようとしたら **停止してユーザーに手動追加を依頼する**（MUST）／**勝手に分散モードへ切り替えない・自分で
allowlist に足して続行しない**（MUST NOT）を、常時層 `AGENTS_COMMON.md` と手順 `shared/docs/net-fetch.md`
（モード節＋手順3）の両方に入れた。依頼にはどのファイルに何を足すかを明示する。

学び: net-fetch のモード選択（集約/分散）は「どこで実行し結果をどの可視性に置くか」の軸であって、allowlist の
穴を埋める手段ではない。allowlist 追加はユーザー統制下の非同期手続きで、即時性より統制を優先する。

## 2026-07-23 net-fetch: consumer 同期 PR の Codex 追加指摘（注入・PEM・クエリ）を正本で修正

nikki-san#636 / private#401（net-fetch を配布した同期 PR）への Codex レビューが、ai-ops#68 には無かった

  対処: 動的値をすべて `env:` 経由で渡し、`$VAR` を `printf` する（env の値は再評価されない）。URL は伏字済み
  meta.txt から拾う。
- **PEM ブロック未伏字（private P2）**: `-----BEGIN … PRIVATE KEY-----` パターンは BEGIN 行しか一致せず、行単位の
  sed 伏字だと base64 本文・END が response.txt に残っていた（集約モードで公開 ci-logs に落ちる）。
  対処: `redact_file()` を追加し、awk で BEGIN〜END を丸ごと `[REDACTED-PRIVATE-KEY]` に置換してから token 類を sed。
- **クエリ/フラグメントで allowlist 誤判定（private P2）**: host 抽出がパスの無い `https://example.com?x=1` /
  `#frag` で `?`/`#` を落とさず、`example.com?x=1` を allowlist と突き合わせて**許可済みでも拒否**していた。
  対処: host 抽出で `?` と `#` も除去。
- **collector 登録（nikki-san P2）**: 「新規 workflow はフル生ログ collector の一覧へ失敗時ゲートで登録」は
  **リポジトリ固有**（collector `collect-deploy-run-logs.yml` と設計 doc は nikki-san ローカル・配布対象外）。
  正本では直せないので nikki-san 側のローカル変更で対応する（別 PR）。

- **userinfo 資格情報の漏洩（#70 への再レビュー P1）**: `SAFE_URL` は token パターンとクエリ値しか伏字にせず、
  `https://user:pass@host/` の `user:pass@` を残していた。userinfo チェックで fetch は reject するが `emit` は
  `SAFE_URL` を `meta.txt` に書く→集約モードで公開 ci-logs に資格情報が残る。対処: `redact_secrets` に
  `s|(://)[^/?#@]*@|\1[REDACTED-USERINFO]@|` を追加（パス/クエリ中の `@` は `/?#` 境界で誤爆しない）。

学び: 配布物への指摘は「同一ファイルを持つ全 consumer 分」を1回で正本修正すれば足りるが、consumer ごとに
Codex が見る文脈（各 repo の AGENTS.md・collector 有無）が違い、**consumer PR にしか出ない指摘**もある
（今回の注入・PEM・クエリは #68 に出ず #636/#401 で出た）。配布した net-fetch のレビューは consumer 側 PR も
必ず確認する。workflow の `run:` に `${{ inputs.* }}` を生で埋めない（env 経由）ことは全 workflow 共通の鉄則。

## 2026-07-23 net-fetch: Codex レビュー指摘（P1 secret 漏洩 / P2 パストラバーサル）を修正

ai-ops#68（および同一ファイルを配布した nikki-san#636・private#401）への Codex レビュー2件を正本で修正した
（配布ファイルなので consumer PR を手編集せず ai-ops で直す）。

- **P1（secret 漏洩）**: secret を含む URL を拒否しても `emit()` が生 URL を `meta.txt` に書き、`net-fetch.yml` は
  rejected でも `net-fetch-out` を publish するため、集約モードだと**公開 `ci-logs` に secret が残る**。
  対処: `redact_secrets()` を追加し、出力に載せる URL は secret パターン＋secret 臭いクエリ値を伏字にした
  `SAFE_URL` を使う（`meta.txt` の `url=`）。workflow の Summarize も生入力ではなく伏字済み `meta.txt` から
  URL を拾う（要約は public な run ログにも出るため）。
- **P2（パストラバーサル）**: publish の `dest` に検証前の生 `request_id` を使っていたため、`../branch-cleanup/latest`
  や `..` で net-fetch/<id> スライス外へ publish できた（スクリプトが reject しても publish は `if: always()`）。
  対処: スクリプトが `request_id` を検証（`^[A-Za-z0-9._-]+$` かつ `..` を含まない）し、通らない id は
  ユーザー制御でない `net-fetch/_invalid-<ts>-<pid>` へ退避した `dest` を GITHUB_OUTPUT に出す。workflow は
  生入力ではなく `steps.fetch.outputs.dest` を publish の dest に使う。空 dest のときは publish しないガードも追加
  （空を publish-ci-logs に渡すと clone を丸ごと消しかねないため）。

学び: net-fetch の結果は集約モードで public な `ci-logs`／run ログに出るので、**出力に載る文字列（URL・dest・
要約）はすべて「拒否した入力でも安全か」を基準に組む**。拒否は「弾いて緑で publish」なので、拒否した生入力が
出力経路に載らないことまで含めて設計する。

## 2026-07-23 net-fetch: エージェントの代理インターネット取得リレーを共通基盤として追加

Claude Code の許可ドメイン egress が機能しない環境向けに、GitHub Actions ランナー（フルのネット接続を持つ）を
中継して**許可ドメインだけ**を取得するリレーを追加した。エージェントは egress 制限下でも GitHub には到達できる
ため、GitHub 自体を中継所にする構図。正本は `shared/`（全 consumer へ配布）、ai-ops 自身にもバイト一致コピー
（`branch-cleanup` と同じ dual placement）。

判断の経緯（コードに残らない前提・制約）:

- **集約 vs 分散**: 実行を public な ai-ops 上で回せば GitHub Actions 分が無料（既存の「ai-ops を public に
  している理由」と同じ）。ただし結果は ai-ops の `ci-logs`＝世界公開に落ちる。そこで両モードを同一 workflow
  で持ち、**どのリポジトリで起動するかだけがモードの違い**にした。現状の既定は集約（枠逼迫のため）。
- **allowlist 2層（共通配布 ∪ リポジトリ固有）**: 共通ベース `.github/net-allowlist.txt`（配布）に加え、
  各リポジトリの `.github/net-allowlist.local.txt`（配布対象外・repo 所有）を union。**機微を取得しうる
  ドメインは private リポジトリのローカルにだけ書く**運用。集約モードの判定は共通ベースのみを見るので、
  機微ドメインは構造的に public 経路を通れない（配置がルールを強制する。人の規律に依存しない）。
  `.local.txt` を配布しない（shared に置かない）のは、置くと manifest 管理下になり同期で上書きされ
  「repo 所有」でなくなるため。
- **secret を fetch に含めさせない縛り**: 取得ジョブに secret を一切渡さない（クリーンルーム）を第一の
  構造的縛りにし、request の URL/クエリの secret パターン拒否・response の secret 伏字を二層目に置いた。
  publish（ci-logs へ push）に使う github.token は取得ステップの env に載せない。
- **consumer 側に dispatch トークンを置かない**: エージェントは自前の GitHub 資格情報で workflow_dispatch
  する。過去に上りの即時化で置いた `OPS_DISPATCH_TOKEN`（consumer→ai-ops 書き込み）を「ルール正本への
  増幅経路」として撤去した経緯（→ ops-sync-design.md）と同じ理由で、consumer に常設トークンを増やさない。
- **SSRF ガード**: allowlist と無関係に、https 以外・URL 内資格情報・IP リテラル・localhost・クラウド
  メタデータ（169.254.169.254 等）・リダイレクト追従を常に禁止。allowlist はドメイン前提なので通常は
  一致しないが、明示的に弾いて意図を固定した。
- **枠連動（quota-gate）は今回作らない**が、あとで共通基盤として差し込めるよう継ぎ目を用意した。集約/分散の
  両実行経路は既に存在するので、将来足すのは「枠残量でどちらを選ぶか」の判定層だけ（この workflow・SOP は
  変更不要）。枠残量は billing API 経由（PAT 必須・アカウント単位・遅延あり）でしか取れないことも確認済み。

学び: 新規 shared workflow なので docs/ci-logs.md に従い publish-ci-logs を組み込む必要があるが、net-fetch は
「取得結果そのものを per-request スライスへ publish する」ことが inline publish を兼ねる（別途 logs/ci/scripts を
足さず、結果 publish で要件を満たした）。

## 2026-07-23 archive-task-history に統合時の重複排除（dedup）を追加

- **なぜ**: PR #58（自動アーカイブ）に Codex P2「重複した履歴エントリ」。`archive-task-history.mjs` は
  inbox フラグメントを本体（`AI_TASK_HISTORY.md`）と突き合わせずに無条件連結していたため、本体に既にある

- **修正（恒久）**: 統合フェーズで、本体にある dated エントリの**本文全体（trim）**を set 化し、同一本文の

  全体一致だけを重複とみなす。
- **スコープの限界**: 重複判定は**本体のみ**が対象で、アーカイブ済みエントリとの突き合わせはしない（Codex
  指摘の本体二重化が対象。年ファイル全ロードは重いので見送り）。
- **応急**: 上記 07-20 重複フラグメントは同 PR で削除済み（恒久修正でも次バッチで掃除されるが、それまでの
  read 時二重を消すため即削除）。テスト基盤が無いため一時スクリプトで本体重複／非重複／inbox 内重複／
  重複のみの4ケースを検証（コミットしない）。

## 2026-07-23 stale ブランチ手動削除 workflow（branch-cleanup）を shared 配布で新設

private の Cloudflare Workers Builds 接続で Production branch 一覧に main が出ない件の根因が、
エージェント生成の stale ブランチ大量残留（private 264本・codex/claude 主体）だったため、手動トリガの
一括削除 workflow を追加。3リポジトリ（private / nikki-san / ai-ops）に同一で入れたいので shared 配布にした。

判断・ハマりどころ:
- GitHub の "Automatically delete head branches" は**マージされた PR の head しか消さない**。close/PR無し/
  設定前のブランチは残る（＝ON でも溜まる。ユーザーが「ON なのに同症状」と指摘。仕様どおり）。だから
  掃除 workflow が要る。
- **workflow ファイルの配布には token 権限の壁**: sync は `OPS_SYNC_TOKEN`（PAT）で consumer に push するが、
  GitHub は `.github/workflows/` 配下を `workflow` 権限の無い PAT で push させない。従来の shared 配布物は
  composite action（`.github/actions/`）止まりで workflow ファイルは初。**OPS_SYNC_TOKEN に Workflows 書き込み
  権限の付与が必要**（無いと sync PR の push が consumer で失敗する）。Codex P1 の指摘どおり README・
  ops-sync-design.md（Secret 表＋設計注記）・sync.yml コメントの token 権限記載を Workflows:RW 込みに更新。
  設計 doc は元々この権限を「blast radius を広げる」と避ける論調だったが、ユーザー判断（A: shared 配布維持）で
  付与する方針とし、対象は token が既に Contents:RW を持つ同じ repo 群に限られる点を注記に明記した。
- ai-ops は sync の consumer ではない（consumers.txt = nikki-san, private のみ）ため、shared の正本に加えて
  ai-ops 自身の `.github/workflows/` にも**バイト一致コピー**を置く（両方を同時に直す）。
- 安全設計: 手動のみ（workflow_dispatch）・**既定 dry-run**・既定ブランチ/keep 一覧/オープン PR head を常に
  除外・prefixes 一致 かつ age_days（既定7）より古いものだけ対象。年齢は git committerdate で判定
  （squash マージだと ancestry でマージ済み判定できないため、prefix＋年齢＋オープン PR 除外で安全側に倒す）。
- keep 既定に nikki-san 固有の hugo-bin/deploy-logs も入れて全 consumer で1ファイルを使い回せるようにした
  （存在しない repo では無害）。

## 2026-07-23 ai-ops を public 化（GitHub Actions 分数の枯渇対策）

ユーザー相談「Actions の月枠が切れそう。履歴アーカイブやリポジトリ間同期をやっている ai-ops を public に
しようと思うが注意点は？」を受けて public 化した。

- **なぜ public 化か**: 月内の Actions 残枠が20分未満まで枯渇し、ai-ops 自身の運用 workflow
  （sync / archive-task-history / collect-outbox）が枠切れで止まりかけていた。consumer（nikki-san / private）は
  既に Cloudflare Workers デプロイへ移行済みで、deploy が主犯ではない。**public repo は GitHub-hosted runner の
  Actions が無料**（アカウント枠を消費しない）ため、ai-ops 自身の workflow を枠から外すのが目的。
  consumer は private のままなので、そちらの Actions 分数は救われない（切り分けて認識する）。
- **public 化前の棚卸し（実施済み・クリア）**: 全 git 履歴の diff を secret パターンで走査 → 混入なし。
  インフラ機密（IP 帯・pfSense・sing-box 等）は private repo 本体にあり ai-ops にはミラーされていない。
  過去に private 宛だった `tasks/` ファイルの中身も運用手順のみ。残る露出は「`65edh5ih/private` という
  非公開 repo の存在」と運用メタ（PR 番号・workflow 名・構成メモ）のみで、これは許容と判断した。
- **入れたガード**: ①`main` のブランチ保護（無料アカウントでは **public でのみ enforced**。private 中は
  "Not enforced" 表示が正常で、public 化の瞬間に自動で効く）。承認必須は **0** にする（archive/collect が
  `gh pr merge` で自分の PR を PAT 自動マージするため、1以上にすると自動化が止まる）。②Settings → Actions →
  General の fork PR を **Require approval for all external contributors**（UI 文言が outside collaborators から
  改称された同一設定）。
- **なぜガードが要る/効く**: 唯一の機微は `OPS_SYNC_TOKEN`（全 consumer への Contents:RW/PR:RW を持つ合鍵）。
  Actions secret なので**可視性変更では露出しない**。かつ ai-ops の workflow はどれも `pull_request` で
  起動しないため fork PR からトークンを窃取する経路が構造的に無い（fork 承認制は二重の保険）。
- **PR #63 との関係**: stale ブランチ削除 workflow の shared 配布は `OPS_SYNC_TOKEN` に Workflows:write を
  要求する（設計が意図的に避けていた格上げ）。ただし PAT は既に Contents:RW を持つ＝既にクラウンジュエルで、
  増分は categorical でなく incremental。public 化は PAT の漏洩確率を上げない（上記の理由）ため、docs 更新
  （README・ops-design のトークン表）＋スコープ付与を条件に許容可、と整理した。
- 恒久的な運用前提（ai-ops=public / consumer=private の可視性モデルと帰結）は `shared/docs/ops-sync-design.md`
  「前提・限界」に現在形で記載した。

## 2026-07-20 タスク履歴をフラグメント方式（history-inbox）に変更

### なぜ

ユーザーから「作業履歴ファイルはコンフリクトを起こしやすいので、別ファイルに書かせてバッチであとで
統合すれば」という提案。`docs/AI_TASK_HISTORY.md` は「新しいエントリが上」＝全セッションが**先頭行に
挿入**するため、並行 PR がほぼ確実にコンフリクトし、アーカイブバッチの自動 PR とも衝突しうる構造だった
（エントリの書き方を工夫しても直らない構造上の問題）。changelog の towncrier / changelog.d と同型の
「1エントリ＝1新規ファイル」にして、各セッションが別々のパスに触れるようにし衝突を原理的に消す。

判断の核（コードから読めない点）:

- **ファイル名の一意性が方式の要（MUST）**: 同名フラグメントを別ブランチで作ると add/add コンフリクトに
  なり、方式の意味が失われる。`<スラッグ>` は作業ブランチ名から採る（このリポジトリ運用のブランチ名は
  末尾ランダム片を持つので一意）と規約に明記した。1依頼=1PR=1ブランチなので実質衝突しない。
- **読む側を必ず2箇所にする**: 統合前の最新エントリは inbox にしか無い＝一番読まれるべきもの。
  セッション開始時の参照を「本体＋`history-inbox/` の全ファイル」に変更（AGENTS_COMMON・task-history 規約・
  skill description・Stop フックを同時に追随）。ここを落とすと「最新の文脈だけ見えない」最悪の穴になる。
- **バッチ頻度は日次のまま**: 衝突回避はバッチ頻度に依存せず達成される（統合は housekeeping）。統合前も
  inbox を読めば最新は拾えるので、PR churn を増やしてまで高頻度化しない。
- **`merge=union` 案を採らない**: GitHub のサーバサイドマージはカスタム merge 戦略を尊重しないため、
  肝心の PR マージ時のコンフリクトが解消されない。分割方式が明確に優る。
- **スクリプトはリネームせず機能拡張**（`archive-task-history.mjs` の名は多所から参照。archive は中核機能の
  まま、consolidate を前段に追加）。inbox の README・見出し無しファイルは取り込み対象外で削除もしない。

### 検証

`archive-task-history.mjs` を fixture で実駆動: (1) 2フラグメント統合＋保持超過1件アーカイブ、
(2) readme/見出し無しのみ＝保持内で no-op（冪等）、(3) 本体不在からの初回起こし、いずれも期待通り。
