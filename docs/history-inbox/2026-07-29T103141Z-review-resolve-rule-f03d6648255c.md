## 2026-07-29 レビュー指摘は resolve までを義務化

旧ルールの発火条件は「**積み残し消化系の依頼を受けたら**」だったため、**通常の PR レビュー対応で
指摘を直したエージェントには何の要求も掛かっていなかった**。直しただけで返信も resolve もしないと、
スレッドは「無視された指摘」と機械的に見分けがつかず、在庫に残り続ける。実際 93 件の未対応在庫を
棚卸ししたところ、大半が「既に直っているが未 resolve」で、指摘そのものより**棚卸しコストの方が
大きい**状態になっていた。発火条件を依頼の種類から「指摘に対応した」という行為そのものへ移した。

`resolve` を「直った」の唯一の信号として扱う以上、**早すぎる resolve も同じ害**になる（未修正の欠陥が
在庫から消える）。修正が未マージ PR にあるうちは resolve せず、マージ後に閉じるところまでを担当に
含める、を MUST NOT 側で明記した。この判断は今回の作業で実際に必要になった——共通配布物の修正 11 件は
ops-sync 側の PR がマージされるまで resolve を保留している。

**「Codex 以外にレビューする人がいない」という前提を明記した**のが、この改訂で一番効く部分。これは
ソースからもリポジトリ構成からも読み取れず、書いていないとエージェントは「人間のレビュアーが最後に
見る」「重要なら誰かがまた指摘する」という**存在しない安全網**を暗黙に仮定する。仮定が置ければ指摘を
落とすのは合理的な省力化になってしまうので、MUST を並べる前に前提を壊す必要があった。
今回取得したスレッドの作成者が全件 `chatgpt-codex-connector`（他は所有者の返信のみ）である点とも一致する。

消化依頼そのものにも完了要件が無かった。「載っている＝未対応」は一覧の読み方でしかなく、**全件を
終端状態にする義務も、落とした分を報告する義務も無い**ため、一部だけ直して完了扱いにしても
ルール上は違反にならなかった。全件終端＋残件報告を MUST にした。あわせて「指摘文だけを見て直し始めない
（先に現在の正本を読む）」も入れた——古い指摘ほど修正済みの割合が高く、確かめずに直すと二重に触るため。

常時ロード層に置いたのは、発火条件が「レビュー指摘に触れたとき」でありオンデマンド doc を開く
きっかけ自体が無いため（+916 文字・約 300 トークン）。詳細手順ではなく前提と MUST/MUST NOT だけを
置き、一覧の読み方は従来どおり生成物側の冒頭に委ねている。
