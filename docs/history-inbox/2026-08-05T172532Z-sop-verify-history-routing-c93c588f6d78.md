## 2026-08-05 教訓の置き場が履歴に流れる構造を塞ぐ

同じセッションで**複数回**、再利用可能な知見を履歴フラグメントに書いて終わりにした。直近の1件は
「書く場所を間違えた」と報告した直後の同じ誤りで、**個人の不注意ではなく規約側の穴**と判断した。

**なぜ履歴に流れるか**: 完了手順が「履歴を1件書く」で終わっており、**そこが作業の終端**になっている。
振り分け規約（共通/固有 × 常時/オンデマンド）は別の場所にあって、履歴を書く瞬間には発火しない。しかも
`task-history.md` は記録対象に「ハマりどころ」を挙げていて、**再利用可能な落とし穴を招き入れる文言**だった。
そこで振り分けの判定を `task-history.md` の手順3そのものに置いた。判定は一文で済む形にした——
**「今後は〜する」と読める文は履歴ではなく doc に置く**。

**もう一方の穴**は `sop-format.md` に「載せるコマンド・SQL を実行して確かめる」規約が無かったこと。
書式・完了条件・ツール中立は要求しているのに、**配布物として一番危険な「そのままコピーされて本番に流れる
クエリ」の正しさ**は要求していなかった。実際、静かに 0 件を返す述語を MUST として配る寸前まで行っている。
規約には「異常がある状態を作って異常を検出できることまで見る」を含めた——エラーで落ちる誤りは次の人が
気づけるが、**0 件で検査を通す誤りは誰も気づかない**という非対称があるため。

**この2つは対になっている**: 実行検証（誤りを作らない）と置き場の振り分け（作った知見を届ける）。
どちらか片方だけでは、正しい知見を誰も読まない場所に置く／誤った知見を全 consumer に配る、のどちらかになる。

**この PR 自身のレビューで出た穴**: 新設した MUST が「doc に載せる形そのままで実行する」だったが、同じ doc が
**プレースホルダを使えと要求している**（実値をハードコードしない）ので、**そのままでは実行できない**——
シェルなら `<...>` がリダイレクトに解釈されすらする。**満たせないゲートを作るなと書いた規約自体が
満たせない MUST になっていた**。「置換だけして実行する／置換以外は形を変えない」に直した。

境界を「そのまま」に置いたのが誤りで、正しい境界は**置換以外を変えないこと**。検証しやすいように書き換えると
検証したものと配るものが別物になる（実際、修飾子を「同じ意味だろう」と動かした結果、比較ではなく別の対象に
付いていた、という取り違えが起きている）。
