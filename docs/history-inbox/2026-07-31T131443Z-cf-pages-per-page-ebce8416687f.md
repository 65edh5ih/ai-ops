## 2026-07-31 Pages の計測が `per_page` の上限で丸ごと落ちていた

CF 枠信号の `pages_builds` がずっと `unknown`（`pages projects list failed (status 400)`）で、
ブログ本体の自動退避が判断できない状態だった。原因は
**`GET /accounts/{id}/pages/projects?per_page=100` が API に拒否されていた**こと:

```
8000024: Invalid list options provided. Review the `page` or `per_page` parameter.
```

**API リファレンスに `per_page` の上限は書かれていない**（`per_page : optional number` としか無い）。
同じスクリプトの deployments 呼び出しは `per_page=25` で通っており、そちらに揃えて解消した。

### 原因より、気づけなかった作りのほうが問題だった

note に `status 400` しか残していなかったため、**何が悪いのか誰にも分からない状態で残り続けていた**。
CF は `errors[]` に code と message を返しているのに、それを捨てていた。先に
「`errors[]` を note に含める」修正を入れてから再実行したら、1回で原因が確定した。

外部 API のエラーは **status だけでなく本文の code/message まで残す**。status だけだと、次に見る人が
同じ推測と切り分けをやり直す（実際このセッションでも、docs を net-fetch で取りにいって
「上限の記載が無い」ところまで確かめてから、実測に切り替えている）。
出力先が public な `ci-logs` なので、本文全体ではなく **code と message だけ**に絞っている。

### 教訓

- **「docs に書いていない ＝ 制約が無い」ではない。** API リファレンスに上限の記載が無くても、実装は
  拒否する。同じ API 群で既に通っている値があるなら、まずそれに揃えるのが速い。
- **同種の呼び出しでパラメータを揃えておく。** 同一ファイル内で 25 と 100 が混在していたのが元凶で、
  片方だけ通っていたので気づきにくかった。コメントで「揃えてある」と明記した。
