## 2026-08-05 D1 撤去手順にテーブル版と網羅的な事前確認を足す

前 PR でスキーマ撤去の節を足したが、レビューで2つの欠陥が出た。どちらも「書いた前提と手順が食い違う」型。

**(1) 見出し・トリガは「列・テーブル」なのに手順が列専用だった**。`DROP COLUMN`・`pragma_table_info` しか
書いておらず、テーブルを消す人は**存在しない手順に案内される**。テーブル版を足した。要点は列と非対称で、
`DROP TABLE` は**依存ビューを道連れにしない**（その場は成功し、後からそのビューを使う経路が壊れる＝作業とは
別のタイミングで顕在化するので原因に辿り着きにくい）。逆に FK 参照があると失敗しうる。検算も
`sqlite_master` で「テーブルが消えた」と「壊れた依存が残っていない」の両方を見る形にした。

**(2) 阻害要因を列挙したのに事前確認が索引しか見ていなかった**。インライン宣言の PK/UNIQUE/CHECK・生成列・FK は
**テーブル自身の DDL 文にしか現れず**、ビュー・トリガは別オブジェクトなので、索引を見ても引っかからない。
索引だけ確認して通すと本番 DDL がその場で拒否される。テーブル自身の `sql` と、列名に言及する
ビュー/トリガの2本を読む形にした。`LIKE` の粗い網なのは、取りこぼし（偽陰性）より偽陽性に倒すため
——偽陽性は定義を読めば捨てられるが、偽陰性は本番で初めて分かる。

**教訓**: 手順 doc で対象範囲を広く書く（「列・テーブル」）なら、広げた分の手順を必ず同時に書く。
トリガだけ広げると、案内された先に手順が無いという最悪の形になる。
