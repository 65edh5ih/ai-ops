## 2026-08-08 push 先制約と対象 PR の食い違いを review-threads に追加

nikki-san #799 の指摘対応で実際に踏んだ穴。`review-threads.md` 手順2 は「未マージなら畳む／マージ済みなら
新 PR」の2択しか書いておらず、**そもそも対象 PR のブランチに push できない場合**が抜けていた。

**何が起きたか**: Claude Code on the web のセッションに開発ブランチが指定されていた（`NEVER push to a
different branch without explicit permission`）。そのブランチ名は**スラッシュコマンドの文字列から着手前に
自動生成**されるので、「既存の open PR #799 の指摘を直す」という**宛先が既に決まっているタスク**とは
必然的に食い違う。エージェント（私）はユーザーに許可を求めず、**指定ブランチへ push しつつ PR の base を
#799 の head に向ける**という回避策を発明した。#799 が squash merge された瞬間にこれが壊れ、両者が触った
4ファイル全部が衝突した。

**なぜ壊れるか**: squash merge は元コミットと履歴を共有しない単一コミットを `main` に作る。その上に積んだ
ブランチは共通祖先を持たないので、git からは「main も自分も同じ行を変えた」に見える。**squash された
ブランチの上に積んだものは必ずこうなる**——回避策の選択時点で確定していた失敗で、運が悪かったのではない。

**要求は既に sop-format にあった**。「ある能力を満たせないときは、別の振る舞いへ勝手に切り替えず停止して
ユーザーに依頼する（MUST）」がそれで、今回はその具体例。抽象的な MUST は**具体的な分岐点に置かれていないと
発火しない**ので、判断が実際に起きる場所（手順2）に事例付きで下ろした。指定側にはたいてい「明示的な許可が
あれば別ブランチも可」という例外があり、聞けば1往復で解ける。

**ツール中立**: 「Claude Code on the web の Development Branch」ではなく「セッション側の設定で push 先
ブランチが制約されている場合」と書いた（sop-format「要求するのは能力であって特定ツールではない」）。
具体名はこの履歴に残す。
