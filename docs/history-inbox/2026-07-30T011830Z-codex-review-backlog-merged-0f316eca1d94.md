## 2026-07-30 マージ済み PR の Codex 指摘消化（net-fetch cleanup・削除の意味・入力境界）

マージ済み PR に残っていた Codex 指摘のうち、正本がこのリポジトリにある4件をまとめて直した
（配布物の欠陥は全 consumer に残るため 🔴 扱いで最優先）。3件は net-fetch まわりで相互に絡むので1 PR にした。

### 退避スライスの名前を「生 ID から決まる」ものに変えた（ops-sync#126 / r3678930579）

`request_id` が構造検査や secret 判定に引っかかった取得は、結果を `net-fetch/_invalid-*` へ退避する。
その名前が `_invalid-<時刻>-<PID>` だったため、**別 run である cleanup 側から再現できなかった**。
エージェントは手元の生 ID を cleanup に渡すので、退避スライスには到達できず「nothing to drop」で緑になる。
手順6は「緑＝スライスが外れた」を完了条件にしているので、**この緑は嘘**だった（退避スライスには
`meta.txt` 経由で secret 形の ID 自体が載っている）。

名前を **生 ID の sha256 先頭12桁**にして決定的にした。cleanup 側が同じ digest を組み立てられるので、
エージェントは今までどおり生 ID を渡すだけでよい（退避先を自分で調べさせない）。digest なので ID 自体は
名前に現れない。Codex が挙げた2案のうち「サニタイズ済みのスライス名を渡す」ではなく「生 ID を退避先に
解決させる」を採ったのは、前者だと**取得 run の summary を読んで名前を転記する手順**がエージェント側に
増え、転記漏れが同じ「緑なのに残っている」に戻るため。

これに伴い `publish-ephemeral` の `drop-slice` を**1行1名のリスト**にした（通常スライスと退避スライスの
両方を落とすため）。生 ID を名前として渡すのは素のスライス名として妥当なときだけにしてある——
複数行の ID をそのまま流すと「複数のスライス名」に化け、**無関係なスライスを消せてしまう**
（従来は複数行 ID が検証で一律 refuse だったので、リスト化で新しく開いた穴。塞いでから入れた）。

### 「削除」は到達不能化であって消去ではない、と書き直した（ops-runner#35 / r3678942811）

`rm` はブランチ先端から辿れなくするだけで、到達不能になった commit・blob は**リモートに残る**。
ブランチが生きている間に SHA を記録した相手はその後も取得できる。GitHub には GC を強制する API が無いので、
**cleanup の成功は消去の証明にならない**（Codex の指摘どおり）。

コード側で解けないので、**主張のほうを実態に合わせた**。縮められるのは堆積と発見可能性だけで、
開示そのものは取り消せない。したがって「あとで cleanup するから数分で消える」を、機微な取得を public 経路に
流す根拠にしてはいけない——機微性の判断は cleanup の有無ではなく**モード選択**（集約/分散）で行う、と
`net-fetch.md`・`ops-sync-design.md`・`README.md`・action の description の4箇所に書き分けた。
既存の「機微を集約モードに流さない」ルールは元から正しかったが、その根拠が「公開時間が短いから許容」に
読める書き方になっていたのを、「public に出した時点で恒久開示」に直した意味が大きい。

ストレージを差し替える案（Codex の第1案）は採らなかった。egress 制限下のエージェントから確実に読めるのは
git と `api.github.com` だけで、artifact 等に移せない制約は設計 doc に既にある（再検討しない旨も含めて）。

### 前提節の cleanup MUST をモード別に直した（private#475 / r3678943015）

手順6は既に「集約=MUST・分散=MAY」に直してあった（#126）が、**前提・パラメータ節に無条件 MUST が残っていて**
矛盾していた。同じ事実が2箇所にある状態そのものが原因なので、前提節は強度の要約＋手順6が正本、という
リンク形に変えた（AGENTS.md「同じ事実の正本は1つに保ち、他からはリンクする」）。

### age_days の正規化を長さで先に縛った（private#474 / r3673413753）

先頭ゼロを1文字ずつ削る while ループが、反復ごとに残りを丸ごとコピーしていた（先頭ゼロの数に対して二次）。
桁数ガードはループの**後**にあるので、数万個のゼロという「数値としては妥当な」手動入力で private ランナーの
分数を焼ける。生入力の長さ上限を正規化より前に置き、ループ自体も `${age_raw%%[!0]*}` の1回操作に置き換えた。
桁数ガード（正規化後）と長さガード（正規化前）は**別物なので両方要る**——`0...0365` は正規化後3桁で通るが
生では任意に長くできる。

### 検証

`drop-slice` のリスト検証を11ケース（`.`・`..`・`../../evil`・`/`・CR・改行+`::error::`・空白・空 等）で実駆動し、
不正な行が1つでもあれば run 全体を refuse することを確認。ローカルの bare repo を remote に見立てて
`publish-ephemeral` を実際に走らせ、(a) secret 形 ID の cleanup で退避スライスが実際に消えること、
(b) 無関係なスライスが残ること、(c) 再実行が緑の no-op になること、(d) 不正行で exit 1 になることを確認した。
退避先 digest が `net-fetch.sh` 側と cleanup 側で一致することも6種の ID 形で突き合わせた。
`age_days` 正規化は9ケースで旧ループと同値であることを確認。
