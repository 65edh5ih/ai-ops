## 2026-08-08 引き継ぎ手順（分岐＋元PR close）を共通化

枠切れで止まったセッションの続きを別セッションが引き継ぐとき、元スレッドが枠復活や PR 購読の
webhook で後から動いて成果を壊す経路があった。最初に検討したのは lease ファイル（所有者・世代を
リポジトリに置き、pre-push で所有者違いを弾く）だが、**この環境では原理的に作れない**と判断した:
`merged-branch-guard.md` に記録済みの壁がそのまま効く——ハーネスが未 push ブランチにも
remote-tracking ref を seed し、git ミラーは今セッションで push したブランチを `ls-remote`/`fetch` で
返さず、shell から GitHub API も叩けない（プロキシが MCP 以外を遮断）。つまりフック内で
「リモートの現在の所有者」を知る手段が無い。今回の実測でも、前セッションのブランチは `ls-remote` で
返るが今セッションのものは返らない、という非対称が再現した（＝引き継ぐ側からの取得は可能なので、
分岐の手順自体は成立する）。

そこで方針を「元スレッドを止める」から「元スレッドが動いても壊せない」へ倒し、**元ブランチに乗らず
分岐し、元 PR を close する**を手順の中心にした。close を選んだのは効き方が2つあるため:
(1) 既存の「push 前に `merged`/`state` を無条件確認」が closed をそのまま拾うので、引き継ぎ専用の
新しいガードを足さずに済む（規約の重複を作らない）。(2) PR 購読の webhook が枯れる——購読は
セッション単位で引き継いだ側から解除できないので、人が見ていないところで元スレッドが起きる
主経路を塞ぐ手段がこれしかない。

元ブランチを force-push で乗っ取る案は捨てた。元スレッドの push は弾けるが、未 push の成果を
失わせるうえ、復活した元スレッドからは「壊れた」としか見えず状況を復元できない。分岐なら両方の
履歴が残り、後から選べる。

検知層（同一タスクを指す open PR の重複を CI で赤くする等）は今回入れていない。まだ観測していない
事象のために常設コストを払うことになるため、実際に二重作業が起きてから足す。
