## 2026-08-05 段階的デプロイと識別子の大文字小文字を SOP に反映

D1 の SOP に3件。いずれも**マージ後の consumer 同期 PR に付いたレビュー**で出た（本体 PR には出なかった）。

**(1) 「有効なバージョンは1つ」と決めつけていた**。段階的デプロイ（`versions deploy` の
`<version-id>@<percentage>`）では複数バージョンが同時に本番を受け持つ。片方だけ見て「これが本番の DB」と
決めると、まだトラフィックを受けている側を見落とす。**トラフィックが 0 でない全バージョン**を確認する形にした。
撤去手順側にも同じ罠があり（分割が残っている間は**旧版の ensure が列を作り直す**）、そちらにも書いた。
この2つは同じ「1バージョンしか見ない」前提から出ている。

**(2) FK 検出の比較が大文字小文字を区別していた**。SQLite の識別子は大小を区別しないのに
`pragma_foreign_key_list` は**宣言どおりの表記**を返す（実測: 子が `REFERENCES Parent(...)` なら `Parent`）。
素の `=` だと 0 件になり、**検査が「異常なし」で通る**。見落としが最悪の形で出る箇所なので `COLLATE NOCASE` を
MUST にした。列名側も同じ性質なので併記。**「探すときは広く」の原則がここにも効く**——同じ判断を、
前回は部分一致の扱いで、今回は大文字小文字で間違えた。

**(3) public リポジトリに private consumer の運用詳細を書いていた**。前回の履歴フラグメントに、別リポジトリの
セッションで得た具体的な構成情報を根拠として書いてしまった。このリポジトリは public で、履歴フラグメントも
開示規約の対象。

**重要な限界**: 本文から消しても**公開は取り消せない**。git 履歴にも PR の diff にも原文が残るからで、
今回やったのは「今後この doc を読む人の目に触れないようにした」だけ。**書いた時点で公開は完了している**と
考えるべきで、事後の削除を対策と数えない。取り消すには履歴の書き換えが要り、それは配布物の同期を壊すので、
このリポジトリでは現実的でない（＝**書く前に止めるしか手が無い**）。この項目で具体を再掲しないのも同じ理由。

一般化の判断を「doc 本文かどうか」でしていたのが誤り。判断軸は**このリポジトリが public か**（AGENTS.md に
そう書いてあり、しかも同種の取りこぼしが過去にあったと記録もされている。読んだうえで再演した）。

**追記（レビューで出た5件と、その過程で見つけた落とし穴）**: 上の (2) を「FK 検出クエリだけ」直したのが浅く、
**同 doc の他の識別子比較（事前確認の `name=` / `tbl_name=`、検算の `col_remains` / `table_remains`）が
素の `=` のまま**残っていた。特に検算側は、テーブルが ensure で復活していても「消えたまま」と誤って合格する
向きに効くので最悪。個別に直すとまた漏れるので、**識別子比較は一貫して `COLLATE NOCASE`** という原則を
節の冒頭に1つ置いた。

その修正中、`WHERE name IN (...) COLLATE NOCASE` と書いてしまい、**エラーも出さずに 0 件**になることを
実測で発見した。正しくは **`name COLLATE NOCASE IN (...)`（左辺に付ける）**。挙動は付ける位置で3通りに分かれ、
**どこに付いたかで理由も違う**（すべて SQLite 3.45.1 で実測）:

| 書き方 | 1要素 | 2要素 | なぜ |
|---|---|---|---|
| `x IN (...) COLLATE NOCASE`（閉じ括弧の後ろ） | 0 件 | 0 件 | `(x IN (...)) COLLATE NOCASE` と解釈され、**比較ではなく真偽値**に照合順序が付く（明示括弧版と結果が完全に一致することで確認）。要素数によらず効かない |
| `x IN ('a' COLLATE NOCASE, 'b')`（要素側） | **1 件** | 0 件 | 1要素は `x = 'a'` に退化して右辺の COLLATE が効く。2要素以上はリストの比較になり無視される |
| `x COLLATE NOCASE IN (...)`（左辺） | 1 件 | 1 件 | 正しい書き方 |

**一番危険なのは2行目**——1要素で試すと効くので「解決した」と結論し、要素を増やした瞬間に静かに 0 件へ戻る。
なお最初にこの記録を書いたとき、私は**挙動を逆の構文に紐づけていた**（末尾付与が1要素で効く、と書いた）ため、
レビュアーに測り直させている。**この表は配布 doc 側の原則ボックスに要点を書いた**（履歴は配布されないので、
consumer が読めるのは doc 側だけ）。計測の作法そのものは `docs/sop-format.md` に規約として置いた。危うく「静かに合格する SQL」を MUST として全 consumer に配るところだった。
以後、**doc に載せる SQL は書いた形のまま実行して確かめる**（この PR では節内の SQL 7本すべてを実行し、
想定どおりの行が返ることを確認した）。

もう1件、**実行手段の無い MUST を自分で新設していた**: 「トラフィックを受けている全バージョンから撤去済みを
確認」は、バージョン単位でコードを取り出す経路が無いので満たせない（`versions view` は bindings であって
コードではない）。今日すでに2回直した「満たせないゲート」を、直した本人が別の形で作っていた。
**確認できる条件に置き換える**——分割が解消して 100% であることを確かめ、分割中は撤去しない（急ぐ理由が無い）。

**さらに次のレビューで出た2件（どちらも「誤って合格する」向き）**: 検算の列チェックに `pragma_table_info` を
使っていたが、**生成列は table_info に出ない**（実測: VIRTUAL/STORED とも hidden=2/3）。対象が生成列なら
DDL が失敗していても 0 件＝合格になる。`pragma_table_xinfo` に変えた。テーブルの検算も `type='table'` の
絞りが無く、**トリガはテーブルと別名前空間なので同名で共存できる**（実測: `Log` テーブルと `log` トリガ）。
`DROP TABLE` 成功後も 1 のままで、今度は満たせないゲートになる。なおこの「同名で共存」は**トリガが別テーブルに
付いている場合**の話で、対象テーブル自身に付いたトリガは `DROP TABLE` の道連れに消える（最初この条件を書き
落としていて、素直に再現すると 0 件になり、実測と食い違って見えた）。

**3回目のレビューで出た2件——「COLLATE NOCASE を一律に付ける」が行き過ぎた箇所**: 原則を節全体に適用する際、
**`<>` による自己除外にも NOCASE を付けてしまった**（`name <> '<table>' COLLATE NOCASE`）。等値の網は NOCASE で
**広がる**が、除外の網は NOCASE で**広がる＝結果が狭まる**。おかげで `DROP TABLE` 事前確認から、大小違いの
同名オブジェクト（別テーブルに付いたトリガ `log` が `Log` へ書いている、等）が丸ごと落ちていた。しかもそれは
道連れに消えない側なので、**事前確認をすり抜けて壊れたまま残る**。`NOT (type='table' AND name=... COLLATE NOCASE)` と
**type と組で**除外する形に直した。**否定文脈では照合順序の緩和が安全側に働かない**——これは今回の原則自体の
例外条件なので doc 側にも書いた。

もう1件は同じ「同名で共存できる」性質の裏返しで、依存オブジェクトの検算 (b) が**名前だけ**で引きながら
**完了条件は「空」**だった。NOCASE を足したぶん無関係な同名（例: 消したビュー `dep` と無関係なトリガ `DEP`）を
拾いやすくなり、消し忘れが無くても空にならない＝また満たせないゲート。**完了条件を「手順2で列挙した
type と name の組が残っていないこと」に変えた**（空は要求しない）。

**この節で犯した誤りは全て同じ形**をしている——「確認しているつもりの述語が、確認したい対象を実際には
見ていない」。索引だけ見る／大小を区別する／table_info で生成列を落とす／type を絞らず別種を数える／
除外側に NOCASE を付けて対象を落とす。
この PR では節内の SQL 全7本を、生成列・同名トリガ・大小違いの FK を含むフィクスチャで実行して確認した
（この確認を毎回行うことは `docs/sop-format.md` の規約にした。履歴に書くと次の人に届かないため）。
