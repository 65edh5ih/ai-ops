## 2026-07-30 CI ログの公開先を『何についてのログか』で決める

- 発端は「public に出て困るログがあるなら、Codex レビュー一覧と同じく private リポジトリへ出したら
  どうか」という提案。実測すると仮定ではなく**実害**があった: ops-sync（public）の `ci-logs` の
  `archive-task-history/<repo>/**` に、private consumer の history-inbox の**ファイル名**（＝タスクスラッグ）が
  毎日出ていた（nikki-san 40件・private 22件が既に公開済み）。`collect-outbox` も提案ファイル名と却下理由を
  出す設計で同じ予備軍だった。`ci-logs.md` は既に「public に機微を出さない（MUST NOT）」と書いていたので、
  規約違反が実装側に残っていた形。
- **宛先を1つの private リポジトリに寄せる案は採らなかった**。理由2つ:
  (1) quota 信号（`quota/actions/actions.json`）は **public であることが要件** ——読み手は全リポジトリの
  エージェントで、public な ops-runner も含む。private に移すと「能力ゼロで読める」（issue ではなくファイルに
  している理由と同根）が崩れる。(2) `ci-logs.md` 手順B は「自分のリポジトリの ci-logs を読む」前提で、
  ops-sync 自身のログを他リポジトリへ移すと CI 失敗調査のたびに `add_repo`＋ユーザー確認が要る。
- 採ったのは**対象リポジトリごとに散らす**形（`publish-ci-logs` に `repository:` 入力を追加）。可視性が
  対象の可視性に自動一致し、かつ読み手（そのリポジトリで作業するエージェント）と同一リポジトリになる、
  この2つを同時に満たせるのはこの形だけ。Codex レビューの全体一覧が private 1箇所でよいのは、あれが
  **人が1本開いてトリアージする成果物**で読み手も置き場も1つだから（性質が違う）。
- 公開側ロールアップの件数は、詳細ログを grep で削るのではなく `$GITHUB_OUTPUT` で**作り分けた**
  （フィルタ方式は新しいログ行が増えるたびに漏れる）。ロールアップに `history-dir` を残したのは、
  齢による prune が効いて**旧方式で積まれた（ファイル名を含む）履歴エントリが保持期間 30 日で枝先から
  落ちる**ため。ただし git 履歴からは消えない（`ci-logs` の作り直しは別途ユーザー判断）。
- 公開してよい上限は**件数・repo 名・成否・PR URL まで**と決めた（既存の `sync/<consumer>/` スライスが
  既にこの粒度で、そこに合わせた）。対象リポジトリの中身に由来する文字列（ファイル名・パス・本文）は出さない。
