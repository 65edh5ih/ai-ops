## 2026-07-30 指紋一致の outbox 提案を自動マージする

取り込み PR の手動マージは「提案内容の再認可」として機能していたが、提案はそれを書いたセッションで
ユーザーが見ている。同じ内容を2度承認していることになり、その待ち時間のあいだ提案が outbox に居座って
上り経路全体を止めていた（選択は全 consumer 横断の最古1件なので、1件の未マージが他 consumer も止める）。

**自動マージの判定に使えるのは「提案が書かれた後に前提が変わったか」だけ**、という切り分けで設計した。
これはスレッドでの承認では原理的に代替できない情報（承認時点では衝突がまだ存在しない）で、逆にこれ以外
——提案内容そのものの妥当性——は取り込み時に機械が判断できない。よって条件は次の3つに絞った:

- 全文置換（`common-block-edit`／`shared-file`）のベースハッシュが現在の正本と一致すること。
- ベース欄の欠落は「判定不能」であって「問題なし」ではないので保留側に倒す。既定を保留にしておかないと、
  ベースを書き忘れた提案が検査を素通りしてしまい、検査を入れた意味が消える。
- `common-block-edit` の常時層の純増が上限内（`COMMON_GROWTH_LIMIT` = 800 文字）。内容が正しいかと
  「全 consumer の全タスクに常時乗るコストを払う価値があるか」は別の判断で、後者は機械には決められない。
  800 は現状 1 万文字弱の区間に対して「節が1つ増える規模」の目安。厳密な根拠は無いので、実運用で
  保留が多すぎ／少なすぎなら動かしてよい。

`task`／`task-done` は全文置換ではなく巻き戻る対象が無いので、検査の対象外＝常に自動マージ可。

**cleanup PR は取り込みが実際に入った後にだけマージする**。先に outbox を空にすると、オーナーが取り込み
PR を close して却下する逃げ道が消える。例外は却下だけの run（applied=0）で、これは取り込み PR 自体が
無く判断待ちも無いのに、人間待ちにすると壊れた提案1件が最古に居座って全 consumer を止めてしまう。

自動マージで通常経路が緑になるぶん、**残るものが見えなくなる**ので、run の最後に「人間を待っている
もの」（保留された取り込み PR・差し戻した提案）を `::error::` で立てて run を失敗させる。赤の意味を
「壊れた」から「人間が見るまで進まない」に寄せた。この step を最後に置いているのは、失敗で ci-logs の
publish やトゥームストーン掃除を巻き添えにしないため。

**ハッシュの取り方を種別で分けた**（consumer 同期 PR 側の Codex 指摘）。`common-block-edit` は
AGENTS.md のマーカー間から切り出す都合で前後の空白が必ず変わるので `.trim()` が要るが、`shared-file` は
バイト一致で配る実ファイルそのもので切り出しが無く、trim する理由が無い。trim したままだと
「末尾改行だけが変わった」ような境界だけの変更を検出できず、鮮度検査をすり抜けた全文置換がその変更を
黙って巻き戻す。自動マージを入れたことで人間の目が入らなくなるぶん、この穴の危険度が上がっていた。
取り込みの書き込みは `本文 + '\n'` に正規化されるので、バイト厳密にしてもラウンドトリップは安定する
（取り込み後のファイルを次の提案のベースにして一致することを確認済み）。

**この指摘は ops-sync の PR には出ず、consumer 同期 PR（private #483）にだけ出た。**
AGENTS.md「配布変更のダウンストリーム確認」が想定している通りの実例で、確認していなければ
配布物の欠陥がそのまま全 consumer に残っていた。

**既知の穴（AGENTS.md にも記載）**: 自動マージされた取り込み PR は扱うセッションが居ないため、
配布変更のダウンストリーム確認（consumer 同期 PR の Codex 指摘を読む）を行う者が誰も居なくなる。
自動マージの条件は「前提が変わっていないこと」しか見ておらず配布物としての正しさは見ていないので、
条件を厳しくしても塞がらない。塞ぐには consumer 側の指摘を拾う別経路が要る。
