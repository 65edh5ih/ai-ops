## 2026-07-31 cloudflare-quota: Pages 一覧のページ送り完了判定を fail-closed にする

`per_page` を渡さない形に直したことで、1ページあたりの件数を呼び出し側で決め打ちできなくなり、
`items.length < 100` という件数ベースの完了判定を捨てた。その結果 `result_info.total_pages` が
読めないケースが「1ページ目で完了」に倒れる形になっていた（fail-open）。2ページ目以降の
プロジェクトの deployment を丸ごと数え落としたまま `ok` を出しうる。この信号は自動退避の判断に
使われるので、**測れなかったものを `ok` として配るのが最悪の壊れ方**——`unknown` に倒した
（消費側は unknown を逼迫と同じに扱うので安全側）。

fail-closed にする前に、**それが現に効いている緑を壊さないか**を実測で確かめた: 修正版で再実行して
`pages_builds` が `ok` のままだったので、`total_pages` は実際に返ってきており、これまでの緑が
fail-open 分岐に乗っていたわけではないと確認できた。乗っていたなら `unknown` に落ちていたはずで、
確かめずにマージしていたら「Codex の指摘に従ったら信号が死んだ」になっていた。ops-sync は public
なので、この確認の dispatch はアカウント共有の Actions 枠を消費しない（枠が tight でも実行してよい）。

fail-closed への直し方自体も1回では正しくならなかった。`Number(rawValue)` を検証してから弾く形にすると、
`null` も `''` も `0` に化けて「有限の数」チェックを通り、`projectPage >= 0` が真＝1ページ目で完了、に
戻ってしまう（fail-closed にしたつもりで fail-open のまま）。**coerce する前に生の値を見る**必要がある。
モックで `null` / `0` / `''` / `1.5` を流して unknown になることを確認した。

診断の残し方も同じ轍を踏まないようにした。この PR の発端は note に `status 400` しか残っておらず
原因が特定できなかったことなので、`total_pages` が読めないときは `result_info` に**何が入っていたか
（キーだけ）**と値の型を note に載せる。出力先が public な ci-logs なので値は載せない。

## 2026-07-31 SKILL の発火条件を SOP の対象拡張に追随させ忘れていた

`gha-trigger-ui.md` の対象に「dispatch しないが枠消費を有効化する操作」を足したとき、
**skill ラッパー `shared/.claude/skills/gha-trigger-ui/SKILL.md` の description を直していなかった**。
description は「workflow を起動するコントロール」「起動有無が変わったとき」しか挙げていないので、
**新しく対象にしたシナリオではエージェントが skill を引かない**——SOP を広げても入口が塞がったまま。

### この指摘は consumer 同期 PR にだけ出た

ops-sync 本体の PR（#143）には指摘が無く、private の同期 PR（#495）で初めて出た。
これは ops-sync の CLAUDE.md「配布変更のダウンストリーム確認」がまさに警告しているパターンで、
**マージ後に consumer の同期 PR を見に行かなければ取りこぼしていた**。手順が機能した実例として記録する。

### 教訓

**SOP の対象（発火トリガ）を変えたら、その SOP の skill ラッパーの description も同じ PR で直す。**
本文とラッパーは「何のときに読むか」を二重に定義していて、片方だけ変えると
「ルールはあるが誰も読まない」状態になる。ラッパーはエージェントが SOP に辿り着く唯一の自動経路なので、
本文だけ正しくても機能しない。各エージェント向けのミラーは配布時に正本から自動生成されるので、
直すのは正本1箇所でよい。

## 2026-07-31 Pages の計測が `per_page` を渡していたせいで丸ごと落ちていた

CF 枠信号の `pages_builds` がずっと `unknown`（`pages projects list failed (status 400)`）で、
ブログ本体の自動退避が判断できない状態だった。原因は
**`GET /accounts/{id}/pages/projects` に `per_page` を渡していたこと**:

```
8000024: Invalid list options provided. Review the `page` or `per_page` parameter.
```

**値の問題ではない。** `per_page=100` を「上限超過だろう」と考えて同ファイル内の deployments 呼び出しと
同じ `25` に揃えたが、**それでも同じエラーだった**（実測）。`per_page` を**付けない**形にして初めて通った。
API リファレンスは `page` / `per_page` をどちらも `optional number` と書くだけで、上限も拒否条件も記載が無い。
ページ送りはレスポンスの `result_info.total_pages` で行う（`per_page` を指定しない以上、1ページあたりの
件数をこちら側で決め打ちできないので、`items.length` と定数を比べる完了判定もやめた）。

### 「原因が分かった」と言う前に、直したもので再実行する

`per_page=100` を見つけた時点で原因だと断定し、25 に直した段階で「直った」と報告してしまった。
実際は**同じエラーが続いていた**。**修正を当てた版で再実行して信号が変わったことを確認する**までは、
原因の特定も修正の成功も主張できない。今回は3回目の実行で初めて `ok` になった。

### 原因より、気づけなかった作りのほうが問題だった

note に `status 400` しか残していなかったため、**何が悪いのか誰にも分からない状態で残り続けていた**。
CF は `errors[]` に code と message を返しているのに捨てていた。先に「`errors[]` を note に含める」
修正を入れてから再実行したら、エラーコードが1回で見えた。外部 API のエラーは **status だけでなく
本文の code/message まで残す**。出力先が public な `ci-logs` なので、本文全体ではなく code と message だけ。

### `ci-logs` は orphan で毎回書き換わる（読み戻しの罠）

検証中、`git fetch origin ci-logs` では**古い内容を読み続けていた**。このブランチは publish のたびに
orphan 1コミットへ書き換えられるため、既に `origin/ci-logs` を持っている作業ツリーでは
`git fetch origin +refs/heads/ci-logs:refs/remotes/origin/ci-logs --force` が要る。
危うく「3回目も直っていない」と誤報するところだった。**信号を読み戻して結論を出すときは、
取得が最新かを疑う**（新規 clone では起きないので、Actions 上では顕在化しない）。

### 教訓

- **「docs に書いていない ＝ 渡してよい」ではない。** optional と書かれたパラメータでも、渡すと拒否される
  組み合わせがある。docs に無い任意パラメータを足さないほうが安全。
- **仮説→修正→再実行の再実行を省かない。** 1回目の断定（値の上限）は外れており、実測が唯一の決め手だった。

## 2026-07-31 経路の推奨を「判断」と「実行」に分けて公開する

`*_DEPLOY_POLICY=auto` を配線する突合処理。最初は ops-sync で**判断も実行も**やる形で書いたが、
**自分で書いた MUST NOT に正面から反していた**ので分離した。

### 何と衝突したか

`ops-sync-design.md` に「**ops-sync に置く CF トークンは読み取り専用にする**（MUST NOT: 書き込み権限を
持たせる）。ops-sync は public で、切替に要る Edit 権限の操作は consumer 側の workflow が自分のトークンで
行う」と書いてある。ops-sync で CF 側を反転するには書き込みトークンが要り、これを破る。

secret 自体は public リポジトリでも露出しないが、ops-sync は配布の要でワークフローの改変経路が多い。
「public 側に権限を集中させない」という設計思想でこの規定を置いたので、**規定を緩めるのではなく設計を
合わせる**ことにした（オーナー判断）。

### 分離の形

| | 場所 | 資格情報 | 頻度 |
|---|---|---|---|
| 判断 | ops-sync（public） | **不要** | 6時間ごと・Actions 分は無料 |
| 実行 | 各 consumer（private） | 自分の CF・変数トークン | 切替が要るときだけ |

**判断側が consumer の状態を持たないことが、資格情報を持たないことと表裏一体**になっている。
policy が `auto` か・CF が実際に出せるか・`HUGO_VERSION` が合っているかは、読み手が自分で確かめる。
結果、頻繁に回る側は無料かつ無権限、権限が要る側は年に数回しか動かない。

副次的な利点として、**オーナーが既に持っている consumer 側の CF トークンがそのまま使える**
（ops-sync 用に新しいトークンを発行する必要が無い）。

### 判断の規則

- **片方向ずつ条件が違う**: `github → cloudflare` は「Actions が逼迫 かつ 逃げ先の CF リソースが ok」、
  `cloudflare → github` は「Actions が ok」だけ。戻る先が空いていれば戻ってよく、CF 側の状態は問わない。
- **CF は対象の種類に対応するリソースだけ見る**。実測でこれが効いた: 現在 `pages_builds` は `unknown`
  （Pages のプロジェクト一覧が status 400 で失敗）だが `workers_build_minutes` は `ok` なので、
  全体 state で判定すると Workers 対象まで止まる。リソース別に見れば admin と private は退避可と出る。
- **信号が無い・壊れている・古いときは推奨を出さない**。推測で動かすと、実態と逆向きに倒して枠を焼くか
  配信を止めるかのどちらかになる。

### 残った問題

`pages_builds` が `unknown`（`pages projects list failed (status 400)`）。ブログ本体の自動退避は
これが直るまで動かない。突合とは別件の既存不具合なので、別途調べる。

## 2026-07-31 「枠消費を有効化する操作」を gha-trigger-ui の対象に足す

`gha-trigger-ui.md` は対象を「`dispatch` を投げるコントロール」で切っていた。しかし consumer 側で
**dispatch しないのに枠消費を左右するボタン**が見つかったので、対象定義を広げる。

### 見つかった穴

nikki-san / private のデプロイ経路スイッチは `actions/variables` を書くだけで dispatch しない。
だが書く値（`*_DEPLOY_ROUTE`）は workflow のゲート（`if:`）が読む値で、`github` に戻すと**以後の push で
deploy ジョブが `ubuntu-latest` 実走に変わる**（private リポジトリなので課金対象）。押した瞬間に run は
作られないが、「押す前に分かるべき副作用」であることは規約が守ろうとしているものと同じ。

字面どおりに判定すると**対象外**になり、印が付かないまま「押すと枠を使い始めるボタン」が並ぶ。
オーナーの意図は「**Actions の枠を消費するものに印**」で、そちらが本来の目的だった。

### 起動用の印を流用しない

consumer 側では既存の `GHA_BADGE`（「Actions」）を流用せず、別バッジ（「枠ON」）を新設した。
「いまこの run が走る」と「これ以降の実行が枠を使うようになる」は意味が違い、同じ印にすると
**手順2の印が「workflow が走る」の信号として読めなくなる**——規約自身が MUST NOT にしている
「印の意味が薄まる」がまさに起きる。この判断を規約側にも手順2b として明文化した。

**枠を使わなくなる向き（Actions 側を止める操作）には付けない**ことも明記した。印は警告なので、
消費が減る操作に付けると意味を成さない。

### 判定手順にも1段足した

手順1を「dispatch があるか」で終わらせず、**無くても「書き換える値が workflow のゲートで、課金対象の
ジョブが実走／skip に変わらないか」を workflow 側で確認する**ようにした。今回の見落としはここを
確認していれば防げた。「よくある失敗」にも同じ趣旨で1件足した。

## 2026-07-31 shared-file の本文をバイトそのままで書き込む

`shared-file` のベースハッシュをバイト厳密にした（#133・#134）のに、**書き込み側が正規化したまま**
だった。`stripFrontmatter()` が `.trim()` し、書き込みが `+ '\n'` していたため、提案本文と違うバイトが
書かれる。「ベースが一致したので安全」と判定した直後に境界バイトを黙って書き換えることになり、
バイト厳密にした意味が消えていた（Codex 指摘・#134 のマージ後に付いたもの）。

`stripFrontmatterRaw()`（trim しない）を分け、`shared-file` はそれを使って**そのまま書く**。
空判定は `!fileBody.trim()` に変えて、改行だけの本文が通らないようにしてある。
`common-block-edit`・`task`・`task-done` は従来どおり trim 版を使う（埋め込み・比較用途で、
バイトが意味を持たない）。

**検査と書き込みは対で直す**。片方だけ厳密にしても、緩い側が最後に上書きすれば保証は成立しない。
今回は「検査を厳密化する」変更だけを見て、その値が守るはずの書き込み経路を見ていなかった。

**この指摘は、マージ後に付いて誰も見ていなかった。** `codex-review-inbox` の一覧を実測確認した
ついでに見つかったもので、まさにその一覧が存在する理由どおりの拾われ方をした（#134 のエスカレーション
を入れた本人が、その仕組みに拾われた形）。

### PR #142 での追加指摘

- **配布 doc の要求文にキーワードを付け忘れた**。`outbox-proposal.md` に足した「1バイトも足し引きせずに
  置くこと」は提案を書くエージェントへの要求なのに RFC 2119 キーワードが無く、`sop-format.md` の
  「キーワードの付いていない文は説明であって要求ではない」に照らすと**従う義務が無い文**だった。
  スクリプト側の不変条件が、それを守る側の文で担保されていない状態。MUST／MUST NOT を付けた。
  実装を直したら、**その実装が前提にしている振る舞いを要求として書けているか**まで見る。
- **仕組みを変えたら設計 doc と README も直す**（`AGENTS.md`「完了手順」）。今回は挙動を
  「正規化する」から「しない」へ変えたので、書いていないと**将来の変更が正規化を戻せてしまう**。
  設計 doc には結論だけでなく**理由（検査と書き込みが同じバイトを見ていることが前提）**を書いた。
- **「バイトそのまま」と言いながら、読み口が utf8 デコードのままだった**。`trim` と `+ '\n'` を
  外しただけで満足し、その手前で `readFileSync(..., 'utf8')` が不正な UTF-8 を U+FFFD に潰している
  ことを見ていなかった（`ff fe 41` → `ef bf bd ef bf bd 41`。実測で再現）。**正規化の除去は
  経路の一番手前まで遡らないと保証にならない**——1箇所でも文字列を経由すれば、そこで落ちた情報は
  下流をいくら厳密にしても戻らない。`stripFrontmatterBytes()` を足し、frontmatter の境界は
  latin1（バイトと文字が 1:1）で位置だけ求めて `Buffer` を切る形にした。
  空判定も `.trim()` をやめてバイトで見る（latin1 の `.trim()` は 0xA0 を空白扱いするので、
  1バイトのバイナリ本文を「空」と誤判定して却下してしまう）。

## 2026-07-31 collect-outbox のチェックアウトを役割で分ける（dispatch 事故の同型を塞ぐ）

- `archive-task-history` で踏んだ「feature ブランチから dispatch すると、そのブランチの差分が
  `base: main` の PR に乗って自動マージされる」の同型が `collect-outbox` にも残っていた。
  こちらは `Checkout ops-sync` 1つが **script source と取り込み PR の作業ツリーを兼ねていた**ため、
  ブランチから dispatch すると intake PR にブランチの差分が乗る。提案が無いと PR 自体が立たないので
  実害は出ていなかった（＝踏まなかっただけで、条件が揃えば同じことが起きる）。
- 直し方は「**1つの checkout に2つの役割を持たせない**」。
  - `ops-sync-src`（ref 省略＝workflow の ref）… スクリプトとローカル action。**ブランチから dispatch して
    マージ前に検証できる**のはこの側が workflow の ref を取るからで、これは意図した動作なので残す。
  - `ops-sync`（`ref: main`）… 書き換えて取り込み PR にする木。PR の base と一致させる。
  - `ops-sync-prune`（`ref: main`）… トゥームストーン掃除 PR の木。同じ理由。
- `AGENTS_COMMON.md` と `consumers.txt` の読み取りは**書き換える木の側**（main）から行う。これらは
  「動かすコード」ではなく**正本のデータ**で、提案の適用対象そのものだから。`ref` を役割で分けるとき、
  この「コードかデータか」の切り分けを間違えるとブランチのデータに対して提案を適用してしまう。
- 設計 doc に「『動かすコード』と『書き換える木』の ref を分ける」節を足した。自分自身を巡回対象に
  含む cross-repo バッチ全部に効く不変条件で、インラインコメントだけだと次に workflow を足す人が
  同じ穴を作る。

## 2026-07-31 feature ブランチからの dispatch が main を書き換えた（target checkout の ref 未指定）

- PR をマージ前に検証するつもりで `archive-task-history` を**自分のブランチの ref で dispatch** したら、
  そのブランチの差分が `main` に自動マージされた（生成された PR #138 に、履歴の統合だけでなく
  ブランチの全変更が入っていた）。**レビュー前のコードが main に入る経路**で、実際に起きた。
- 原因は `Checkout target repo` の **`ref:` 未指定**。`repository:` を指定しても、それが
  *この workflow を走らせているリポジトリ自身*（ops-sync は巡回対象に自分を含む）だと、
  actions/checkout は ref 省略時に **workflow の ref** を取る。consumer 側は別リポジトリなので
  既定ブランチが取れており、**自分自身を対象にしたときだけ**成立する。
  そこから `git checkout -B ops-sync/archive-task-history` → `base: main` の PR → `MERGE_MODE=direct`
  で自動マージ、と一直線に繋がる。
- **この穴は今回の変更で作ったものではない**（checkout ステップは元から同じ）。`peter-evans` 時代から
  あって、feature ブランチから dispatch する人が居なかったので露見していなかっただけ。
  自分でそれをやって踏んだ。
- 対処は `ref: main` の明示。**script source 側の checkout は ref 省略のまま**にする——そちらは
  「そのブランチのスクリプト・action で動かす」ことが dispatch 検証の目的なので、意図的に workflow の
  ref を使う。**取ってくる木（対象）と、動かすコード（スクリプト）で ref の意味が違う**のが要点。
- **collect-outbox にも同型の危険が残っている**: `Checkout ops-sync` が script source と
  「取り込み PR の作業ツリー」を兼ねているので、ブランチから dispatch すると intake PR にブランチの
  差分が乗る。こちらは提案が存在しないと PR 自体が立たないので今回は踏んでいない。分離するには
  checkout をもう1つ足す必要があり、別 PR にする。
- 教訓: **dispatch による事前検証は「読むだけ」ではない**。書き込み側（PR 作成・自動マージ）を持つ
  workflow をブランチ ref で回すのは、それ自体が main への書き込み操作になりうる。回す前に
  「この run が書き込む先はどの ref から作られるか」を確認する。

## 2026-07-31 承認点の記述を全配布 doc に伝播させる

承認点の訂正（→ 直前のエントリ）を入れたあと、**同じ主張をしている他の doc が古いまま残る**という
同種の指摘を続けて受けた（#134 で3回、#136 で2回、その配布分でさらに2回）。今回で打ち止めにするため、
残っていた2箇所を直したうえで、承認点に触れる全箇所を grep で洗って一致を確認した。

- `outbox-proposal.md` … 「オーナーのマージを**1回**通る」が public 発では偽（consumer 側＋ops-sync 側で
  2回）。「最低1回」に直し、private/public を別項目に分けて回数を明示した。**2回目は冗長ではない**と
  書いたのは、自動マージされないことを異常や手戻りと誤解させないため。
- `net-fetch.md` … allowlist 追加の節が「マージするのは ops-sync 側」のままだった。net-fetch は
  outbox 経路で allowlist を直す手順を含むので、承認点の記述が食い違うと**2つの必須 SOP が別々の PR を

- `ops-sync-design.md` の「上りの認可」節 … 「『ユーザーが見ている』は検証できないので代わりに

  public はそれが成り立たないので ops-sync 側でもレビュー、という現行の説明に置き換えた。

**なぜ何度も取りこぼしたか**: 「同じ主張をしている箇所」を*言い回し*で探していたため。
「マージするのは ops-sync 側」で grep しても「1回通る」は引っかからない。承認点のような**横断する
概念を変えるときは、言い回しではなく概念に触れる箇所を列挙する**（今回は「オーナーのマージ／
オーナーのレビュー／人間のレビュー付きマージ／N 回」を並べて grep し、全ヒットを1件ずつ現行の
記述と突き合わせた）。

**書き換えた箇所の「前提文」も見る**。上の grep を通したあとでも、書き換えた段落の**すぐ上にある
根拠の一文**「承認を1点に集約する」が残っていた（言い回しが違うので回数の grep に当たらない）。
箇条書きの本体だけ直して、その上のリード文を読み返していなかった。回数の話ではなく
「**承認する主体をオーナーだけに絞る**（集約するのは*誰が*であって回数ではない）」に直した。

**「その SOP 自身が outbox 経路を使うか」で洗う**。承認点を述べているのは承認について書いた doc だけ
ではない。`net-fetch.md`（allowlist 追加）と `cross-repo-tasks.md`（タスク依頼）は、**手順の一部として
outbox 経路を指している**ので、そこにも「オーナーがどの PR をマージするか」が書かれていた。どちらも
「2回マージ」「ops-sync の PR → 同期 PR」と経路を決め打ちしており、自動マージ後は誤案内になる。
特に net-fetch は依頼元が `ops-runner`（public）になりやすく、**取り込み PR が open のまま残って
allowlist が配布されない**のに「追加した」と報告する事故につながる。
横断する概念を変えたら、**その概念を使う手順 doc** も洗う。

**条件付きの数値は条件と一緒に書く**。「private 発＝合計1回」と書いたが、これが真なのは*機械確認を
通ったとき*だけで、ベース不一致・肥大化・タスク名衝突で保留されれば private でも取り込み PR の
マージが要る＝2回。数値だけを目立たせると、条件を読み飛ばした利用者が consumer 側 PR のマージで
止めてしまう。「自動マージされない場合（public 発／機械確認に引っかかった）は、それもオーナーが
マージして初めて反映される」という形に統一した。**2回になる条件は2つある**（可視性と機械確認）ので、
片方だけを条件として書くと同じ穴が開く。

常時層（`AGENTS_COMMON.md`）は「最初の承認点」という表現に留め、public の2回目は配布 doc 側にだけ
書いた（増減 +0 文字）。エージェントの義務は経路によらず「自分でマージしない・PR にする」で同じであり、
2回目はオーナー側の手続きなので、常時層に載せる価値がコストに見合わない。

## 2026-07-31 outbox 経路の承認点を consumer 側 PR のマージとして明文化

自動マージを入れたとき「承認の実体は提案を書いたセッションでのユーザー確認」と書き、それを担保する
つもりで「ユーザーが見ていない提案を outbox に置かない（MUST NOT）」を SOP に足した。これが誤りだった。

第一に、常時層は「ユーザー不在の自律実行では outbox に置け」と指示しているので、2つの MUST が衝突して
自律実行のエージェントはどちらかを必ず破る（Codex が3 consumer すべてで指摘）。第二に、そもそも
**セッションでの確認は ops-sync 側から検証できない**ので、要求として書いても担保にならない。

**実際の承認点は既に存在していた**: outbox 経路の完了条件は「提案ファイルを含む open な PR があり、
`main` へのマージはオーナーが行う」で、提案は**オーナーが consumer 側 PR をマージして初めて main に載る**。
collect が拾うのはその後。つまり承認は消えておらず、**場所が違うだけ**（直接 PR は ops-sync 側、
outbox は提案を載せた consumer 側 PR）。取り込み PR の自動マージは、同じ変更を二度承認させないための
自動化であって、承認の省略ではない。

この整理により3つが同時に解ける:

- 自律実行との矛盾 … 「セッションで見たか」を要求しなくてよい（オーナーの PR マージが承認）。MUST NOT を削除。
- `sop-format.md` の経路等価性の実例 … 承認点が違うのではなく**場所**が違うだけなので、実例として
  引き続き妥当。ただし「マージするのは ops-sync 側」という書き方は不正確だったので直した。
- 「可視性は信頼境界ではない」（Codex P1） … 攻撃者モデルの指摘。このアカウントは全リポジトリ・
  全エージェントがオーナーのもので、write 権を持つ主体が侵害される前提なら outbox の有無に関わらず
  同じ被害が出る（outbox が新しい攻撃面を足すわけではない）。オーナー判断として対応しないことにし、
  理由を返信して resolve した。public/private の区別は、**不特定の第三者が fork/PR で内容を持ち込めるか**
  という別の理由で維持する。

教訓: 検証できない前提を要求として書くと、担保にならないうえに既存の経路と衝突する。書く前に
「その要求は誰がどこで満たすのか」を実在する手順の中で特定する。

**規約が自分と矛盾していたので規約側を直した**。`sop-format.md` の「経路違いの例外」は、条件を
「結果・承認点・保証が**同一**」と書きながら、判別条件を「その分岐で要求が1つでも**緩むか**」と
書いていた。同一のときは両者が一致するので今まで露呈しなかったが、public 発の outbox（承認が1回増える
＝安全側に振れる）で初めて食い違った。厳密な同一を求めると**安全側の経路まで禁止**され、エージェントは
満たせる要求を前に停止するしかない。条件を「同一か、より強い方向にしか変わらない」に直し、判別条件と
一致させた。最初は「判別条件の方が operative だから例外の範囲内」と返信して規約の文言を残そうとしたが、
それは規約の2文のうち都合のいい方だけを採る読み方で、規約を読むエージェントには通用しない
（Codex に再指摘された）。**規約に矛盾があるなら、運用側で読み替えず規約を直す。**

**同じ主張は全箇所を一度に直す**。承認モデルの訂正を SOP 1箇所だけ直したところ、常時層・生成される
取り込み PR 本文・workflow コメント・設計 doc・書き手の表に古い主張が残り、Codex に3回に分けて
指摘された（配布 SOP と常時層が食い違うと、エージェントは SOP を開く前後で違う指示を受ける）。
特に**生成物のテキスト**（取り込み PR 本文）は grep 対象から漏れやすい——自動マージされた PR に
「セッションでユーザーが確認しています」と書かれ続けると、承認の出所として嘘の記録が残る。
主張を変えるときは、その主張を述べている全箇所を grep で洗ってから直す。

## 2026-07-30 指紋一致の outbox 提案を自動マージする

取り込み PR の手動マージは「提案内容の再認可」として機能していたが、提案はそれを書いたセッションで
ユーザーが見ている。同じ内容を2度承認していることになり、その待ち時間のあいだ提案が outbox に居座って
上り経路全体を止めていた（選択は全 consumer 横断の最古1件なので、1件の未マージが他 consumer も止める）。

**自動マージの判定に使えるのは「提案が書かれた後に前提が変わったか」だけ**、という切り分けで設計した。
これはスレッドでの承認では原理的に代替できない情報（承認時点では衝突がまだ存在しない）で、逆にこれ以外
——提案内容そのものの妥当性——は取り込み時に機械が判断できない。よって条件は次の3つに絞った:

- 全文置換（`common-block-edit`／`shared-file`）のベースハッシュが現在の正本と一致すること。
- ベース欄の欠落は「判定不能」であって「問題なし」ではないので保留側に倒す。既定を保留にしておかないと、
  ベースを書き忘れた提案が検査を素通りしてしまい、検査を入れた意味が消える。
- `common-block-edit` の常時層の純増が上限内（`COMMON_GROWTH_LIMIT` = 800 文字）。内容が正しいかと
  「全 consumer の全タスクに常時乗るコストを払う価値があるか」は別の判断で、後者は機械には決められない。
  800 は現状 1 万文字弱の区間に対して「節が1つ増える規模」の目安。厳密な根拠は無いので、実運用で
  保留が多すぎ／少なすぎなら動かしてよい。

`task`／`task-done` は全文置換ではなく巻き戻る対象が無いので、検査の対象外＝常に自動マージ可。

**cleanup PR は取り込みが実際に入った後にだけマージする**。先に outbox を空にすると、オーナーが取り込み
PR を close して却下する逃げ道が消える。例外は却下だけの run（applied=0）で、これは取り込み PR 自体が
無く判断待ちも無いのに、人間待ちにすると壊れた提案1件が最古に居座って全 consumer を止めてしまう。

自動マージで通常経路が緑になるぶん、**残るものが見えなくなる**ので、run の最後に「人間を待っている
もの」（保留された取り込み PR・差し戻した提案）を `::error::` で立てて run を失敗させる。赤の意味を
「壊れた」から「人間が見るまで進まない」に寄せた。この step を最後に置いているのは、失敗で ci-logs の
publish やトゥームストーン掃除を巻き添えにしないため。

**ハッシュの取り方を種別で分けた**（consumer 同期 PR 側の Codex 指摘）。`common-block-edit` は
AGENTS.md のマーカー間から切り出す都合で前後の空白が必ず変わるので `.trim()` が要るが、`shared-file` は
バイト一致で配る実ファイルそのもので切り出しが無く、trim する理由が無い。trim したままだと
「末尾改行だけが変わった」ような境界だけの変更を検出できず、鮮度検査をすり抜けた全文置換がその変更を
黙って巻き戻す。自動マージを入れたことで人間の目が入らなくなるぶん、この穴の危険度が上がっていた。
取り込みの書き込みは `本文 + '\n'` に正規化されるので、バイト厳密にしてもラウンドトリップは安定する
（取り込み後のファイルを次の提案のベースにして一致することを確認済み）。

**この指摘は ops-sync の PR には出ず、consumer 同期 PR（private #483）にだけ出た。**
AGENTS.md「配布変更のダウンストリーム確認」が想定している通りの実例で、確認していなければ
配布物の欠陥がそのまま全 consumer に残っていた。

**認可の根拠を可視性に置いた**（Codex P1 指摘への対応。実際に経路が通ることを確認して受け入れた）。
初版は「提案はスレッドでユーザーが見ている」を自動マージの根拠にしていたが、これは ops-sync 側から
検証できない。提案は consumer の main に置かれたただのファイルで、署名も承認記録も無い。実際、新規の
`shared-file` はベース欄が不要なので保留理由がゼロになり、`shared/.github/workflows/` に任意の workflow を
入れて `OPS_SYNC_TOKEN`（全 consumer に Contents:RW＋Workflows:RW）で全 consumer へ配布できた。
これは設計 doc が「consumer が1つ侵害されると全リポジトリへルールを注入できる増幅経路」として
廃した構造を、トークンではなく**ファイル配置を入口として**再導入していたことになる。

代わりの根拠に **提案元 main への書き込み権**を採った。private なら main に載った時点でオーナーの
アクセス下にあり、置かれたこと自体がスレッドに現れる。public にはこの前提が無い（誰でも fork して
PR を出せる）ので種別によらずレビューに回す。可視性の判定は workflow が行い、**判定できなかった repo は
public 扱い**、判定ステップ自体が動かなかった run は全 consumer を public 扱いにする（fail closed）。
「public が1件も無い」と「判定していない」を同じ空リストで表すと関門が黙って消えるため、
`VISIBILITY_CHECKED` で両者を区別している。

**ダウンストリーム確認の穴を codex-review-inbox に受け持たせた**。自動マージされた取り込み PR は
扱うセッションが居ないので、配布変更の確認（consumer 同期 PR の Codex 指摘を読む）を行う者が居なくなる。
自動マージの条件は「前提が変わっていないこと」しか見ておらず配布物としての正しさは見ていないため、
条件を厳しくしても埋まらない。

調べたところ **inbox は収集側は既に完成していた**——毎時・全リポジトリ横断で未 resolve の Codex
スレッドを集め、マージ済み PR に残るものを 🔴 で最優先表示する。欠けていたのは**エスカレーション**で、
一覧はファイルなので誰かが見に行かない限り気づけない（従来はセッションが生きている前提のルールが
その役目を担っていたが、自動マージ経路にはそのセッションが無い）。そこで 🔴 が1件でもあれば run を
失敗させるようにした。取得失敗も同様に失敗扱いにする——読めなかったものを緑で流すと「指摘ゼロ」と
区別できない。open PR の指摘（🟡）は、その PR を見ている者が居るので失敗させない。

**エスカレーションを入れると「緑」の意味が変わる**（Codex 指摘）。inbox には元々、レビュースレッドが
1ページ（50件）を超えた PR を注記するだけで済ませる経路があった。一覧を読む前提なら注記で足りたが、
run の成否で伝えるようにした以上、**読み残しがあるのに緑**は「確認済み」の嘘になる。取得失敗と同じ
「読めなかったものは落とさない」側に寄せて failures に積む。エスカレーションは既存の fail-open の
許容度を下げる——信号を強くするなら、その信号が依拠する網羅性も上げないと整合しない。

**`create-pull-request` の no-op には2形態ある**（Codex 指摘）。差分が消えたとき、PR が未作成なら
url が空になるが、**前の run で PR を作ってあると既存 PR を close して url を返す**。url の有無だけで
「無変更」を判定すると後者を取りこぼし、掃除がされず提案が最古に居座る。レビュー待ちで保留された提案の
内容が、その後べつの経路で正本に入ると実際に起きる。`pull-request-operation == 'closed'` を併せて見る。

## 2026-07-30 shared-file 提案にベースハッシュ（鮮度検査）を追加

`common-block-edit` にだけ `ベース:` の鮮度検査があり、同じ全文置換である `shared-file` には
何も無かった。提案が書かれてから取り込みまでには cron 1周（約6時間）＋他提案の待ち行列ぶんの
時間が空くので、その間に正本が変わっていると、取り込んだ瞬間にその変更が黙って巻き戻る。
差分上は「提案者が意図的にその行を消した」ようにしか見えず、レビューでも捕まらない。

不一致には2系統の原因があるが区別しない: (1) 提案後に正本が変わった (2) 提案元 consumer に
最新の配布が届いておらず、古いコピーを基に書かれた。(2) は「エージェントがさっき読んだばかり」
でも起こるが、巻き戻る危険は (1) と同じなので、どちらも等しく要確認にする。

提案側は自分のリポジトリの `<対象パス>`（配布されたコピー）をハッシュし、取り込み側は
`shared/<対象パス>` をハッシュする。`apply-shared.mjs` がバイト一致でコピーするので両者は同値になる
（`hash12` は `.trim()` してから SHA-256 なので、末尾改行の差では割れない）。この前提が崩れる
——配布時に内容を変換するようになる——と検査が常時不一致になるので、そのときは両側を合わせて直す。

新規ファイル追加は「差し替える既存内容が無い」ので `ベース:` 無しが正常。逆にベース付きで対象が
存在しない場合は、対象パスの誤りか提案後の削除を疑う状態なので不一致として扱う。

検査は今回も**警告どまり**（無くても取り込む）で、`common-block-edit` と揃えた。将来これを
自動マージの判定に使う場合は、「ベース無し」を自動マージ対象外にする必要がある
（判定不能を「問題なし」と読み替えないため）。

## 2026-07-30 net-fetch の public 側の痕跡を定期 sweep 側で消し切る

#126 の続き。#126 は「読了後の cleanup dispatch を主経路にする」までで、**公開時間の上限が
エージェントの協力に依存していた**（cleanup を投げ損ねると TTL 3日＋sweep 1日 ≒ 4日残る）。
指摘を受けて、上限の担保を**エージェント非依存の側（public の定期 sweep）に移した**。

**判断の軸**: public は Actions 無料なので、ワークフロー側の仕事を増やすコストが 0。
一方エージェントは落ちる・忘れる・中断されるので、**MUST と書いても強制力がない**。
よって「エージェントの cleanup ＝ 正確な信号（秒で消す最適化）」「定期 sweep ＝ 上限の担保」に
役割を分けた。private は露出しないので従来どおり sweep なし・TTL 3日・枠消費ゼロ。

**やったこと**:

- **TTL を可視性で分けた**（public 60分・private 3日）。`publish-ephemeral` の `retention-days` は
  整数日で下限1日だったので、`retention-minutes` を新設した（正の整数のときだけ日側に勝つ。
  空・不正値は日側に fallback＝**タイポで TTL 0 になって読み中のスライスを消さない**方に倒す）。
- **sweep を日次→毎時**。掃除間隔がそのまま TTL の超過分になるので、TTL 60分に対して日次だと
  最大25時間残る。毎時なら上限 ≒ 2時間。
- **public では sweep が「1日より古い成功 run」を run ごと削除する**。本文をログから外しても
  run には `meta`（取得 URL・時刻）と dispatch 入力（`url`/`request_id`）が残り、これは結果ブランチの
  TTL の対象外で Artifact and log retention（ops-runner は7日設定）に従うため、public では
  TTL や cleanup で縮めた公開時間がログ側で無効になっていた。

**なぜ run_id の台帳を作らなかったか**（当初は「run 側が run_id を記録すればよい」と考えた）:
**Actions API が run 一覧そのものを持っている**ので記録は不要。`GET .../workflows/net-fetch.yml/runs
?status=success` を `created_at` で絞れば削除対象が出る。台帳をブランチに置くと、cleanup が
スライスを消したときに記録も消えて run が孤児になる順序問題も抱える。

**なぜログだけ削除（`DELETE .../runs/{id}/logs`）ではなく run ごと削除か**: 前者では run が残り、
**dispatch 入力の URL が見え続ける**ため目的を達しない。

**捨てたもの**: public では1日より後に「いつ何を取得したか」を遡れない（net-fetch は `ci-logs` に
publish しないので他に記録がない）。失敗 run は残すので障害調査は可能——retention 7日は
「エージェントのトークンが切れて後日調べる」ために設定されており、成功 run の削除はこれを損なわない。

**副作用（許容）**: `schedule` は workflow 単位でしか設定できず可視性で cron を分けられないので、
private consumer では毎時 skip の run が履歴に並ぶ（分数は 0）。

**権限**: `actions: write` は **sweep ジョブにだけ**与えた（job-level `permissions`）。
クリーンルームの fetch ジョブには渡さない。

**検討して却下した案**:
- **5分 cron** — GitHub の scheduled run は数十分遅延が常態で高負荷時には落とされるので、上限が名目だけになる。
- **run 内で `sleep` して自分で消す** — public なら無料だが run が `in_progress` のまま居座り、
  エージェントの読み取り合図（run completed）と衝突する。合図をジョブ単位に変える必要が出て、
  エージェントへの要求が増える。
- **遅延 cleanup run の自己 dispatch** — `GITHUB_TOKEN` 起点の `workflow_dispatch` は再帰防止で抑止され、
  PAT が必要になる。`consumers.txt` の「ops-runner に書き込み資格情報を置かない」に反する。

## 2026-07-30 マージ済み PR の Codex 指摘消化（net-fetch cleanup・削除の意味・入力境界）

### 退避スライスの名前は「別 run から再現できる」ことが要件（ops-sync#126）

`request_id` が弾かれた取得の退避先が `_invalid-<時刻>-<PID>` だった。**cleanup は取得とは別 run** なので
この名前は誰にも再現できず、エージェントが持っている生 ID からは到達できない——退避スライスが残ったまま
「nothing to drop」で緑になり、手順6の「緑＝外れた」が嘘になる。生 ID の digest にして決定的にした。

Codex の2案のうち「サニタイズ済みスライス名を渡す」を採らなかったのは、**取得 run の summary から名前を
転記する手順がエージェント側に増え、転記漏れが同じ失敗に戻る**ため。決定的な名前なら手順が増えない。

### 「削除」は到達不能化であって消去ではない（ops-runner#35）

`rm` も TTL もブランチ削除も、ブランチ先端から辿れなくするだけ。到達不能な object はリモートに残り、
公開中に SHA を記録した相手は取得できる（GitHub に GC を強制する手段は無い）。**コード側で解けないので
主張のほうを実態に合わせた**。重要なのは帰結で、**機微性の判断は cleanup の有無ではなくモード選択で行う**
——「あとで cleanup するから数分で消える」を public 経路に流す根拠にしてはいけない。既存ルール
（機微を集約モードに流さない）は正しかったが、根拠が「公開時間が短いから許容」に読める書き方だった。

### 予約・改名は「導入前のデータ」を到達不能にしうる（自 PR の指摘より）

digest 退避先の導入自体が新しい衝突を2つ作り、どちらも Codex に拾われた:

- 退避先 `_invalid-<digest>` を**ユーザーが request_id に選べた**ので、ある ID の cleanup が無関係な結果を
  消しえた。`_invalid-*` を予約して名前空間を分離した。決定的な名前と自由に選べる ID は分離して初めて両立する。
- その予約を**消す側にも掛けてしまい**、予約導入前に `_invalid-foo` で publish された既存スライスが名前で
  指せなくなった。予約の目的は「新しく作らせない」ことなので**作る側だけに掛ける**。削除は常に安全な方向。
  予約・改名を入れるときは**導入前に作られたデータが到達不能にならないか**を必ず見る。

もう1件は、multiline output のデリミタを固定にしていたもの。`__NET_FETCH_SLICES__` 自体が妥当な
request_id なので入力が output を閉じられた。**サニタイズは「値がデリミタと一致しない」ことを保証しない**。
`net-fetch.sh` は既に乱数＋衝突チェックをしていたのに、**同じ出力プロトコルを2箇所で別々に書いたため**
こちらで再発させている。

### ops-sync は自分の配布物の consumer ではない（branch-cleanup の二重管理）

`branch-cleanup.yml` は `shared/` の正本と `.github/workflows/` の実行コピーの**2箇所にある**
（ops-sync 自身は sync の consumer ではないため）。正本だけ直して実行コピーを放置し、
**ops-sync 自身では脆弱なまま**という状態を作った。ファイル冒頭に「変更するときは両方を同時に直す」と
書いてあるのに見落としている——`shared/` を直したときは、それが ops-sync 自身にも要るファイルかを確認する。

### 入力境界は「正規化の前」に要る（private#474）

先頭ゼロ除去が二次時間で、桁数ガードはループの後にあった。**桁数ガード（正規化後）と長さガード（正規化前）は
別物なので両方要る**——`0...0365` は正規化後3桁で通るが、生では任意に長くできる。

  （フィルタ方式は新しいログ行が増えるたびに漏れる）。ロールアップに `history-dir` を残したのは、
  齢による prune が効いて**旧方式で積まれた（ファイル名を含む）履歴エントリが保持期間 30 日で枝先から
  落ちる**ため。ただし git 履歴からは消えない（`ci-logs` の作り直しは別途ユーザー判断）。
- 公開してよい上限は**件数・repo 名・成否・PR URL まで**と決めた（既存の `sync/<consumer>/` スライスが
  既にこの粒度で、そこに合わせた）。対象リポジトリの中身に由来する文字列（ファイル名・パス・本文）は出さない。
