# ai-ops 作業履歴

ai-ops での作業の「**なぜ**」の記録。書き方・アーカイブは共通規約 [`task-history.md`](task-history.md) に従う
（consumer に影響する変更・内部だけの変更の区別なくここ1箇所 → [`AGENTS.md`](../AGENTS.md)「履歴ファイル」節）。

---

## 2026-07-26 public repo の Codex review inbox を全体一覧だけにする

ops-sync の `main` は PR 必須の ruleset で保護されており、毎時更新する review inbox の直接 push が必ず
拒否されていた。ops-runner も同じ保護を導入するため、両 public repo に bypass 権限を与えたり定期 PR を
量産したりせず、走査対象には残したまま private の全体一覧だけへ載せる。リポジトリ別スライスは直接 push を
許容する private consumer に限定する。

## 2026-07-26 ops-sync の Codex 指摘の積み残し

未 resolve 一覧には後続 PR で修正済み・outdated の指摘も残っていたため、現在の正本と履歴を照合し、
未修正だった安全側のページングと cleanup の fail-safe だけを追加対応した。Cloudflare API の一覧取得は
上限到達時に集計結果を採用すると過少カウントで `ok` を出しうるため、完走を証明できなければ `unknown` に倒す。
揮発ブランチは削除不能な履歴を残さないことが目的なので、marker 欠落と最後の slice の失効も保持ではなく
削除側に倒す契約として設計・運用 doc に明記した。

## 2026-07-26 Codex履歴ファイル名の衝突防止

Codexの作業ブランチが一意なランダム片付きではなく汎用名 `work` になる実例があり、ブランチ名由来の
`2026-07-26-work.md` が並行セッション間で衝突した。一意性を実行環境のブランチ命名へ依存させず、
UTC時刻・12桁の暗号学的ランダムID・排他的作成を組み合わせた共通スクリプトへ集約する。

## 2026-07-26 Codex review inbox の積み残し対応


public repo は保護された main へ review inbox のスライスを直接 push しない設計なので、全 consumer に配る共通指示も
スライスの存在を前提にできない。ローカル生成物が無い場合は、依頼に添付された全体一覧の当該欄を読む経路を明記した。
また履歴ファイル名は手作業では衝突しうるため、Stop フックは旧形式のパスを案内せず、一意なフラグメントを作る生成スクリプトの
具体的な実行コマンドを案内する。

## 2026-07-26 集約モードの実行先を、入口すべてで揃え損ねていた（Codex P1 ×2）

net-fetch の実行先を ops-runner へ移したとき、**手順 doc（`net-fetch.md`）だけ直して、そこへ至る入口を
直し忘れていた**。Codex が nikki-san #681 と private #436 の同期 PR で同時に指摘した。

取りこぼしていた入口:

- **`AGENTS_COMMON.md`（常時ロード層）** — 「集約モード（public な ai-ops 上で実行）」。全タスクで
  読まれる層なので、ここが古いと手順 doc を開く前に誤った前提が入る。
- **`docs/actions-quota.md`** — 枠が逼迫したときの代替案として「public な ai-ops での集約実行」を提示。
  つまり**枯渇時のフォールバック経路が、撤去済みの workflow を指していた**。
- **`net-fetch.yml` のコメント**・**`net-allowlist.txt` のコメント** — 「集約は ai-ops 上で実行」。

### 一括リネームが取りこぼしを悪化させた

さらに悪いことに、直後の `ai-ops` → `ops-sync` 一括置換がこれらを **`ops-sync`** に変えた。
文字列としては置換されるが、**意味としては最悪の方向**——「エージェントが外部コンテンツを持ち込む実行先」が
`OPS_SYNC_TOKEN` のあるリポジトリを指す文になり、今回の分離の目的そのものを打ち消していた。

**学び: 同じ固有名詞でも役割が違えば置換先が違う。** `ai-ops` という文字列には
(1) 実行先 → `ops-runner`、(2) 配布の正本・トークンの置き場・quota 信号の場所 → `ops-sync` の
2種類が混在していた。`net-fetch.md` ではこの区別に気づいて手で分けたのに、**他ファイルには同じ区別が
あることを確認しなかった**。1ファイルで「役割が混在している」と気づいたら、**同じ語を使う全ファイルを
同じ観点で洗う**（grep して意味ごとに仕分ける）。

### 入口の網羅は「発火トリガから逆算」する

手順 doc を直すときは、その doc に**辿り着く経路を列挙してから**直す。今回なら
常時ロード層のトリガ・関連 SOP のフォールバック・実ファイルのコメントの3系統。
doc 単体を直して満足すると、常時層が古いまま残って**doc を開く前に誤判断させる**。

## 2026-07-26 codex-review-inbox の fail-open を塞ぐ（持ち越し）＋ task-done を MUST に

配布直後の同期 PR に付いた Codex 指摘2件。どちらも自分が作ったものへの指摘で、片方は
**この一覧の存在意義を無効化する欠陥**だった。

**1. 一覧が古い指摘を黙って落とす（private #443 P2）**: collector は「直近 N 日に更新された PR」しか
見ないので、未 resolve のスレッドが載った PR が窓から外れると、**resolve されていないのに一覧から消える**。
「未 resolve のスレッド自体がキュー＝取りこぼしを防ぐ」と設計 doc に書きながら、実装は時間で
取りこぼす fail-open だった。

対処: **前回の出力を持ち越しの入力として使う**。生成済み一覧から PR の URL を拾い、直近スキャンの窓に
入らなかったものは**名指しで再確認**する。エントリが消える条件を「古くなった」から「resolve された
（または PR ごと読めなくなった）」に固定した。別の状態ストアを持たずに耐久性を出せるのは、出力自身が
そのまま前回状態になっているため（この一覧が markdown の表であることの副次的な利点）。再確認に失敗した
PR は「取得失敗」行として残す——読めなかったものを落とすと持ち越しの意味が無い。

コストは「未対応の指摘を持つ PR 数」に比例して有界（初回実測で 92 件・PR にして数十）。全 PR を毎回
ページングする案は 15 分間隔だと GraphQL のレート上限に近づくので採らなかった。

**2. task-done の消化に MUST が無い（private #442 P1）**: #101 で2経路化したときに
`cross-repo-tasks.md` の消化手順から強制力が抜けていた（`sop-format.md` 自身が「無キーワード文は説明で
あって要求ではない」と定めているので、実行側は消さずに完了扱いできてしまう）。`.ops-sync/tasks/` は
同期管理下で、消さないと次の sync で復活し**別セッションが同じ依頼を再実行する**。#101 で自分が定めた
「要求を経路によらない MUST として先に置き、経路はその下に満たし方として並べる」形に直した。

教訓（#101 と同型）: 経路を増やす改訂では、**元の文にあった強制力が経路の説明に薄まって消えていないか**を
確認する。2経路化の3箇所目で同じ抜けをやっている。

## 2026-07-26 codex-review-inbox の cron を `*/15` から毎時に落とす

**`*/15` は一度も発火しなかった。** workflow が main に入ってから 12:00 / 12:15 / 12:30 の3枠連続で run が
作られず、`ci-logs` に記録が残らなかった（この workflow は成功・失敗を問わず毎 run ログを publish するので、
記録が無い＝実行されていない）。同じ時間帯に sync の run は動いていたので、アカウント側でも権限でもない。
GitHub は高頻度のスケジュールほど優先度を落として間引くため、**確実に回る頻度に下げる**判断をした。

実行分のコストは関係ない（ops-sync は public で GitHub-hosted runner が無料）。**間引かれるかどうか**だけが
制約なので、「無料だから細かく回す」は成立しない。

実効の気づきは 15〜30分 → 60〜90分に伸びるが、そもそも 15分設定では**永遠に気づかなかった**ので改善。
急ぐときは `workflow_dispatch` で即時に回せる（過去分の洗い直し用に `lookback_days` 入力もある）。

教訓: **「動くはず」の周期実行は、動いた証跡で確認するまで動いていないものとして扱う。** この workflow は
毎 run ログを publish する設計にしてあったので、記録の不在から間引きを特定できた。設計時にログを
`if: always()` にしておいたのがそのまま診断手段になった。

## 2026-07-26 codex-review-inbox の push 競合とレート消費を実測で直す

スライス化（#104）の初回実行が **failure** で終わり、一覧が更新されなかった。実測で分かった2件を直す。

**1. push 競合（実測で発生）**: run は 11:51:04〜11:51:40。その間に private の main が
11:51:20（sync PR #444）と 11:51:35（#445）で2回動き、`--depth 1` の clone から出した push が
non-fast-forward で弾かれた。**15分ごとに回るうえ、対象は sync PR が頻繁にマージされる main** なので、
これは例外ではなく日常的に起きる。同じ run の中で `publish-ci-logs` も1回目の push に失敗しており
（あちらは retry+rebase を持っていて回復する）、対処の前例も社内にあった。

生成物は毎回作り直せるので、マージせず**「main を取り直して上書きし直す」**方式にした:
push 失敗 → `fetch --depth=1 origin main` → `reset --hard FETCH_HEAD` → 退避しておいた生成物を再適用 →
再コミット・再 push（5回まで、指数バックオフ）。再取得の結果すでに同じ内容なら差分ゼロで抜ける。
1リポジトリの失敗で残りを諦めない点は据え置き（他の一覧まで古いまま据え置かれる）。

**2. 直近スキャンの窓を 30日 → 3日に狭めた**: ページング（#104）を入れたら実測が
`nikki-san pages=10 prs_scanned=500`（＝上限に張り付き、30日を見切れず）、`private pages=9`、
合計23ページになった。GraphQL は 5,000 ポイント/時で、この規模を15分ごとに回すと上限に接近する
（1ページあたり PR50件×スレッド50件のノード数を要求している）。

**直近スキャンの役目は「新しい指摘の発見」だけでよい**——Codex は PR イベントの数分後に投稿し、
この workflow は15分ごとに回る。一度載ったものは #103 の持ち越しが resolve まで守る。よって窓は狭くてよく、
広い窓が要るのは**過去分の洗い直し1回だけ**。それは `workflow_dispatch` の `lookback_days` 入力で渡す。
あわせて `rateLimit{ remaining }` をログに出し、消費を観測できるようにした（推測で運用しない）。

補足: ページング導入で件数が **92 → 175** に増えた。増えたのではなく、`first:50` で切れていて
**最初から半分近く見えていなかった**。「件数が安定しているから正しい」とは限らない例。

## 2026-07-26 codex-review-inbox をリポジトリごとのスライス＋グループ化した全体一覧に分ける

初回実行で **92件（うち91件がマージ済み PR）** が出た。ユーザーの判断: 「こんなにあったら1本の通し一覧では
運用が回らない。せめてリポジトリごとにグループ化され、簡単にコピペできる形であってほしい」。あわせて
Codex の指摘（nikki-san #687 P2「受動的なファイルを cron で更新してもセッションは起動しないし、他リポジトリの
エージェントは private のファイルを読めない」）にも応える形にした。

出力を2つに分けた:

- **全体一覧** `.ops-sync/codex-review-inbox-all.md`（private のみ）— リポジトリごとにグループ化し、各グループに
  **そのリポジトリのセッションに貼る依頼文**をコードブロックで添える（`cross-repo-tasks.md` の「コピペ用の
  指示文」と同じ作法。冒頭1行の概要＝セッションタイトル生成のため）。人のトリアージ用。
- **リポジトリごとのスライス** `.ops-sync/codex-review-inbox.md`（各リポジトリ）— 自分の分だけ。
  **全リポジトリで同じパス**にしたので、共通ブロックの発火トリガを「このリポジトリの
  `.ops-sync/codex-review-inbox.md` を読め」の1文に固定できる。可視性も自然に成立する: スライスは
  そのリポジトリ自身の指摘しか含まないので、public な ops-runner・ops-sync に置いても公開範囲が変わらない。
  全リポジトリ分が混ざる全体一覧だけが private 限定。

副産物として実測で見つけた欠陥も直した: 初回実行のログが `prs_scanned=50` で3リポジトリとも揃っていた
＝GraphQL の `first:50` で切れており、**lookback 期間内でもそれより古い PR は最初から見ていなかった**。
ページングを入れた（上限10ページ＝500件の安全弁つき。上限に当たったら「取得失敗」行として一覧に残す——
黙って諦めると持ち越しの対象にすら入らない）。

push 先を4リポジトリに増やすので、**どのリポジトリも `.ops-sync/` が push トリガの paths に入っていない**
ことを確認した（nikki-san は content/layouts/assets/... と workers/admin、private は cloudflare_workers/**、
ops-runner は push トリガ自体なし、ops-sync の sync.yml は shared/** ほか）。入っていたら15分ごとに CI が
起動して Actions 枠を焼く。consumer に workflow を足すときの注意点として workflow のコメントにも書いた。

## 2026-07-26 上り口2経路化の残り穴を塞いだ（同期 PR の Codex 指摘・2巡目）

#100 を配布した同期 PR3本すべてに Codex 指摘が付いた（nikki-san #685 / private #440 / ops-runner #5）。
2件は同じ論点で、**書いている最中に気づいていながら手当てしなかった箇所**だった:

- 能力ベースの経路分岐（ops-sync を足せるか否か）は `sop-format.md:45-47` の「判断・分岐をツールの
  有無に紐づけない（MUST NOT）」に文面上そのまま抵触する。`outbox-proposal.md` 側に「要求は緩まない」
  と書いただけで、**規約本体に例外を定義しなかった**ため、2つの配布 doc が矛盾したまま残っていた。
  → `sop-format.md` に判別条件つきの例外を明記した: **結果・承認点・保証が経路によらず同一なら
  能力で経路を選んでよい（MAY）。判別は「その分岐で要求が1つでも緩むか？」**。緩む例として
  net-fetch のモード選択（集約=世界公開／分散=非公開で保証が変わる）を対に置いた。
- `task-done` の消化だけ outbox 経路に固定されたままだった（AGENTS_COMMON と cross-repo-tasks の2箇所）。
  → 起票と同じ2経路に揃えた。直接経路での消化は `tasks/<owner>/<repo>/<ファイル名>` を消す PR。

教訓: **「気づいたが今回のスコープ外」と判断して残した不整合は、そのまま次の Codex 指摘になる。**
配布 doc は相互参照で成り立っているので、片方に例外を書いたら規約側にも同時に書く。

## 2026-07-26 上り口を「outbox 一本」から2経路に開いた（Codex 指摘 nikki-san #661 / private #419）

consumer 同期 PR に付いた Codex 指摘2件のうち、生きていたのは「共通 allowlist の直接編集ルートが
共通ブロックの『outbox が唯一の上り口』と矛盾する」というもの（もう1件の「pause 状態を run conclusion
から推定するな」は #84 の実測信号への一本化で既に解消済みだった。なお Codex の事実認識は正しく、
job-level `if` の skip では run の conclusion が `success` になりうる＝あの間接判定はそもそも誤りだった）。

矛盾を消す方向として、直接編集ルートを撤去して outbox に戻す案もあったが、**outbox は Claude Code が
1セッションで複数リポジトリを扱えることを知らずに設計した**ものなので、能力がある側に合わせて上り口を
2つに開く方を選んだ（ユーザー判断）。

書き方は `sop-format.md` の「判断・分岐をツールの有無に紐づけない（MUST NOT）」に抵触しないよう、
**要求（正本だけを直す・人間のマージでしか入らない・自分でマージしない・「なぜ」を1行残す）を経路に
よらない MUST として先に置き、直接 PR / outbox はその満たし方**として書いた。net-fetch のモード選択が
可視性・機微性という判断軸をツール能力にすり替えて壊れた前例があるが、上り口は**どちらの経路でも
結果と承認点が同一**なので、能力で選んでよい種類の分岐だと整理した。

承諾まわりは Codex の指摘どおり穴があったので塞いだ: ops-sync をセッションに足すのは「編集して PR を
出す」用途なので **push 権限付きで足す**必要があり、net-fetch step 2 で ops-runner を足した承諾は
別リポジトリ・別目的なので流用できない。

経緯として、この直接編集ルートを最初に書いたのは #83 自身で、**その PR は `add_repo` で ops-sync を
直接編集したセッションが自分の行動を正本に成文化したもの**だった（逸脱が次のルールになる経路）。
今回はユーザーが明示的に承認した上での成文化なので同じ形ではないが、この経路自体は覚えておく。

## 2026-07-26 Codex レビューの未対応在庫を自動集約する（codex-review-inbox）

Codex 指摘の取りこぼしが増えていた件の対策。ユーザーの困りごとは「メール通知のリンクを1件ずつ辿って
対応済みかを確認する手間」で、求められたのは**検知と統合された一覧まで**（対応の自動化は不要）。

判断の根拠になった制約:

- **「定期 workflow は月枠で動かせない」は ops-sync には当てはまらない。** 枠信号は現在 `tight` だが、
  逼迫しているのは private リポジトリぶん。ops-sync は public なので GitHub-hosted runner が無料で、
  既存 cron 一族（sync 日次・collect-outbox 6h・quota 6h）も現に動いている。だから15分ごとに回せる。
- **一覧を issue にしない。** ユーザーの「AIエージェントも読めますか？」で判断が変わった。issue は
  GitHub API アクセスが要る＝エージェントのランタイム依存になる。`.ops-sync/tasks/` と同じく
  **ファイルとして物理的に置く**ほうが、どのエージェントでも能力ゼロで読める。
- **一覧の置き場は private リポジトリ。** ops-sync は世界公開なので private のレビュー内容を置けない。
  実行（public・無料）と成果物（private）を分ける。ci-logs に出すログは件数と repo 名だけにした。
- **`private` の push トリガは `cloudflare_workers/**` のパス限定**なので、`.ops-sync/` への push で
  CI は起動しない（逼迫している private の枠を食わない）ことを確認した上で直接 push にした。
- **状態を持たせない。** 「未 resolve の Codex スレッド」自体をキューにする。管理表を別に持つと実態と
  ずれるが、resolve 状態を正本にすれば構造的にずれない。
- 取得に失敗したリポジトリは**「取得失敗」行として一覧に残す**。黙って短い一覧を出すと「指摘が無い」と
  「読めなかった」が区別できず fail-open になる（actions-quota の unknown と同じ考え方）。
- 生成時刻だけの差分でコミットしない（15分ごとなので履歴が埋まる）。時刻行を除いて比較する。

ルール側で解けない理由も設計 doc に書いた: `AGENTS.md` の「配布変更のダウンストリーム確認」は
**セッションが生きている間しか効かない**（指摘はセッション終了後に届く。上り提案由来の取り込み PR では
そもそも提案元セッションが居ない）。届かない層があるので機械で埋める、という切り分け。

## 2026-07-26 揮発ブランチの掃除が「最後の1件」を消せなかった（#94 の P1 修正）

`publish-ephemeral` の掃除（`prune-only`）が、**全スライスが期限切れになったときだけ push せずに終了**していた。
結果、最後に残った1件が TTL を過ぎても永久に残る——集約モードは public なので、揮発させる仕組みを入れた
のに最後の取得結果だけ世界公開で残り続ける、という目的を裏切る状態だった。

原因は変更検出の書き方。orphan ブランチに `checkout --orphan` した直後は HEAD が unborn なので、
`git diff --cached --quiet` は**インデックスを空ツリーと比較する**。全スライスを消してインデックスが空に
なると「変更なし」と判定され、`return 0` で push せずに正常終了する（ログには `expiring ...` が出るのに
リモートは変わらない）。**ローカル実行が緑で、ログにも作業した形跡が出るのに、結果が反映されない**タイプ。

直し方は、インデックス比較をやめて**再構築後のツリーと出発点のツリーを直接比較する**（`write-tree` と
`<base>^{tree}`）。空にすることが本物の変更として扱われ、空コミットを作れるよう `--allow-empty` を添える。
副作用として「変更が無いときは push しない」判定も正確になった（掃除が毎日空振りしてもブランチは動かない）。

### なぜローカル検証をすり抜けたか

前段でローカルの bare repo 相手に TTL 失効を確認していたが、テストが**常に残るスライスを1つ持っていた**
ため、ツリーが空になる経路を一度も通っていなかった。境界値（0件）を試していない典型的な穴。
今回は修正前スクリプトで**バグを先に再現**してから直し、(1) 全件失効で空になる、(2) 空になったブランチへ
publish して復帰できる、(3) 失効が無い掃除はブランチを動かさない、の3ケースを実駆動で固定した。

### 発見経路: consumer 同期 PR でだけ出た

この P1 は **ai-ops 本体の PR（#94）には出ず、nikki-san #678 と private #433 の同期 PR で Codex が指摘した**。
AGENTS.md「配布変更のダウンストリーム確認」が想定しているとおりの事象で、あの手順を踏まなければ配布物の
欠陥が全 consumer に残っていた。**shared/ を触ったらマージ後に consumer の同期 PR を見る、は実際に効く**
（今回オーナーから、この確認は都度の許可を取らず自動で行ってよいと承認を得た）。

### ローカルで実駆動検証した（GitHub を回す前に4項目）

action の shell を action.yml から抽出し、remote を `github.com` からローカルの bare repo に差し替えて
実行した。**GitHub 上で回す前に、ローカルの bare repo 相手に一通り確認できる**（次に触る人も同じ手が使える）:

- 結果ブランチが無い状態からの初回作成 → OK（orphan 経路）。
- 2回目の書き込みでもコミット数が 1 のまま → OK（履歴に堆積しない）。既存スライスも保持される。
- TTL 失効 → OK（`.published-at` を10日前にしたスライスが次の書き込みで消える）。`prune-only` の掃除も同じ。
- **並行実行**: clone と push の間に `sleep` を挟んだ変種を同時に走らせてレースさせ、
  `attempt 1 failed ... retrying` → やり直し → **両方のスライスが生存**を確認。

### テストハーネス自身のバグで「リースが効かない」と誤読しかけた

最初のレーステストは `sed` のアンカーがずれて `sleep` が挿入されておらず、**そもそも競合していなかった**
のに「通った」と読みかけた。続けてリース単体を確かめたときは `git push ... | sed` と書いたため、
**パイプの終了ステータスが `sed` のものになり**「push SUCCEEDED（リースが効いていない）」と出た——
実際には git の出力に `! [rejected] (stale info)` が出ており、リースは効いていた。

学び: **緑/赤の判定そのものを疑う**。特に (1) 差し込んだはずの遅延が本当に入ったかを grep で確認する、
(2) パイプした先の終了ステータスで成否を判定しない。action 本体は push をパイプしていないので影響なし。

### 恒久ログと一次データを分ける、を設計 doc に昇格させた

今回の切り分け（`ci-logs`＝恒久・`net-fetch-results`＝揮発）は net-fetch 固有の話ではなく、**git ブランチ
では削除が削除にならない**という一般則から来る。将来また「揮発させたい出力」が出たときに同じ判断へ
辿り着けるよう、`ops-sync-design.md` に節を立て、`ci-logs.md` の前提にも「一次データを混ぜない」を
MUST NOT で書いた。

**artifact 案を再検討させないための記述も同時に入れた**（`net-fetch.md` の「よくある失敗」＋
ops-sync-design）。一見最適に見えて実際は egress で読めない、という失敗は放っておくと必ず再発する。

### ジョブログ併設は「手順の分岐」にしない

ログ本文を取得できるランタイムはブランチを fetch せず1回で読める。ただし sop-format の
「判断・分岐をツールの有無に紐づけない」に従い、**要求（結果を読み戻す）は経路によらない MUST 一つ**とし、
ブランチとジョブログは同格の「満たし方」として並べた。「MCP を持つなら A、無いなら B」とは書いていない。

### 残り

`stop-commands` ガード（外部コンテンツ中の `::error::` 等が workflow command として解釈されるのを止める）
だけは Actions ランタイム固有でローカル再現できない。**マージ後に `::error::` を含む本文を1回取得させ、
run に注釈が出ないことを確認する**こと。

## 2026-07-26 net-fetch の結果を揮発ブランチへ移す（作業途中・引き継ぎあり）

ai-ops をゼロベースで設計し直すなら機能分離すべきか、という相談から派生した作業。net-fetch の取得結果が
public な ai-ops の `ci-logs` に**恒久堆積**している（中断時点で 16 リクエスト・64 ファイル）のを、
専用の揮発ブランチ `net-fetch-results` へ分離して TTL を付ける。**未完**——残作業は
`docs/reference/NET_FETCH_EPHEMERAL_HANDOFF.md` に全部書いた。

### 「artifact に出す」案を実測で潰した

当初 artifact（`retention-days` で自動失効）を推した。これは**間違いで、実測で潰れた**。artifact と run
ログの zip はダウンロード URL が `results-receiver.actions.githubusercontent.com` や blob ホストへ 302 するが、
エージェント実行環境の egress プロキシがそれを拒否する（`curl: (56) CONNECT tunnel failed, response 403`。
プロキシの `recentRelayFailures` にも記録された）。`productionresultssa0.blob.core.windows.net` と
`pipelines.actions.githubusercontent.com` も到達不可。一方 `api.github.com`・`objects.githubusercontent.com`・
`codeload.github.com`・`git fetch` は通る。

しかもこれは特定エージェント固有ではない。`gh run download` も REST も同じホストに当たるので、artifact に
すると**全エージェントで結果を読み戻せなくなる**。MCP の `get_job_logs` だけはサーバ側取得なので通るが、
それに依存すると sop-format の「判断・分岐をツールの有無に紐づけない」に反する。

**学び: `ci-logs` がブランチ方式なのは正解だった**（git と `api.github.com` が egress 制限下で確実に届く
唯一の経路）。出口を動かすのではなく寿命を付けるのが正しい。**設計を変える前に到達性を1回測る**——
測らずに実装していたら net-fetch を全エージェントで壊していた。

### 恒久ログと一次データを同じブランチに混ぜていたのが根因

`ci-logs` は「消しても履歴に残る」ので、public リポジトリでは削除が削除にならない。quota 信号や archive
ログは**現在値を読ませる恒久データ**で残ってよいが、net-fetch の結果は**読んだら用済みの一次データ**。
この2種類を同居させたまま purge しようとすると、恒久側の履歴まで巻き込む。分離してブランチごと
使い捨てにするのが正しい切り分け。

### `publish-ci-logs` を拡張せず別 action にした

`publish-ephemeral` は挙動が大きく違う（追記型 vs 毎回 orphan 書き換え・TTL 失効・force-with-lease）うえ、
`publish-ci-logs` は nikki-san の deploy 系が依存する敏感な経路。AGENTS_COMMON の「敏感なコードの共通化は
挙動を変えない形に留める」に従い、共通化せず新規に分けた。

### 並行実行で他人のスライスを消さない

毎回 orphan で force push する設計なので、素の force だと同時刻の別リクエストの結果を消す。開始時の sha を
`--force-with-lease` のリースにして、拒否されたら相手の状態から作り直す（相手のスライスが生き残る）。

### 外部コンテンツをジョブログに出すときの注入

MCP 等でログ本文を読めるランタイム向けに、結果をジョブログにも出す方針にした。ただし**取得した外部
コンテンツをそのまま出すと本文中の `::error::` 等が workflow command として解釈される**。
`::stop-commands::<ランダムトークン>` で解釈を止めてから出す（トークンを固定値にすると本文側から
推測して止め損なえるのでランダム）。

なお「MCP を持つエージェントはログから、持たないものはブランチから」という書き方は sop-format 違反。
**要求（結果を読み戻す）は経路によらず1つ**で、ログとブランチは「満たし方」の補足として書く。

### セッション中断について

クライアント側の不具合で選択ダイアログ（AskUserQuestion）が消えなくなり、作業継続が不能になった。
実装は composite action 1本まで。**中断時点で既存ファイルは1つも変更していない**ので、残作業は
引き継ぎ doc からそのまま再開できる。

### アクセスした外部 URL

到達性検証のみ: `results-receiver.actions.githubusercontent.com`（403）・
`productionresultssa0.blob.core.windows.net`（到達不可）・`pipelines.actions.githubusercontent.com`（到達不可）・
`api.github.com`・`objects.githubusercontent.com`・`codeload.github.com`（到達確認）。

## 2026-07-26 net-fetch: request_id に貼られた secret が公開結果に残る穴を塞ぐ

P1 のトリアージで net-fetch 系4件を実地確認した結果、**3件は既に修正済みで resolve だけされていない**もの
（2026-07-23 に返信付きで直っていた）、**1件だけが本物**だった。

本物のほう（ops-runner #1）: `request_id` の検証が文字種（`^[A-Za-z0-9._-]+$`）と `..` だけで、
**secret 判定を通していなかった**。GitHub token（`ghp_...`）等は文字種を素通りするので、request_id に
secret を貼ると (1) publish 先パス `net-fetch/<id>`、(2) `meta.txt` の `request_id=`、(3) ジョブログ、の
3経路に生のまま残る。**集約モードの実行先 ops-runner は public** なので世界公開に落ちる。URL 側は
`matches_secret` で弾いているのに、id 側だけ抜けていた（同じ出力に載るのに基準が非対称だった）。

対処: id 検証に `matches_secret` を追加（2箇所の検証条件を揃える）し、出力に載せる id は
`redact_secrets` を通した `SAFE_REQUEST_ID` にした。あわせて `matches_secret` の定義を前方へ移した
——bash は定義を実行するまで関数を呼べず、id 検証は定義より前にあったため。

実駆動で確認: `ghp_...` 形は `invalid request_id` で拒否され `meta.txt` は `[REDACTED-SECRET]`、
通常 id は従来どおり通過、`../escape` も従来どおり拒否。

教訓: **同じ出力に載る入力は、同じ基準で検査する。** URL には secret 判定・SSRF ガード・allowlist と
何重にも掛けていたのに、隣にある request_id は「パスに使うから」という理由で path traversal だけ見ていた。
入力ごとに「何に使うか」で検査を設計すると、出力経路が共通であることを見落とす。

## 2026-07-26 計算基盤 `ops-runner` を consumer として追加（実行基盤分離の第1段）

エージェントが dispatch する計算（現状 net-fetch）を ai-ops から切り出すための下準備。この段階では
**配布先を1つ増やしただけ**で、net-fetch の実行先はまだ ai-ops のまま（切り替えは次段）。

### なぜ分けるか

ai-ops には `OPS_SYNC_TOKEN`（全 consumer への Contents/Workflows:RW）がある。一方 net-fetch は
**エージェントが任意のタイミングで起動でき、任意の外部 URL の中身を持ち込む唯一の経路**で、性質が
まったく違う。現時点で穴が空いているわけではない（fetch ジョブに secret を渡さない・`pull_request`
トリガが無い・fork PR は承認必須・main はブランチ保護）が、その不変条件は **workflow 1つ1つの
レビューで担保している**状態。今後この種の機能は増えるので、リポジトリ境界にして構造で保つ。

**分割線は「計算 vs 配布」ではなく「`OPS_SYNC_TOKEN` が要るか」**。archive-task-history のようなバッチは
計算だが cross-repo write が要るので ai-ops 残留。quota 信号も cron 専用で外部入力を取らないため残留。

### コストが安い理由

新リポジトリを `consumers.txt` に1行足すだけで、既存の配布機構が `net-fetch.yml`・allowlist・
`publish-ephemeral`・共通ルールを届ける。**新しい仕組みはゼロ**。分離完了後は、ai-ops が抱えている
「`shared/` の正本と root の実コピーを byte 一致で手動同期」という二重管理も消える。

### 限界（誤解しないため）

この分離は**一方向**。runner に配るには `OPS_SYNC_TOKEN` が runner にも書き込める必要があるので、
「runner が ai-ops を触れない」は成立するが「ai-ops が runner を触れない」は成立しない。守っているのは
*鍵のある場所に外部コンテンツを持ち込ませない*ことであって、鍵の影響範囲を狭めることではない。

また `ci-logs` が2箇所になる。quota 信号は ai-ops 側に残るので、分散モードのエージェントは
「枠の信号は ai-ops、取得結果は runner」と2箇所を見る。読むだけなので実害は小さいが doc で明示が要る。

### ops-runner は public

無料枠のため（private だと分を消費し、枠はアカウント単位で全 private リポジトリが共有する）。
帰結として、ここへ配る `shared/` の内容も net-fetch の取得結果も世界公開になる。機微な取得は
従来どおり private リポジトリの分散モードで行う（この分離で変わらない）。

## 2026-07-26 リネームの一括置換が、除外指定の副作用で配布ファイルを1つ取りこぼした

`ai-ops` → `ops-sync` の一括置換で **`shared/docs/history-inbox/README.md`** が対象から漏れ、
全 consumer へ旧名のまま配られた（マージ後の全リポジトリ突合で発見）。

原因は置換対象を集めるときの除外指定:

```
grep -rIl "ai-ops\|AI-OPS" --exclude-dir=history-inbox ...
```

意図は「**このリポジトリ自身の履歴フラグメント**（`docs/history-inbox/`）を書き換えない」ことだったが、
`--exclude-dir` は**名前が一致する全ディレクトリ**に効くため、まったく性質の違う
`shared/docs/history-inbox/`（＝全 consumer へ配る placeholder）まで除外された。

**学び: `--exclude-dir` はパスではなくディレクトリ名で効く。** 同名ディレクトリが別の役割で存在する
リポジトリでは、意図しない範囲まで黙って外れる。除外したいのが特定パスなら
`--exclude-dir` ではなくパスで弾く（`grep -v '^./docs/history-inbox/'` 等）。

**検証の穴も同じ形だった**: 置換後の残存チェックにも同じ除外指定を使ったため、
**取りこぼしたファイルは検証でも見えなかった**。置換と検証で同じフィルタを使うと、
フィルタ自体の誤りは原理的に検出できない。今回は全 consumer をマージ後に突合して初めて見つかった
（＝配布後の実物を見る確認が効いた）。除外条件を変えた再スキャンで、他に漏れが無いことを確認済み。

## 2026-07-26 リポジトリを ai-ops から ops-sync へリネームし、識別子も移行

「ai-ops」という名前をゼロベースで見直した結果の改名。実行基盤の分離（ops-runner）と同時にやることで、
移行ウィンドウを1回に収めた。

### なぜ改名したか

1. **業界用語との衝突**。「AIOps」は Gartner 由来の確立した語で **IT運用にAIを適用する**ことを指す。
   このリポジトリは逆向きで、**AIエージェントのための運用基盤**。しかも読者の主体は LLM エージェントで、
   彼らの学習データには AIOps の一般的な意味が入っているため、名前が読み手を誤誘導する。
2. **「ops」の情報量が低い**。運用スクリプト置き場か IaC かランブック集か制御基盤か判別できない。
   実体は「ルールと共有CIファイルを consumer へ一方向配布し、逆方向は提案として集約する control plane」。

`ops-sync` を選んだのは、**すでにリポジトリ内で使われていた語だから**（設計 doc が `ops-sync-design.md`、
仕組みの呼称も一貫して「同期」）。設計 doc のファイル名を変えずに済み、`ops-runner` と対で読める。

**単体では改名しない判断だった**。名前の改善幅に対して識別子移行のコスト・リスクが見合わないため。
①（実行基盤の分離）をやる回に相乗りさせたのはそのため。

### 何を変えたか

- リポジトリ名（オーナー操作）。GitHub がリダイレクトするので git remote は張り替え不要だった。
- テキスト参照の一括置換（41ファイル）。**履歴系は除外**（`AI_TASK_HISTORY.md`・`history-inbox/`・
  `history-archive/` は過去の記録で、現在形ルールの対象外）。
- 識別子: `AI-OPS:COMMON` → `OPS-SYNC:COMMON`、`.ai-ops/` → `.ops-sync/`、同期ブランチ
  `ai-ops/sync-common` → `ops-sync/sync-common`。**`.ai-ops/` とブランチ名は「ai-ops」を含む文字列なので、
  テキスト置換と同じ一括処理で自然に移った**（別作業にしなくてよかった）。
- 配布ルールファイルの改名: `.clinerules/ai-ops.md` 他4件 → `ops-sync.*`。旧ファイルは manifest 差分で
  consumer から自動削除される。

### 後方互換を入れないと全 consumer が壊れる箇所

**`apply-common.mjs` のマーカー認識が最重要**。consumer の AGENTS.md には旧マーカーが入っているので、
新マーカーだけを探すと見つからず「末尾に追記」の経路へ落ち、**全 consumer で共通ブロックが二重になる**。
新旧どちらの区間も拾って新マーカーで置き換える `findRegion()` を入れた。

`apply-shared.mjs` は削除判定を新旧 manifest の和にし、**旧 manifest ファイル自体も明示的に削除対象へ入れた**
（manifest は manifest に載らないので差分削除では消えない）。旧配置の `.ai-ops/tasks/**` は旧 manifest に
載っているため自動で消える。

`collect-outbox.mjs` は新旧どちらの outbox も走査する。配布 doc が新パスに切り替わる前に始まったセッションが
旧パスへ提案を置きうるため。差し戻し先も**提案が置かれていた側**に合わせた（新パスへ差し戻すと提案者が
自分の置いた場所を見ても見つけられない）。

これらの LEGACY 分岐は、全 consumer から `.ai-ops/` と旧マーカーが消えたら削除してよい（各所にコメント済み）。

### 移行を実駆動で検証した

旧マーカー・旧 manifest・旧 `.ai-ops/tasks/` を持つ偽の consumer を作り、実際に両スクリプトを走らせた:
新マーカー1個・旧マーカー0個（**二重化なし**）、リポジトリ固有パートの保持、`.ai-ops/` の完全撤去、
旧 manifest 記載ファイルの削除、新ルールファイル名の配布、そして**2回目実行が no-op**（冪等）。

移行は outbox が空のときにやる必要があり（走査対象が変わる瞬間に提案があると取りこぼす）、
着手前に両 consumer とも `.ai-ops/outbox/` が存在しないことを確認した。

## 2026-07-26 task-done の完了条件をセッション内で到達できるものに直す（Codex ops-runner #8/#9）

自分が同日に出した2つの変更への指摘。どちらも正当だった。

**1. 完了条件がエージェントに到達不能だった（ops-runner #8 P2）**: `task-done` の消化を MUST に格上げした
とき（#103）、完了条件を「削除が ops-sync の main に入り、次の sync で `.ops-sync/tasks/` から消えている」
と書いた。直接 PR 経路ならまだしも、**outbox 経路ではオーナーのマージ＋collect の cron＋sync を挟む**ので、
エージェントはセッション中にその状態へ到達できない（しかもエージェントは自分でマージしない、と別のルールで
禁じている）。`outbox-proposal.md` が outbox 経路の完了を「提案が consumer の main に載ること」と定義して
いるのとも食い違っていた。

→ **セッション内の完了条件**（エージェントが自分で確認できる範囲）と**非同期の消化条件**（オーナーの
マージ以降）を分けた。あわせて「消えるまで待たない」を MUST NOT で明記した——待っても自力では到達
できないので、待つ実装は無限に止まる。

教訓: 完了条件を書くときは「**その主体が自分で確認できる状態か**」を必ず確かめる。SOP 規約は完了条件に
「検証可能な事実」を求めているが、*誰にとって*検証可能かまでは書いていなかった。強制力（MUST）を足す
改訂ほど、到達不能な条件を書くと実行が止まる。

**2. 設計 doc の記述が実装と食い違っていた（ops-runner #9 P2）**: 出力を2種類に分けた（#104）とき、
「出力」節は直したが**「しくみ」段落の「1本の markdown 一覧に落とす」を直し忘れた**。同じ doc 内に
現行の姿が2通り併存する状態。あわせて #105 で既定の走査窓を3日にした件も doc に反映した
（設計と実装を乖離させない、というこのリポジトリの完了手順）。

教訓: 節を足す形の改訂では、**同じ事実を述べている既存の文**が他にないか探す。今日は「経路を増やす改訂で
強制力が薄まる」パターンを3回、この「節を足して既存記述と二重化」パターンを1回踏んだ。

## 2026-07-25 「ジョブ0・課金0分の failure は workflow 側ではない」を切り分けとして残す

デプロイ経路スイッチ改名の PR をマージした直後、`deploy.yml` と `deploy-admin-worker.yml` が同時に
`failure` になり、**自分の変更した `if:` や新設の検証ステップを疑った**。実際にはどちらの run も
ジョブが1件も起動しておらず（`total_jobs: 0`）、`billable` も空だったので、変更とは無関係だった。

さらにそこから**「枠切れだ」と決めつけてユーザーに報告してしまった**。ジョブ0・課金0という証拠が
示していたのは「workflow の中身が原因ではない」ところまでで、その先（なぜ起動しなかったか）は
推測でしかなかった。ユーザーに billing 画面が 1,992/2,000 のままだと指摘されて誤りが判明し、
run ページを見てもらったところ **`Internal server error. Correlation ID: …`**——GitHub 側の一過性障害だった。

この2段階（**切り分けは正しかったが、その先を推測で埋めた**）が再発しやすいので doc に残した:

- ジョブ0・課金0 で分かるのは「workflow 側ではない」ことだけ。
- 「GitHub の内部エラー」か「アカウント側の実行拒否」かは **run ページの表示でしか分からない**。
  API のジョブ一覧からは区別できないので、推測で断定しない。
- 「同じ push で複数 workflow が同時に同じ壊れ方」はアカウント側を*示唆*するが、決め手ではない
  （今回まさにそれで誤った——内部エラーも同じ push の run をまとめて巻き込む）。

### Codex 指摘 P1×2 で書き直した

最初に書いた「**ジョブ0件・課金0分なら workflow 側の不具合ではない**（MUST NOT: workflow を疑う）」は
**誤り**だった。**invalid workflow file・式の不正・reusable workflow の参照エラーはジョブ生成前に弾かれる**
ので、まさにこの見え方（ジョブ0・課金0）になる。つまりあのルールは、**自分が直前に壊したときにこそ
真犯人から目を逸らさせる**。しかも配布 doc なので全 consumer に伝播していた。

原因は3種類（ワークフロー側の不正／GitHub 内部エラー／アカウント側の実行拒否）で、**ジョブ数と課金では
区別できない**。区別できるのは run ページ（または annotation）の文言だけ。表にして、
「**ワークフローを変更した直後の失敗はまず自分の変更を疑う**（MUST）」を明示した。

皮肉なことに、この doc を書く動機になった今回の私の誤りは「切り分けの1段目で止めず推測で2段目を
埋めた」ことで、最初の草稿は**1段目自体を間違えて**同じ轍を踏んでいた。

あわせて sop-format 準拠に組み直した（「触れたついでに準拠させる」規約）。目的／トリガ／前提・
パラメータ／番号付き手順＋完了条件／よくある失敗、の形にし、**手順A（新規ワークフローへの組み込み）と
手順B（失敗の切り分け）を別立て**にした。既存の内容（2層の使い分け・collector の失敗ゲートと式の
略記禁止・net-fetch の登録例外）は削らずそのまま手順Aに収めてある。

## 2026-07-25 Cloudflare 月枠の信号を追加（`actions-quota` の対）

GitHub Actions の枠が尽きたときの退避先は Cloudflare だが、**CF 側にも月枠がある**（Free: Pages の
ビルド 500回/月・Workers Builds 3,000分/月・ともにアカウント単位）。GitHub 側だけ見て自動退避すると
今度は CF を溶かして「どこにもデプロイできない」に至るので、対になる信号を作った。将来の
`*_DEPLOY_POLICY=auto` の突合が読む前提。

### 実測で分かった、設計を変えた事実

この信号は**先に手で測ってから**設計した。推測で作っていたら間違えていた点が3つある:

1. **枠を消費しない deployment が圧倒的多数**。2026-07 の Pages は deployment 2,079 件のうち課金対象は
   **94 件（4.5%）**だけだった。除外すべきは `deployment_trigger.type == "ad_hoc"`（`wrangler pages deploy`
   ＝Direct Upload。CF のビルド枠を使わない）と、watch paths 不一致で `is_skipped: true` になったもの。
   単純に deployment を数えていたら **20 倍以上**過大評価していた。
2. **使用率だけでは判断できない**。同じ月内で日次レートが不連続に変わる——実測の日次分布は
   `7/19: 32 → 7/20: 32 → 7/21: 14 → 7/22: 5 → 7/23: 3 → 7/24: 6 → 7/25: 2` で、watch paths を絞った
   前後で 10 倍以上違う。そこで**直近 N 日（既定7）の窓**でレートを出し、残枠が月末まで持たなければ
   `tight` にする。**月累計 ÷ 経過日数の平均は使わない**（設定変更の前後をまたぐと実態とずれる）。
   - このセッションで実際に、私は「94 件 ÷ 推定1日 = 94件/日」と外挿して「7/29 に枯渇する」と誤報告した。
     切替日を run 履歴から推測したのが誤りで、実際は7日分だった。**平均レートの罠**そのものなので、
     実装では窓方式を採った。
3. **Workers Builds の「分」は API が返さない**。`running_on`〜`stopped_on` から算出する推定値で、
   Cloudflare の課金定義と一致する保証は無い。桁の把握には足りるが、閾値には余裕を持たせる前提で使う。

### fail-closed の作り

`actions-quota` と同じく、測れなければ必ず `unknown`（消費側は逼迫扱い）。加えてこの信号固有の穴として
**ページングが進まないと黙って過少カウント＝fail-open になる**（＝「まだ余裕がある」と誤って言う）ので、
同じ先頭要素が返り続けたら `unknown` に倒す。数値設定（上限・閾値・窓）が壊れていたら既定へ黙って
戻さず `unknown`——`actions-quota` で踏んだ「`NaN` で割ると `pct >= threshold` が常に false」と同型。

### トークンの置き場

**ai-ops は public** なので、ここに置く CF トークンは**読み取り専用に限る**。切替（Pages の自動デプロイ
反転・watch paths 変更）に要る Edit 権限の操作は、consumer 側の workflow が自分のトークンで行う。
なお Workers Builds API は **user-scoped トークン必須**（account-scoped は "Invalid token"）なので、
public repo に user-scoped トークンを置くことになる——read-only である点が担保。
アカウント ID も secret で持つ（public repo のログに出さないため）。

### 全体 state は最悪値に揃える

`pages_builds` と `workers_build_minutes` の悪いほうを全体 state にする（片方でも逼迫していれば
「CF へ退避してよい」とは言えない）。リソース別の state も併記する——退避先として使えるのが
どちらかで、消費側の判断が変わるため。

検証: CF API をスタブして24ケース実駆動（各リソースの ok/tight/exhausted、閾値未満でも直近レートで
月末超過なら tight、ad_hoc と skip の除外、先月分の除外、片方 tight/unknown のときの全体 state、
exhausted > unknown の優先順、ページング停滞、各種取得失敗、Workers Builds 未接続の 404、
token/account 未設定、数値設定の typo、上限変更）。**生の数値を publish していないことも各ケースで検査**。

### Codex 指摘 P1×2

**1. 同じ `dest` に publish する2つの workflow は互いを消し合う。** `publish-ci-logs` は publish 前に
`rm -rf "${tmp}/${DEST}"` で dest を丸ごと消してから source を置く。`actions-quota` と同じ `dest: quota`
にしていたので、**cron が回るたびに片方がもう片方の JSON を削除する**——既存の Actions 信号を壊す
ところだった。信号ごとに `quota/actions` / `quota/cloudflare` へ分離し、両方の workflow に理由を
コメントで残した（`quota` 自体を dest にしないので、3つ目の信号を足しても同じ事故は起きない）。
消費側のパスが変わるので配布 doc（`actions-quota.md`・`net-fetch.md`）も同一 PR で更新した。
移行の一瞬はファイルが見つからず `unknown` になるが、消費側は unknown を逼迫扱いにするので安全側。

**2. 月初はレート窓が実際より長く割られて fail-open になる。** 当月のレコードしか数えないので、
月の1日目には窓（既定7日）ぶんのデータが存在しない。それでも 7 で割ると**レートを実際より小さく
見積もる**——「1日目に 60 ビルド」が 8.6件/日 と読まれ、`ok` を出してしまう。窓と経過日数の
**小さいほう**で割るよう直した。

この2件目は**月初にしか現れない**ので、今日（25日）のテストでは通らない。時刻を固定できないと
永久に未検証のままなので、テスト専用の時刻上書き `CFQ_NOW` を入れて月初のケースを再現できるように
した（本番では設定しない旨をコメントと doc に明記）。実際、旧実装だと `60 + 8.6*30 = 317 < 500` で
`ok`、新実装だと `60 + 60*30 = 1860 ≧ 500` で `tight` になる——この差をテストで固定した。

### セットアップ手順に直リンクが無かった

共通ルール「ユーザーへの操作指示は直リンク URL で」に反して、README のセットアップ手順が
「本リポジトリの Actions Secret に登録する」と書くだけで **URL を出していなかった**（PAT 発行画面も
同様）。オーナーからの指摘で気づいた。長く残る doc なので、URL に加えてメニュー経路も併記した
（サイト構造が変わって URL が無効になっても辿れるように、という同ルールの後段）。

## 2026-07-25 Actions月枠の逼迫を billing API で実測する共通基盤を追加

同セッションで一度「deploy workflow の run が `skipped` 続きかで枠逼迫を間接判定してよい」と
net-fetch.md に書いたが、ユーザーから「間接判断は危ない」と却下された。妥当な指摘で、あの判定は
**ユーザーが退避スイッチ（`PAUSE_GH_DEPLOY` 等）を入れ忘れていれば「余裕あり」と誤読する**——
逼迫の検出を人間の運用手順の副作用に依存させており、本当に危険なときほど外す。実測に置き換えた。

設計判断（コードに残らない前提）:

- **ai-ops でだけ測る**（`shared/` に置かず consumer へ配布しない）。Actions の月枠は**アカウント単位**で
  `65edh5ih` 配下の private repo が全部同じ枠を共有するので測定は1箇所でよい。加えて ai-ops は public
  なので測定自体が枠を食わない（枠を測るために枠を消費する矛盾を避ける）。consumer に billing PAT を
  配らずに済むのも効く（「consumer に常設トークンを増やさない」原則）。
- **公開先が world-public なので生の使用分数・使用率を出さない**。ai-ops の `ci-logs` は世界公開で、
  アカウントのCI使用状況が晒される。`ok`/`tight`/`exhausted`/`unknown` の band と閾値だけで
  「9割超えたら分散モードを使わない」ルールは成立するため、実数はアカウントの billing 画面に留める。
- **測れなかったら必ず安全側**。token 未設定・API 変更・ネットワーク断・応答形の変化は全部 `unknown` で、
  消費側は `unknown` を `tight` と同じ扱いにする。実装でも2重に塞いだ: (1) `fetch` を try/catch して
  例外で落ちないようにし、(2) それでもスクリプトが結果を残せず落ちた場合に備え workflow 側で
  `unknown` を書く保険ステップを置いた。**これが無いと `ci-logs` に前回の古い `ok` が残り続け、
  消費側が古い ok を掴む fail-open になる**（publish-ci-logs は source-dir が無いと何もせず緑で終わるため）。
- **鮮度も契約に入れた**（`stale_after_hours`・既定24h）。月枠は月初にリセットされ日中に伸びるので、
  古い `ok` を根拠にさせない。ファイル自身に閾値と鮮度を埋めて自己記述にしてある。
- **旧 billing API 優先・enhanced はフォールバック**。「含有枠の何割か」を直接返すのは旧 API だけで、
  enhanced billing platform は金額ベースの明細しか無い。後者では「課金発生＝含有枠超過＝`exhausted`」
  しか断定できず、未課金でも割合は不明なので `ok` と断定せず `unknown` に倒す。どちらの経路が
  このアカウントで生きているかは docs を読んでも確定できなかったため、**両方試して実測で決まる**
  実装にした（初回実行の `source` フィールドに出る）。

閾値90%はユーザー指定。運用中に変えられるよう ai-ops の repo variable
`ACTIONS_QUOTA_THRESHOLD_PCT` で上書き可能にした（未設定なら90）。

検証: billing API をスタブして8ケース実駆動（85%→ok / 89.95%→ok / 90.0%ちょうど→tight /
97.5%→tight / 課金発生→exhausted / 0%→ok / 閾値80に変えて85%→tight / 応答破損→unknown）。
token 未設定・不正tokenの degrade も実行して `unknown` を確認。

### Codex レビューで塞いだ穴（いずれも「安全側に倒すはずが倒れない」系）

- **しきい値の typo で fail-open（P1）**: `Number('9O')` は `NaN` で `pct >= NaN` が常に false になり、
  **使用率にかかわらず `ok` を publish していた**。100超の値も同じく判定が発火しない。しきい値は
  private repo の dispatch を認可する値なので、`(0,100]` の有限数以外は `unknown` に倒すよう検証を追加。
  併せて `threshold_pct` に必ず妥当な数を載せる（`NaN` は `JSON.stringify` で `null` になり消費側が読めない）。
- **workflow の `run:` に `${{ vars.* }}` を直接埋めていた**: このリポジトリの鉄則（注入経路になる）違反で、
  かつ非数値が混ざると actions.json が壊れて消費側が読めなくなる。env 経由＋数値サニタイズに変更。

## 2026-07-25 含有枠の出どころを経路ごとに正す（consumer 同期 PR の Codex 指摘）

## 2026-07-25 Actions月枠の使用率算出（enhanced billing 経路）を完成させる

`docs/reference/ACTIONS_QUOTA_NEXT_STEPS.md` の引き継ぎ手順に沿った作業。判断根拠を残す。

- **含有枠は設定値で持つしかない**（API が返さない）。既定は GitHub Free の 2,000 分（ユーザー確認済み）で、
  repo variable `ACTIONS_QUOTA_INCLUDED_MINUTES` で上書きする。**不正値は既定へ黙ってフォールバックさせず
  `unknown` に倒す**——typo した上書き値を既定で置き換えると「設定したつもりの枠と違う枠で測った ok」を
  publish しうる。`Number('2OOO')`＝`NaN` で割ると使用率が `NaN` になり `pct >= threshold` が常に false ＝
  使用率にかかわらず ok を出す fail-open で、これは `AQ_THRESHOLD` で実際に踏んだ穴と同型。
  上限 1,000,000 分の sanity check は分と秒の取り違え等の桁違いを弾くため（含有枠は最大でも
  Enterprise の 50,000 分程度）。
- **引き継ぎ doc が挙げていた「private リポジトリで publish せずに実レスポンスを確認する」案は使えない**。
  それ自体がエージェント自発の private repo dispatch であり、`quota/actions.json` が `unknown` の間は
  `docs/actions-quota.md` が禁止している行為そのもの（枠の状態を測るために枠のガードを破る循環）。
  実レスポンスの確認はユーザーのローカル実行で行った。
- **API 仕様の裏取りは net-fetch の集約モードで行った**（`docs.github.com` がセッションの egress で 403）。
  public な ai-ops 上の実行なので枠を消費せず、取得対象も公開ドキュメントで機微でない。
- **`quantity` は「素の実行分数」と解釈した**（引き継ぎ doc が「取り違えると数倍ずれる」と警告していた分岐）。
  根拠は実レスポンスの `pricePerUnit` が SKU 別（Linux の分単価が単独の値として出る）で、GitHub の公表単価も
  Linux:Windows:macOS = 1:2:10 の比＝**倍率は価格側で表現されている**こと。よって含有枠の消費は
  `quantity × OS倍率` で数える。取り違えていた場合（＝ `quantity` が倍率換算済みだった場合）この実装は
  使用率を**過大**に見積もる＝早めに `tight` に倒れる安全側に外れる。
- **実レスポンスは docs の例と表記が違った**: `product` は小文字 `"actions"`（docs の例は `"Actions"`）、
  `unitType` は `"Minutes"`（docs の例は `"minutes"`）、`date` は `"2026-07-01T00:00:00Z"`（docs の例は
  `"2023-08-01"`）。**docs の例をそのまま前提に実装していたら全件取りこぼして誤判定していた**ので、
  比較は全部大小無視にした（未確認の仮説で実装しない、という引き継ぎ doc の要求が実際に効いた）。
- **`Actions storage`（GigabyteHours）を分の枠と混ぜない**。含有枠が別建てなので、artifact が溢れて
  storage に課金が乗っただけで `exhausted` にすると、自発 dispatch が無関係な理由で恒久的に止まる。
  分の枯渇は分課金項目の `netAmount` と使用率で直接見る。
- **分課金項目が1件も無い月は `ok`（使用0）ではなく `unknown` にした**。「本当に使用0」と
  「`unitType` の表記が変わって全件落ちた」を区別できず、後者を `ok` と読むと*恒久的な*誤 `ok` になる。
  月初に一時的に `unknown` が出る不便より fail-open を嫌う。同じ理由で未知 SKU の分項目も `unknown`
  （倍率を推測しない）。

## 2026-07-25 net-fetch共通allowlistにFlickr写真CDNを追加

nikki-san で Flickr移行写真の `_o`/`_z` 実サンプルをnet-fetch経由で取得し、JPEG圧縮パラメータ
（Flickrの縮小版生成クオリティ）を調査する必要が生じた。取得先の `live.staticflickr.com`・`filedn.eu`
はどちらも不特定多数のユーザーの公開コンテンツを配信する汎用CDNで、ドメイン自体に個人性は無い
（取得する特定のURLが個人の写真を指すだけ）ため、機微ドメイン判定の対象外とし共通ベースに追加した。

判断根拠の整理: allowlistの共通/固有区分は「そのドメインが一般に機微データを扱うか」で決めるべきで、
「今回取得したい個々のコンテンツが機微か」で決めるべきではない（後者は実行モード＝集約/分散の判断軸）。
当初これを混同し、nikki-sanのローカルallowlistに追加しようとして手戻りになった。

副産物として、net-fetch.md の「共通ベースへの追加」手順が、consumer から出す outbox 提案（非同期・
collect cron待ち）と、`add_repo` を持つエージェントが ai-ops を直接編集する経路のどちらを使うべきか
明示していなかったため誤って前者を選んだ。手順に優先順位を明記する修正を別途 shared-file として本PRに
含めた。

さらにユーザーから、ドメインの機微性とは別に GitHub Actions の月枠逼迫がある指摘を受けた。枠残量その
ものを直接取得する手段は無い（billing API はPAT必須・アカウント単位・遅延あり）が、ユーザーの再指摘で
「間接判定は可能」と気付いた: このアカウントの consumer リポジトリは枠逼迫時にdeployをCloudflare側へ
手動退避する repo variable を運用しており（nikki-sanの`PAUSE_GH_DEPLOY`/`PAUSE_ADMIN_WORKER_DEPLOY`）、
変数の値を直接読めなくても、対象repoのpush起点deploy workflowの直近runがconclusion=skipped続きなら
「枠逼迫で退避中」と判定できる（`list_workflow_runs`で取得可能・追加の資格情報不要）。実際に nikki-san
の`deploy.yml`を確認したところ直近複数runが軒並みskippedで、現在まさに逼迫中と確認できた。同一
アカウント配下の他privateリポジトリもActions枠を共有するため、この判定は分散モードの可否判断に転用
できる。net-fetch.md に「間接判定をまず試み、それでも確信が持てなければユーザーに確認する」形で追記した
（判定できないリポジトリでは引き続きユーザー確認が必須）。quota-gateの自動化自体は今後の課題として残る。

## 2026-07-25 net-fetch 共通 allowlist に developers.cloudflare.com を追加

「枠が `tight` のとき GitHub Actions 側の deploy を自動で止められるか」を設計するのに、
**Cloudflare 側の切替設定（Pages の Build watch paths / Workers Builds の設定）が API で
変更できるか**の裏取りが要る。ここが可能なら両側を自動で反転でき、不可能なら
「GitHub 側だけ止める＝両方 off（どこにもデプロイされない）」を受け入れるかの判断になる——
設計の分岐点そのものなので、推測で決めない。

`developers.cloudflare.com` は公開ドキュメントで認証不要・機微でないため共通ベース
（集約モード＝ public な ai-ops 上での取得）に置ける。機微なら private リポジトリの
ローカル allowlist に置く判断になるが、これは該当しない。
