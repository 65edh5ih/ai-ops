## 2026-08-08 push 先制約と対象 PR の食い違いを review-threads に追加

ある private consumer の PR で、指摘対応中に実際に踏んだ穴。`review-threads.md` 手順2 は「未マージなら畳む／マージ済みなら
新 PR」の2択しか書いておらず、**そもそも対象 PR のブランチに push できない場合**が抜けていた。

**何が起きたか**: セッション側の設定で開発ブランチが指定され、指定外への push は明示的な許可が要る状態
だった。そのブランチ名は**依頼の文面から着手前に
自動生成**されるので、「既存の open PR の指摘を直す」という**宛先が既に決まっているタスク**とは
必然的に食い違う。エージェント（私）はユーザーに許可を求めず、**指定ブランチへ push しつつ PR の base を
対象 PR の head に向ける**という回避策を発明した。対象 PR が squash merge された瞬間にこれが壊れ、
両者が触った4ファイル全部が衝突した。

**なぜ壊れるか**: squash merge は元コミットと履歴を共有しない単一コミットを `main` に作る。その上に積んだ
ブランチは共通祖先を持たないので、git からは「main も自分も同じ行を変えた」に見える。**squash された
ブランチの上に積んだものは必ずこうなる**——回避策の選択時点で確定していた失敗で、運が悪かったのではない。

**要求は既に sop-format にあった**。「ある能力を満たせないときは、別の振る舞いへ勝手に切り替えず停止して
ユーザーに依頼する（MUST）」がそれで、今回はその具体例。抽象的な MUST は**具体的な分岐点に置かれていないと
発火しない**ので、判断が実際に起きる場所（手順2）に事例付きで下ろした。指定側にはたいてい「明示的な許可が
あれば別ブランチも可」という例外があり、聞けば1往復で解ける。

**ツール中立**: 特定エージェント・特定機能の名前ではなく「セッション側の設定で push 先ブランチが
制約されている場合」と書いた（sop-format「要求するのは能力であって特定ツールではない」）。

**追記: 「都度聞く」から「恒久的な許可」に変えた**。初版は「停止してユーザーに許可を求める（MUST）」に
していたが、`--fix` は日常的に使う機能なので、毎回1往復挟むのは運用として重すぎるとオーナーから指摘。
食い違いの解決先は**常に対象 PR の head ブランチ**で一意に決まる（判断の余地が無い）ので、聞く価値が無い。
許可の範囲を「対象 PR の head ブランチのみ」に絞り、`main`・無関係なブランチへの拡大を MUST NOT で塞いだ
うえで事前許可に変えた。**停止して聞く**のは、対象 PR が特定できない・複数あるなど**本当に判断が要る場合**
だけに残した。

**`--fix` の正しい使い方も同じ節に書いた**。`--fix` は*作業ツリーを書き換えるだけ*で、ブランチもコミットも
作らない。したがって**作業ツリーに対象 PR の変更が入っていること**が前提で、**未マージのうちに**走らせるのが
本来の形。マージ後に走らせると、当てた先が squash 前の古いブランチになり、そのままでは `main` に載らない。

**「セッションを対象 PR のブランチから開始する」という助言は誤りだったので撤回した**。オーナーから
「web セッションに『居る』の概念は無い」と指摘され、reflog で確認したところそのとおりだった——コンテナの
初期状態は既定ブランチで、セッション側が作るのは指定ブランチだけ。**対象 PR の head は、先行セッションが
自分で `fetch` + `checkout` して取ってきていた**。

ここから枠組みを組み直した: **制約されているのは push 先だけで、fetch とチェックアウトは一切制約が無い**。
2つを混同していたために「セッションの開始状態」を人間が整える話にしてしまい、エージェントが1コマンドで
できることをユーザーへの依頼にしていた。doc も「開始状態を当てにせず自分で取りに行く（MUST）」
「開始状態を判断材料にしない（MUST NOT）」に書き換えた——開始状態に依存する手順は、同じ依頼でも
実行するたびに結果が変わる。

**追記: レビュー指摘で2点直した**（この PR 自身への `/code-review --fix`）。

1. **新しい3つの MUST に「未マージのとき」というスコープを付けた**。手順2 は直前で「マージ済みなら新しい
   PR にする（MUST）」と言っているのに、その後の3つ（head を fetch/checkout する・自動適用の前に head を
   取る・head にコミットして push する）を無条件で書いていた。マージ済み PR でこれを読んだエージェントは、
   同じ節の「よくある失敗」が警告している穴にそのまま落ちる——squash merge された head ブランチは
   削除されていることが多く（fetch が失敗する）、残っていても `main` と共通祖先を持たないので修正が載らない。
2. **`git checkout <head>` を `git checkout -B <head> origin/<head>` にした**。前者は*それ自体が開始状態に
   依存する*コマンドで、同じ箇条書きの MUST NOT に反していた。実際に確認したところ、同名のローカル
   ブランチが古いまま残っていると、fetch は `origin/<head>` を更新するがチェックアウトは古いローカル
   ブランチに乗り、`up to date with 'origin/main'` と表示する。自動適用した修正が**古い内容に当たり、
   push で本物の head を上書きする**。「開始状態を当てにしない」と書いた同じ箇条書きが、当てにする
   コマンドを配っていた。

**追記: この履歴自身と PR 本文・コミットメッセージを汎用化した**。ops-sync は public だが、事例の出所は
private な consumer。**配布 doc 本体はツール中立に書いたので固有名ゼロだったのに、説明文の側**——PR 本文
（private repo のディレクトリ構成とローカル doc のファイル名、コンフリクト出力、PR 番号）・コミット
メッセージ・この履歴——**から漏れていた**。doc をきれいに書いても説明文で漏れる、という抜け方をする。
同じ PR で `outbox-proposal.md` にルール化した（公開後は編集履歴と旧 SHA が残るので戻せない＝書く前に
落とすしかない）。

**並行セッションの衝突を `--force-with-lease` が止めた**。別セッションがこの PR をレビューして修正を
push していたのに、こちらは古い remote-tracking ref を基準に force-push しようとした。lease が
`stale info` で弾き、相手のコミット2件（未マージ限定のスコープ付け・`checkout -B`）を消さずに済んだ。
**同じブランチを2セッションが触る状況では、素の `--force` を使わない**。

## 2026-08-08 常時層ルールのレビュー指摘を反映（満たせない MUST・概念の数え落とし）

前 PR で入れた「オンデマンド層へ移したら常時層の同記述を消す」の書き方に4件の欠陥があり、直した。
**足したルール自身が、同じ節にある既存の要求と衝突していた**——`AGENTS_COMMON.md` の「ルールを足したら
既存の要求といま出す diff の両方に当てて読み直す」が名指しで警告している形にそのまま嵌まっている。
自分でその検査を回したつもりで見落としたので、何を見落としたかを残す。

- **「同じ PR で消す」が、消す対象が共通ブロックだと定義上満たせない**。共通ブロックは同期配布なので
  consumer からは手編集できず、直すのは ops-sync 側の別 PR＋オーナーのマージになる。対になる導線ルールは
  「共通 doc の導線も**上りで**共通ブロックに足す」と逃げ道を明示していたのに、**逆方向を書くときにその
  但し書きだけ写し損ねた**。対の規則を足すときは、**対になる既存規則の例外・但し書きも対称に写す**。
- **「残すのは導線の1行だけ」が、4行上の「発火トリガ＋不可逆ガード＋ポインタ」と矛盾**。字義どおり従うと
  net-fetch の「allowlist に無ければ停止してユーザーに依頼する（MUST）」のような、doc を開くと決める
  **前**にしか効かないガードが削られる。**同じ概念を2箇所で別の語で言い直すと、後から書いたほうが
  暗黙に前を上書きする**——語を借りずに言い直した時点で不整合が入る。既存の語をそのまま使う。
- **「常時ロード層」の定義を1箇所でしか広げていなかった**。注入 doc を含める拡張を「正本は1つ」節にだけ
  書き、振り分け節の bullet と `sop-format.md` の同義の列挙は旧定義（AGENTS.md のみ）のまま残した。
  振り分けを判断するエージェントが実際に読むのは振り分け節のほうなので、**拡張が効かない場所に
  拡張を書いた**ことになる。同じ PR の履歴で「注入 doc を数え落とすと常時層の半分を見ない」と
  書いておきながら、その数え落としを規約側で再現した。
- **理由づけの限定が配布本文だけ落ちていた**。PR 本文と履歴には「**置きっぱなしの**記述は diff に
  現れない」と書いたのに、規約本文は「常時層の二重化は diff に出ない」と無条件になっていて、
  「常時層は何を書いてもレビューされない」と読めた。**要約するときに落ちるのは限定詞**で、
  規約では限定詞が効力範囲そのものになる。

**運用面のメモ**: 指摘を受けた時点で対象 PR は既にマージ済みだった（即マージ運用では珍しくない）。
未マージなら同じ PR に畳むところだが、マージ済みなので**同じブランチ名のまま最新 main から切り直して
別 PR**にした。このとき `git reset --soft` で基点だけ動かすと、**index が古い基点のままなので、間に
入った別 PR を巻き戻す差分が乗る**（実際に直前の PR のリネームを打ち消す形で出た）。修正だけを
`git diff` でパッチに落とし、`reset --hard` してから当て直すのが安全。

## 2026-08-08 常時層の棚卸しを consumer にも広げ、二重化を作る穴を塞ぐ

先の棚卸し（共通ブロック側）と同じ検査を各 consumer の**固有**常時層に当てた。結論から言うと、
共通ブロックのときと同じで**削れたのはほぼ全部「オンデマンド doc と重複している詳細」**だった。
文量で選ぶのではなく「他所に正本があるか」から見るのが早い、が2回続けて再現した。

**注入 doc を常時層として数え落としていた**。consumer によっては session-start フックが
`docs/AI_CONTEXT.md` を全文注入するので、常時層は AGENTS.md だけではない。棚卸しの対象を
「AGENTS.md の固有パート」と考えると、実際の常時層の半分近くを見ないまま終わる。**次に同じ検査を
するときは、先にそのリポジトリのフックが何を注入するかを読む**（`.claude/settings.json` →
`session-start.sh`）。実際、最大の重複節はフック注入される側にあった。

**なぜ誰も気づかなかったのか（＝規約の穴）を2つ特定して塞いだ**。Codex の在庫は 0 件で、
「指摘されたのに放置」ではない。

1. **レビューは diff しか見ない**。常時層に置きっぱなしの記述は diff に現れないので、
   構造的にレビュー対象にならない。人間のレビュアーが居ない前提では、ここは規約でしか埋まらない。
2. **振り分けの規約が「足すとき」しか発火しなかった**。「オンデマンド doc を足したら導線を用意する」
   （下り）はあったが、**逆——詳細を doc に移したら常時層の同記述を消す——が無かった**。だから
   「doc に正本を作る」たびに二重化が1件生まれる構造になっていた。今回はこの逆方向を MUST で足し、
   併せて「正本は1つ」の節が字面上 `docs/` の doc だけを対象に読めていたのを、常時層も含むと明示した。

**二重化の害は「重い」ではなく「腐る」**。ある consumer で、環境にツールを入れる手順が doc 側では
実測で更新済みなのに常時層には失効した旧手順が残っていた。**古いほうが全タスクに読まれる側**に
残るので、コスト増より誤誘導のほうが実害が大きい。共通ブロックの棚卸しでも同じ形（常時層の側だけが
古い）が出ていて、これで2例目。

**トリガの位置で残す/移すを決めた**のは前回と同じ。「その doc を開くと決める前」に効くもの——
不可逆ガード（`〜と断らない`・`〜して終わらせない`）とポインタ——は圧縮に留め、手順の中身・識別子
（secret 名・テーブル名・外部サービスの ID・切替変数）は doc へ落とした。識別子は「読む人が決まって
いる」ので常時層に置く理由が無く、かつ最も腐りやすい。

## 2026-08-08 レビュー在庫の収集を投稿者非依存にする

**なぜ許可リストではなく「選別しない」にしたか**: 当初の想定は「レビュアーの login をもう1つ足す」だった。
成立しない。専用の bot login を持つレビュアーもいれば、**セッションのトークンの identity（＝オーナー本人の
login）で投稿されるレビュー**もあり、後者は人間のコメントや PR 作成者と区別が付かない（`get_me` で確認）。
許可リストは「足したつもりで落とし続ける」形になる。在庫の原則（未 resolve のスレッド1本＝誰も見ていない
欠陥1件）がもともと投稿者に依存していないので、選別そのものを外した。設計判断は配布 doc
`shared/docs/ops-sync-design.md`「レビューの取りこぼし対策」に置いた（履歴だけに残さない）。

**この変更だけでは目的を達しない**という発見: レビューを走らせても**既定では GitHub に何も残らない**
（結果はセッション内に返るだけ）。スレッドにならない指摘は resolve 状態を持てず、収集側をいくら広げても
在庫に入らない。収集の一般化と、投稿するという運用は**セットで初めて効く**ので、常時層に
「その場で直しきらない指摘はスレッドとして投稿する」（SHOULD）を同じ PR で入れた。

**改名で踏みかけた2つの罠**（どちらも「生成物は manifest 管理外・直接 push」という性質から来る）:

1. 旧名のファイルは改名しても消えない。manifest 差分で追随するのは配布ファイルだけで、この一覧は
   workflow が consumer の main へ直接 push している。→ スクリプトで旧名を削除し、**削除数も
   `files_changed` に数える**（数えないと「変化なし」で commit ステップごと飛び、旧ファイルが残る）。
   push 競合時の再適用は `cp` なので削除が再現しない。そこにも `rm -f` を置いた。
   `.ops-sync/` 丸ごとの同期（`rsync --delete` 等）にしなかったのは、取り直した main が持つ
   他セッションの更新（`sync-manifest.txt` 等）まで巻き戻すため。
2. 持ち越しの入力は「前回の全体一覧」なので、改名の初回は入力が空＝**窓の外の未 resolve が1回だけ全滅**
   する（「古くなったからではなく resolve されたから消える」が崩れる）。→ 新パスが無ければ旧名から読む。

**優先度バッジの扱いを変えた理由**: `P1`〜`P3` は特定のレビュアー固有の書式で、他の指摘には付かない。
既存の doc は「優先度の付かない提案は P3 と同じに扱う」と書いており、**2周目以降は P3 を着手しない**という
止める基準と組み合わさると、バッジの無い指摘（＝今後の大半）が自動的に切り捨てられる。収集を広げた意味が
消えるので、「バッジが無い指摘は内容を読んで自分で P1〜P3 を割り当ててから止める基準に入れる」に変えた。
止める基準の**決定可能性は保ったまま**、既定値だけを外した形。

**広げた入口には、広げた分の入力が入ってくる**（`/code-review 185 --fix` で釣れた）: 指摘の見出しを
拾う関数は、専用 bot の書式（必ず太字ヘッダで始まる）しか入らない前提で書かれていた。投稿者を
問わなくなった時点で「地の文に強調を含むだけ」の本文が入るようになり、太字を非アンカーで拾うと
*文中の強調*が見出しとして表に出る。**フィルタを外したら、そのフィルタが暗黙に保証していた入力の
形も一緒に外れる**——外す変更では、下流のパーサが何を前提にしていたかを数える。同種の穴が
`RI_REVIEWERS` にもあった（絞り込み時に author 不明のスレッドが落ち、「読めなかった」と「無い」を
区別しないという不変条件を絞り込み経路だけが破っていた）。

## 2026-08-08 review-threads doc の内部矛盾と 1依頼=1PR との衝突を解消

#182 で追加した `shared/docs/review-threads.md` を、#182 自身が足した検査（「ルールを足したら、既存の
要求といま出す diff の両方に当てて読み直す」）に改めて当てたところ、**満たせない要求が2件**残っていた。

- **手順5 の完了条件が同じステップの本文と矛盾していた**。本文は「マージ待ちは決着ではない／そこまで
  済ませずに終えるなら手順7の残件として報告する」と明示しているのに、完了条件は「残るのは手順6の
  代行依頼分だけ」と書いていた。手順2 の既定（未マージ PR に積む）を通ると**必ず**マージ待ちの
  スレッドが残るので、素直に読むと「完了条件を満たすために先に resolve する」——直前の MUST NOT
  （未マージのうちに resolve しない）を破る方向へ誘導する。完了条件側を2種類（マージ待ち・代行依頼）に
  直した。手順6 の完了条件も「未 resolve の各スレッド」だと同じ取り違えを招くので、権限で決着させ
  られなかった分に限定した。
- **手順2 の MUST が常時層「1依頼=1PR」の「例外はユーザーが明示した場合のみ」と正面から衝突していた**。
  消化依頼で 🟡（open PR）の指摘に当たると、片方は「同じ PR に積む（MUST）」、もう片方は
  「別の依頼で作ったブランチに積み足さない」になる。**どちらの文にも「のみ」相当の閉じ方があるので、
  doc 側に例外を書くだけでは常時層しか読まないエージェントに届かない**——常時層の例外を2つに広げ、
  doc 側にも「これは積み足しではなくその PR 自身の指摘を閉じる修正だ」と理由を書いた。

あわせて常時層のポインタ要約2項目に RFC 2119 キーワードが無かったのを補った（同じ箇条書きの1項目目
だけ MUST NOT が付いていたので、無キーワードの2項目は「説明であって要求ではない」と読める。
`sop-format.md` の前提そのもの）。よくある失敗の「クローズ済み PR」の項も、生成物 `codex-review-inbox`
側が「同じ問題が `main` にも当てはまるときは別途拾う」と案内しているのに doc 側が
「直す先が無い」で閉じていたため、拾う経路を書き足した。

**教訓**: 完了条件は本文と別に書くので、本文を直したときに**完了条件だけ古い前提のまま残る**。
数え上げ（「残るのは○○だけ」）を書いた箇所は、その数がステップ間で増減しうるかを疑う。

## 2026-08-08 レビュー往復を止める規約と常時層の棚卸し

「レビューと修正を延々繰り返している」という観察の原因調査から入り、**規約で塞げる分だけ**を入れた。
実測は直近の非 chore PR 12本中7本が「直前の PR の指摘・取りこぼしを直す PR」。連鎖の駆動力は3つに分かれ、
**それぞれ効く層が違う**ことが分かったのが今回の中心。

- **一般化が次の欠陥を生む**（規約で塞げる）。指摘は具体的な反例で来るのに、対象がルール文書だと
  「原則として書き直す」誘引が強い。広げた先に反転する例外があり、そこは検証されない。
- **止め時が定義されていない**（規約で塞げる）。LLM レビューは差分がある限り何か返すので、
  「全件を決着させる」だけを MUST にすると周回が進んだ低優先度の指摘まで同じ重みで PR 化される。
- **マージがレビューより速い**（規約では塞げない）。指摘はイベントの数分後に届き、即マージ運用では
  必ず後追いになる＝修正が構造的に別 PR になり、その PR がまた新しいレビュー対象になる。**これが
  最大の増幅器だが、マージはオーナーの操作なのでエージェント側の規約にはしなかった**。エージェント側に
  書けるのは「未マージなら同じ PR に畳む」までで、そこまでにした。

**止める基準を「回数」ではなく「優先度」に置いた**のは、回数の上限が実質機能しないため。「あと1周だけ」は
どの周回でも正当化でき、上限を書いても守る根拠にならない。優先度は指摘ごとに外から付いてくる値なので、
エージェントの自己申告が入らない。ただし **P1・P2 は周回によらず着手**にしてある（周回で重要度が下がる
わけではない。下がるのは「新しく出てくる指摘の質」のほう）。

**「対応しない」を放置と区別できる形にしておく必要があった**。既存の常時層は「二次意見だから後回しで
よい」を否定していたので、そのまま P3 の停止規則を足すと矛盾する。実際には既存規約にも「理由を返信して
resolve」という出口があり、これは決着であって後回しではない。常時層からは否定文のうち「後回しでよい」を
落とし、doc 側に「これは後回しではない・判断せずに開いたまま終えることだけが禁止」と明記して繋いだ。

**自分で足したルールを自分の diff に当てたら、実際に2件出た**。①「修正は指摘された範囲に閉じる」と
既存の「主張を変えたら述べている箇所を全部数えて直す」は、そのままでは正面から衝突する（1箇所だけ直すと
新旧併存になる）。範囲の定義を**「同じ誤りの取りこぼし解消」と「規則を新しい対象へ拡大」に割った**ことで
両立した。②「決着は3状態」と数えていたが、3つ目（未マージのうちは resolve しない）は決着ではなく
**タイミングの制約**で、そのまま読むと「マージ待ち＝決着済み」でセッションを終えられてしまう。決着を2状態に
し、resolve のタイミングを別の MUST NOT に分けた。**②は今回の圧縮が作った欠陥ではなく、1週間前にこの節へ
箇条書きを足したときから居座っていたもの**——種類の違うものを1つの数え上げに混ぜても、節ごと書き直すまで
誰も数え直さないので、そのあいだ全 consumer に配られ続ける。だから「同じ数え上げに種類の違うものを
混ぜていないか」は、短くするときだけでなく **MUST の箇条書きを足す/並べ替えるとき**にも見る。この検査を
規約として足した当の PR で2件釣れた（うち1件は既存の在庫）ので、検査自体の費用対効果は確認できた形。

**常時層の棚卸しでは、削れたのは「配布 doc と重複している詳細」だった**。gha-trigger-ui 節は判定規則の
全文が配布 doc 側にもあり、しかも**常時層の側だけが古い**（月枠の消費と直接課金の区別が入っていない）
状態だった——二重化は放っておくと必ず片側が腐る、が実物で出た。逆に、レビュー節・外部 URL 報告節のように
**発火トリガが「完了報告の直前」「指摘に対応する瞬間」にあるもの**は、doc に落とすと開かれないので
不可逆ガードだけ常時層に残した。判断軸は文量ではなく「**どのタイミングで読まれる必要があるか**」。

結果は 27,565 → 26,878 バイト（-687）。新規ルールを足したうえで純減にできたが、**削減の主因は棚卸しでは
なく重複の解消**なので、次に同じことをやるなら「配布 doc がある節の本文が doc と重複していないか」から
見るのが早い。

## 2026-08-08 履歴に溜まった再利用可能な知見を doc へ移す（過去分の洗い出し）

`task-history.md` 手順3（「今後は〜する」と読める文は履歴ではなく doc へ）を**過去の履歴に遡って適用**した
棚卸し。全リポジトリの `AI_TASK_HISTORY.md`・`history-archive/`・`history-inbox/`（4リポジトリ・約 430 エントリ）を
読み、教訓として書かれていた文をひとつずつ「該当 doc に既にあるか」で振り分けた。

**判断の基準**（次に同じ棚卸しをするとき用）: 「履歴にしか無い」だけでは移す理由にならない。移すのは
**次に同じ状況に入る人が、その doc を開く導線を持っている**ものだけ。導線が無い知見は doc を新設するより
先に「どのトリガで読まれるか」を決める必要があり、決まらないなら移しても読まれない（履歴と同じ）。

**大半は移す必要が無かった**。教訓が書かれたエントリの多くは、その作業自体が doc の改訂だった（＝既に
正本に入っている）か、一度きりの実装判断だった。移したのは**別々の作業で繰り返し踏まれている**もの——
同じ失敗が複数エントリ・複数リポジトリに現れていて、それでも doc に無かった7件に絞った。繰り返し回数を
選別の基準にしたのは、1回しか起きていない教訓は「次も起きる」の根拠が弱く、常時層・配布 doc の
コストに見合わないため。

**常時層（`AGENTS_COMMON.md`）に入れたもの**は、発火トリガが「doc を開こうと決める前」にあるものだけ:
主張を変えるときの全箇所洗い出し（doc 編集中に発火）・推測の断定禁止（完了報告の直前）・基点の鮮度
（push の直前）・incidents の宿題の引用（doc を読むとき）・2実装の突き合わせ。オンデマンド doc に置くと
「開かない人」には届かない種類のもので、逆に手順の詳細は入れていない。+931 文字（自動マージの目安 800 を
超えるが、これは7件を1回で入れたため。1件あたりは 100〜300 文字）。

**オンデマンド doc に入れたもの**は、既にトリガを持つ doc へ足した: SOP の対象を広げたときの導線追随
（`sop-format.md`）・外部 API エラーの残し方と slice の鮮度確認（`ci-logs.md`）・定期実行の頻度と時刻
（`actions-quota.md`）。最後の1件は doc の対象そのものを広げたので、**同じ PR で `AGENTS_COMMON.md` の
トリガ1行と skill の `description` も広げた**——ちょうど今回入れた「対象を広げたら導線も広げる」の
1件目の適用になる。

**この棚卸しで見えた構造**: 履歴に教訓が溜まるのは書き手の不注意ではなく、**教訓が生まれる瞬間と、それが
要る瞬間が別のタスクにある**ため。書いている本人にとっては「今の作業のなぜ」なので履歴が自然な置き場に
見える。だから「履歴に書くな」より「**どのトリガで読まれるか**を決めてから置く」のほうが実行しやすい。

**レビュー指摘の反映（同 PR 内の追記）**: 6件を直した。以下は次の棚卸しでも効く形。

- **移す判断（導線があるか）と、移す中身の真偽は別の検査**。今回 `ci-logs.md` に、実測で再現しなかった
  「掃除でブランチを作り直す」を*背景説明として*書いてしまっていた。PR 本文には「再現しなかった」と
  自分で書いてあるのに、である。履歴由来の文は「その doc に置くべきか」で読むうちに、**書いてある事実
  そのものを疑う目線が抜ける**。移す前に、機序を主張している箇所は正本（ここでは
  `publish-ci-logs/action.yml`。`--orphan` はブランチ未作成時のみ）で裏を取る。
- **ルールを足したら、逆のことを言っている古い記述を同じ PR で消す**。`AGENTS.md` の「改名は消すだけで
  よい」を残したまま 40 行下に追加手順を足していた。読む人は先に出てくるほうで判断を終えるので、
  後ろの新ルールには到達しない——今回 `AGENTS_COMMON.md` に入れた「主張を変えたら述べている箇所を全部
  直す」の対象そのもの。**自分が今 PR で足したルールを、その PR の diff 自身に適用して読み直す**。
- **「唯一」「〜しか」は数え上げの節と両立しない**。「3箇所を数える」節の中で各項を「唯一の経路」と
  書くと、どれか1つを読んだ人に他を飛ばす license を与える。数え上げる節では各項を「**誰にとっての
  導線か**」で書き分ける。

## 2026-08-08 引き継ぎ手順のレビュー指摘を反映（在庫の抜け・closed の行き止まり）

引き継ぎ規約を入れた PR のレビューで5件。うち2件は設計の土台に関わるもので、指摘の根拠を
実装で確かめたうえで採用した。

**在庫の抜け（最も重い）**: `codex-review-inbox.mjs` は `!pr.merged && pr.state === 'CLOSED'` を
在庫から外す。header に書かれた前提は「その変更は `main` に入っていない」だが、**引き継ぎは
まさにこの前提を破る**——手順は元ブランチ*から*分岐するので、レビュー済みのコミットは新ブランチ
経由で `main` に入る。外れた指摘は「⚪ 対象外」注記へ回り、そこは持ち越しの対象外なので
`CRI_LOOKBACK_DAYS`（既定3日）を過ぎると消える。つまり引き継ぎが**レビュー済みの欠陥を静かに
消して配布する**経路になっていた。スクリプト側で「closed だが head が main に入っている」を
判定する案は取らず（判定が高価で不安定）、手順側で未 resolve スレッドの URL を後継 PR 本文へ
引き写す MUST にした。

**土台の主張が成り立っていなかった**: 「元 PR を close すれば既存の無条件確認が closed を拾って
止める」を層1の中心に据えたが、その無条件確認が closed に対して指示しているのは
「最新の `main` から新ブランチを切り直す」＝**作業を続けろ**だった。止まる振る舞いはオンデマンド
doc 側にしか無く、しかも「自分の PR がたまたま closed だった」エージェントにはその doc の
発火トリガが1つも当たらない＝永久に開かれない。常時層の側に「クローズ済みは切り直す前に close
コメントを読む」を足して繋いだ。**既存ルールに寄りかかる設計は、寄りかかる先の文面を読んで
確かめないと成立しない**（今回は「拾って止まるはず」という思い込みで書いていた）。

残る3件は手順の穴（step 4 の完了条件が誰も満たさない往復・未 push で `FETCH_HEAD` が古い値の
まま分岐しうる・closed 枝が行き先未定義）で、いずれも分岐と MUST を足して閉じた。

**ついでに直したもの**: `sop-format.md` の skill ミラー一覧が5パス・「4パス」表記のままだったが、
`apply-shared.mjs` の `SKILL_MIRROR_ROOTS` は6ミラー＝計7パス（`.qwen`・`.cline` が後から追加された）。
配布テストの出力が7パスだったので実測で確定し、その場で直した。

## 2026-08-08 引き継ぎ元の規律（早期PR＋PR本文を作業ログに）

引き継ぎ手順の受け側（分岐＋元 PR close）を入れたあと、元スレッド側の規律が
「復活したあとの反応」しか無いことが残っていた。オーナーの指摘は
**「PR が存在せず、そもそも引き継ぎようがない例を何度も見ている」**——つまり実際に効いている
失敗は情報の質ではなく**引き継ぐ対象の不在**なので、規律の中心を「早く push して PR を開く」に置いた。

**トリガ型の手順にはできない**。枠切れは予告なく来るので「切れそうになったら残す」は書けず、
常時の規律にするしかない。常時層のコストに乗るが、対象が存在しなければ他の工夫が全部無効になるので
ここは払う判断をした。

**「なぜ」をタスク履歴だけに頼らせない**のが2点目。履歴の記録は「作業完了時の必須手順」なので、
**途中で止まったセッションでは走らない**——引き継ぎが要る場面でだけ判断根拠が残らない、という
構造的な抜けになっていた。PR 本文を作業ログの正本にすれば、PR は早期に存在するので抜けが埋まり、
かつ状態ポインタ・残作業・不可逆操作の記録を1箇所に集約できる（正本を増やさない）。

**実行済みの不可逆な外向き操作を書かせる**のが3点目。引き継ぐ側にはデプロイ・dispatch 済みかを
知る手段が無く、二度実行すると枠を食う。

残作業を別ファイルに切り出す形は過去に2回実践されている（cold start でもパス1つで追える利点がある）
ので禁止せず MAY に留めたが、PR 本文からパスを指すことと、完了 PR で削除することを MUST にした。
消し忘れると「現在形で書く」に反する古い残作業リストが残るため。

**draft PR は規定しなかった**。作業中の PR に Codex のレビューが付くと未 resolve 在庫が増える懸念は
あるが、このリポジトリの直近40 PR に draft は0件で前例が無く、Codex が draft を飛ばすかを実測できて
いない。推測で規約に書かず、未確認事項としてオーナーに報告するに留めた。

## 2026-08-08 引き継ぎ手順（分岐＋元PR close）を共通化

枠切れで止まったセッションの続きを別セッションが引き継ぐとき、元スレッドが枠復活や PR 購読の
webhook で後から動いて成果を壊す経路があった。最初に検討したのは lease ファイル（所有者・世代を
リポジトリに置き、pre-push で所有者違いを弾く）だが、**この環境では原理的に作れない**と判断した:
`merged-branch-guard.md` に記録済みの壁がそのまま効く——ハーネスが未 push ブランチにも
remote-tracking ref を seed し、git ミラーは今セッションで push したブランチを `ls-remote`/`fetch` で
返さず、shell から GitHub API も叩けない（プロキシが MCP 以外を遮断）。つまりフック内で
「リモートの現在の所有者」を知る手段が無い。今回の実測でも、前セッションのブランチは `ls-remote` で
返るが今セッションのものは返らない、という非対称が再現した（＝引き継ぐ側からの取得は可能なので、
分岐の手順自体は成立する）。

そこで方針を「元スレッドを止める」から「元スレッドが動いても壊せない」へ倒し、**元ブランチに乗らず
分岐し、元 PR を close する**を手順の中心にした。close を選んだのは効き方が2つあるため:
(1) 既存の「push 前に `merged`/`state` を無条件確認」が closed をそのまま拾うので、引き継ぎ専用の
新しいガードを足さずに済む（規約の重複を作らない）。(2) PR 購読の webhook が枯れる——購読は
セッション単位で引き継いだ側から解除できないので、人が見ていないところで元スレッドが起きる
主経路を塞ぐ手段がこれしかない。

元ブランチを force-push で乗っ取る案は捨てた。元スレッドの push は弾けるが、未 push の成果を
失わせるうえ、復活した元スレッドからは「壊れた」としか見えず状況を復元できない。分岐なら両方の
履歴が残り、後から選べる。

検知層（同一タスクを指す open PR の重複を CI で赤くする等）は今回入れていない。まだ観測していない
事象のために常設コストを払うことになるため、実際に二重作業が起きてから足す。

## 2026-08-08 アーカイブ棚卸しの取りこぼし（裸の #番号）を落とす

前回の棚卸しは **consumer 名が隣接している形**（`nikki-san#NNN` / `private #NNN`）しか拾えておらず、
`docs/history-archive/2026.md` に **19 行** 取りこぼしていた。落ちていたのは3パターン:

- **裸の `#NNN`**（consumer 名が付いていない後方参照）。最悪なのは、前回の修正で名前側だけ伏せた結果、
  同じ節の数行下に `#<番号>/#<番号>` が残り、**伏せた名前と残った番号が並んで対応が読める**状態に

- **見出し**（`（Codex #<番号>/#<番号>）`）。本文だけ見て直すと落ちる。見出しは TOC・コード検索に最も露出する。
- **名前と番号の間に語が挟まる形**（`nikki-san PR #<番号>`・`private の同期 PR（#<番号>）`）。

教訓: **「consumer 名 + 番号」を探す検索では足りない**。public リポジトリで棚卸しするときは
「**ops-sync 自身の PR 番号の範囲を超える `#NNN` を全部挙げる**」側から攻める（番号の大小は
リポジトリをまたいで一意なので、名前が無くても機械的に絞れる）。前回のエントリが
「36 箇所を落とした」と完了形で残っていたため、次のセッションが再走査をスキップしかねなかった。

削除は今回も公開の取り消しではない（git 履歴・PR 記録に原文は残る）。効くのは HEAD とコード検索まで。

## 2026-08-07 配布の判定が CI で効いていなかった穴を塞ぐ

`apply-common.mjs` のマーカー検査は「壊れていたら黙って直さず失敗させる」設計だが、**その失敗が
CI で握り潰されていた**。`sync.yml` の3ステップが `... | tee /tmp/ci-logs/*.log` で、`run:` の
既定シェルが `bash -e {0}`——`shell: bash` を明記したときだけ `-eo pipefail` が付く——なので、
パイプの終了コードは tee の 0 になる。実測でも `bash -e -c 'false | tee /dev/null'` は rc=0。

結果、旧マーカーが残った consumer でも判定は素通りし、同期 PR が作られて direct マージまで進む。
**判定を厳しくする作業を重ねても、判定が読まれていなければ意味が無い**。`apply-shared.mjs` は
削除の伝播を含むので、途中失敗の部分適用がそのままマージされる分もっと悪い。3ステップとも
複数行 `run` にして `set -euo pipefail` を置いた。

**回帰テストを走らせる CI も無かった**（`grep -rn 'node --test' .github/` が 0 件）。テストを
足しても、次に判定を触る人がどちらかへ倒したときに気づける保証が無い。`prepare` ジョブに
`node --test` を置いた。`sync` は `needs: prepare` なので、落ちれば全 consumer への配布が止まる。

**これは PR のゲートではない**。このリポジトリに `pull_request` 起点の CI は無く、`sync.yml` は
main への push・cron・手動でしか走らない。止められるのはマージではなく**配布**（＋cron の
ドリフト自己修復）。`node --test` は `scripts/*.test.mjs` を全部走らせるので、配布に関係しない
スクリプトのテストが落ちても配布は止まる——「赤い main では配らない」が意図。

**現行マーカーの重複判定は緩めなかった**。旧マーカー側と同じ誤検知（本文に丸ごと引用すると
`ne=2` になり配布が止まる）は現行側にもあるが、区間の切り出し `findRegion` が `indexOf` で
位置を決める以上、引用と実マーカーを区別できない。緩めると引用の側を境界に選んで**本文を
削りうる**——誤検知して人に掃除させるより悪い側へ倒れる。代わりにエラー文へ「引用も数える」
と書き、人が引用を崩して再実行できるようにした。**両側を同じ形に揃えるのが常に正しいわけでは
ない**という判断の記録。

## 2026-08-07 統合の空エントリ警告を復元可能にし、規約 doc と同期させる

空エントリを落とすガードのレビューで3点。

**警告に見出し行を載せる**。落とすブロックがあっても他に有効エントリが1つでもあればフラグメントは
削除されるので、警告に見出しが無いと**落とした内容を後から復元できない**。ログの出力先は対象
リポジトリ自身の ci-logs（既にフラグメント名を含む＝機微の扱いは同じ）なので、見出しを載せてよい。
「黙って捨てない」を主張するなら、捨てた物の識別子まで渡さないと主張が成立しない。

**0件時の skip 理由を実態に合わせる**。全ブロックが空だと従来の「日付付き `## YYYY-MM-DD` エントリが
無い」経路に合流するが、この文言は**嘘**になる（見出しは正しい形で存在する）。読んだ人はファイルを
開いて正しい見出しを見つけ、バッチ側の不具合だと誤読する。落とした件数を持ち回って理由を出し分けた。

**規約 doc を同時に直す**。`shared/docs/task-history.md` と `README.md` は統合の例外として dedup しか
書いておらず、「空見出しは取り込まない」「取り込めるエントリが0件のフラグメントは削除もしない」が
抜けていた。後者は挙動として重い——書きかけのフラグメントが inbox に**残り続ける**ので、doc に
書かないとエージェントは統合されない理由に辿り着けない。「よくある失敗」にも見出し二重書きを足した。

## 2026-08-07 アーカイブから private consumer の PR 番号を落とす

public リポジトリに private consumer の PR 番号が残っていないかを、追跡ファイル全体に対して
実際に検索した。AGENTS.md「private consumer の内部をこのリポジトリに書かない」の規約は
書く側の作法として整えてあったが、**既に書かれたものを一度も棚卸ししていなかった**。
結果、`docs/history-archive/2026.md` に 36 箇所（26 行・27 種）残っていた。

在庫が1ファイルに集中していたのは偶然ではない。履歴フラグメントは統合バッチで本体へ、
本体からアーカイブへ流れるので、**規約を破った記述は必ずアーカイブに沈む**。フラグメント
段階のレビューを通り抜けたものが、そこで止まらずに溜まっていく構造だった。

落としたのは PR 番号だけで、consumer 名は残した（`consumers.txt` で公開済みなので規約の
対象外）。日本語が壊れる4箇所——見出し末尾の括弧・`（private #<番号> P2）` のような優先度との
併記——だけ手で書き換え、残りは機械的に番号を削っている。`ops-runner` は public なので
番号をそのまま残した。

**この削除は公開の取り消しにならない**。git 履歴・PR の diff・コミットメッセージには
原文が残る（コミットメッセージ側は消せない。マージ済み PR の記録も同様）。効くのは
「HEAD が公開され続ける・コード検索に載り続ける」のを止めるところまで。**書く前に止める
以外に対処が無い**ことの裏付けとして残す。

## 2026-08-07 旧マーカー検出をコメント構文まで一致させる

`apply-common.mjs` は旧マーカー（`AI-OPS:COMMON`）を**素の部分文字列**で数えて、1つでもあれば
同期を失敗させていた。旧マーカーの自動移行をやめた以上、実物が残っていたら止めるのは正しい
——が、判定が広すぎた。`AGENTS.md` の本文に「旧マーカーは使うな」と**書いただけ**で同じ判定に
かかり、その consumer への配布が止まる。しかも `apply-common.mjs` は全 consumer に対して回る
ので、「マーカーの掃除を促す注意書き」を1つ書いた副作用で配布そのものが落ちる。

判定を `<!-- AI-OPS:COMMON START|END … -->` の骨格を見る正規表現にした。START 側の説明文は
consumer ごとに揺れうるので、そこは `[^>]*` で吸収して**コメントであることと START/END の別**
だけを見る。バッククォートで囲んだ言及・散文中の言及は当たらない。

同時に `shared/docs/ops-sync-design.md` の記述も直した。実装が旧マーカーを一切受け付けなく
なったのに、配布 doc 側は「**新旧どちらか一方**の組が1組なら健全」のままだった。この doc は
consumer に配られるので、読んだ人は移行が走ると期待して、実際にはエラーで止まる。**仕組みを
変えたら同じ PR で配布 doc も直す**（AGENTS.md「完了手順」）を踏み外していた。

回帰テスト `scripts/apply-common.test.mjs` を新設した。「実物の旧マーカーは弾く」と「言及だけは
通す」を対で置いてある——片方だけだと、次に判定を触る人がどちらかへ倒しても気づけない。

## 2026-08-07 統合で空エントリを本体に入れない

フラグメントに見出しが2本あると（生成した見出しの後ろに手で同じ見出しを書く等）、1本目が
「見出しだけ・本文なし」のブロックになり、統合でそれが**本体やアーカイブに恒久的に残る**。
統合件数も水増しされる。実際に起きた。

**入力の作法違反だが、直す先はスクリプト**という判断。フラグメントは人とエージェントが書く場所で、
規約（1エントリ＝1ファイル）を破る書き方はこれからも起きる。恒久履歴に壊れたレコードを入れる
のは復旧が面倒（後から見分けが付かない）なので、**受け側で落として警告する**方が安い。

落とすのは「日付付き見出しだが本文が空」のブロックだけ。残りの正当なエントリは取り込み、
フラグメントも通常どおり消費する（全部が空なら従来どおり「エントリが無い」として消さずに残す）。
