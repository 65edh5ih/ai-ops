## 2026-08-05 列の撤去に inbound FK の事前確認を足す

スキーマ撤去 SOP の事前確認が、対象テーブル自身の DDL とビュー/トリガしか見ておらず、**他テーブルから
対象列への外部キー参照（inbound FK）**を取りこぼしていた（`CREATE TABLE child(x REFERENCES parent(old_col))`）。

**実測で挙動を確認した（SQLite 3.45.1）**。ここは他の阻害要因と性質が違う:

- inbound FK がある列でも、`PRAGMA foreign_keys` が ON でも OFF でも **DROP COLUMN は成功する**
- 子の DDL は `REFERENCES parent(old_col)` のまま残る（宙に浮く）
- 破綻はその場では出ず、**後から子テーブルへの INSERT が `foreign key mismatch` で失敗する**
- `PRAGMA foreign_key_check` を流しても、行が返るのではなく**同じエラーで落ちる**（後から気づく手段も塞がる）

索引・PK・UNIQUE・生成列・CHECK・ビュー/トリガは DDL 実行時にその場で拒否されるので「やってみれば分かる」が、
inbound FK だけは**事前に見るしかない**。この非対称性が、SOP に検出クエリを明記する価値そのもの。

検出は `pragma_foreign_key_list` の表値関数を `sqlite_master` と join して、対象テーブルを参照している
子テーブルを列挙する形にした（クエリも実際に流して確認済み）。`"to"` が NULL の行は**親の PK を暗黙参照**
しているだけなので、PK でない列を消すぶんには無関係——この読み分けも書いた（書かないと偽陽性で詰まる）。

**気づいた経路**: ops-sync 本体の PR ではなく、**マージ後の consumer 同期 PR に付いたレビュー**で出た。
ops-sync の AGENTS.md が「配布変更を出したらマージ後に consumer 同期 PR も確認する」と要求している
とおりの事例で、本体 PR だけ見て終わっていたら配布済みの欠陥が全 consumer に残っていた。

## 2026-08-05 D1 撤去手順にテーブル版と網羅的な事前確認を足す

前 PR でスキーマ撤去の節を足したが、レビューで2つの欠陥が出た。どちらも「書いた前提と手順が食い違う」型。

**(1) 見出し・トリガは「列・テーブル」なのに手順が列専用だった**。`DROP COLUMN`・`pragma_table_info` しか
書いておらず、テーブルを消す人は**存在しない手順に案内される**。テーブル版を足した。要点は列と非対称で、
`DROP TABLE` は**依存ビューを道連れにしない**（その場は成功し、後からそのビューを使う経路が壊れる＝作業とは
別のタイミングで顕在化するので原因に辿り着きにくい）。逆に FK 参照があると失敗しうる。検算も
`sqlite_master` で「テーブルが消えた」と「壊れた依存が残っていない」の両方を見る形にした。

**(2) 阻害要因を列挙したのに事前確認が索引しか見ていなかった**。インライン宣言の PK/UNIQUE/CHECK・生成列・FK は
**テーブル自身の DDL 文にしか現れず**、ビュー・トリガは別オブジェクトなので、索引を見ても引っかからない。
索引だけ確認して通すと本番 DDL がその場で拒否される。テーブル自身の `sql` と、列名に言及する
ビュー/トリガの2本を読む形にした。`LIKE` の粗い網なのは、取りこぼし（偽陰性）より偽陽性に倒すため
——偽陽性は定義を読めば捨てられるが、偽陰性は本番で初めて分かる。

**教訓**: 手順 doc で対象範囲を広く書く（「列・テーブル」）なら、広げた分の手順を必ず同時に書く。
トリガだけ広げると、案内された先に手順が無いという最悪の形になる。

**追記（同 PR のレビューで出た3件目）**: テーブル版の検算に `sql LIKE '%<table>%'` の件数を使い、
`dangling_refs` が 0 を完了条件にしていたが、これは**満たせないゲート**だった（`log` を消したあとに
無関係な `login_events` が引っかかる）。**探すときは広く・判定するときは完全一致**が正しい切り分けで、
事前確認（人が読んで分類する）に粗い網を使うのはよいが、同じ網を機械的なゲートに流用してはいけない。
ゲートは「手順2で洗い出した具体的なオブジェクト名」に紐づける形に変えた。満たせないゲートは
やがて誰も見なくなる（形骸化する）ぶん、無いより悪い——この失敗自体を「よくある失敗」に追記した。

**在庫から拾った既存指摘（別 PR・マージ済みで未 resolve だったもの）**: 「稼働中バージョンのバインディングを
確認する」手順が `wrangler deployments status` を挙げていたが、**このコマンドはデプロイ一覧と version ID を
出すだけでバインディングを報告しない**。エージェントは確認手段があるのに「示せない」と詰まる。正しくは
2段階（`wrangler deployments status` で active version ID → `wrangler versions view <version-id>` で bindings）。
同じ doc を触っている PR だったのでここで直した。**この欠陥は実際に効いた**——同じセッションでこの手順を
実行しようとして稼働中バインディングを直接引けず、間接証拠（アカウント内の D1 が3個で同名系が無い・当該
テーブルを書くのはその Worker だけ）で代用する羽目になっている。撤去手順側でも同じコマンドを
「稼働中コードの確認」に挙げてしまっていたので、そちらは「スクリプトの中身を取得して grep する」に正した
（デプロイ一覧はバージョンが進んだことしか示さず、中身を見せない）。

## 2026-08-05 d1-capacity.md を d1-operations.md に改名しスキーマ撤去手順を追加

ある consumer で、役目を終えた一度きりの移行機能を撤去し、その機能だけが使っていた D1 の列も消す作業が
あった。そこで判明したことを共通 doc に上げる。

**発見（コードを読んでも分からない類）**: Worker が持つ**冪等なスキーマ ensure**（`ALTER TABLE ... ADD COLUMN`
を毎ティック流して失敗を握りつぶす実装）が生きている間に列を消すと、**次の実行が黙って作り直す**。
cron 駆動なら数十秒で戻るので「消したつもり」になる。したがって撤去は「コードの撤去を本番へデプロイし、
**稼働中のコードそのもの**に参照が無いことを確かめてから」の順序が要る。「PR がマージされた」では不足で、
マージとデプロイは別物（デプロイが別 workflow・別経路のこともある）。合わせて、SQLite が索引・PK・UNIQUE 等に
関与する列を DROP できない点も、事前確認の手順として書いた。

**改名した理由**: この doc は既に「本番データの直接確認」という容量と無関係の節を持っていて、`d1-capacity`
という名前が実態からずれていた。そこにスキーマ撤去が加わると乖離が決定的になるので、`d1-operations.md` に
改める（扱うのは容量・本番確認・スキーマ撤去の3つ）。**節を分けて別 doc にはしない**——分けると常時ロード層に
発火トリガが2つ要り、全タスクのコストが増える。「本番の D1 に対して何をしてよいか」という同じ判断軸なので
1 doc に置き、トリガも1つに保つ。

**改名の伝播**: `shared/docs/` と `shared/.claude/skills/` の rename だけでよい（manifest 差分で consumer から
旧パスが消え、skill のミラー4種は配布時に導出される）。`sync-deletions.txt` は manifest 導入前の unmanaged
ファイル用なので今回は不要。ただし**consumer のローカル doc・コード内コメントが旧パスを参照している場合は
そちらは自動では直らない**ので、consumer 側で別途直す必要がある（今回の作業元 consumer では追随の PR を出した）。

**読み取り専用ルールとの関係**: 既存の「本番データの直接確認」は読み取り専用を MUST としているが、撤去そのものは
DDL なので例外になる。無条件に許すと本番スキーマをエージェントの判断で変えられてしまうため、
**ユーザーの明示依頼があるときだけ**という条件を明記した。撤去のためにアプリ側へ一時的な移行経路を足すのは
本末転倒（撤去したはずの残骸を新たに増やす）なので、直接 DDL を認める側に倒している。

## 2026-08-03 リネーム移行の後方互換分岐を撤去

`ai-ops` → `ops-sync` の移行用に入れた LEGACY 分岐を撤去した。撤去条件（**全 consumer から `.ai-ops/` と
旧マーカーが消えたら**）は nikki-san / private / ops-runner の3リポジトリとも満たしている。

- `apply-shared.mjs`: `LEGACY_MANIFEST`、削除判定の新旧 manifest 和、旧 manifest の明示削除。
- `collect-outbox.mjs`: 新旧 outbox の二重走査と提案ごとの `outboxDir` 追跡。差し戻し先も固定へ。
- `apply-common.mjs`: `findRegion()` の旧マーカー分岐（＝移行そのもの）。

### `apply-common.mjs` だけは「検出」を残した

撤去条件を書いた時点では存在しなかった `markerProblems()`（マーカー健全性の全数検査）が、後から
旧マーカー定数の上に作られていた。**移行分岐と検出を一緒に消すと退行する**: 旧マーカーだけの
AGENTS.md が来たとき、変換されず・検出もされず・追記フォールバックへ落ちて**共通ブロックが二重に載る**。
黙って壊れる経路なので、旧マーカーは「もう変換しないが、あったらエラーで止める」に変えた。

**撤去条件のコメントは、書いた時点の実装を前提にしている。** 後から別の依存が生えていないかを、
消す前に実際のコードで確認する必要がある（今回は grep で `LEGACY_*` の使用箇所を数えて気づいた）。

### 撤去後に4ケースで実駆動

配布済み nikki-san の実物 AGENTS.md（正常に更新・マーカー1個）、旧マーカーのみ（**exit 1 で停止し、
ファイルは不変＝二重化しない**）、マーカー皆無（初回配線として追記）、現行マーカー重複（exit 1）。
`apply-shared` は実物に対して**削除0件**・2回目 no-op。

### ブランチを切り直した

作業中、ローカルのブランチが古い `main` を基点にしていることに気づいた。その間に main では
`collect-outbox.mjs` が8回・`apply-common.mjs` が1回変更されており、**そのまま PR にすると他セッションの
作業を巻き戻すところだった**。最新 main から切り直して撤去をやり直した。

きっかけは `origin/main` の直近コミットが見慣れない題材だったこと。**他セッションが並行で動く前提では、
push 前に「自分の基点が origin/main の先端か」「触るファイルが基点以降に変更されていないか」を見る**
（`git merge-base` と `git log <base>..origin/main -- <path>`）。

## 2026-08-03 collect-outbox の ci-logs スライスを全件削除

ユーザー依頼で、collect-outbox の CI ログを `latest`・`history` とも全件消した。対象は ops-sync の
公開ロールアップと、詳細ログが出ていた consumer 1件の `ci-logs`（残りの consumer にはスライス自体が
無かった）。**7日 retention を待たずに history が欠けているのは事故ではない**——次のセッションが
「history が欠けている」と調査を始めないようにここに残す。

ci-logs はブランチの先頭を書き換えるだけなので、**ファイルを消しても内容は git 履歴に残る**（public な
ops-sync では削除が削除にならない）。そのため ops-sync 側は先頭からの削除に加えて**ブランチを orphan で
作り直した**（現行ファイルはそのまま・過去のコミットを切り離す）。他の slice の履歴も一緒に失う操作
なので、ci-logs には現在値だけ置く運用（`docs/ci-logs.md`）が前提になっている。到達不能コミットは
しばらく SHA 指定で参照できるため、完全な消去には GitHub サポートが要る点も変わらない。
consumer 側は private なので、作り直しはしていない（先頭からの削除のみ）。

再生成のされ方は**公開ロールアップと詳細ログで違う**。ロールアップは `if: always()` で毎 run 出るので
6時間ごとの cron の次回 run で `latest` が戻るが、詳細ログは `steps.collect.outputs.consumer != ''`
（＝提案を持つ consumer を実際に処理した run）でしか publish されない。提案が無い run・別の consumer を
処理した run では戻らないので、consumer 側の `latest` が数日空くのは正常。恒久的に残したくないなら
slice を消すのではなく publish 側（`.github/workflows/collect-outbox.yml`）を変える必要がある。

## 2026-08-03 課金判定は全ジョブ・matrix 展開後まで見る

指摘の範囲を読み違えて**部分的にしか直さなかった**分の追加。元の指摘は「全ジョブ、reusable workflow、
matrix 展開後の `runs-on` まで辿る」で、こちらが足したのは `workflow_call` の分だけだった。resolve すると
返信した後に範囲不足に気づいたので、訂正を投稿して残りを別 PR にしている。**指摘の要求範囲を数えてから
直す**（要素が3つ並んでいたら3つとも潰す）。

内容として要るのは次の2点:

- **run で走りうる全ジョブを見る**。1ジョブだけ見て「無料」と判断できない——1つでもコストを伴うジョブが
  あればその run にはコストがある。
- **`matrix` で `runs-on` を組み立てている場合は展開後の値**を見る。式のままでは判定できず、入口の
  ジョブ定義を読んだだけでは larger runner が混ざっていても気づけない。

印の文言（月枠を消費する／実行のたびに課金される）はこの判定の結果で決まるので、**見る場所を間違えると
文言が逆になる**。ここが「読めば分かる」ではなく手順として書く価値のある所。

## 2026-08-03 課金判定は呼ばれる workflow まで辿る

`runs-on` を読め、と書いたが**入口の workflow だけ**を見る形になっていた。`workflow_call` で別の
workflow を呼んでいると、実際に走るジョブの `runs-on` は呼ばれた側にあるので、入口が無料の標準ランナー
でも呼び先が larger runner なら課金される。**印の文言を決める判断が、見ている場所のせいで逆になる**。

この repo 群では `workflow_call` の多段呼び出しが実際に使われている（デプロイを他のフローの一段として
呼ぶ）ので、入口だけ見る運用は現実に踏む。

## 2026-08-03 public repo に private の識別子を書かない範囲を広げる

配布 doc → タスク履歴 → **コミットメッセージ**と、同じ識別子が3回連続で public 側に残った。1回目は
doc、2回目は「doc から履歴へ移せば隠れる」という誤解、3回目は PR 本文がそのままコミットメッセージに
なる経路。**塞いだつもりの穴が別の出口から出ていた**ので、規約の対象を「doc」ではなく
「public な履歴として残るものすべて（doc・履歴フラグメント・コミットメッセージ・PR タイトル/本文）」
に広げて AGENTS.md に書いた。

判断軸は「どの層に書くか」ではなく**そのリポジトリが public か**。ops-sync では consumer 名
（`consumers.txt` で公開済み）を超える情報を書かない。

もう1件、**doc に「実装が無い」と断定して事実と食い違った**件も直した。ある consumer には
`decision.json` を読んで経路を自動で切り替える実装が既にあり、「読み手はまだ無い」という記述は
**その consumer の運用者に「`auto` にしても何も起きない」と誤解させる**（実際は本番の経路が人手なしで
変わる）。**consumer ごとに違いうるものを配布 doc で断定しない**——「実装しているかは consumer ごとに
違う。`auto` を選ぶ前に自分のリポジトリの実装を確認する」と書くのが正しい形だった。元の記述は
別の consumer で「未実装なのに現行構成のように読める」という逆向きの指摘に応えて足したもので、
**片方の consumer だけを見て一般化した**のが原因。

## 2026-08-03 public な ops-sync に private consumer の PR 詳細を書かない

配布 doc から「実例（PR 番号入りの年代記）」を外して**タスク履歴へ移した**が、**移した先の
`docs/history-inbox/` も public な ops-sync**なので、private consumer のリポジトリ名・PR 番号・
レビューの有無・欠陥が入っていた期間がそのまま世界公開に残っていた。同期 PR のレビューで判明。

**「doc から履歴へ移す」は秘匿の手段にならない**（同じリポジトリの中で場所が変わるだけ）。判断軸は
「どの層に書くか」ではなく**そのリポジトリが public か**。ops-sync では、consumer 名（`consumers.txt`
で公開済み）を超える情報——PR 番号・欠陥の内容・タイムライン——を書かない。同種の指摘は過去にも出ており
（履歴フラグメントに private の実装識別子を書いた件）、**同じ間違いを別の入口で繰り返した**形になる。

書き方の落とし所: 教訓（何が起きうるか・なぜその設計にしたか）は残し、**どの repo のどの PR で起きたかは
書かない**。「ある private consumer で」「別の PR で」まで一般化しても教訓の価値は落ちない。

**git 履歴に残る分は別問題**。既にマージ済みのコミットには元の記述が残っており、作業ツリーを直しても
消えない。public リポジトリの履歴書き換えは影響が大きいのでオーナー判断に委ねる（この修正では
現在の内容だけを一般化した）。

## 2026-08-03 Codex 積み残し（private/ops-runner 分）の消化

**自分が直した配布 doc の同期 PR に、その修正が生んだ新しい指摘が付いた**（ops-runner と private consumer の同期 PR）。
配布物を触ると同じ内容が3リポジトリの同期 PR でレビューされるので、**正本 PR には出ない指摘が下流でだけ出る**
——ops-sync 側で緑でも、下流の同期 PR を見るまで消化は終わっていない。

今回それが起きた3件:

- **design doc に PR 年代記を書いた**（ops-sync#153）→ 現在形ルール違反。`docs/` は現在の姿だけを書き、経緯は
  git とタスク履歴に残す場所がある。根拠を doc に残したくなったら、**主張だけを doc に、実例は履歴に**置く。
  加えて、実例に挙げた PR がその時点の生成物（inbox）では 🟡 と表示されていて、doc が自分の生成元と
  矛盾しているという指摘も付いた（🟡 の誤表示自体は ops-sync#152 で直した当のバグ）。**public な ops-sync に
  private consumer の PR 番号・欠陥の経緯を書かない**（後述の指摘で判明。実例は書かず主張だけ残す）。
- **概念を2つに割ったのに、割り残しがあった**（ops-sync#154 で「月枠の消費」と「直接課金」を分離）→ 概要文と
  手順2b が旧概念のままで、larger runner を有効化する操作に対応する文言が規約から消えていた。
  **区別を導入したら、その語が出てくる箇所を全部数える**（概要・トリガ・手順・完了条件・よくある失敗）。

その他、機序が非自明だったもの:

- **鍵の無いハッシュは秘匿にならない**。cleanup ブランチ名に提案ファイル名の 12 桁ハッシュを
  使っていたが、提案名は「日時＋人が読めるスラッグ」で推測できるので、候補をオフラインでハッシュして
  突き合わせれば復元できる（48ビットの一致確認は総当たりを妨げない）。**既に公開されている値**
  （consumer 名。`consumers.txt` にある）に置き換えた。1 run = 1 consumer 分のバッチなので、
  consumer ごとに固定でも掃除 PR の再利用性は落ちず、むしろバッチ先頭が変わるたびに2本目の掃除 PR が
  できる問題も消える。切替時に取り残される open な cleanup PR が無いことは事前に確認した。
- **`|| true` で列挙失敗を握りつぶしていた**。「削除対象なし」と「一覧が取れなかった」が同じ緑に
  なるので、取得 URL を含む public run が警告も無く残り続ける。掃除の付随処理なので run は落とさず
  warning にした（エラー本文は URL を含みうるので出さない）。
- **設定ファイルは本番の binding の証拠にならない**。設定が本番より進んでいる／遅れていると、
  期待どおり 0 件が返っても本番は別 DB を向いたまま互換コードを消すことになる。稼働中バージョンの
  binding と突き合わせてから使う、に変えた。
- **publish だけ先に出して読み手が無い状態を「現行構成」と書いていた**。`decision.json` の
  consumer 側リーダーは未実装で、`auto` にしても切り替わらない。未実装であることを doc に明記した。

## 2026-08-03 Codex 積み残し（ops-sync/ops-runner分）の消化

90日で洗い直した全体一覧の ops-sync 15件・ops-runner 8件を消化した。作業前に分かっていなかった点を残す。

**ops-runner の8件はすべて配布ファイル宛だった**（`docs/*.md`・`.github/actions/`・`.github/workflows/`）。
consumer 側に手を入れる余地はゼロで、全部 ops-sync の `shared/` を直せば消える。public consumer の
指摘は「その repo の問題」ではなく「正本の問題が別の入口から見えているだけ」なので、**リポジトリごとに
分けて消化しようとすると同じ修正を2回考えることになる**。一覧はリポジトリ別に並ぶが、消化は
「どのファイルの正本を直すか」で束ねる方が速い。

**指摘の半分以上（23件中15件）は既に直っていた。** 同じ欠陥が連続する PR で繰り返し指摘され、後の PR で
直したときに前の PR のスレッドを resolve していなかったのが主因（`create-pr-quiet` の doc 化は #138 と
#139 の両方に出て #139 側だけ resolve、`shared-file` のバイト保持は #134 と #142 に分散）。**指摘文だけ
見て直し始めると二重に触る**という既存ルールの実例がまた増えた形。

実際に直した8件のうち、機序が非自明だったもの:

- **`reject()` が utf8 で読んでいた**。書き込み側は Buffer 化済みだったが差し戻し経路が残っていて、
  非 UTF-8 の提案を却下すると U+FFFD に化けたものが consumer の main に書き戻る。却下は「ヘッダを直して
  出し直す」ための経路なので、ここでバイトが変わると同じ内容を再提出できない（過去リビジョンからの復元が要る）。
- **`status=success` の run 検索はサーバ側 1,000 件打ち切り**で、`--paginate` でも越えられない。保持期間内に
  成功 run が 1,000 件を超えると古い run が cutoff の判定にすら乗らず、公開のまま残り続ける（掃除の目的
  そのものが達成できない）。絞り込みをクライアント（jq）へ移した。
- **`$(( 08 * 86400 ))` は八進数として読まれて `value too great for base` で落ちる**。桁チェックは通るので
  検証では捕まらない。`10#` を付けた。
- **`run:` のスクリプト本文は展開後にジョブログへ出る**（`> detail.log 2>&1` は stdout/stderr にしか効かない）。
  ci-logs の「漏れる経路は3つ」に、この4つ目が抜けていた。YAML に書いた `env:` も同じ見出しの下に出るので、
  そこへ移すだけでは塞げない。
- **archive-task-history に concurrency が無かった**。無差分の枝が「同じ head の open PR を close する」
  破壊的な経路になった時点で、直列化が前提条件に変わっていた（close の判断材料は自分の差分であって
  head の中身ではないので、他の run が force-push した有効な PR を消せる）。

**対応しない判断1件**: net-fetch の cleanup で `_invalid-*` を予約名として弾く件。予約は「作る側」
（退避先がユーザーの ID と衝突しないこと）が目的で、消す側で同じ予約を掛けると予約導入前のスライスが
消せなくなる。任意のスライス名を渡せる点は予約の有無と無関係なので、予約は防御になっていない。

## 2026-08-03 クローズ済み PR 注記の根拠を実例で裏付ける

`codex-review-inbox` からクローズ済み（未マージ）PR を在庫から外したとき、完全ドロップにせず注記を残した
理由は「放棄された PR の指摘が `main` にも当てはまることがある」だったが、doc にはその一文しか無く、次に
読む人が「本当にあるのか？」を再調査する状態だった。実際に在庫に出ていた3件を確認したところ、
**注記の必要性を示す実例と、成り立たない反論の両方が出た**ので書き残す。

- 放棄された PR の指摘と同じコードが**別の PR で `main` に入ったが、その PR にはレビュースレッドが0本**。
  欠陥を指す文はクローズ済み PR にしか無く、それを読んだ人が起こした後続 PR で直るまで `main` に残っていた。
  → 「同じ変更が別 PR で入るならその PR にも同じ指摘が付くから拾える」は**反例つきで否定**される。
- 残り2件は PR 限りの指摘で、`main` には効かない（一方は landed しなかったコードの話、もう一方はその PR
  自身の履歴フラグメントの話）。

3件中1件が「在庫の外に置くと誰も知らなくなるクラス」だった。注記は3日で消える数行なので、この頻度なら
保険として妥当という判断。逆に言えば注記が埋めるのは「同じ欠陥が別 PR で `main` に入り、その PR には
レビューが付かなかった」という穴だけで、それ以外の用途を期待しない。

なお、確認の過程で3件とも既に対応済み（未 resolve のまま残っていただけ）と分かったので、返信のうえ
resolve した。「載っている＝未対応」ではなかった典型例。

## 2026-08-03 codex-review-inbox: クローズ済み PR を在庫から外す

マーカーが `merged ? 🔴 : 🟡` の二値だったため、**マージされずクローズされた PR**（`state=CLOSED`・
`merged=false`）が凡例どおりの「🟡 = open PR」として出ていた（実測: ある private consumer で3件）。
`state` はクエリで取得済みなのに未使用だった。

**在庫から外す**判断にした理由: この一覧の在庫は「`main` に残っている欠陥（🔴）」か「これからマージ
される PR の欠陥（🟡）」のどちらかで、クローズ未マージはどちらでもない（直す対象が `main` に無い）。
それでも載せると、消化プロトコル（一覧の全件を3状態のいずれかで終える）が「理由を返信して resolve」
という実コストを必ず要求する。`codex/*` の放棄 PR は今後も増え続けるので、載せ続けると表が死に行で
埋まって読まれなくなる——この一覧にとって最悪の壊れ方。

**それでも黙って消さない**: 放棄された PR の指摘が `main` にも当てはまることがある（指摘が指していた
ファイルが `main` に現存しているケースを実際に確認した）。
人が気づく余地として件数だけを末尾の注記に出す。

**注記を持ち越しの対象外にしたのが要点**: 持ち越しは「前回の出力に載っていた PR URL」を入力にするので、
注記にリンクを出したまま持ち越すと、在庫から外したはずのクローズ済み PR が永久に残って注記が単調増加
する（在庫に載せているのと変わらなくなる）。持ち越し経由で届いたクローズ済み PR は注記にも出さず、
直近スキャンで見つけた分だけ載せる＝窓（既定3日）から外れれば消える。reopen されれば `updatedAt` が
動くので直近スキャンが拾い直す。

クローズ済み PR ではレビュースレッドの読み残し（1ページ50件超）も「取得失敗」に数えない。対象外の PR を
読み残しても直す先が無く、run を赤くしても誰も動けないため。
