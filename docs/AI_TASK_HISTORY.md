# ai-ops 作業履歴

ai-ops での作業の「**なぜ**」の記録。書き方・アーカイブは共通規約 [`task-history.md`](task-history.md) に従う
（consumer に影響する変更・内部だけの変更の区別なくここ1箇所 → [`AGENTS.md`](../AGENTS.md)「履歴ファイル」節）。

## 2026-08-07 統合の空エントリ警告を復元可能にし、規約 doc と同期させる

空エントリを落とすガードのレビューで3点。

**警告に見出し行を載せる**。落とすブロックがあっても他に有効エントリが1つでもあればフラグメントは
削除されるので、警告に見出しが無いと**落とした内容を後から復元できない**。ログの出力先は対象
リポジトリ自身の ci-logs（既にフラグメント名を含む＝機微の扱いは同じ）なので、見出しを載せてよい。
「黙って捨てない」を主張するなら、捨てた物の識別子まで渡さないと主張が成立しない。

**0件時の skip 理由を実態に合わせる**。全ブロックが空だと従来の「日付付き `## YYYY-MM-DD` エントリが
無い」経路に合流するが、この文言は**嘘**になる（見出しは正しい形で存在する）。読んだ人はファイルを
開いて正しい見出しを見つけ、バッチ側の不具合だと誤読する。落とした件数を持ち回って理由を出し分けた。

**規約 doc を同時に直す**。`shared/docs/task-history.md` と `README.md` は統合の例外として dedup しか
書いておらず、「空見出しは取り込まない」「取り込めるエントリが0件のフラグメントは削除もしない」が
抜けていた。後者は挙動として重い——書きかけのフラグメントが inbox に**残り続ける**ので、doc に
書かないとエージェントは統合されない理由に辿り着けない。「よくある失敗」にも見出し二重書きを足した。

## 2026-08-07 アーカイブから private consumer の PR 番号を落とす

public リポジトリに private consumer の PR 番号が残っていないかを、追跡ファイル全体に対して
実際に検索した。AGENTS.md「private consumer の内部をこのリポジトリに書かない」の規約は
書く側の作法として整えてあったが、**既に書かれたものを一度も棚卸ししていなかった**。
結果、`docs/history-archive/2026.md` に 36 箇所（26 行・27 種）残っていた。

在庫が1ファイルに集中していたのは偶然ではない。履歴フラグメントは統合バッチで本体へ、
本体からアーカイブへ流れるので、**規約を破った記述は必ずアーカイブに沈む**。フラグメント
段階のレビューを通り抜けたものが、そこで止まらずに溜まっていく構造だった。

落としたのは PR 番号だけで、consumer 名は残した（`consumers.txt` で公開済みなので規約の
対象外）。日本語が壊れる4箇所——見出し末尾の括弧・`（private #<番号> P2）` のような優先度との
併記——だけ手で書き換え、残りは機械的に番号を削っている。`ops-runner` は public なので
番号をそのまま残した。

**この削除は公開の取り消しにならない**。git 履歴・PR の diff・コミットメッセージには
原文が残る（コミットメッセージ側は消せない。マージ済み PR の記録も同様）。効くのは
「HEAD が公開され続ける・コード検索に載り続ける」のを止めるところまで。**書く前に止める
以外に対処が無い**ことの裏付けとして残す。

## 2026-08-07 旧マーカー検出をコメント構文まで一致させる

`apply-common.mjs` は旧マーカー（`AI-OPS:COMMON`）を**素の部分文字列**で数えて、1つでもあれば
同期を失敗させていた。旧マーカーの自動移行をやめた以上、実物が残っていたら止めるのは正しい
——が、判定が広すぎた。`AGENTS.md` の本文に「旧マーカーは使うな」と**書いただけ**で同じ判定に
かかり、その consumer への配布が止まる。しかも `apply-common.mjs` は全 consumer に対して回る
ので、「マーカーの掃除を促す注意書き」を1つ書いた副作用で配布そのものが落ちる。

判定を `<!-- AI-OPS:COMMON START|END … -->` の骨格を見る正規表現にした。START 側の説明文は
consumer ごとに揺れうるので、そこは `[^>]*` で吸収して**コメントであることと START/END の別**
だけを見る。バッククォートで囲んだ言及・散文中の言及は当たらない。

同時に `shared/docs/ops-sync-design.md` の記述も直した。実装が旧マーカーを一切受け付けなく
なったのに、配布 doc 側は「**新旧どちらか一方**の組が1組なら健全」のままだった。この doc は
consumer に配られるので、読んだ人は移行が走ると期待して、実際にはエラーで止まる。**仕組みを
変えたら同じ PR で配布 doc も直す**（AGENTS.md「完了手順」）を踏み外していた。

回帰テスト `scripts/apply-common.test.mjs` を新設した。「実物の旧マーカーは弾く」と「言及だけは
通す」を対で置いてある——片方だけだと、次に判定を触る人がどちらかへ倒しても気づけない。

## 2026-08-07 統合で空エントリを本体に入れない

フラグメントに見出しが2本あると（生成した見出しの後ろに手で同じ見出しを書く等）、1本目が
「見出しだけ・本文なし」のブロックになり、統合でそれが**本体やアーカイブに恒久的に残る**。
統合件数も水増しされる。実際に起きた。

**入力の作法違反だが、直す先はスクリプト**という判断。フラグメントは人とエージェントが書く場所で、
規約（1エントリ＝1ファイル）を破る書き方はこれからも起きる。恒久履歴に壊れたレコードを入れる
のは復旧が面倒（後から見分けが付かない）なので、**受け側で落として警告する**方が安い。

落とすのは「日付付き見出しだが本文が空」のブロックだけ。残りの正当なエントリは取り込み、
フラグメントも通常どおり消費する（全部が空なら従来どおり「エントリが無い」として消さずに残す）。

## 2026-08-05 教訓の置き場が履歴に流れる構造を塞ぐ

同じセッションで**複数回**、再利用可能な知見を履歴フラグメントに書いて終わりにした。直近の1件は
「書く場所を間違えた」と報告した直後の同じ誤りで、**個人の不注意ではなく規約側の穴**と判断した。

**なぜ履歴に流れるか**: 完了手順が「履歴を1件書く」で終わっており、**そこが作業の終端**になっている。
振り分け規約（共通/固有 × 常時/オンデマンド）は別の場所にあって、履歴を書く瞬間には発火しない。しかも
`task-history.md` は記録対象に「ハマりどころ」を挙げていて、**再利用可能な落とし穴を招き入れる文言**だった。
そこで振り分けの判定を `task-history.md` の手順3そのものに置いた。判定は一文で済む形にした——
**「今後は〜する」と読める文は履歴ではなく doc に置く**。

**もう一方の穴**は `sop-format.md` に「載せるコマンド・SQL を実行して確かめる」規約が無かったこと。
書式・完了条件・ツール中立は要求しているのに、**配布物として一番危険な「そのままコピーされて本番に流れる
クエリ」の正しさ**は要求していなかった。実際、静かに 0 件を返す述語を MUST として配る寸前まで行っている。
規約には「異常がある状態を作って異常を検出できることまで見る」を含めた——エラーで落ちる誤りは次の人が
気づけるが、**0 件で検査を通す誤りは誰も気づかない**という非対称があるため。

**この2つは対になっている**: 実行検証（誤りを作らない）と置き場の振り分け（作った知見を届ける）。
どちらか片方だけでは、正しい知見を誰も読まない場所に置く／誤った知見を全 consumer に配る、のどちらかになる。

**この PR 自身のレビューで出た穴**: 新設した MUST が「doc に載せる形そのままで実行する」だったが、同じ doc が
**プレースホルダを使えと要求している**（実値をハードコードしない）ので、**そのままでは実行できない**——
シェルなら `<...>` がリダイレクトに解釈されすらする。**満たせないゲートを作るなと書いた規約自体が
満たせない MUST になっていた**。「置換だけして実行する／置換以外は形を変えない」に直した。

境界を「そのまま」に置いたのが誤りで、正しい境界は**置換以外を変えないこと**。検証しやすいように書き換えると
検証したものと配るものが別物になる（実際、修飾子を「同じ意味だろう」と動かした結果、比較ではなく別の対象に
付いていた、という取り違えが起きている）。

## 2026-08-05 段階的デプロイと識別子の大文字小文字を SOP に反映

D1 の SOP に3件。いずれも**マージ後の consumer 同期 PR に付いたレビュー**で出た（本体 PR には出なかった）。

**(1) 「有効なバージョンは1つ」と決めつけていた**。段階的デプロイ（`versions deploy` の
`<version-id>@<percentage>`）では複数バージョンが同時に本番を受け持つ。片方だけ見て「これが本番の DB」と
決めると、まだトラフィックを受けている側を見落とす。**トラフィックが 0 でない全バージョン**を確認する形にした。
撤去手順側にも同じ罠があり（分割が残っている間は**旧版の ensure が列を作り直す**）、そちらにも書いた。
この2つは同じ「1バージョンしか見ない」前提から出ている。

**(2) FK 検出の比較が大文字小文字を区別していた**。SQLite の識別子は大小を区別しないのに
`pragma_foreign_key_list` は**宣言どおりの表記**を返す（実測: 子が `REFERENCES Parent(...)` なら `Parent`）。
素の `=` だと 0 件になり、**検査が「異常なし」で通る**。見落としが最悪の形で出る箇所なので `COLLATE NOCASE` を
MUST にした。列名側も同じ性質なので併記。**「探すときは広く」の原則がここにも効く**——同じ判断を、
前回は部分一致の扱いで、今回は大文字小文字で間違えた。

**(3) public リポジトリに private consumer の運用詳細を書いていた**。前回の履歴フラグメントに、別リポジトリの
セッションで得た具体的な構成情報を根拠として書いてしまった。このリポジトリは public で、履歴フラグメントも
開示規約の対象。

**重要な限界**: 本文から消しても**公開は取り消せない**。git 履歴にも PR の diff にも原文が残るからで、
今回やったのは「今後この doc を読む人の目に触れないようにした」だけ。**書いた時点で公開は完了している**と
考えるべきで、事後の削除を対策と数えない。取り消すには履歴の書き換えが要り、それは配布物の同期を壊すので、
このリポジトリでは現実的でない（＝**書く前に止めるしか手が無い**）。この項目で具体を再掲しないのも同じ理由。

一般化の判断を「doc 本文かどうか」でしていたのが誤り。判断軸は**このリポジトリが public か**（AGENTS.md に
そう書いてあり、しかも同種の取りこぼしが過去にあったと記録もされている。読んだうえで再演した）。

**追記（レビューで出た5件と、その過程で見つけた落とし穴）**: 上の (2) を「FK 検出クエリだけ」直したのが浅く、
**同 doc の他の識別子比較（事前確認の `name=` / `tbl_name=`、検算の `col_remains` / `table_remains`）が
素の `=` のまま**残っていた。特に検算側は、テーブルが ensure で復活していても「消えたまま」と誤って合格する
向きに効くので最悪。個別に直すとまた漏れるので、**識別子比較は一貫して `COLLATE NOCASE`** という原則を
節の冒頭に1つ置いた。

その修正中、`WHERE name IN (...) COLLATE NOCASE` と書いてしまい、**エラーも出さずに 0 件**になることを
実測で発見した。正しくは **`name COLLATE NOCASE IN (...)`（左辺に付ける）**。挙動は付ける位置で3通りに分かれ、
**どこに付いたかで理由も違う**（すべて SQLite 3.45.1 で実測）:

| 書き方 | 1要素 | 2要素 | なぜ |
|---|---|---|---|
| `x IN (...) COLLATE NOCASE`（閉じ括弧の後ろ） | 0 件 | 0 件 | `(x IN (...)) COLLATE NOCASE` と解釈され、**比較ではなく真偽値**に照合順序が付く（明示括弧版と結果が完全に一致することで確認）。要素数によらず効かない |
| `x IN ('a' COLLATE NOCASE, 'b')`（要素側） | **1 件** | 0 件 | 1要素は `x = 'a'` に退化して右辺の COLLATE が効く。2要素以上はリストの比較になり無視される |
| `x COLLATE NOCASE IN (...)`（左辺） | 1 件 | 1 件 | 正しい書き方 |

**一番危険なのは2行目**——1要素で試すと効くので「解決した」と結論し、要素を増やした瞬間に静かに 0 件へ戻る。
なお最初にこの記録を書いたとき、私は**挙動を逆の構文に紐づけていた**（末尾付与が1要素で効く、と書いた）ため、
レビュアーに測り直させている。**この表は配布 doc 側の原則ボックスに要点を書いた**（履歴は配布されないので、
consumer が読めるのは doc 側だけ）。計測の作法そのものは `docs/sop-format.md` に規約として置いた。危うく「静かに合格する SQL」を MUST として全 consumer に配るところだった。
以後、**doc に載せる SQL は書いた形のまま実行して確かめる**（この PR では節内の SQL 7本すべてを実行し、
想定どおりの行が返ることを確認した）。

もう1件、**実行手段の無い MUST を自分で新設していた**: 「トラフィックを受けている全バージョンから撤去済みを
確認」は、バージョン単位でコードを取り出す経路が無いので満たせない（`versions view` は bindings であって
コードではない）。今日すでに2回直した「満たせないゲート」を、直した本人が別の形で作っていた。
**確認できる条件に置き換える**——分割が解消して 100% であることを確かめ、分割中は撤去しない（急ぐ理由が無い）。

**さらに次のレビューで出た2件（どちらも「誤って合格する」向き）**: 検算の列チェックに `pragma_table_info` を
使っていたが、**生成列は table_info に出ない**（実測: VIRTUAL/STORED とも hidden=2/3）。対象が生成列なら
DDL が失敗していても 0 件＝合格になる。`pragma_table_xinfo` に変えた。テーブルの検算も `type='table'` の
絞りが無く、**トリガはテーブルと別名前空間なので同名で共存できる**（実測: `Log` テーブルと `log` トリガ）。
`DROP TABLE` 成功後も 1 のままで、今度は満たせないゲートになる。なおこの「同名で共存」は**トリガが別テーブルに
付いている場合**の話で、対象テーブル自身に付いたトリガは `DROP TABLE` の道連れに消える（最初この条件を書き
落としていて、素直に再現すると 0 件になり、実測と食い違って見えた）。

**3回目のレビューで出た2件——「COLLATE NOCASE を一律に付ける」が行き過ぎた箇所**: 原則を節全体に適用する際、
**`<>` による自己除外にも NOCASE を付けてしまった**（`name <> '<table>' COLLATE NOCASE`）。等値の網は NOCASE で
**広がる**が、除外の網は NOCASE で**広がる＝結果が狭まる**。おかげで `DROP TABLE` 事前確認から、大小違いの
同名オブジェクト（別テーブルに付いたトリガ `log` が `Log` へ書いている、等）が丸ごと落ちていた。しかもそれは
道連れに消えない側なので、**事前確認をすり抜けて壊れたまま残る**。`NOT (type='table' AND name=... COLLATE NOCASE)` と
**type と組で**除外する形に直した。**否定文脈では照合順序の緩和が安全側に働かない**——これは今回の原則自体の
例外条件なので doc 側にも書いた。

もう1件は同じ「同名で共存できる」性質の裏返しで、依存オブジェクトの検算 (b) が**名前だけ**で引きながら
**完了条件は「空」**だった。NOCASE を足したぶん無関係な同名（例: 消したビュー `dep` と無関係なトリガ `DEP`）を
拾いやすくなり、消し忘れが無くても空にならない＝また満たせないゲート。**完了条件を「手順2で列挙した
type と name の組が残っていないこと」に変えた**（空は要求しない）。

**この節で犯した誤りは全て同じ形**をしている——「確認しているつもりの述語が、確認したい対象を実際には
見ていない」。索引だけ見る／大小を区別する／table_info で生成列を落とす／type を絞らず別種を数える／
除外側に NOCASE を付けて対象を落とす。
この PR では節内の SQL 全7本を、生成列・同名トリガ・大小違いの FK を含むフィクスチャで実行して確認した
（この確認を毎回行うことは `docs/sop-format.md` の規約にした。履歴に書くと次の人に届かないため）。

## 2026-08-05 列の撤去に inbound FK の事前確認を足す

スキーマ撤去 SOP の事前確認が、対象テーブル自身の DDL とビュー/トリガしか見ておらず、**他テーブルから
対象列への外部キー参照（inbound FK）**を取りこぼしていた（`CREATE TABLE child(x REFERENCES parent(old_col))`）。

**実測で挙動を確認した（SQLite 3.45.1）**。ここは他の阻害要因と性質が違う:

- inbound FK がある列でも、`PRAGMA foreign_keys` が ON でも OFF でも **DROP COLUMN は成功する**
- 子の DDL は `REFERENCES parent(old_col)` のまま残る（宙に浮く）
- 破綻はその場では出ず、**後から子テーブルへの INSERT が `foreign key mismatch` で失敗する**
- `PRAGMA foreign_key_check` を流しても、行が返るのではなく**同じエラーで落ちる**（後から気づく手段も塞がる）

索引・PK・UNIQUE・生成列・CHECK・ビュー/トリガは DDL 実行時にその場で拒否されるので「やってみれば分かる」が、
inbound FK だけは**事前に見るしかない**。この非対称性が、SOP に検出クエリを明記する価値そのもの。

検出は `pragma_foreign_key_list` の表値関数を `sqlite_master` と join して、対象テーブルを参照している
子テーブルを列挙する形にした（クエリも実際に流して確認済み）。`"to"` が NULL の行は**親の PK を暗黙参照**
しているだけなので、PK でない列を消すぶんには無関係——この読み分けも書いた（書かないと偽陽性で詰まる）。

**気づいた経路**: ops-sync 本体の PR ではなく、**マージ後の consumer 同期 PR に付いたレビュー**で出た。
ops-sync の AGENTS.md が「配布変更を出したらマージ後に consumer 同期 PR も確認する」と要求している
とおりの事例で、本体 PR だけ見て終わっていたら配布済みの欠陥が全 consumer に残っていた。

## 2026-08-05 D1 撤去手順にテーブル版と網羅的な事前確認を足す

前 PR でスキーマ撤去の節を足したが、レビューで2つの欠陥が出た。どちらも「書いた前提と手順が食い違う」型。

**(1) 見出し・トリガは「列・テーブル」なのに手順が列専用だった**。`DROP COLUMN`・`pragma_table_info` しか
書いておらず、テーブルを消す人は**存在しない手順に案内される**。テーブル版を足した。要点は列と非対称で、
`DROP TABLE` は**依存ビューを道連れにしない**（その場は成功し、後からそのビューを使う経路が壊れる＝作業とは
別のタイミングで顕在化するので原因に辿り着きにくい）。逆に FK 参照があると失敗しうる。検算も
`sqlite_master` で「テーブルが消えた」と「壊れた依存が残っていない」の両方を見る形にした。

**(2) 阻害要因を列挙したのに事前確認が索引しか見ていなかった**。インライン宣言の PK/UNIQUE/CHECK・生成列・FK は
**テーブル自身の DDL 文にしか現れず**、ビュー・トリガは別オブジェクトなので、索引を見ても引っかからない。
索引だけ確認して通すと本番 DDL がその場で拒否される。テーブル自身の `sql` と、列名に言及する
ビュー/トリガの2本を読む形にした。`LIKE` の粗い網なのは、取りこぼし（偽陰性）より偽陽性に倒すため
——偽陽性は定義を読めば捨てられるが、偽陰性は本番で初めて分かる。

**教訓**: 手順 doc で対象範囲を広く書く（「列・テーブル」）なら、広げた分の手順を必ず同時に書く。
トリガだけ広げると、案内された先に手順が無いという最悪の形になる。

**追記（同 PR のレビューで出た3件目）**: テーブル版の検算に `sql LIKE '%<table>%'` の件数を使い、
`dangling_refs` が 0 を完了条件にしていたが、これは**満たせないゲート**だった（`log` を消したあとに
無関係な `login_events` が引っかかる）。**探すときは広く・判定するときは完全一致**が正しい切り分けで、
事前確認（人が読んで分類する）に粗い網を使うのはよいが、同じ網を機械的なゲートに流用してはいけない。
ゲートは「手順2で洗い出した具体的なオブジェクト名」に紐づける形に変えた。満たせないゲートは
やがて誰も見なくなる（形骸化する）ぶん、無いより悪い——この失敗自体を「よくある失敗」に追記した。

**在庫から拾った既存指摘（別 PR・マージ済みで未 resolve だったもの）**: 「稼働中バージョンのバインディングを
確認する」手順が `wrangler deployments status` を挙げていたが、**このコマンドはデプロイ一覧と version ID を
出すだけでバインディングを報告しない**。エージェントは確認手段があるのに「示せない」と詰まる。正しくは
2段階（`wrangler deployments status` で active version ID → `wrangler versions view <version-id>` で bindings）。
同じ doc を触っている PR だったのでここで直した。**この欠陥は実際に効いた**——同じセッションでこの手順を
実行しようとして稼働中バインディングを直接引けず、別リポジトリでの作業で間接証拠に頼らざるを得なかった。撤去手順側でも同じコマンドを
「稼働中コードの確認」に挙げてしまっていたので、そちらは「スクリプトの中身を取得して grep する」に正した
（デプロイ一覧はバージョンが進んだことしか示さず、中身を見せない）。

## 2026-08-05 d1-capacity.md を d1-operations.md に改名しスキーマ撤去手順を追加

ある consumer で、役目を終えた一度きりの移行機能を撤去し、その機能だけが使っていた D1 の列も消す作業が
あった。そこで判明したことを共通 doc に上げる。

**発見（コードを読んでも分からない類）**: Worker が持つ**冪等なスキーマ ensure**（`ALTER TABLE ... ADD COLUMN`
を毎ティック流して失敗を握りつぶす実装）が生きている間に列を消すと、**次の実行が黙って作り直す**。
cron 駆動なら数十秒で戻るので「消したつもり」になる。したがって撤去は「コードの撤去を本番へデプロイし、
**稼働中のコードそのもの**に参照が無いことを確かめてから」の順序が要る。「PR がマージされた」では不足で、
マージとデプロイは別物（デプロイが別 workflow・別経路のこともある）。合わせて、SQLite が索引・PK・UNIQUE 等に
関与する列を DROP できない点も、事前確認の手順として書いた。

**改名した理由**: この doc は既に「本番データの直接確認」という容量と無関係の節を持っていて、`d1-capacity`
という名前が実態からずれていた。そこにスキーマ撤去が加わると乖離が決定的になるので、`d1-operations.md` に
改める（扱うのは容量・本番確認・スキーマ撤去の3つ）。**節を分けて別 doc にはしない**——分けると常時ロード層に
発火トリガが2つ要り、全タスクのコストが増える。「本番の D1 に対して何をしてよいか」という同じ判断軸なので
1 doc に置き、トリガも1つに保つ。

**改名の伝播**: `shared/docs/` と `shared/.claude/skills/` の rename だけでよい（manifest 差分で consumer から
旧パスが消え、skill のミラー4種は配布時に導出される）。`sync-deletions.txt` は manifest 導入前の unmanaged
ファイル用なので今回は不要。ただし**consumer のローカル doc・コード内コメントが旧パスを参照している場合は
そちらは自動では直らない**ので、consumer 側で別途直す必要がある（今回の作業元 consumer では追随の PR を出した）。

**読み取り専用ルールとの関係**: 既存の「本番データの直接確認」は読み取り専用を MUST としているが、撤去そのものは
DDL なので例外になる。無条件に許すと本番スキーマをエージェントの判断で変えられてしまうため、
**ユーザーの明示依頼があるときだけ**という条件を明記した。撤去のためにアプリ側へ一時的な移行経路を足すのは
本末転倒（撤去したはずの残骸を新たに増やす）なので、直接 DDL を認める側に倒している。
